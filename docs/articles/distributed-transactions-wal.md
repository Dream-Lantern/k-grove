# 第十九章 事务、WAL 与崩溃恢复

> 阅读标签：WAL通用原则 / PostgreSQL17示例。

事务不只是“依次执行几条语句”。原子性、可见性和持久性分别关注不同问题：故障后是否留下部分更新、其他事务能够看到什么，以及成功提交后能从哪些故障中恢复。锁与日志各自参与其中，不能互相替代。

## 1. 从转账不变量出发

教学例子：X=500、Y=750，转账 10 后应为 X=490、Y=760，余额总和保持 1250。只更新 X 就崩溃，或其他事务读到新 X 与旧 Y，都可能破坏使用者的判断。

需要明确事务边界、并发控制与恢复策略。数据库可以并发执行多个事务，只要对外结果满足所选隔离保证；“事务存在，所以物理上一定串行执行”不成立。

## 2. WAL 的先行规则是什么？

![内存更新、日志与恢复](/assets/notes/distributed-systems/dist-wal.svg)

Write-Ahead Logging 要求相关数据页持久化之前，对应恢复日志先安全保存。事务提交的持久性确认也需满足所声明的日志条件；写入操作系统缓存与达到抗故障介质不是同一事实。[PostgreSQL 17 WAL 简介](https://www.postgresql.org/docs/17/wal-intro.html)

数据页可在之后批量写回，无需每次提交都将所有页面刷入磁盘。多个事务的日志也可合并刷盘，因此不能用单次设备 I/O 延迟的倒数，直接推定数据库吞吐上限。

图采用同步持久提交的具体顺序：生成恢复日志→写入提交所需记录→WAL刷到包含提交记录的位置→成功回复。不是只刷修改日志、再把尚未持久的commit记录留在内存就宣称持久成功。页面写回遵守页对应WAL先持久的规则，但不要求所有页面在回复前落盘。若显式采用异步提交，成功回复可能领先于该屏障，故障时有丢失最近成功事务的窗口。[PostgreSQL17异步提交](https://www.postgresql.org/docs/17/wal-async-commit.html)

## 3. 未提交的数据页能不能落盘？

取决于缓冲管理与恢复方案。某些引擎允许未提交修改进入持久页，需要 undo 或适用的版本可见性与恢复机制处理；不能把“提交前数据永远只在内存”写成所有数据库的共同实现。

同样，日志不一定统一保存完整旧值、新值和一条 commit 三项。物理、逻辑或混合日志，配合事务状态和并发机制，有不同格式。教学简化要标明自己省略了什么。

## 4. 用故障点理解 redo

| 故障位置                             | 要分析的问题                           |
| ------------------------------------ | -------------------------------------- |
| 尚未形成足够的持久恢复记录           | 不能声称提交持久性已经成立             |
| 提交记录持久化，但部分数据页尚未更新 | 能否根据日志重建已提交效果             |
| 数据已提交，成功回复丢失             | 客户端结果未知，应按业务身份查询或去重 |
| 有未提交页面或旧版本                 | 由引擎规则决定撤销、忽略或可见性处理   |

redo 是恢复所需变更，不必等同再次调用业务接口；重新调用转账 API 可能又扣一次钱。恢复记录还要具有重复重放安全的条件，例如页位置、日志序号与版本检查。

## 5. checkpoint、复制和备份

checkpoint 缩短需要重放的历史或推进可回收边界，但不是任意删除旧日志的许可。备份需要完整、一致的恢复集合；复制则传播另一份状态，可能把误操作一同传播出去。

WAL 与共识日志不是同一概念。单个节点的日志已落盘，并不意味着多数副本已接受；多数副本已复制，也不代表外部业务副作用可以自动重放。分析系统时，应分别明确这些边界。

## 6. 与原笔记的关系

保留“先日志、后相应页面、故障可恢复”的学习主线，去掉“所有数据库都用锁、所有日志只有三条、未提交页绝不落盘”等过度概括。实际数据库的同步提交参数、存储保证和恢复工具要按确切版本核对，本轮未运行数据库。
