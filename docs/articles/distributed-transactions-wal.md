# 第十九章 事务、WAL 与崩溃恢复

> 阅读标签：WAL通用原则 / PostgreSQL17示例。

事务把一组操作组织成有明确提交与恢复语义的工作单元。原子性约束部分更新，可见性规定其他事务能观察的状态，持久性规定提交后可恢复的范围。本章从转账例子出发，解释日志如何连接内存修改、页面写回和崩溃恢复。

## 1. 从转账不变量出发

教学例子：账户 A=500、B=750，转账 100 后应为 A=400、B=850，余额总和保持 1250。只更新 A 就崩溃，或其他事务读到新 A 与旧 B，都可能破坏使用者的判断。

需要明确事务边界、并发控制与恢复策略。数据库可以并发执行多个事务，只要对外结果满足所选隔离保证；“事务存在，所以物理上一定串行执行”不成立。

事务常用 ACID 四项属性描述，各自回答不同问题：

| 属性 | 英文 | 中文 | 解决的问题 |
| --- | --- | --- | --- |
| A | Atomicity | 原子性 | 事务内的数据库修改作为整体提交或中止，避免只完成一半 |
| C | Consistency | 一致性 | 事务前后满足规定的约束与业务不变量 |
| I | Isolation | 隔离性 | 并发事务允许怎样观察彼此、形成什么结果 |
| D | Durability | 持久性 | 在声明的故障与存储条件下，提交成功的效果能够恢复 |

可见性是隔离级别、事务快照与具体实现共同规定的观察规则，不是 ACID 的第五项。数据库约束和正确的业务逻辑共同维护一致性；即使每个事务能原子提交，程序若漏掉收款账户或在并发中错误检查余额，仍可能破坏业务规则。

预写日志（Write-Ahead Logging，WAL）主要支持崩溃恢复与持久性，并配合事务状态等机制维护原子结果；锁、多版本或验证等并发控制负责隔离性。WAL 不是单独实现全部 ACID 的开关，数据库事务也不会自动覆盖外部转账 API、邮件等不可回滚副作用。

## 2. WAL：恢复日志先于相应数据页持久化 {#_2-wal-的先行规则是什么}

![内存更新、日志与恢复](/assets/notes/distributed-systems/dist-wal.svg)

Write-Ahead Logging 要求相关数据页持久化之前，对应恢复日志先安全保存。事务提交的持久性确认也需满足所声明的日志条件；写入操作系统缓存与达到抗故障介质不是同一事实。[PostgreSQL 17 WAL 简介](https://www.postgresql.org/docs/17/wal-intro.html)

数据页可在之后批量写回，无需每次提交都将所有页面刷入磁盘。多个事务的日志也可合并刷盘，因此不能用单次设备 I/O 延迟的倒数，直接推定数据库吞吐上限。

图采用同步持久提交的具体顺序：生成恢复日志→写入提交所需记录→WAL刷到包含提交记录的位置→成功回复。不是只刷修改日志、再把尚未持久的commit记录留在内存就宣称持久成功。页面写回遵守页对应WAL先持久的规则，但不要求所有页面在回复前落盘。若显式采用异步提交，成功回复可能领先于该屏障，故障时有丢失最近成功事务的窗口。[PostgreSQL17异步提交](https://www.postgresql.org/docs/17/wal-async-commit.html)

### LSN 与两个持久化屏障

日志序列号（Log Sequence Number，LSN）标识日志在 WAL 中的位置；页面日志序列号（Page Log Sequence Number，pageLSN）记录某页最近修改所对应的日志边界，用来判断写回或恢复所需的日志进度。它们不是事务业务编号，也不是墙钟时间。

下面用简化位置数字作教学推演：页面 P 的 `pageLSN=500`，当前持久 WAL 边界只有 480。即使 P 已在内存修改完成，也要先让覆盖该修改的 WAL 持久到至少 500，才能把 P 写到持久存储。若 WAL 记录占多个字节，必须覆盖**整条记录的结束边界**，不能只写到记录起点。PostgreSQL 17 页头的实际字段是 `pd_lsn`，其含义是该页最后一次修改对应 WAL 记录末字节的下一位置；真实 LSN 的显示格式也不同于本例整数。[PostgreSQL 17 页面布局](https://www.postgresql.org/docs/17/storage-page-layout.html)

| 屏障 | 必须等待什么 | 不要求什么 |
| --- | --- | --- |
| 同步事务提交屏障 | 包括提交记录（Commit Record）在内的适用 WAL 达到所声明的持久化条件，再返回成功 | 不要求提交前所有业务数据页都已写回 |
| 数据页写回屏障 | 覆盖页面 pageLSN 的 WAL 先持久，再允许该页写回（Data Page Flush） | 不要求所属事务已经提交；未提交效果由恢复与可见性机制约束 |

两条路径共享 WAL 持久进度，却不是同一时刻：页面可能在提交前写回，也可能在提交后很久才写回；同步提交仍必须等到自己的提交记录跨过屏障。图中的异步提交只放宽客户端成功回复的等待，不解除页面写回的 WAL 先行规则。

### PostgreSQL 17：同步、异步与复制的边界

以下讨论正常启用 `fsync`、存储栈履行同步承诺的 PostgreSQL 17。同步提交等待适用 WAL 刷新（WAL Flush）条件后再回复；`synchronous_commit=off` 则允许事务逻辑完成后先返回成功，WAL 随后由后台刷新：

```text
T1  修改账户数据
T2  生成修改日志及提交记录
T3  返回 COMMIT 成功（异步提交）
T4  对应 WAL 尚未持久
T5  系统突然断电：最近已回复成功的事务可能丢失
```

这与 `fsync=off` 不同。异步提交保留恢复一致性，但承担最近事务丢失的风险；关闭 fsync 会破坏数据库依赖的持久写入顺序保证，操作系统崩溃或掉电时还可能导致严重损坏。这里不是建议修改生产配置。[PostgreSQL 17 异步提交](https://www.postgresql.org/docs/17/wal-async-commit.html)

配置同步备库后，`synchronous_commit` 还可以选择远端等待边界：例如 `on` 可等待同步备库持久化，`remote_write` 等待远端文件系统写入而不等于远端抗操作系统崩溃持久化，`remote_apply` 进一步等待重放应用；`local` 则只等待本地持久化。具体还取决于 `synchronous_standby_names` 等配置。**本地 WAL 持久化、远端收到、远端持久化与远端应用是不同条件**，这些复制配置也不能直接称为 Raft 多数派提交。[PostgreSQL 17 WAL 参数](https://www.postgresql.org/docs/17/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT)

## 3. 数据页写回与未提交状态处理 {#_3-未提交的数据页能不能落盘}

取决于缓冲管理与恢复方案。某些引擎允许未提交修改进入持久页，需要 undo 或适用的版本可见性与恢复机制处理；不能把“提交前数据永远只在内存”写成所有数据库的共同实现。

同样，日志不一定统一保存完整旧值、新值和一条 commit 三项。物理、逻辑或混合日志，配合事务状态和并发机制，有不同格式。教学简化要标明自己省略了什么。

多版本并发控制（Multi-Version Concurrency Control，MVCC）使 PostgreSQL 能保留不同事务创建的行版本，并根据快照和事务状态决定哪些可见。一个页面包含某事务写出的字节，不等于其他事务就能看到这笔写入。下一章会详细说明快照与并发观察规则。[PostgreSQL 17 MVCC](https://www.postgresql.org/docs/17/mvcc-intro.html)

## 4. 用故障点理解 redo

| 故障位置                             | 要分析的问题                           |
| ------------------------------------ | -------------------------------------- |
| 尚未形成足够的持久恢复记录           | 不能声称提交持久性已经成立             |
| 提交记录持久化，但部分数据页尚未更新 | 能否根据日志重建已提交效果             |
| 数据已提交，成功回复丢失             | 客户端结果未知，应按业务身份查询或去重 |
| 有未提交页面或旧版本                 | 由引擎规则决定撤销、忽略或可见性处理   |

redo 是恢复所需变更，不必等同再次调用业务接口；重新调用转账 API 可能又扣一次钱。恢复记录还要具有重复重放安全的条件，例如页位置、日志序号与版本检查。

重做（Redo）依据恢复日志重建数据库状态；撤销（Undo）则指处理未完成或中止事务效果的恢复思路。不同引擎的具体日志与版本管理不同，不应把 PostgreSQL 直接画成某种传统 Undo Log 的拷贝。

**案例一：已提交但页面未写回。** 假设 account 表的 id=1 余额原为 1000，T1 执行以下语句后，修改日志与提交记录已经持久，数据页仍未写回，此时崩溃：

```sql
BEGIN;
UPDATE account SET balance = 900 WHERE id = 1;
COMMIT;
```

恢复通过 WAL 重建所需页面与事务状态，使 900 的已提交效果保留；它不会重新调用一次“扣减 100”的业务接口。否则既可能重复产生业务副作用，也无法准确还原原来的数据库变更。

**案例二：T2 未提交。** 接着假设 T2 把同一余额更新为 800，却在 COMMIT 前崩溃。其修改 WAL 可能已因刷盘或其他事务活动而持久化，相关物理变更也可能被重放；但 **WAL 被重放与事务已提交是两回事**。恢复后的事务状态及 MVCC 判断使未提交的 800 不会自动成为对其他事务可见的已提交余额；在本例既定历史下，逻辑上仍保留 T1 的 900。无效版本可在后续清理中回收。

PostgreSQL 17 的恢复入口按 WAL 类型调用相应 redo 过程，不能概括为“先筛出已提交事务，再只重放它们的修改”。实现定位可查 [REL_17_0 的 xlogrecovery.c](https://raw.githubusercontent.com/postgres/postgres/REL_17_0/src/backend/access/transam/xlogrecovery.c) 与 [heapam_visibility.c 的可见性规则](https://raw.githubusercontent.com/postgres/postgres/REL_17_0/src/backend/access/heap/heapam_visibility.c)。上述仅为普通事务教学案例，不包含下一篇 2PC 中需要保留的 Prepared 状态。

回到 A、B 的转账，假设两账户存在、无其他转账干扰，且两个修改处于同一事务：

| 故障点 | 教学结果 |
| --- | --- |
| 修改前崩溃 | 未发生转账，A=500、B=750 |
| 只改了 A 后崩溃，事务尚未提交 | 不能形成只扣 A 的部分提交；恢复后的普通已提交视图仍为原余额 |
| 提交记录已经持久，但数据页未写回 | 恢复重建 A=400、B=850 的已提交效果 |
| 已提交，客户端成功回复丢失 | 数据库可能已完成转账，客户端结果未知；按操作身份查询或去重 |
| 异步提交回复后、WAL 持久化前崩溃 | 最近成功事务可能丢失；不能依赖该回复承诺抗此故障的持久性 |

数据库结果未知不等于提交失败；客户端重新发起一笔新转账可能重复扣款。这里的 SQL 和故障分支均为纸面推演，没有运行数据库实验。

## 5. checkpoint、复制和备份

checkpoint 缩短需要重放的历史或推进可回收边界，但不是任意删除旧日志的许可。备份需要完整、一致的恢复集合；复制则传播另一份状态，可能把误操作一同传播出去。

WAL 与共识日志不是同一概念。单个节点的日志已落盘，并不意味着多数副本已接受；多数副本已复制，也不代表外部业务副作用可以自动重放。分析系统时，应分别明确这些边界。

### Checkpoint 为什么可以缩短崩溃恢复时间

检查点（Checkpoint）为恢复提供一个已保证页面进度的基准。以 **PostgreSQL 17** 为例，可以按以下过程理解：

1. Checkpointer 开始检查点，确定这次检查点相关的恢复边界；数据库不必因此停止所有新事务。
2. 将这次检查点要求持久化的脏页及相关数据文件状态写回并同步，期间仍遵守 WAL 先行规则。
3. 完成相应工作并写入检查点记录，保存恢复需要的 Redo 起点及其他状态。
4. 崩溃恢复读取适用的检查点信息，从其指定 Redo 位置开始重放，而不是从数据库建立之初或简单从“检查点记录自身的字节位置”开始。
5. 根据恢复、归档、复制槽及备库保留等要求，才决定哪些旧 WAL 可以移除或复用；检查点完成不是删除全部旧日志的许可。

这是实现过程的教学概括。核心在于把较早的修改落实到数据文件，缩短必须再次重做的区间；检查点记录中保存的恢复起点与该记录自己的位置不同，新事务产生的修改也可能需要继续恢复。[PostgreSQL 17 WAL Configuration](https://www.postgresql.org/docs/17/wal-configuration.html)

### full_page_writes 与 Torn Page

撕裂页（Torn Page）指一次页面写入在崩溃时只完成了一部分，例如部分扇区是新内容、其余仍旧。若日志只记“修改几个字节”，其余损坏部分可能让恢复失去正确的页面基底。

PostgreSQL 17 在启用 `full_page_writes` 时，检查点后页面第一次修改会将完整页面镜像写入 WAL；恢复可用镜像重建完整基底，再接续所需修改。这帮助处理部分页面写入，不等于修复存储介质永久丢失、任意内存错误或全部日志损坏，也不是所有数据库统一使用的机制。[PostgreSQL 17 full_page_writes](https://www.postgresql.org/docs/17/runtime-config-wal.html#GUC-FULL-PAGE-WRITES)、[可靠性与存储假设](https://www.postgresql.org/docs/17/wal-reliability.html)

## 6. 结合具体数据库理解恢复契约 {#_6-与原笔记的关系}

学习主线是恢复日志先于相应页面持久化，再由提交记录、页面状态与并发控制共同解释恢复结果。实际数据库的同步提交参数、存储保证和恢复工具，应按确切版本核对；本章未运行数据库实验。
