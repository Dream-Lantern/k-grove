# 第四章：etcd——集群状态为什么需要多数派和备份？

控制平面需要记住哪些对象存在、期望运行多少副本，以及组件已经观察到什么状态。若这些信息只存在于某个进程的内存里，进程退出后就无法可靠继续协调。

etcd 为标准 Kubernetes 控制平面提供关键的持久状态存储。这一章先解释它在架构中的位置，再用三个投票成员的例子理解多数派，最后区分复制、快照和恢复。

以下以 etcd 3.5 官方资料核对基础机制，不据此认定原安装实验实际运行的补丁版本。所有状态和故障例子均为教学示例，没有连接真实 etcd，也没有执行恢复。

## 1. etcd 保存什么，不保存什么？

Kubernetes 的 API 对象包含名称、标签、期望配置和已观察状态等信息。API Server 需要把相关状态持久保存，etcd 是标准控制平面中的核心存储。

但下面几件事不能混为一谈：

| 数据                            | 通常归属的管理范围                 |
| ------------------------------- | ---------------------------------- |
| Deployment 的副本目标、Pod 对象 | Kubernetes API 状态                |
| Secret 对象中的敏感配置         | API 状态的一部分，需要额外安全保护 |
| 应用镜像的层和清单              | 镜像仓库及节点运行时相关存储       |
| 数据库业务表、上传文件          | 应用及其卷、后端存储               |
| 某个进程当前执行到哪条指令      | 运行时进程状态，不等于 API 对象    |

因此，etcd 快照不是应用数据目录的全量备份。恢复了 Deployment 对象，不代表恢复了应用数据库的业务内容。

原笔记将 etcd 称作“控制节点唯一的 StatefulSet 组件”。准确的区别是：**etcd 是有状态服务，但不等于它一定通过 StatefulSet 资源部署。** kubeadm 常见叠放拓扑通常以静态 Pod 等方式组织本地 etcd；外置 etcd 则有不同部署安排。[kubeadm 拓扑](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/ha-topology/)

## 2. 为什么其他组件不直接修改 etcd？

![API 状态与 etcd 的访问边界](/assets/notes/kubernetes/k8s-etcd-state-boundary.svg)

图中只画标准 API 状态路径，省略响应、缓存和外部工具。应用数据路径单独表示，不经过 etcd 保存业务文件。

如果 Scheduler、控制器和用户程序各自直接修改存储，就会绕开 API 对象处理、权限和约束。Kubernetes 通过 API Server 形成统一的访问边界，使组件能够在对象模型上协作。

管理员的诊断、备份和恢复工具可能需要在受控条件下直接访问 etcd，但这不是普通客户端的日常工作方式。不能把 etcd 客户端端口公开给所有应用，也不应在教程中直接编辑内部键来“修好”某个 Pod。

原笔记列出的 `/registry/...` 是内部存储理解线索，不是为业务程序设计的稳定 API。本章不会提供直接删改该前缀下键值的命令。

## 3. 多数派究竟在解决什么问题？

设三个投票成员为 A、B、C，其中一个成员承担 Leader 职责。写入需要按协议复制、提交并应用，客户端才能得到相应成功结果；不能让每个失联分区都自行宣布写入成功。

如果 A 与 B 仍可正常通信，而 C 暂时失联，A、B 可以构成多数。反过来，只有 C 的孤立部分不能单独凑出三个成员中的多数。

这是在特定故障假设下避免状态分歧的机制，不是“发生任何网络问题都照常可写”的承诺。Leader 变化、通信延迟、磁盘问题和恢复过程仍会影响服务。

对 N 个投票成员，多数数量为 `floor(N / 2) + 1`。这不是把 Learner 等所有进程一概计入的公式。

![投票成员数量与多数要求](/assets/notes/kubernetes/k8s-etcd-quorum.svg)

| 投票成员数 | 所需多数 | 在剩余多数可正常通信等条件下，可容忍失效数 |
| ---------: | -------: | -----------------------------------------: |
|          1 |        1 |                                          0 |
|          2 |        2 |                                          0 |
|          3 |        2 |                                          1 |
|          4 |        3 |                                          1 |
|          5 |        3 |                                          2 |

增加一个成员未必能提高故障容忍度，却可能增加复制成本。因此，不能仅凭“节点更多”就判断方案更好，更不能认为两个 etcd 投票成员足以容忍其中一个故障。[etcd 3.5 FAQ](https://etcd.io/docs/v3.5/faq/)

## 4. 复制、提交、应用与持久化，不是一句话

入门时可以按四个问题理解：

1. 日志或相关状态是否已传播到所需成员？
2. 协议是否已经确认可以提交？
3. 对应操作是否已经应用到键值状态？
4. 恢复依赖的持久数据是否按实现与配置要求保存？

这些问题相关，但不能用“Follower 收到了一个网络包”代替所有条件，也不能把“主节点写了一次内存”直接称作持久成功。

本章不展开 Raft 的任期和日志安全证明，也不把一个简化箭头图当作完整存储实现。etcd 的 API 保证、集群配置与硬件故障条件都应一起阅读。[etcd API 保证](https://etcd.io/docs/v3.5/learning/api_guarantees/)

## 5. Watch、revision 与 Kubernetes resourceVersion

etcd 可以提供键空间变化的观察能力，API Server 也基于其存储机制组织 Kubernetes API 状态访问。两者有关联，但不意味着用户应直接订阅内部 etcd 键，绕开 Kubernetes API。

还应分清：

- etcd 的 revision 描述其相应键空间修改版本。
- Kubernetes 的 `resourceVersion` 是 API 暴露的版本协调字段，应按 Kubernetes 的约定使用。
- 业务更新时间、镜像版本与上面两者不是一回事。

不要在业务程序中用内部数值公式推导对象“几秒前更新”，也不要认为 Watch 连接永远不会断开。历史压缩、连接恢复和重新建立当前视图，都可能影响观察方式。[Kubernetes 1.28 API 概念](https://raw.githubusercontent.com/kubernetes/website/release-1.28/content/en/docs/reference/using-api/api-concepts.md)

## 6. etcd 异常时，应用真的“完全不受影响”吗？

原笔记认为 etcd 中断不会影响已运行应用，但这个判断需要限定条件：已有容器可能暂时继续运行，却不能据此认定整个服务、管理面和恢复能力都不受影响。

例如：

- 依赖存储的 API 变更可能失败或无法正常推进。
- 新调度、控制循环和故障后的对象协调可能受影响。
- 应用如果依赖 Kubernetes API 动态发现或管理资源，也可能受到间接影响。
- 网络、存储和其他依赖的状态还要另行评估。

故障分析应说明“哪个对象、哪个路径、哪一段时间”，而不是只写一句“业务不会受影响”。

## 7. 为什么复制不能代替备份？

假设管理员通过合法 API 误删了对象，复制机制仍会推进各成员达成相同状态。从一致性角度看，这可能符合协议要求，但复制机制不会自动识别管理员的操作意图有误。

因此，高可用副本主要帮助应对某些成员故障；备份则提供另一个可恢复的数据时间点。两者不能互相替代。

快照还要配合这些材料理解：

- 生成时间、来源集群及相应版本信息。
- 文件完整性和访问权限。
- 恢复时需要的证书、配置和成员安排。
- 恢复后的 API、Watch 消费者和控制器行为检查。
- 不包含其中的业务数据及外部系统恢复。

“目录里有一个 snapshot.db”只能证明文件存在，不能证明它完整、来自正确集群，或者恢复流程已演练成功。[etcd 3.5 恢复文档](https://etcd.io/docs/v3.5/op-guide/recovery/)

## 8. 备份与恢复记录应怎样写，才便于以后使用？

本章不在未知集群上提供可直接执行的恢复指令。可以先把复盘记录分为四类：

| 阶段   | 应记录的证据                                 |
| ------ | -------------------------------------------- |
| 备份前 | 版本、成员、健康状态、快照目标与安全存放位置 |
| 备份后 | 工具返回结果、快照检查、时间与完整性信息     |
| 恢复前 | 隔离环境、原数据保留、逻辑成员规划、匹配工具 |
| 恢复后 | API 可访问性、对象状态、控制循环及业务侧验收 |

不同版本的 `etcdctl`、`etcdutl` 及恢复选项需要对应说明，不应把当前文档后来补充的选项反向写成原 1.28 实验当年已经验证过的操作。

恢复并不意味着直接将快照覆盖到正在运行的集群目录。具体方法应结合选定版本、拓扑和隔离条件单独审核，避免修复操作造成二次数据损失。

## 9. 排查时先建立证据，不先修改成员

看到 API 延迟时，不一定已经证明 etcd 有故障。需要关联 API 侧错误、etcd 日志与指标、磁盘和网络情况，再检查成员通信、Leader 状态与所需多数是否可用。

同样，增删成员不是无风险的“扩容按钮”。成员变更会改变协议中的集群配置，在多数不足或成员状态不清时盲目添加节点，可能无法解决问题。

这一章先建立三个边界：**API 状态不同于业务数据，多数复制不同于无条件可用，集群副本不同于可用备份。**
