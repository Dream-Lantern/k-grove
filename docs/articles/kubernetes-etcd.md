# 第四章：etcd——集群状态为什么需要多数派和备份？

控制平面需要记住哪些对象存在、期望运行多少副本，以及组件已经观察到什么状态。若这些信息只存在于某个进程的内存里，进程退出后就无法可靠继续协调。

etcd 为标准 Kubernetes 控制平面提供关键的持久状态存储。这一章先解释它在架构中的位置，再用三个投票成员的例子理解多数派，最后区分复制、快照和恢复。

本章按 etcd 3.5 官方资料核对基础机制，不涉及原安装实验的具体补丁版本。所有状态与故障例子均为教学推演，未连接真实 etcd，也未执行恢复。

## 1. etcd 保存的 API 状态 {#_1-etcd-保存什么-不保存什么}

Kubernetes 的 API 对象包含名称、标签、期望配置和已观察状态等信息。API Server 需要把相关状态持久保存，etcd 是标准控制平面中的核心存储。

下面几类数据的归属不同：

| 数据                            | 通常归属的管理范围                 |
| ------------------------------- | ---------------------------------- |
| Deployment 的副本目标、Pod 对象 | Kubernetes API 状态                |
| Secret 对象中的敏感配置         | API 状态的一部分，需要额外安全保护 |
| 应用镜像的层和清单              | 镜像仓库及节点运行时相关存储       |
| 数据库业务表、上传文件          | 应用及其卷、后端存储               |
| 某个进程当前执行到哪条指令      | 运行时进程状态，不等于 API 对象    |

因此，etcd 快照只覆盖 API 状态，不是应用数据的全量备份；恢复 Deployment 对象，也不会带回数据库里的业务记录。

Secret 也属于 API 状态，Base64 编码不提供保密性。Kubernetes 默认不会自动加密 etcd 中的 Secret 静态数据；是否加密取决于 API Server 的加密配置和提供程序。快照可能包含敏感数据，应限制读取权限，采用加密存储和安全传输，并保管好恢复所需的加密配置与密钥。[Kubernetes 静态数据加密](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/)

**etcd 是有状态服务，StatefulSet 则是一种 Kubernetes 工作负载资源。** 前者说的是 etcd 这个软件自身的性质——数据要落盘、成员之间要互相识别；后者说的是在集群里用哪种对象把它跑起来。 kubeadm 常见叠放拓扑通常以静态 Pod 等方式组织本地 etcd；外置 etcd 则有不同部署安排。[kubeadm 拓扑](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/ha-topology/)

## 2. 为什么其他组件不直接修改 etcd？

[![etcd 的边界：API 状态不是业务文件](/assets/notes/kubernetes/k8s-etcd-state-boundary.svg)](/assets/notes/kubernetes/k8s-etcd-state-boundary.svg)

图中只画标准 API 状态路径，省略响应、缓存和外部工具。应用数据路径单独表示，不经过 etcd 保存业务文件。

如果 Scheduler、控制器和用户程序各自直接修改存储，就会绕开 API 对象处理、权限和约束。Kubernetes 通过 API Server 形成统一的访问边界，使组件能够在对象模型上协作。

管理员的诊断、备份和恢复工具会在受控条件下直接访问 etcd，这不是普通客户端的日常路径。etcd 客户端端口只对受控来源开放；用直接编辑内部键的方式“修好”某个 Pod，会绕过 API 的处理边界。

`/registry/...` 可用于理解内部存储组织；业务程序应使用 Kubernetes API，直接修改内部键会绕过 API 的处理边界。

## 3. 多数派究竟在解决什么问题？

etcd 使用 Raft（分布式共识算法）让成员就日志顺序达成一致。Leader（领导者）推进日志复制和提交，Follower（跟随者）接收复制并按协议更新状态。Quorum（法定多数）是一次决定至少要多少个成员点头才算数；三个成员时是 2 个，这样网络断开后落在少数那一半的成员，没法自己确认一条新写入。

设三个投票成员为 A、B、C。一次写入要经过复制、提交和应用，客户端才会得到成功结果；多数派的作用，是阻止失联分区自行宣布写入成功。

如果 A 与 B 仍可正常通信，而 C 暂时失联，A、B 可以构成多数。反过来，只有 C 的孤立部分不能单独凑出三个成员中的多数。

多数派能防的只是“断开的两半各自以为写成功了”这种状态分歧，而且只在既定故障假设下成立；Leader 变化、通信延迟、磁盘问题和恢复过程仍会影响服务可用性。

对 N 个投票成员，多数数量为 `floor(N / 2) + 1`，只统计投票成员，Learner 不计入。

[![三个投票成员：多数可用与孤立成员](/assets/notes/kubernetes/k8s-etcd-quorum.svg)](/assets/notes/kubernetes/k8s-etcd-quorum.svg)

| 投票成员数 | 所需多数 | 在剩余多数可正常通信等条件下，可容忍失效数 |
| ---------: | -------: | -----------------------------------------: |
|          1 |        1 |                                          0 |
|          2 |        2 |                                          0 |
|          3 |        2 |                                          1 |
|          4 |        3 |                                          1 |
|          5 |        3 |                                          2 |

增加成员未必提高故障容忍度，还会增加复制成本。节点数量本身说明不了方案好坏；两个投票成员也容忍不了其中一个故障。[etcd 3.5 FAQ](https://etcd.io/docs/v3.5/faq/)

## 4. 复制、提交、应用与持久化是四个阶段

入门时可以按四个问题理解：

1. 日志或相关状态是否已传播到所需成员？
2. 协议是否已经确认可以提交？
3. 对应操作是否已经应用到键值状态？
4. 恢复依赖的持久数据是否按实现与配置要求保存？

这四个问题彼此相关：Follower 收到网络包不等于完成复制，主节点写入内存也不等于持久化成功。

本章不展开 Raft 的任期与日志安全证明；箭头图只表示主要关系，完整实现还要结合 etcd 的 API 保证、集群配置与硬件条件。[etcd API 保证](https://etcd.io/docs/v3.5/learning/api_guarantees/)

### 4.1 三节点写入推演：A 是 Leader

假设 A、B、C 均为投票成员，A 是当前任期的 Leader，B、C 是 Follower，成员配置没有变化。客户端向 A 提交一次修改键值的请求。下面描述协议上的主要关系，省略请求批处理、磁盘写入调度及响应传输等实现细节：

1. **接收请求**：A 将请求对应的操作组织为日志条目。A 本地记录只完成第一步，集群尚未提交。
2. **复制日志**：A 向 B、C 复制日志；Follower 按日志一致性检查等规则接收并持久记录后确认。WAL（Write-Ahead Log，预写日志）记录恢复所需的日志等信息，帮助成员在崩溃后恢复；WAL 落盘与客户端收到成功响应是两件事。
3. **判断提交**：假设 A 的当前任期条目已在 A、B 上满足持久复制要求，即达到 2/3 的多数，Leader 可按 Raft 规则推进提交索引。多数条件要结合任期、日志顺序和成员配置：两个成员保存了旧任期条目，并不构成独立提交的充分条件；旧条目可以随当前任期条目的提交被间接提交。
4. **应用状态机**：已提交的日志按顺序应用为键值状态。提交意味着协议已作出决定，不表示所有 Follower 此刻都已完成应用；落后的 C 可以随后追赶。
5. **返回操作结果**：请求在服务端完成相应提交与应用等处理后，客户端收到符合 etcd API 保证的成功结果。Follower 只收到日志，无法绕开 Leader 独立宣布写入成功。客户端超时或连接断开时，结果不确定：既可能已写入，也可能没有。

把过程压缩成“Leader 写完 → 成功”，就丢掉了复制、提交与应用的边界。持久化还依赖实现、文件系统及硬件正确履行写入要求；WAL 与数据库文件的作用参见 [etcd 3.5 持久存储文件](https://etcd.io/docs/v3.5/learning/persistent-storage-files/)，提交的当前任期规则参见 [Raft 论文第 5.4.2 节](https://raft.github.io/raft.pdf)。

### 4.2 两种失联情况

- **C 失联，A、B 正常通信**：仍有两个投票成员。在 Leader 有效、磁盘与复制等条件正常时，A、B 可以继续推进写入；不需要等待 C 也返回成功。C 恢复后再按协议追赶。
- **只剩一个成员可通信**：无论它此前是 Leader 还是 Follower，都不能独立满足三个投票成员所需的多数，无法提交新的写入。成员可能仍保存旧数据，但“有数据”与“能确认新写入”不同。

这里假定仍是原来的三成员配置；忽略失联成员并不会把多数门槛降成一票。[etcd 故障模式](https://etcd.io/docs/v3.5/op-guide/failures/)

## 5. Watch、revision 与 Kubernetes resourceVersion

etcd 可以提供键空间变化的观察能力，API Server 也基于其存储机制组织 Kubernetes API 状态访问。两者有关联，但业务侧仍应通过 Kubernetes API 访问，而不是直接订阅内部 etcd 键。

还应分清：

- etcd 的 Revision（修订版本）给键空间的每次修改排一个递增序号；一次修改事务可以改多个键，它们共享同一个修订版本。它是逻辑序号，不是时间戳——不能拿来算“几秒前改的”，也不是 Raft 日志里的条目序号。
- Kubernetes 的 `resourceVersion` 是 API 暴露的版本协调字段，应按 Kubernetes 的约定使用。
- 业务更新时间、镜像版本与上面两者不是一回事。

业务程序无法用内部数值公式推出对象“几秒前更新”；Watch 连接也会断开。历史压缩、连接恢复和重建当前视图都会影响观察方式。[etcd 3.5 API 版本模型](https://etcd.io/docs/v3.5/learning/api/#revisions)、[Kubernetes 1.28 API 概念](https://raw.githubusercontent.com/kubernetes/website/release-1.28/content/en/docs/reference/using-api/api-concepts.md)

## 6. etcd 异常的影响范围 {#_6-etcd-异常时-应用真的-完全不受影响-吗}

etcd 中断后，已有容器可能暂时继续运行；API 状态变更、控制循环和故障恢复则可能受阻。评估业务影响时，需要沿依赖路径逐项检查。

例如：

- 依赖存储的 API 变更可能失败或无法正常推进。
- 新调度、控制循环和故障后的对象协调可能受影响。
- 应用如果依赖 Kubernetes API 动态发现或管理资源，也可能受到间接影响。
- 网络、存储和其他依赖的状态还要另行评估。

故障分析要落到“哪个对象、哪条路径、哪段时间”，一句“业务不受影响”说明不了什么。

## 7. 复制与备份分别解决的问题 {#_7-为什么复制不能代替备份}

假设管理员通过合法 API 误删了对象，复制机制仍会推进各成员达成相同状态。从一致性角度看，这可能符合协议要求，但复制机制不会自动识别管理员的操作意图有误。

因此，高可用副本主要帮助应对某些成员故障；备份则提供另一个可恢复的数据时间点。两者不能互相替代。

Snapshot（快照）保存某个时间点的键值数据库状态，作为恢复起点；它不持续复制，快照之后的写入需要另行补齐。

快照还要配合这些材料理解：

- 生成时间、来源集群及相应版本信息。
- 文件完整性和访问权限。
- 恢复时需要的证书、配置和成员安排。
- 恢复后的 API、Watch 消费者和控制器行为检查。
- 不包含其中的业务数据及外部系统恢复。

目录里有 snapshot.db，只说明文件存在；完整性、来源集群和恢复流程是否演练过，都要另外验证。[etcd 3.5 恢复文档](https://etcd.io/docs/v3.5/op-guide/recovery/)

### 7.1 离线、只读检查快照

前提：已有合法取得的 `snapshot.db` 文件，当前用户有读取权限；已安装与快照及目标 etcd 版本兼容的 `etcdutl`，并核对对应 3.5 补丁版本的帮助。以下只读取本地快照，不连接在线集群，不启动或恢复 etcd。命令是教学示例。

```bash
# 离线检查 snapshot.db 的快照元信息；-w table 以表格输出，不向正在运行的 etcd 恢复数据
etcdutl snapshot status snapshot.db -w table
```

| 字段         | 应怎样理解                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------- |
| `REVISION`   | 快照内数据库的修订版本，用于识别恢复起点；不是生成时间                                         |
| `TOTAL KEYS` | 工具统计的数据库键条目数量；不能直接当作 Kubernetes 对象数                                     |
| `TOTAL SIZE` | 快照数据库的体积；不能据此推算完整业务数据量                                                   |
| `HASH`       | 工具计算的数据库内容哈希，提供内容检查线索；不是来源认证，也不等于外部记录的 SHA256 文件校验值 |

应另行记录来源集群、生成时间、工具版本、文件校验值及受控存放位置。该命令只读出快照自身的状态；来源可信、内容正确和恢复演练成功都要另外验证，完整性校验也替代不了。[etcd 3.5 快照状态检查](https://etcd.io/docs/v3.5/op-guide/recovery/#status-of-a-snapshot)

## 8. 备份与恢复记录应怎样写，才便于以后使用？

本章不给可直接执行的恢复指令，先把复盘记录分为四类：

| 阶段   | 应记录的证据                                 |
| ------ | -------------------------------------------- |
| 备份前 | 版本、成员、健康状态、快照目标与安全存放位置 |
| 备份后 | 工具返回结果、快照检查、时间与完整性信息     |
| 恢复前 | 隔离环境、原数据保留、逻辑成员规划、匹配工具 |
| 恢复后 | API 可访问性、对象状态、控制循环及业务侧验收 |

不同版本的 `etcdctl`、`etcdutl` 及恢复选项要分别对照文档；当前文档后来补充的选项，不等于 1.28 实验当年验证过的操作。

恢复不是在运行中的集群目录上直接覆盖快照；具体方法要结合版本、拓扑和隔离条件单独审核，避免修复操作造成二次数据损失。

### 8.1 为什么恢复 etcd 后，还需要关注 Kubernetes 控制器缓存？

假设快照保存时 Revision 为 `1000`，之后集群运行到了 `1800`。从旧快照恢复数据库后，内容回到较早时间点；若版本号也回退，某些客户端仍可能持有接近 `1800` 的本地缓存或 Watch 进度。连接恢复后，客户端缓存未必与数据库一致。

Kubernetes 的 Informer 是通过 List/Watch 维护本地对象视图的常见机制，Controller 和 Operator 可能依赖它。恢复后的版本回退会影响后续变化观察，导致旧视图没有按预期刷新。这里的 Revision 是 etcd 层的教学数字，不能换算成 Kubernetes `resourceVersion` 的通用规则。

etcd 3.5 官方恢复文档针对 Kubernetes 等有 Watch/缓存消费者的场景，建议结合两种机制：

- **Revision Bump**：恢复时提高修订版本，使新起点超过恢复前客户端可能已观察到的版本。提高编号不会找回 `1000` 之后丢失的业务变更。
- **Mark Compacted**：将包括提高后范围在内的历史标记为已压缩，使旧 Watch 不能继续依赖失效历史，促使客户端按错误恢复逻辑重新获取状态；它不替客户端实现正确的重连和缓存刷新。

对应文档把 `--bump-revision`、`--mark-compacted` 用于 **`etcdutl snapshot restore`**；例如 [etcd v3.5.16 的工具源码](https://github.com/etcd-io/etcd/blob/v3.5.16/etcdutl/etcdutl/snapshot_command.go)提供了这两个参数，但原 Kubernetes 1.28 安装环境没有验证过这条恢复记录。实际操作前核对 3.5 文档、工具版本和 `snapshot restore --help`：不同补丁版本、主次版本或 `etcdctl` 未必支持同名参数，bump 数值也要按现场确定。[etcd 3.5 修订版本回退与恢复](https://etcd.io/docs/v3.5/op-guide/recovery/#restoring-with-revision-bump)

恢复后还需验证 API Server 能否访问存储、关键对象是否符合快照时间点、控制器是否重新建立视图并继续协调，以及应用卷、数据库和外部依赖是否匹配。etcd 恢复只是其中一层，业务恢复还要看这些下游。

## 9. 排查时先建立证据，不先修改成员

API 延迟未必来自 etcd。先关联 API 侧错误、etcd 日志与指标、磁盘和网络情况，再检查成员通信、Leader 状态与多数是否可用。

增删成员也不是“扩容按钮”：成员变更会改写协议中的集群配置，多数不足或成员状态不清时加节点，问题往往还在。

本章留下三个边界：**API 状态与业务数据分离，多数复制不保证无条件可用，集群副本替代不了备份。**

etcd 保存了状态，下一步要理解谁持续观察并推进这些状态：见[第五章 Controller Manager](/articles/kubernetes-controller-manager.html)。
