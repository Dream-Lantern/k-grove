# 附录 B：速查与纸面练习

## 术语速查

| 术语              | 简明解释                              | 不要混同                 |
| ----------------- | ------------------------------------- | ------------------------ |
| RF                | 分区的配置副本数                      | 实时 ISR 数              |
| ISR               | 符合适用同步要求的副本集合            | 固定多数派列表           |
| Offset            | 分区日志的逻辑位置                    | 段文件字节地址           |
| LEO               | 某副本末端下一位置                    | 一切消费者可见上界       |
| HW                | 复制提交相关边界                      | 所有物理盘 fsync 完成    |
| LSO               | 本册 Last Stable Offset，稳定前缀上界 | Log Start Offset         |
| Store             | C 客户端本地保存待提交位点            | 已向 Broker 持久提交     |
| Commit            | 保存恢复位点或提交事务，依上下文区分  | 业务数据库一定已更新     |
| Compact           | 按 Key 清理旧值                       | gzip 等字节编码压缩      |
| Controller        | 协调元数据状态                        | 每个分区的业务消息中转站 |
| Group Coordinator | 协调消费组                            | 外部业务事务协调者       |

| 缩写 | 英文全称                           |
| ---- | ---------------------------------- |
| RF   | Replication Factor（副本因子）     |
| ISR  | In-Sync Replicas（同步副本集合）   |
| LEO  | Log End Offset（日志末端位置）     |
| HW   | High Watermark（高水位）           |
| LSO  | Last Stable Offset（最后稳定位置） |

## 练习 1：确认与复制

条件：RF=3、minISR=2、acks=all。ISR 从 A/B/C 变成 A/B，再变成 A。分别判断是否仍能满足写入门槛，并解释为什么不能用“all 表示现有全部，所以必成功”来判断最后一种情况。

参考思路：A/B/C 和 A/B 在相应运行条件下可以满足 minISR=2，只有 A 时不满足。再结合 ISR 变化与错误返回窗口判断；响应失败仍可能已经追加，复制确认与物理盘同步刷盘也应分别记录。

假定 A 始终是可用 Leader。A/B/C 时满足门槛，成功确认需满足当时 ISR 的复制条件。A/B 时仍达到门槛，C 已不在当前 ISR。只有 A 时低于门槛，新请求在追加前可收到 `NOT_ENOUGH_REPLICAS`。若请求已通过门槛并追加，等待确认时 ISR 缩小，则可能收到 `NOT_ENOUGH_REPLICAS_AFTER_APPEND`。超时也可能只丢失响应。应区分追加前拒绝与追加后结果未知。复制确认与磁盘 `fsync` 是两种边界。参见[确认机制](/articles/kafka-acks-min-isr.html)。

## 练习 2：业务乱序完成

100、101、102 已交付，100 和 102 完成。正确安全提交值是 101。101 完成后可以推进到 103。若直接提交 103，崩溃后可能跳过未完成的 101。

扩展：实际交付记录为 100、103、107，不能假定 101/102 永远会回来补齐。应根据客户端位置和实际交付顺序维护前沿，理解清理与过滤导致的空洞。

若 100 和 107 已完成但 103 尚未完成，队首未完成记录为 103，可安全提交 103。108 会跳过 103。103 完成后按交付顺序移除 103、107，可提交 108。每分区先登记实际交付的记录，再按队首的完成标记推进。业务完成的是具体记录，Kafka 提交值是下一恢复位置。参见[完成前沿](/articles/kafka-offset-watermarks.html)。

## 练习 3：消费起点

已有有效提交位置 500，配置 latest 并重启，会不会直接跳到最新？通常不会，已有有效位置仍是恢复依据。若 500 已不在可读范围，再讨论 reset 策略。earliest 只承诺当前范围，不承诺完整历史。

| 位置条件             | earliest         | latest           | Java 3.9 none / C 2.8.0 error |
| -------------------- | ---------------- | ---------------- | ----------------------------- |
| 500 有效             | 从 500 恢复      | 从 500 恢复      | 从 500 恢复                   |
| 无提交位置           | 从当前保留起点读 | 从重置时末端继续 | 报错                          |
| 提交位置超出可读范围 | 从当前保留起点读 | 从重置时末端继续 | 报错                          |

## 练习 4：C 内存

FREE 入队立即失败时谁释放 Payload？调用方仍负责。COPY 入队后能否复用原缓冲？可以按应用规则复用，但仍需检查最终投递结果。Delivery Report 里的消息能否 destroy？不能当作 consumer_poll 返回对象来释放。

FREE 成功入队时才把释放责任交给库。COPY 返回后原缓冲可复用，借用模式应等到适用投递报告。Consumer Poll 返回的非空消息由应用销毁，回调消息只在回调中借用。全局配置只在 `rd_kafka_new()` 成功后转移，Topic 配置由 `rd_kafka_topic_new()` 消费。退出前检查 Flush 返回值、投递失败与未确认记录。Consumer Close 后仍需 Destroy，回调上下文保留到销毁结束。参见[C 对象契约](/articles/kafka-librdkafka-ownership.html)。

## 练习 5：Exactly Once

Kafka 事务输出成功，为什么不能据此证明某个 HTTP 扣款只发生一次？因为外部接口不自动属于 Kafka 事务。需要对端幂等键或其他能协调效果与恢复的协议。

订单事务提交后，`read_committed` 可读取该事件。若 HTTP 已扣款但进程在位点提交前崩溃，重启会重放并可能再次扣款。若 HTTP 失败而位点先推进，重启可能跳过未扣款事件。用稳定的业务操作 ID 请求对端幂等，可让重放复用同一扣款结果。事务性 Outbox 可将本地状态和待发意图原子保存，跨 HTTP 的结果仍需对端幂等或可核对的恢复协议。参见[外部业务幂等](/articles/kafka-delivery-semantics.html)。

## 三个故障反例与参考解释 {#复核后的三个反例}

- 主线程每 100ms poll，工作线程却一直卡在数据库：组协议可能继续保持成员资格，但连续完成前沿已经停滞，因此需要独立监测业务活性。
- A=v1 后写入 tombstone，持有旧快照的消费者错过了删除标记窗口：earliest 不会自动修复旧状态，需要按恢复协议判断。
- 一个事务写入 P0/P1，两个消费者分别处理其中一个分区：read_committed 不保证一次 poll 取得整个事务，也不保证两个外部效果同时完成。

以上为纸面推演；原有后续隔离实验范围保持不变。

Tombstone 是压缩日志中的删除标记。`delete.retention.ms` 影响删除标记保留窗口，实际清理由 Cleaner 进度决定。持有 A=v1 的离线消费者错过标记时，继续增量读取可能保留旧值。从空状态用保留下来的日志重建与从旧快照继续追赶有不同风险，需按恢复协议核对。跨分区事务的提交状态约束各分区的事务可见性，两个消费者仍可在不同时间返回和处理各自记录。

### 综合题

| 条件                                         | 推演与答案                                                                                      | 易错点与联读                                                                                                                                |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Java 和 C 以同一订单文本作 Key，生产结果超时 | 先核对实际序列化与分区器。结果未知时沿用事件 ID；批次等待单独计量                               | 同名 Key 不保证跨客户端同分区。见[配置对照](/articles/kafka-client-configuration.html)、[重试](/articles/kafka-retries-idempotency.html)    |
| 新成员接管，旧 Worker 回报成功，Lag 同时下降 | 隔离旧世代结果，核对业务前沿与已确认位点                                                        | Lag 下降无法证明旧提交有效。见[交接](/articles/kafka-rebalance.html)、[Lag](/articles/kafka-capacity-lag.html)                              |
| Bootstrap TLS 成功，但 Fetch 被拒绝          | 检查目标 advertised Listener、后续认证主体及 Topic/Group ACL                                    | TLS 握手仅覆盖连接层。见[安全](/articles/kafka-network-security.html)                                                                       |
| 订单导入、窗口计数与库存写入需要选型         | Connect 负责接入，Streams 适合窗口聚合，库存外部事务仍需业务去重。Outbox 确认前崩溃允许重复发布 | Kafka 事务或任一组件都不能独自完成跨系统扣减。见[生态](/articles/kafka-connect-streams.html)、[订单案例](/articles/kafka-order-events.html) |
