# 第二十六章 观测、限流、背压与故障验证

> 阅读标签：通用协议/应用模型，具体前提见本章。

请求延迟由排队、通信、执行和持久化等阶段共同形成。观测用指标、日志和追踪关联这些阶段；过载时，再通过限流、背压和熔断管理进入系统的工作。本章沿定位、控制与故障验证三条线组织方法。

## 1. 先区分指标、日志与追踪

指标适合观察时间窗口中的速率、分布与资源；日志记录事件细节；Trace 通过相关上下文关联一次请求的多个 Span。追踪能帮助看调用结构与耗时，但采样可能遗漏请求，异步边界也需要正确传播或建立关联。

不能从“没有这个 Span”直接证明操作未发生，也不能靠不同机器的墙钟日志拼出绝对准确的提交顺序。业务 operation_id、事务 ID、版本与持久化状态仍是重要证据。[OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/)

| 类型            | 主要回答的问题       | 典型数据                                           |
| --------------- | -------------------- | -------------------------------------------------- |
| Metrics（指标） | 系统整体表现如何     | QPS（每秒查询数）、错误率、P99、CPU 使用率         |
| Logs（日志）    | 某个事件发生了什么   | 异常、事务状态、请求失败详情                       |
| Traces（追踪）  | 一次请求经过哪些步骤 | Trace（一次追踪）中的 Span（操作片段）、依赖与耗时 |

Context Propagation（上下文传播）把 Trace ID、上游 Span ID 等上下文传到下游，使新 Span 能关联同一次请求。Sampling（采样）则决定哪些 Trace 或 Span 被记录、保留并导出；传播正常不代表遥测一定保留。

Head-based Sampling（头部采样）尽早决定，开销较低，却无法仅凭请求开始时的信息保证保留所有最终失败的请求。Tail-based Sampling（尾部采样）先收集更多 Span，再按错误、耗时等条件决定，代价是暂存数据与维护采样状态；也无法找回之前已经被丢弃的数据。

找不到某个 Span，可能是未采样、传播中断、缺少插桩或遥测丢失。排查订单是否提交，仍应结合业务 ID 查询持久状态。[OpenTelemetry 上下文传播](https://opentelemetry.io/docs/concepts/context-propagation/)与[采样](https://opentelemetry.io/docs/concepts/sampling/)分别说明这两个机制。

### 看延迟分布，也控制指标标签数量

Histogram（直方图）按区间聚合观测值，用于观察请求延迟的分布；分位数表示排序后某个比例的位置。假设 1000 个请求中，950 个耗时 20 ms、40 个为 100 ms、10 个为 2000 ms，平均值只有 43 ms，却有 1% 的请求等待两秒。

按教学例子采用的 nearest-rank（向上取整秩）口径，将耗时升序排列，P50、P95、P99 分别取第 500、950、990 个值，得到 20、20、100 ms。最慢的 10 个请求位于 P99 之后；因此既要看多个分位数，也要看超时率和尾部区间。实际监控从直方图桶估算分位数时，还会受桶边界和插值方式影响，不能把所有实现的 P99 当成完全相同的精确值。

Cardinality（基数）指指标中不同标签组合的数量，每种组合通常形成独立时间序列或聚合状态。`service_name`、`http_method`、模板化的 `http_route` 和 `status_code` 通常便于控制；`user_id`、`request_id`、`session_id`、完整 URL 则容易快速增加组合数和内存、存储成本。这里的路由应是 `/orders/{id}`，不是每个订单各一个路径。

Trace ID 适合用于日志和追踪关联，不直接作为普通 Prometheus 指标标签；需要从指标跳到样本追踪时可用后端支持的 exemplar（样本关联）机制。[OpenTelemetry Metrics：直方图与基数](https://opentelemetry.io/docs/concepts/signals/metrics/)

## 2. 沿请求时间拆分延迟

教学中的延迟分解是：入口排队 → 连接池等待 → 网络 → 服务端排队 → 执行 → 持久化/复制等待 → 回复与客户端处理。慢日志可能只覆盖其中一段，平均值也会掩盖 P99 尾部。

Raft 提交慢可以来自磁盘、网络、Follower 追赶或 Leader 过载，不能一看到心跳告警就修改选举超时。跨服务请求慢也可能是上游堆积，重启某个看似最忙的服务未必解决根因。

上面的阶段分解适合互不重叠的串行时间段。Trace 中父 Span 往往已包含子调用时间，多个下游也可能并行，不能把所有 Span 直接求和。

以订单查询的并行聚合为教学例子：Gateway（入口网关）调用 Order Service（订单服务），后者同时获取库存、支付状态和用户信息，并等待三者完成。

| 并行分支            |   耗时 |
| ------------------- | -----: |
| Inventory（库存）   | 100 ms |
| Payment（支付状态） | 800 ms |
| User（用户信息）    | 200 ms |

若同时开始且必须全部返回，忽略额外开销，这一并行区间约为 `max(100,800,200)=800 ms`，不是 1100 ms。Critical Path（关键路径）是决定完成时间的最长依赖路径；完整响应还要加上它前后的串行排队、处理与汇合开销。若分支开始时间不同、有重试或后续依赖，就要按实际依赖关系重新判断。

![并行调用的关键路径](/assets/notes/distributed-systems/dist-latency-critical-path.svg)

## 3. 限流、背压与熔断的职责 {#_3-限流、背压与熔断各管什么}

限流控制准入速率，背压使上游感知下游的处理能力，熔断则在持续失败时停止部分无益调用。队列长度、并发数和请求截止时间都需要明确预算，不能靠无界缓冲无限接收请求。

过载时盲目自动扩容，还可能同时扩大数据库连接、缓存回源和重试量。应选择有用工作，区分关键请求、可降级查询和可延迟任务。[AWS 的超时、重试与退避分析](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

### 同一个过载场景，分别在哪一层控制

教学假设：在给定请求成本下，服务每秒完成 1000 个请求，持续进入 1500 RPS（Requests Per Second，每秒请求数）。如果无限接收，队列每秒净增约 500 个；排队占用内存，等待使客户端超时，重试又增加新工作，可能把局部过载扩散成级联故障。真实容量还随请求复杂度和资源瓶颈变化，1000 RPS 只是本例假设。

| 机制                             | 解决的问题             | 具体动作                                 |
| -------------------------------- | ---------------------- | ---------------------------------------- |
| Rate Limiting（限流）            | 进入速度过高           | 按约定时间窗口限制请求数，并处理突发     |
| Concurrency Limiting（并发限制） | 在途工作过多           | 限制正在占用执行槽位的请求数             |
| Backpressure（背压）             | 下游压力没有反馈到上游 | 上游暂停、减速，或停止提交新工作         |
| Load Shedding（负载丢弃）        | 过载时仍接收低价值工作 | 按优先级拒绝或丢弃部分请求，保住关键工作 |
| Circuit Breaker（熔断器）        | 持续调用失败依赖       | 暂停调用，只在允许时探测恢复             |

队列应有容量和等待预算，超过预算就按业务规则拒绝、降级或丢弃。截止时间应向下游传递，并在开始昂贵工作前检查剩余预算；前台调用超时仍不代表副作用没有发生。背压不能靠无限排队实现，扩容也应受数据库连接和回源预算约束。[Google SRE：过载处理](https://sre.google/sre-book/handling-overload/)与[级联故障](https://sre.google/sre-book/addressing-cascading-failures/)

### 多层重试怎样放大工作量

先明确“重试三次”意味着首次加重试，共四次尝试。教学调用链为：

```text
Client → Frontend → Backend → Database
  4 次调用前端   4 次调用后端   4 次数据库调用
```

这里 **Client、Frontend、Backend 三个调用层**都各自重试下游，且每次上层尝试都耗尽下层四次尝试，最坏会产生：

\[
4 \times 4 \times 4 = 64
\]

次数据库请求。若只有 Frontend 和 Backend 两个调用层重试，则相应是 `4×4=16`；不能仅因为链上有三个组件，就数成三个重试层。这是最坏上界推演，实际次数还受成功返回、截止时间和重试策略影响。

只重试适合重试的临时错误，采用 Exponential Backoff（指数退避，逐次增加等待）和 Jitter（随机抖动，打散同时重试）。同时限制单请求次数、总时间，以及进程或服务的 Retry Budget（重试预算，即允许用于重试的额外流量）。优先明确由哪个层承担重试，避免各层独立放大；扣款等非幂等操作必须先建立幂等键及结果查询机制。[Google SRE 的 64 次推演与重试预算](https://sre.google/sre-book/addressing-cascading-failures/)；[AWS 的退避与抖动](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

### 熔断用状态控制故障传播

```text
CLOSED（关闭）：正常转发
  → 失败达到配置阈值 → OPEN（打开）：快速拒绝
  → 冷却时间到 → HALF-OPEN（半开）：放行少量探测
      → 探测满足成功条件 → CLOSED
      → 探测失败 → OPEN
```

阈值可以按时间窗口中的失败数或失败率等配置，不能把一次偶发错误等同于必须打开。熔断器不修复下游，也不是自动重试；它在恢复期间限制无益调用，避免探测瞬间再次压垮依赖。[熔断器的典型状态模型](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker)

## 4. 故障测试先定义不变量

![从故障窗口到业务验收](/assets/notes/distributed-systems/dist-triage.svg)

新增纸面实验表，不对真实系统执行：

| 故障点                 | 预期关注的状态           | 要防的错误结论           |
| ---------------------- | ------------------------ | ------------------------ |
| 提交后、回复前断连     | 持久结果与请求去重       | 超时就代表没执行         |
| Leader 与多数失联      | 角色、任期、提交与安全读 | 旧主还活着就能正常确认   |
| 租约交接期间暂停旧进程 | 下游令牌、版本与重复操作 | 锁到期会杀掉旧线程       |
| 消息处理后、确认前崩溃 | 消费去重与业务提交       | 再投递就一定重复副作用   |
| 迁移切换时旧客户端写入 | 所有权代际与增量边界     | 初始复制完成等于迁移完成 |

将上面五类场景展开时，可使用下面的验收记录模板。表中是预期与取证方案：

| 故障动作                               | 预期不变量                               | 观察证据                       | 恢复条件                           |
| -------------------------------------- | ---------------------------------------- | ------------------------------ | ---------------------------------- |
| 对指定请求在提交后、回复前断连         | 重试不产生重复业务效果                   | 请求 ID、事务状态、幂等记录    | 查询到最终状态，客户端与之协调     |
| 将指定 Leader 与多数隔离               | 旧主不能独立确认未获多数的新提交         | 任期、提交索引、日志与回复历史 | 新 Leader 正常服务，旧主按协议追赶 |
| 在租约交接期间暂停旧进程               | 资源确认新代际后，旧执行者不能覆盖新结果 | 令牌、资源代际与拒绝记录       | 资源端拒绝旧令牌，新结果保持有效   |
| 对指定消息在业务提交后、消费确认前崩溃 | 重投不重复产生业务副作用                 | 去重记录与同事务业务状态       | 重投后幂等处理、积压恢复           |
| 迁移切换后让旧客户端继续写             | 旧所有者不能绕过新代际修改已切换资源     | 所有权、增量边界、资源写入记录 | 旧写被拒绝，增量追平且路由有效     |

每次记录明确故障对象、持续窗口和恢复动作，并给每个不变量指定可追溯证据。Leader 场景按本册崩溃容错日志协议推演；Fencing 场景则必须真的存在资源端校验，单凭锁服务发出新令牌不能判定通过。

## 5. 结果记录要可复查

固定软件版本、拓扑、数据规模、负载、故障动作与时间窗口，保留调用与响应历史。测试期间必须有授权范围、隔离对象、恢复点与停止条件；不要在未知生产环境上“断网试试看”。

恢复验收不能只检查服务是否启动，还需检查不变量、备份可恢复性、遗留 Prepared 事务、积压和重复处理情况。
