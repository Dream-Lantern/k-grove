# 第二十六章 观测、限流、背压与故障验证

> 阅读标签：通用协议/应用模型，具体前提见本章。

请求延迟由排队、通信、执行和持久化等阶段共同形成。观测用指标、日志和追踪关联这些阶段；过载时，再通过限流、背压和熔断管理进入系统的工作。本章沿定位、控制与故障验证三条线组织方法。

## 1. 先区分指标、日志与追踪

指标适合观察时间窗口中的速率、分布与资源；日志记录事件细节；Trace 通过相关上下文关联一次请求的多个 Span。追踪能帮助看调用结构与耗时，但采样可能遗漏请求，异步边界也需要正确传播或建立关联。

不能从“没有这个 Span”直接证明操作未发生，也不能靠不同机器的墙钟日志拼出绝对准确的提交顺序。业务 operation_id、事务 ID、版本与持久化状态仍是重要证据。[OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/)

## 2. 沿请求时间拆分延迟

教学中的延迟分解是：入口排队 → 连接池等待 → 网络 → 服务端排队 → 执行 → 持久化/复制等待 → 回复与客户端处理。慢日志可能只覆盖其中一段，平均值也会掩盖 P99 尾部。

Raft 提交慢可以来自磁盘、网络、Follower 追赶或 Leader 过载，不能一看到心跳告警就修改选举超时。跨服务请求慢也可能是上游堆积，重启某个看似最忙的服务未必解决根因。

## 3. 限流、背压与熔断的职责 {#_3-限流、背压与熔断各管什么}

限流控制准入速率，背压使上游感知下游的处理能力，熔断则在持续失败时停止部分无益调用。队列长度、并发数和请求截止时间都需要明确预算，不能靠无界缓冲无限接收请求。

过载时盲目自动扩容，还可能同时扩大数据库连接、缓存回源和重试量。应选择有用工作，区分关键请求、可降级查询和可延迟任务。[AWS 的超时、重试与退避分析](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

## 4. 故障测试先定义不变量

![从故障窗口到业务验收](/assets/notes/distributed-systems/dist-triage.svg)

新增纸面实验表，不对真实系统执行：

| 故障点                 | 预期关注的状态           | 要防的错误结论           |
| ---------------------- | ------------------------ | ------------------------ |
| 提交后、回复前断连     | 持久结果与请求去重       | 超时就代表没执行         |
| Leader 与多数失联      | 角色、任期、提交与安全读 | 旧主还活着就能正常确认   |
| 租约交接期间暂停旧进程 | 下游令牌、版本与重复操作 | 锁到期会杀掉旧线程       |
| 消息处理后、确认前崩溃 | 消费去重与业务提交       | 再投递就一定重复副作用   |
| 迁移切换时旧客户端写入 | 所有权代际与增量边界     | 初始复制完成等于迁移完成 |

## 5. 结果记录要可复查

固定软件版本、拓扑、数据规模、负载、故障动作与时间窗口，保留调用与响应历史。测试期间必须有授权范围、隔离对象、恢复点与停止条件；不要在未知生产环境上“断网试试看”。

恢复验收不能只检查服务是否启动，还需检查不变量、备份可恢复性、遗留 Prepared 事务、积压和重复处理情况。一次测试通过，仅说明相应测试历史满足要求，并不能证明所有故障组合都正确。

## 6. 从纸面推演进入运行验证 {#_6-本册的验证边界}

本册示例用于纸面推演，尚无故障注入、压测、共识实现编译或数据库运行结果。静态排版和链接检查验证材料的可阅读性，运行时正确性需要在明确环境与测试范围下另行验证。

后续实践可按附录 B 的问题顺序逐步设计，不必先安装大量软件，也不能将运行时没有报错视为已经理解分布式一致性。
