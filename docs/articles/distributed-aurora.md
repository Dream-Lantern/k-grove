# 第二十三章 Aurora 计算存储分离与日志下沉

> 阅读标签：Aurora2017论文，不代表今日全部实现。

Aurora 2017 年论文将事务计算与分布式存储分开：计算实例执行数据库工作，存储侧处理适用的 redo、页面状态与修复。本章先看两层的职责，再区分正常读取和恢复读取，理解日志下沉与网络写放大的关系。讨论范围限于该论文，不外推到所有 RDS、Aurora DSQL 或当前全部云数据库。

## 1. 分开管理计算实例与数据卷 {#_1-为什么计算与存储分开}

计算实例与数据存储的生命周期不同：实例可能重启、调整规格或发生切换，数据库卷却需要持续存在。将存储独立为可复制、可修复的服务，便于分别处理容量、恢复和计算伸缩问题。

历史镜像写路径可以作为对照，具体部署需要等待哪些持久化环节，取决于该产品与配置的提交协议。

## 2. 保护组中的存储副本与持久化门槛 {#_2-存储副本不是数据库写实例}

[![Aurora：计算与持久化存储分离](/assets/notes/distributed-systems/dist-aurora.svg)](/assets/notes/distributed-systems/dist-aurora.svg)

论文以保护组为粒度在三个 AZ 放置六份存储副本，每 AZ 两份；数据库计算实例下发 redo，并按相应持久化边界判断写入。图里的六份不是六个独立接受业务 SQL 写入的主库。[Aurora 2017 论文 §2—3](https://cdn.amazon.science/dc/2b/4ef2b89649f9a393d37d3e042f4e/amazon-aurora-design-considerations-for-high-throughput-cloud-native-relational-databases.pdf)

写 quorum 为 4/6，恢复读 quorum 为 3/6。一个 AZ 丢失两份，数量上仍可满足写 quorum；再失去一份会只剩三份，不能继续把它描述成仍满足四份写确认。真实服务能力还依赖实例、网络和恢复协议。

Quorum（法定票数）指协议要求的最少副本数。设总数为 \(V\)，读、写法定票数分别为 \(V_r\)、\(V_w\)，基本交集条件为：

\[
V_r + V_w > V, \qquad V_w > \frac{V}{2}
\]

在论文的保护组（Protection Group，PG）中，\(V=6\)、\(V_w=4\)、\(V_r=3\)。例如写集合 `{A,B,C,D}` 与读集合 `{D,E,F}` 相交于 D；任意三份读取都不可能完全避开已经写到的四份。两个四份写集合也必有交集，例如 `{A,B,C,D}` 与 `{C,D,E,F}` 至少共享 C、D。不过，交集只保证有机会发现相应日志，识别日志缺口、处理版本和重建一致边界仍依赖下面的协议。

| 故障情况                 | 剩余副本 | 数量上满足写 4/6 | 数量上满足恢复读 3/6 |
| ------------------------ | -------: | ---------------- | -------------------- |
| 正常                     |        6 | 是               | 是                   |
| 一个 AZ 故障             |        4 | 是               | 是                   |
| 一个 AZ 再加一个节点故障 |        3 | 否               | 是                   |
| 两个独立节点故障         |        4 | 是               | 是                   |

这是六副本保护组的故障推演，不是完整的服务可用性承诺；副本必须可达且处于可用协议状态。论文描述的数据卷按 10 GB 粒度划分，六份对应 segment 组成 PG；这个大小属于 **2017 年设计**，不作为今日产品规格。

### 先读懂五个日志位置

日志位置用于区分“收到了一些日志”“前面的日志都齐了”和“能在这里安全截断”。以下含义按论文 §4.1—4.2 使用：

| 缩写 | 英文                  | 含义                                                            |
| ---- | --------------------- | --------------------------------------------------------------- |
| LSN  | Log Sequence Number   | 日志序列号；数据库分配的单调递增位置                            |
| SCL  | Segment Complete LSN  | Segment 完整日志位置；单份 segment 对本 PG 日志的无缺口完整进度 |
| VCL  | Volume Complete LSN   | 卷完整日志位置；存储服务能保证此前日志都可获得的最高位置        |
| CPL  | Consistency Point LSN | 一致性点日志位置；数据库标记的、允许存储恢复截断的边界          |
| VDL  | Volume Durable LSN    | 卷持久化日志位置；不超过 VCL 的最高 CPL                         |

每个 PG 只接收修改本组页面的日志，LSN 不要求在某个 segment 内数字连续；日志中的反向链接指向该 PG 的前一条记录，用它检测真正的缺口。SCL 不是“看到的最大 LSN”，VCL 也不能只取任意单节点的最大值。

\[
VDL = \max\{CPL \mid CPL \leq VCL\}
\]

沿用论文的边界例子：若 CPL 只有 900、1000、1100，VCL 已到 1007，则 VDL 仍为 1000。1001～1007 的日志虽然齐全，却尚未构成下一个可安全保留的完整分组；恢复必须按 VDL 处理尾部。VDL 表示存储的一致持久化边界，不表示这个位置之前的所有 SQL 事务都已提交。

### MTR 是内部原子分组

MTR（Mini-Transaction，微事务）把连续的一组日志作为有序、原子应用的单位，最后一条日志是 CPL。一个数据库级 SQL 事务可以包含多个 MTR，两种事务的边界不能混用。下面另设一个独立教学场景，不沿用上一例的 CPL 集合：

```text
SQL Transaction T1
  MTR-1：LSN 1001、1002、1003（CPL）
  MTR-2：LSN 1004、1005、1006（CPL）
  ……其余操作与事务提交记录
```

若第二个 MTR 只完整到 1005，就不能把它的一部分当作已完成的内部操作对外提供。MTR 完成也不等于 T1 提交；SQL 隔离、提交状态与 Undo 仍由数据库引擎管理。[日志边界与 MTR：Aurora 2017 §4.1—4.2](https://cdn.amazon.science/dc/2b/4ef2b89649f9a393d37d3e042f4e/amazon-aurora-design-considerations-for-high-throughput-cloud-native-relational-databases.pdf)

## 3. 正常读取与恢复读取的不同路径 {#_3-正常读不一定向三份存储都取数据}

正常计算实例跟踪运行中的日志与持久化进度，可按论文规则进行单副本页面读取；恢复时丢失了这些运行时状态，需要读 quorum 重建可信边界。不能由“R=3”直接推导每个 SELECT 必须等待三个存储节点。

因此，不能只看 quorum 数量：版本、LSN、持久化边界和缺口处理也参与提供保证。仅列出 R+W>6，不足以描述 Aurora 的恢复协议。

Buffer Cache（缓冲缓存）命中时，计算实例直接使用缓存页面；未命中才进入存储读取路径。按论文 §4.2.3 的正常读协议：

1. 发出页面请求时，将当时的 VDL 固定为 Read Point（读取点）。
2. 数据库根据自己跟踪的 segment 完整进度，选择对该读取点已有完整日志的副本。论文写作 SCL 大于 Read Point，不能只凭该副本“在线”就选择它。
3. 请求并返回读取点对应的页面版本，页面内容还须满足 MTR 原子应用的语义。页面尚未构建到所需位置时，存储侧可应用相应 redo。

例如教学场景中 Read Point 为 1000，已知一份 segment 的 SCL 为 1006，另一份只有 990；前者具备相应日志完整条件，后者需要先追赶。正常实例已有进度信息，因而可以定向请求一份合格副本。重启后这些运行时信息丢失，才需要通过每个 PG 的读 quorum 重新建立边界。返回页面之后，事务可见性仍由计算端的并发控制及 Undo 等机制处理。

## 4. redo 下沉与页面构建 {#_4-日志下沉为什么减少写放大}

数据库把适用 redo 送到存储层，由存储侧推进日志与页面状态，避免每次都跨网络发送全部修改页面。日志不保证永远只有几十字节，收益随操作、页面变化和实现而异，不能用固定大小倍数宣传性能。

页面构建可由日志驱动，存储端也可后台合并与修复，不是一定等到某次读请求才做所有工作。日志副本有缺口时，副本间需要发现并补齐相应历史。

### 一次提交如何等到持久化

```text
计算端生成 redo 并分配 LSN
  → 按目标 PG 分发日志批次到六份 segment
  → 存储节点持久化日志后返回 ACK
  → 计算端跟踪各批次写 quorum 与完整进度，推进 VDL
  → VDL ≥ 事务的 Commit LSN
  → 专用线程向等待中的客户端发送提交确认
```

单节点 ACK 只表示它持久化了对应日志，不表示整个事务完成。论文 §4.2.2 中，请求线程把 Commit LSN 加入等待列表后处理其他工作，随着 VDL 推进，由专用线程确认符合条件的事务。这里异步组织了工作线程，客户端成功确认仍须满足持久化条件。

### 存储节点把哪些工作移到后台

论文图 4 将存储侧工作分为：接收 redo 到 Incoming Queue（内存接收队列）；持久化日志并 ACK；整理日志、识别缺口；与同 PG 副本 Gossip（交换进度并补齐缺失记录）；Coalesce（合并并应用日志）生成页面；定期将日志和新页面送到 S3；定期 GC（回收旧版本）；定期校验 CRC（检测数据损坏）。

其中接收与日志持久化处于前台写路径，其余工作异步安排，不是每笔事务提交都串行等待“构建全部页面 → 上传 S3 → GC → 校验”。旧版本回收还受在途读请求的最低读取点约束，不能只因某份新页面生成就立即删除所有旧日志。[存储节点与读写路径：Aurora 2017 §3.3、§4.2](https://cdn.amazon.science/dc/2b/4ef2b89649f9a393d37d3e042f4e/amazon-aurora-design-considerations-for-high-throughput-cloud-native-relational-databases.pdf)

## 5. 细粒度修复与相关故障

将大卷拆成较小保护单元，使损坏后的修复可以从多节点并行进行，降低重建窗口。容错不仅看副本总数，还看副本跨 AZ 的安排、同时修复的单元、剩余容量与带宽。

不能把论文里的分片大小、恢复秒数和容量上限直接搬成今日产品规格，也不能把日志持久化等同业务事务已完整提交；事务提交仍需其完整的记录与边界规则。

### 存储层恢复：重建边界并处理尾部

计算实例重启后，与存储服务协作恢复数据卷，先建立统一的存储视图：

1. 对每个 PG 联系读 quorum 的 segment，发现可能已经到达写 quorum 的日志，重建完整进度，确定卷的 VCL。
2. 根据数据库标记的 CPL 计算新的 VDL，不能把只完整到一半的 MTR 留作可用状态。
3. 生成截断范围，使新 VDL 之后、直到可证明覆盖全部潜在在途日志的上界之间的日志失效。这个上界与数据库的 LSN 分配限制有关，不仅是某个节点此刻已见的最大值。
4. 截断范围带有 epoch（恢复代际）并持久化到存储服务。若恢复中再次崩溃，重启后仍能分辨截断的版本和持久化状态，避免把旧尾部重新当作有效日志。

这里的截断是按协议使日志失效，不要求把分布式节点上的尾部一次性物理删除完再开始下一步。

![Aurora 日志边界与恢复分层](/assets/notes/distributed-systems/dist-aurora-recovery.svg)

### 数据库事务恢复：还有运行时与 Undo

数据卷恢复之后，引擎还要从 Undo 段识别崩溃时未完成的事务、重建相应运行时状态，并执行必要的 Undo，撤销这些事务的操作。论文允许在建立未完成事务列表后在线进行 Undo 恢复；Redo 下沉减少了启动时集中回放页面的工作，并没有消除数据库事务恢复。VDL 之前也可能包含未提交事务的修改，这正是不能用存储边界替代事务提交状态的原因。[恢复协议：Aurora 2017 §4.3](https://cdn.amazon.science/dc/2b/4ef2b89649f9a393d37d3e042f4e/amazon-aurora-design-considerations-for-high-throughput-cloud-native-relational-databases.pdf)

## 6. 只读副本与跨区域能力要分开

存储共享不表示只读计算副本的缓存立刻更新，也不表示跨区域复制没有延迟。读己之写、故障切换和事务可见性需要产品与客户端的具体保证。

学习时，可以在纸面上分别推演计算实例故障、一个 AZ 故障，以及额外失去一个存储副本的情况，列出各场景中仍可依赖的状态。文中依据论文解释设计，实际产品能力和性能需按目标环境另行验证。
