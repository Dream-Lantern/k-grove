# 第二十七章 缓存更新、穿透、击穿与雪崩

[返回本册目录](/collections/redis/)

缓存通过复用查询结果减轻权威存储的负载。完整流程包括读取命中、未命中回源、更新失效和故障降级。本章先沿 Cache-Aside 观察读写，再用穿透、击穿和雪崩分别分析无效查询、单热点失效与大范围失效。

先区分三种问题；这些是应用架构术语，不是 Redis 的错误码或三个命令：

| 问题                          | 典型场景                   | 核心原因                 | 主要措施                           |
| ----------------------------- | -------------------------- | ------------------------ | ---------------------------------- |
| Cache Penetration（缓存穿透） | 不存在的 ID 被反复查询     | 无效请求绕过缓存         | 参数校验、短期空值缓存、布隆过滤器 |
| Cache Breakdown（缓存击穿）   | 一个热点键失效             | 同一键的大量请求同时回源 | 请求合并、协调重建、逻辑过期       |
| Cache Avalanche（缓存雪崩）   | 大批键到期或缓存服务不可用 | 回源压力集中爆发         | 到期抖动、限流、熔断和降级         |

加锁主要解决重建并发，不能统一解决不存在对象的查询和整个缓存层不可用。以下是应用协议分析，流程、时序和数值均为教学假设，没有执行数据库、Redis 或压力实验。[Redis Cache-Aside 的问题与边界](https://redis.io/docs/latest/develop/use-cases/cache-aside/)

[![Cache Aside：命中与未命中必须分流](/assets/notes/redis/redis-study-cache-aside.svg)](/assets/notes/redis/redis-study-cache-aside.svg)

## 1. Cache-Aside：数据库与缓存各自提交

Cache-Aside（旁路缓存）由应用负责读写缓存。HIT（命中）直接返回，MISS（未命中）才查询权威数据库并回填。常见写入路径是数据库提交成功后删除缓存，让下一次读取重新加载：

```text
读：请求 → 查询 Redis
          ├─ HIT → 返回缓存值
          └─ MISS → 查询数据库 → 按策略回填 Redis → 返回查询结果

写：更新数据库 → 提交成功 → 删除 Redis 对应缓存
                            → 后续读取 MISS 时重新回填
```

两套系统各自提交，没有自动组成一个原子事务，即不能保证数据库和缓存的改变作为一个不可分割整体完成。数据库提交后删缓存失败，旧值仍可能继续被读取。

另一种竞态来自慢读：请求 A 读到数据库旧值后暂停，请求 B 随后更新数据库并删除缓存，而 A 恢复后又将旧值回填。因此，先更新数据库再删除缓存，并不会自动消除所有旧值回填问题。

下面是应用协议的时序推演，不是 Redis 实验记录。假设两个请求之间没有额外的版本校验或串行协调：

| 时刻 | 请求 A：读取             | 请求 B：更新      | 缓存状态 |
| ---- | ------------------------ | ----------------- | -------- |
| t1   | 查询缓存未命中           | —                 | 空       |
| t2   | 读取数据库旧值 v1 后暂停 | —                 | 空       |
| t3   | 暂停中                   | 提交数据库新值 v2 | 空       |
| t4   | 暂停中                   | 删除缓存成功      | 空       |
| t5   | 将先前读到的 v1 回填     | 已完成            | 旧值 v1  |

如果 t5 才开始计算 TTL（Time To Live，剩余生存时间），TTL 限制的是这次回填的存活时间，不能直接当成“从数据库提交起最多陈旧这么久”的证明。要阻止迟到的旧值覆盖，还需要可验证的版本、协调或重建协议。

可根据业务容忍度选择较短 TTL、失效重试、可靠变更事件、版本校验或受控重建。每种方案都要说明延迟、失败处理和可接受的不一致窗口；“延迟双删”只是缓解特定时序的工程手段，不是强一致性证明。

删除失败的重试需要可靠记录；只在进程内排一次任务，进程退出就可能丢失。Outbox（Transactional Outbox，事务发件箱）把业务更新和待发布事件写入同一个数据库事务，再由投递者重试失效通知；CDC（Change Data Capture，变更数据捕获）则消费数据库已提交的变更记录。这些办法降低通知丢失风险，但仍有投递延迟、重复和顺序问题，消费处理要支持幂等，即重复通知不会破坏正确结果。[事务发件箱与 CDC](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

可靠删除事件本身仍不能阻止上述 t5 的迟到回填。若采用缓存版本校验，需携带可比较的数据库版本，并在发布时原子地检查条件与写入；不能先检查、再无条件 SET。若版本高水位也随缓存删除或淘汰而丢失，就不能仅靠“和当前缓存值比版本”证明安全。应明确版本记录的保留、失效与恢复规则，按业务约定验收最长陈旧时间。这是协议设计推论，不是 Redis 自动提供的数据库一致性能力。

还要区分客户端缓存与这里的数据库 Cache-Aside：Redis 的客户端缓存跟踪用于通知客户端 Redis 键发生变化，并不自动跟踪外部数据库事务，也不是跨数据库一致性协议。[客户端缓存跟踪的适用范围](https://redis.io/docs/latest/develop/reference/client-side-caching/)

## 2. 穿透：反复查询不存在的数据

如果请求的对象根本不存在，每次未命中都会访问数据库。可在入口校验明显无效参数，对不存在结果使用较短的空值缓存，并对异常请求限流。

空值缓存也有失效问题：对象刚被创建时，原先缓存的“不存在”必须失效或等待到期。缓存值还应区分“不存在”“查询失败”“权限不足”，避免把临时数据库错误缓存成对象不存在。

Bloom Filter（布隆过滤器）是一种概率型集合判断结构，用多个哈希位置记录元素是否可能加入过。若必要位缺失，可判断“不在过滤器中”；位都满足只表示“可能存在”，仍可能误报，需要继续查询缓存或数据库。[官方 Bloom Filter 说明](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/)

```text
请求 user:999999 → 参数及访问条件校验 → 查询 Bloom Filter
  ├─ 判断不存在 → 在过滤器已完整、及时覆盖有效数据的前提下返回不存在
  └─ 可能存在 → 查询 Redis
                  ├─ HIT → 返回
                  └─ MISS → 查询数据库 → 按结果决定缓存
```

过滤器无假阴性的性质针对已正确加入且状态完整的元素，不保证业务记录永远不会被误拦。新增记录未及时加入、重建遗漏或过滤器丢失时，数据库里已存在的对象也可能被应用拦掉。应设计新增更新顺序、重建校验与故障时的降级；过滤器不能替代权威数据库。

普通 Bloom Filter 的位可能由多个元素共享，不能直接清位来删除一个元素；计数型等变体有不同代价，不能与普通实现混用。在 Redis Open Source 7.2.0 原生服务中，`BF.ADD`、`BF.EXISTS` 不是默认核心命令，需要 RedisBloom 等扩展能力。Redis Open Source 8.0.0 的官方统一分发整合了这些原模块能力，仍需核对实际版本和发行包，不能把 8.x 的支持情况套到所有安装。[8.0 分发变化](https://redis.io/docs/latest/develop/whats-new/8-0/)、[第三十三章扩展能力](/articles/redis-extensions.html)

## 3. 击穿：单个热点同时失效

![热点重建的控制环节](/assets/notes/redis/redis-study-stampede.svg)

同一个热点键过期，大量请求同时回源，即使总键数不多也能压垮数据库。Singleflight（重复请求合并）让同一个应用进程、同一协调组内的相同键请求共享一次正在进行的查询；它是应用机制，不是 Redis 命令，也不会自动跨机器协调。[Go singleflight 的范围与语义](https://pkg.go.dev/golang.org/x/sync/singleflight)

| 机制         | 工作范围             | 作用及代价                                           |
| ------------ | -------------------- | ---------------------------------------------------- |
| Singleflight | 单进程中的同一协调组 | 合并重复回源；需要处理等待超时和共享错误             |
| 分布式锁     | 多个应用实例         | 协调跨进程重建；需要租约、释放及写入保护协议         |
| 逻辑过期     | 业务缓存值中的有效期 | 允许在约定窗口内返回旧值，不适用于必须立即最新的结果 |
| 提前刷新     | 缓存尚有效时         | 提前重建热点，但也需要限制刷新并发                   |

教学假设：`product:1001` 失效，1000 个请求同时进入同一个进程的同一协调组，重建期间没有失败或主动取消：

```text
1000 个请求 MISS → 请求合并
  ├─ Leader（本次重建负责人）1 个 → 再查缓存 → 仍 MISS 才查询数据库
  |                                         → 校验发布资格 → 重建缓存
  └─ Followers（跟随请求）999 个 → 等待共享结果，或按业务允许返回旧值
                                     → 超时则有限降级，不无界排队
```

这里的 Leader 不是 Redis 节点选举角色。多进程各有独立 Singleflight 时，仍可能各自回源；若重建失败，应唤醒等待者、返回受控错误，并限制下一轮重试并发，不能让 999 个请求同时直接冲向数据库。

“逻辑过期”通常把数据及其业务期限一起缓存，允许在满足条件时先返回旧值，再由少量请求重建。采用这种方式前，必须明确旧值是否可接受、最长陈旧时间和重建失败策略；Redis 键本身仍可能被淘汰或丢失。

### 锁过期后，旧 Worker 仍可能写入

以下是教学时序，Worker 指应用中的重建任务：

```text
t1：A 获得重建锁，锁内保存唯一 Token（身份令牌）
t2：A 读取旧值 v1 后长时间暂停
t3：锁 TTL 到期
t4：B 获得新锁
t5：B 读取新值 v2，回填缓存并释放自己的锁
t6：A 恢复，将先前的 v1 写回缓存
```

唯一 Token 加原子比较后释放，可以防止 A 误删 B 的锁；**只在解锁时检查 Token，不能阻止 t6 的旧值写入。** 锁获取、锁释放、缓存发布是三个不同问题。[Redis 分布式锁的令牌与租约边界](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

发布阶段可按业务选择数据版本校验、原子条件写入，或 Fencing Token（栅栏令牌）：每次授予更大的序号，由实际接收写入的一方记录并拒绝过期序号。仅把序号放进请求但写入端不校验，没有保护作用；随机唯一 Token 也不等于递增栅栏令牌。版本或栅栏状态的持久性、淘汰和回退同样要纳入协议。具体锁与幂等边界见[第二十八章](/articles/redis-locks-rate-limits.html)。

### 回源压力的数值推演

假设热点键每秒 5000 次请求，缓存失效后这一秒全部直接回源，而数据库这类查询只能承受每秒 500 次，则发往数据库的查询需求是承载能力的 10 倍，不表示数据库能成功完成每秒 5000 次查询。QPS（Queries Per Second，每秒查询数）在这里按单位时间发起的数据库查询次数统计，与 Redis 请求次数区分。

如果同一波请求只有一个有效重建任务，则这一波只产生一次数据库重建查询；这是“每波一次”，不能不带时间单位就写成 QPS≈1。只有再假设某一秒内恰好只重建一次、其他请求均被合并或命中，才可说这一秒该键的回源 QPS≈1。锁过期、多实例、失败重试和等待超时都可能使实际次数增多。

## 4. 雪崩：大量键或整个缓存层同时失效

两种场景需要分开处理：

| 场景                | 压力路径                                  | 主要措施                                           |
| ------------------- | ----------------------------------------- | -------------------------------------------------- |
| A：大量键同时过期   | 相近时间到期 → 大量 MISS → 集中查询数据库 | TTL 抖动、分批预热、提前刷新、限制回源并发         |
| B：Redis 整体不可用 | 缓存访问失败 → 若全部旁路到数据库则过载   | 超时、限流、熔断、降级、本地缓存、数据库连接池保护 |

限流限制进入的请求速率；熔断是在持续失败时暂时停止调用故障依赖；降级则返回简化结果、明确拒绝或使用允许的旧值。它们都需要业务定义，不能把缓存异常当成普通 MISS 后无条件回源。

TTL 抖动指分散到期时间。例如教学假设基础 TTL 为 600 秒，实际为 `600 + 随机整数[-60, 60]` 秒，即 540～660 秒。这是应用计算的示意，不是 Redis 的随机过期命令。如果业务最多允许设置 600 秒，就应改用不突破上限的范围，例如 540～600 秒。它不能解决 Redis 整体不可用，也不能无限延长旧数据寿命。

提前刷新可在键仍有效时更新，但要限制刷新任务数量并保护发布顺序，避免预热或重试本身形成回源洪峰。返回旧值时应设置明确陈旧窗口，过窗后的行为也要预先确定。过期与内存淘汰分别见[第十三章](/articles/redis-ttl-lifecycle.html)、[第二十五章](/articles/redis-memory-eviction.html)。

缓存失效后，如果让全部请求不受限制地访问数据库，通常会扩大局部故障。应事先确定保护策略：哪些业务必须拒绝，哪些允许使用旧数据，哪些可以直接计算，而不是等故障发生时再临时决定。

## 5. 用权威状态、陈旧窗口与回源预算验收 {#_5-验证业务约束-而不只看命中率}

命中率高不等于缓存正确：权限信息陈旧、库存旧值回填、空值缓存掩盖新数据，都可能在高命中率下持续发生。

| 应用监控指标                          | 用途                                                |
| ------------------------------------- | --------------------------------------------------- |
| Cache Hit Ratio（缓存命中率）         | 命中次数 / 约定口径下的查询次数，需明确是否排除错误 |
| Cache Miss QPS（缓存未命中查询速率）  | 观察未命中是否突然集中在热点或一批键                |
| DB Fallback QPS（数据库回源查询速率） | 核对真实数据库压力；合并后不应直接等于 MISS 数量    |
| Rebuild Concurrency（重建并发数）     | 检查单键和全局是否超预算                            |
| Cache Error Rate（缓存错误率）        | 区分超时、连接失败等错误与正常未命中                |
| Stale Read Ratio（陈旧读取比例）      | 按业务版本或时间戳检查旧值比例，并统计陈旧时长      |
| P95/P99 Latency（95/99 百分位延迟）   | 识别回源、等待和重试对慢请求的影响                  |

这些是应用层监控口径，不是 Redis INFO 中必有的同名字段。还要记录回填失败、失效事件投递延迟和数据库连接池压力，不能只看命中率。[Cache-Aside 验收边界](https://redis.io/docs/latest/develop/use-cases/cache-aside/)

设计检查可以依次记录：权威数据在哪里；键如何映射实体；更新与失效由谁负责；最长不一致窗口多大；回源总并发能否承受；缓存完全不可用时怎样退化。这些是方案选择问题，没有一种通用 Redis 命令能代替业务判断。
