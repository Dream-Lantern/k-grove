# 第二十七章 缓存更新、穿透、击穿与雪崩

[返回本册目录](/collections/redis/)

缓存不是把查询结果 SET 进去就结束。真正困难的是更新竞态、失效时的回源压力，以及缓存不可用时怎样保护权威存储。本章保留原笔记的问题分类，补充每种方案的适用条件。

[![Cache Aside：命中与未命中必须分流](/assets/notes/redis/redis-study-cache-aside.svg)](/assets/notes/redis/redis-study-cache-aside.svg)

## 1. Cache-Aside：数据库与缓存各自提交

读取先查缓存，未命中再查数据库并回填；更新常见做法是先提交数据库，再删除对应缓存。这里没有跨系统原子事务：数据库提交后删缓存失败，旧值仍可能继续被读取。

另一种竞态来自慢读：请求 A 读到数据库旧值后暂停，请求 B 随后更新数据库并删除缓存，而 A 恢复后又将旧值回填。因此，先更新数据库再删除缓存，并不会自动消除所有旧值回填问题。

下面是应用协议的时序推演，不是 Redis 实验记录。假设两个请求之间没有额外的版本校验或串行协调：

| 时刻 | 请求 A：读取                            | 请求 B：更新                    | 缓存状态 |
| ---- | --------------------------------------- | ------------------------------- | -------- |
| t1   | 缓存未命中，读到数据库旧值 v1，随后暂停 | —                               | 空       |
| t2   | 暂停中                                  | 提交数据库新值 v2，然后删除缓存 | 空       |
| t3   | 将先前读到的 v1 回填                    | 已完成                          | 旧值 v1  |

如果 t3 才开始计算 TTL，那么 TTL 限制的是这次回填的存活时间，不能直接当成“从数据库提交起最多陈旧这么久”的证明。要阻止迟到的旧值覆盖，还需要可验证的版本、协调或重建协议。

可根据业务容忍度选择较短 TTL、失效重试、可靠变更事件、版本校验或受控重建。每种方案都要说明延迟、失败处理和可接受的不一致窗口；“延迟双删”只是缓解特定时序的工程手段，不是强一致性证明。

还要区分客户端缓存与这里的数据库 Cache-Aside：Redis 的客户端缓存跟踪用于通知客户端 Redis 键发生变化，并不自动跟踪外部数据库事务，也不是跨数据库一致性协议。[客户端缓存跟踪的适用范围](https://redis.io/docs/latest/develop/reference/client-side-caching/)

## 2. 穿透：反复查询不存在的数据

如果请求的对象根本不存在，每次未命中都会访问数据库。可在入口校验明显无效参数，对不存在结果使用较短的空值缓存，并对异常请求限流。

空值缓存也有失效问题：对象刚被创建时，原先缓存的“不存在”必须失效或等待到期。缓存值还应区分“不存在”“查询失败”“权限不足”，避免把临时数据库错误缓存成对象不存在。

Bloom Filter 可以在合适假设下挡掉部分必然不存在的查询，但要考虑数据写入顺序、误报率、重建和丢失。它不应成为漏写权威记录的借口，详见第 33 章。

## 3. 击穿：单个热点同时失效

![热点重建的控制环节](/assets/notes/redis/redis-study-stampede.svg)

同一个热点键过期，大量请求同时回源，即使总键数不多也能压垮数据库。可以用进程内 singleflight 或适用的跨进程协调合并重建，但必须控制等待时间、回源并发和失败后的释放。

“逻辑过期”通常把数据及其业务期限一起缓存，允许在满足条件时先返回旧值，再由少量请求重建。采用这种方式前，必须明确旧值是否可接受、最长陈旧时间和重建失败策略；Redis 键本身仍可能被淘汰或丢失。

## 4. 雪崩：大量键或整个缓存层同时失效

大批相同 TTL 的键在同一时刻到期，会集中回源。给 TTL 加抖动可以分散部分压力，但不能抵御缓存集群整体不可用。系统还需要连接和请求超时、熔断、限流、分级降级以及数据库容量预算。

缓存失效后，如果让全部请求不受限制地访问数据库，通常会扩大局部故障。应事先确定保护策略：哪些业务必须拒绝，哪些允许使用旧数据，哪些可以直接计算，而不是等故障发生时再临时决定。

## 5. 验证业务约束，而不只看命中率

命中率高不等于缓存正确：权限信息陈旧、库存旧值回填、空值缓存掩盖新数据，都可能在高命中率下持续发生。

新增教学检查清单是：权威数据在哪里；键如何映射实体；更新与失效由谁负责；最长不一致窗口多大；回源总并发能否承受；缓存完全不可用时怎样退化。这些是方案选择问题，没有一种通用 Redis 命令能代替业务判断。
