# 第9章 多模态与实时交互

## 9.1 实时多模态的处理链与交互方式 {#_9-1-实时多模态为什么特别难}

一次性文本处理可以容忍较长等待；语音、GUI 和机器人交互则要求持续感知和低延迟响应。多模态能力不只在于识别图片，还在于**持续输入、动作反馈、不同模态时间同步**。

### 模型处理链和交互方式是两个维度

| 模型/处理链             | 关注点                          | 主要权衡                                       |
| ----------------------- | ------------------------------- | ---------------------------------------------- |
| ASR → 文本LLM → TTS级联 | 模块之间传递文本，逐段流式连接  | 模块可替换，但会损失部分声学信息并引入跨段协调 |
| 原生语音/多模态端到端   | 如何保留声学信息及生成音频/文本 | 模态支持、流式粒度和可控性取决于具体模型契约   |

| 交互/轮替方式 | 关注点                               | 主要权衡                               |
| ------------- | ------------------------------------ | -------------------------------------- |
| 分轮/半双工   | 按轮切换输入与输出                   | 实现较简单，但重叠和自然插话受限       |
| 全双工        | 持续接收与输出，处理双讲、重叠及打断 | 回声、取消、已交付状态和轮次建模更复杂 |

级联与端到端均可与不同交互策略组合；“Omni”是常见命名，不能据此推定所有输入输出模态或实时能力。能打断TTS也不足以单独证明完整全双工对话建模。[Moshi论文v2](https://arxiv.org/abs/2410.00037v2)提供了语音模型与全双工框架结合的具体实例，不把该论文时延外推成通用SLA。

**VAD（Voice Activity Detection）**识别人声活动或停顿，**ASR（Automatic Speech Recognition）**将语音转成文字，**TTS（Text-to-Speech）**生成语音。

## 9.2 流式优化

- 流式 ASR：在用户还没完全说完时持续输出增量文字。
- LLM 增量输出：按句或语义片段尽早把内容交给 TTS。
- 流式 TTS：边收到文本边合成、播放。
- 端到端感知：把连续声学信号与上下文联合建模，减少纯文本中间表示的损失。

**注意**：书中的 `0.9–2.3s` 等数字是特定级联示例/假设下的延迟分解，不应作为所有语音产品的普遍性能指标。真实延迟取决于硬件、模型、网络、负载、VAD/ASR/TTS 参数和流式架构。

### 延迟应如何计算

用户体感首先关注 Time to First Audio（首次可听响应时延），其次是中断恢复和完整回答时长。分段记录：VAD End-of-Turn、ASR 首字、LLM 首 Token、TTS 首音频、网络传输、播放缓冲。端到端总延迟不能机械相加已经重叠的流式阶段。

### 从哪一刻开始计时，会改变首次响应数字

以下为合成教学时间戳，描述一次级联语音交互，不是模型实测或性能承诺。假设在同一时钟上记录：

| 时间    | 事件                     | 此时能确认什么                          |
| ------- | ------------------------ | --------------------------------------- |
| 0 ms    | 用户开始说话             | 开始采集输入                            |
| 500 ms  | ASR 已有部分文字         | 用户尚未说完，识别结果仍可能修订        |
| 1200 ms | 用户结束说话             | 事后标注的真实语音结束点                |
| 1350 ms | VAD/端点检测确认本轮结束 | 系统此刻才确认交棒，晚于真实结束 150 ms |
| 1410 ms | ASR 给出本例最终文字     | 可交给后续回答生成；此前已经在流式识别  |
| 1490 ms | LLM 首次输出             | 有了文字，不代表用户已经听到声音        |
| 1570 ms | TTS 产生第一段音频       | 音频还要经过传输与播放缓冲              |
| 1700 ms | 第一段音频实际开始播放   | 本例的首次可听响应终点                  |

相同终点对应不同的起点：从用户开始说话算是 `1700-0=1700 ms`；从用户结束说话算是 `1700-1200=500 ms`；从系统端点确认算是 `350 ms`；从最终 ASR 文字就绪算是 `290 ms`。报告必须写明起止事件；只说“首响应 350 ms”会隐藏端点等待，文字首 Token 的时间也不能代替可听时间。

ASR 在 500 ms 已经工作，与用户剩余讲话重叠；后续文本分块生成、TTS 和播放也可重叠。应沿实际事件时间线计算关键路径，不能把各模块从启动到完成的整段耗时全部相加。跨设备测量还需处理时钟同步或使用同一观测端，网络块到达也不等于扬声器输出。

### 用户插话后，还要等谁确认

继续用合成时间线：用户在 `2400 ms` 插话，检测器在 `2430 ms` 触发，控制器在 `2440 ms` 接纳取消请求，播放器在 `2520 ms` 返回针对当前播放代次的停止 ACK（Acknowledgement，确认）。检测等待为 30 ms，请求接纳后到确认又有 80 ms；按这份记录，用户插话到播放器确认停止共 120 ms，不能只报告 40 ms 的请求接纳时间。

ACK 必须明确表示“停止已完成”，而非仅“已收到命令”。若停止 ACK 同时返回该回复已播放 `12800` 个采样点，在明确的 16 kHz 单声道输出下对应 `0.8 s` 音频；还需音频—文本对齐才能确定哪些文字已交付。没有 ACK 或已播位置时，停止状态或交付范围保持 UNKNOWN。确认所覆盖的设备缓冲和观测边界也应记录；真实声学停止时刻可能还需要回环采集测量。

## 9.3 前台交互与后台深思考

把低延迟交互循环与复杂推理解耦：前台模型负责持续回应、确认和插话，后台模型负责耗时规划；后台结果通过结构化事件交接前台。需要处理旧任务取消、回答过期、插话优先级和权限问题。

## 9.4 Computer Use

基本循环：**观察截图/元素树 → 定位控件 → 采取鼠标键盘动作 → 重新观察并验证**。

| 感知方式          | 优势                           | 风险                              |
| ----------------- | ------------------------------ | --------------------------------- |
| 屏幕截图/视觉定位 | 接近人类 UI 操作，适配未知应用 | 坐标脆弱、UI 变化、分辨率影响     |
| DOM/无障碍树      | 结构信息丰富、元素可定位       | 并非所有 App 可用；可能缺视觉线索 |
| 混合方式          | 视觉验证 + 结构定位            | 实现复杂但更可控                  |

**安全原则**：填写文本和点击提交应区分权限。遇到支付、发送、删除、权限变更等动作，先识别当前页面状态并请求必要确认，再执行后读回校验。

### 一次“保存文件”需要怎样的反馈

假设用户授权保存当前文档。Agent 先观察文档名称、目标路径和是否存在覆盖提示，再点击保存；随后重新读取界面状态，并在权限允许时检查目标文件是否存在、内容或版本是否符合预期。“点击成功”只说明动作已发送，不能证明文件落盘。对话框遮挡、焦点错误、异步保存失败都可能让动作完成而任务失败；遇到覆盖已有文件等超出原授权的情况应停下确认，而不是重复点击。

## 9.5 机器人与 VLA

机器人操作把 Agent 的工具输出变成物理动作，常见框架涉及视觉-语言-动作（VLA）模型、实时控制、仿真和 Sim2Real。相比网页 Agent，物理环境存在碰撞、延迟抖动、观测误差、运动学限制，因此需要更严格的安全控制与低层控制器兜底。

### 同样的闭环，物理动作多了一层约束

VLA 是 Vision-Language-Action（视觉—语言—动作）模型；Sim2Real 指从仿真迁移到真实环境。以“把杯子移到托盘”为教学任务，观察需要杯子位置、可达范围和周围障碍；动作是交给控制器的受限运动目标；反馈来自关节、力/触觉或视觉；验证要确认杯子实际位于托盘且没有跌落。

| 环节         | GUI 保存                           | 移动杯子                              |
| ------------ | ---------------------------------- | ------------------------------------- |
| 动作被接收   | 点击事件送达应用                   | 控制指令被接收                        |
| 结果反馈     | 保存状态与文件读回                 | 传感器、物体位置与抓取状态            |
| 主要失败风险 | 覆盖错误文件、未落盘、重复提交     | 碰撞、滑落、观测过期、动作延迟        |
| 失败后的处理 | 停止重复提交，读取错误与原文件状态 | 由低层安全控制器限力/停机，再重新感知 |

物理动作不能仅靠语言模型下一轮解释来兜底；运动和安全约束须由独立控制链强制执行。这里比较反馈机制，不提供真实机器人运行或安全认证结论。

## 9.6 语音打断与已交付状态 {#_9-6-语音打断的关键是-已交付状态}

上游实现位于 `chapter6/streaming-speech/interruption_manager.py`。沿 `DuplexInterruptionManager.handle_barge_in()` 可以理解一次打断的状态变化：它将示例内存中的播放标志设为停止、清理待播音频、标记最后一轮被打断，再生成重规划事件；这里没有真实播放器停止 ACK。若当前未播放，则返回`ignored`，只表示未播放状态下不再取消。该方法没有外部输入event_id和目标播放代次，不能提供跨回复代次的事件去重。

源码节选（上下文依赖见原文件）：[chapter6/streaming-speech/interruption_manager.py](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter6/streaming-speech/interruption_manager.py#L307-L318)。

```python
self.stop_playback()
self.barge_in_count += 1
truncated_turns_count = 0
if self.dialogue_context:
    last_turn = self.dialogue_context[-1]
    if last_turn.role in ("assistant", "system", "agent") and last_turn.status != "interrupted":
        last_turn.status = "interrupted"
        truncated_turns_count += 1
        if truncated_length is not None and truncated_length < len(last_turn.content):
            last_turn.content = last_turn.content[:truncated_length] + " [interrupted...]"
        else:
            last_turn.content = last_turn.content + " [interrupted]"
```

这里的 `truncated_length` 由外部提供。未提供时，示例仅追加 interrupted 标记，不能证明文本已截断到用户实际听到的位置。真实系统需结合播放器的已播采样数/时间戳，以及音频片段与文本的对齐关系，区分“已生成”“已发送”和“已播放”。

[![语音打断：合法输入才触发重规划](/assets/notes/ai-agent/09-barge-in.svg)](/assets/notes/ai-agent/09-barge-in.svg)

这张 SVG 是事件入口概览：合法性检查分向“合法新输入”与“无效/过期/重复”，后者保持当前回复，不通向重规划。它没有展开 PCM、RMS、目标代次、播放判断或播放器 ACK 的独立节点；这些细节见 DOT 与第 9.7～9.8 节。图中的取消是请求路径，不能读成扬声器已停止。[放大查看 SVG](/assets/notes/ai-agent/09-barge-in.svg)。[原始 DOT 语义图源](/assets/notes/ai-agent/09-barge-in.dot)供对照，不是本版配图的可编辑源文件。

### 三份材料分别表达了什么

| 语义             | 现有 SVG                               | DOT 与正文的细化                                            |
| ---------------- | -------------------------------------- | ----------------------------------------------------------- |
| 输入及能量检测   | 从“新语音事件”起步，没有格式和检测节点 | DOT 从显式 PCM 帧到 RMS；§9.7 说明能量不等于人声            |
| 身份、重复与过期 | 合法性分支明确；目标代次没有单独展开   | DOT 增加 event_id/target_generation 校验，§9.8 区分两种标识 |
| 当前是否播放     | 只笼统提会话状态与取消策略             | DOT 有播放判断及未播放继续接收分支                          |
| 取消到停止       | 概览未画 ACK 与已播位置                | DOT 将取消请求、播放器 ACK、交付范围和 UNKNOWN 分开         |
| 重规划           | 合法分支可交外层处理，无效分支断开     | DOT 在交付状态处理后交外层，新输出还要检查代次              |

这些材料不是同一图的不同文件格式。SVG 用于建立概览，DOT 用于细读依赖和异常路径；不能根据概览缺一个盒子，就宣称对应状态已由上游实现。上游进程内示例也没有实现 DOT 中全部建议；下面的本地实验是另一个独立教学实现。

### 推荐实验：播放状态保护与事件身份分别测试

先用合成音频块检查状态机：开始播放后触发打断，检查 `is_playing=False`、待播队列清空、被打断轮次和 `barge_in_id`；在未重新开始播放期间再次调用，确认不会增加计数；新播放开始后再调用仍会打断新回复，因此它不是输入事件去重测试。这个测试验证状态逻辑，不代表麦克风、VAD、网络传输或播放器延迟已测量。

实际接入语音后，应记录用户开始说话、VAD 检测、停止提交音频、缓冲队列排空和首次新响应的时间。停止生成并不意味着扬声器立即停止播放，还需处理已进入设备缓冲的音频。后台任务结果应附带任务/回复代次，防止已取消的旧回复重新进入播放队列。

同一章的 `async-agent` 适合补做长任务取消实验：取消信号传给子进程后，要验证进程退出和晚到消息处理。文本 Agent 的取消问题与语音打断问题共享这一状态一致性要求。

## 9.7 明确音频输入契约，再谈检测

上游`calculate_energy()`会根据部分列表样本的幅度或字节长度猜测格式。同一int16波形的低振幅样本100，以列表、int16数组或显式int16列表输入时，可能得到不同RMS；不能从振幅判断位宽，也不能从字节奇偶判断PCM编码。

入口至少固定编码、dtype/位宽、signedness、endianness、采样率、声道布局和帧时长。例如`pcm_s16le, signed, little-endian, 16000Hz, 1 channel, 10ms`，每帧160样本、320字节。相同波形换成列表/数组/字节必须经同一显式格式转换到统一浮点范围。空帧、错误块对齐、NaN、超范围值应按契约拒绝或由协议缓冲层处理，不能悄悄更换编码。

独立的本地教学入口为 `examples/ai-agent/ch9-11-review/audio_state.py`，其中 `AudioSpec` 与 `normalize_audio()` 只接受本例固定的 16 kHz、10 ms、int16 单声道契约。它不是上游公开接口，也不是音频编解码库；立体声、奇数字节、空帧和其他不合约输入会被拒绝，实际链路还要验证设备格式与时间戳。

### RMS 能量门控与人声 VAD 的分工 {#rms活动不等于人声vad}

上游`is_voice_active()`只做能量与阈值比较；直流、高能量噪声、播放回声都可能触发。图中因此写作“RMS能量门控”；上述本地脚本的 `EnergyGate` 返回 `energy_active` 并明确 `speech_verified=false`，不把它包装成已识别人声。

累计检测窗口用毫秒表示。块长度不固定时，“连续3块”没有固定延迟含义；`sample_rate`参数存在也不自动完成时长归一化。真实实验要测误打断、漏检、双讲、噪声、AEC与端点检测。若采用[py-webrtcvad](https://github.com/wiseman/py-webrtcvad/blob/master/README.rst)，遵循该实现支持的16位单声道PCM、采样率与10/20/30ms帧要求；这些不是所有VAD的通用限制。

## 9.8 输入代次与播放器确认

公共字段及去重定义见 [第4章事件契约](/articles/ai-agent-tools-events.html#event-contract)。`barge_in_id`是接受打断后生成的输出流水号，不能替代输入`event_id`。同一本地脚本中的 `PlaybackGuard` 先校验输入身份和 `target_generation`：同ID重投递去重、旧代次晚到不影响新播放、新代次真实事件可请求取消；晚到的旧音频输出同样被挡住。

返回`CANCEL_REQUESTED`只代表取消请求被接纳。只有真实播放器ACK、设备缓冲状态与已播位置才能证明已停止或已交付范围。没有ACK/位置时保持UNKNOWN，不能把待播队列清空当成扬声器已经静音。未播放的输入继续交给接收流程，并非把用户话语丢弃。

这是进程内内存状态示例，未提供持久化去重、跨进程原子性、真实播放器或网络投递保障。检验同ID、同ID不同代次冲突、旧代次晚到、新代次真打断，并分开记录取消请求与停止确认。

### 最小离线实验：只验证输入和状态

在本项目仓库根目录，用 Python 3.11～3.13 运行，不需要麦克风、模型 API、GPU 或额外依赖：

```bash
python examples/ai-agent/ch9-11-review/audio_state.py
python -m unittest discover -s examples/ai-agent/ch9-11-review -p "test_audio*.py" -v
```

脚本用 160 个 int16 样本构造 10 ms 帧，分别输入列表、`array('h')`、小端字节以及显式归一化浮点列表；低振幅值 100 均按 `100/32768` 处理，避免靠振幅猜位宽。RMS（Root Mean Square，均方根）为 `sqrt(mean(x²))`；固定高能量交替信号可以让门控触发，但 `speech_verified` 仍为 false。

事件实验采用内存中的合成播放代次，输出逐项状态：

| 合成输入/状态                                    | 本地约定结果                              |
| ------------------------------------------------ | ----------------------------------------- |
| 当前代次正在播放，首次合法事件                   | CANCEL_REQUESTED；停止确认 UNKNOWN        |
| 同 event_id、同代次再次投递                      | DUPLICATE，不重复发取消                   |
| 同 event_id 改换代次                             | IDENTITY_CONFLICT，不改变新回复           |
| 新事件但 target_generation 已过期                | STALE_GENERATION，不影响当前播放          |
| 当前未播放                                       | IDLE_NO_CANCEL，继续接收输入              |
| 已请求取消但无播放器 ACK                         | 仍为 CANCEL_REQUESTED，不能确认停止       |
| 测试适配器提供匹配代次/事件的停止 ACK 和采样位置 | STOPPED，记录已播位置；ACK 本身由测试构造 |

这只验证合成数据与进程内状态转移，不测真实 ASR、VAD、声学人声识别、回声消除或播放时延。上游 `interruption_manager.py` 的变量置位、此处教学 Guard 的状态，以及真实播放器停止是三层不同事实；本地测试通过不代表完整语音链路通过。

## 本章要点 {#检查理解}

1. 实时交互需持续接收与输出，并处理重叠、打断和时间同步；离线录音识别只覆盖其中一环。
2. 流式阶段可能重叠执行，应沿时间线测量端到端延迟，避免重复累加。
3. Computer Use 在动作前确认页面、目标与权限，动作后重新观察实际结果。
4. GUI 与机器人 Agent 都依赖观察、动作、反馈闭环；物理动作还需低层控制器处理碰撞与运动约束。
