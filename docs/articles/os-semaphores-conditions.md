# 第九章 信号量、条件变量与丢失唤醒

> 阅读标签：通用同步原语 / POSIX条件等待。

信号量和条件变量用于协调执行流的等待与继续。一次可靠的等待要把条件检查、等待注册、状态修改和唤醒衔接起来，使资源已经就绪时的通知不会落在空隙中。本章先区分两种原语的语义，再用生产消费过程理解丢失唤醒。

## 1. 计数信号量的资源语义

信号量可以表示可用资源数量。wait/P 获取一个单位，不满足时阻塞或按接口报错；post/V 归还或增加单位，并使适用等待者获得推进机会。二值信号量与互斥锁的所有权规则也不完全相同。

有些教学实现用负数表示等待者数量，这是内部计数约定。使用 POSIX 接口时，应按该接口的返回值和计数语义理解状态。P/V 的计数更新与等待队列必须在同步协议中原子配合。[OSTEP Semaphores](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-sema.pdf)

## 2. 条件变量等待受锁保护的谓词 {#_2-条件变量不保存一份资源计数}

条件变量用于等待某个受锁保护的谓词，例如 queue 非空。通知只是提醒重新检查，不意味着某份资源已经永久留给这个等待者；没有等待者时的一次通知，也不应按信号量计数理解。

![从谓词检查到重新唤醒](/assets/notes/operating-systems/os-wakeup.svg)

教学伪代码：

```text
消费者：
    加锁
    while 队列为空:
        condition_wait：原子释放锁并等待，返回时重新持锁
    取出一项
    解锁
生产者：
    加锁，放入一项并更新谓词
    按协议通知等待者
    解锁
```

伪代码展示检查与等待的配合，实际使用时还要按 API 处理错误、取消和对象生命周期。

## 3. 唤醒后用 while 重新检查条件 {#_3-为什么必须用-while}

等待者从被唤醒到重新获得锁之间，资源可能已被其他线程取走；接口也可能允许虚假唤醒。如果只用 if，唤醒后直接访问队列而不重新检查，就可能尝试取出不存在的元素。

POSIX 条件等待要求调用方先持有指定互斥锁，等待过程原子释放并阻塞，返回时再次持锁。将它改成“解锁；普通 sleep”会重新打开丢失唤醒窗口。[pthread_cond_wait](https://man7.org/linux/man-pages/man3/pthread_cond_wait.3p.html)

## 4. 丢失唤醒的反例

反例：消费者检查队列为空后，还没进入等待队列；生产者放入数据并通知，因为此时没人等待而结束；消费者随后睡下，可能再没有下一次通知。数据已存在，它却一直睡眠。

修复时，需要正确协调谓词访问、等待注册和锁释放，而不是反复发送通知。内核等待队列也面临类似问题，只是所用原语和执行上下文不同。

## 5. 用有界缓冲区练习

容量 K 的队列可用 empty=K、full=0 和适用互斥保护组织生产消费。操作顺序与错误回滚要避免持有保护队列的锁等待根本不可能出现的资源。

验收不变量为 0≤队列项数≤K，不丢、不重复消费允许范围外的数据，停止和取消可解除等待。
