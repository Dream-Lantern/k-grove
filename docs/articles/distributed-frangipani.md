# 第二十四章 Frangipani 缓存一致性与恢复

> 阅读标签：Frangipani1997论文。

Frangipani 1997 年论文研究的是多个文件服务器共享同一个 Petal 虚拟磁盘、同时各自缓存数据的设计。共享底层存储，并不能让上层缓存自动保持一致；文件系统语义需要由锁交接、元数据日志和故障恢复共同维护。

## 1. 三层职责

[![Frangipani 1997：锁协议与Petal I-O分开](/assets/notes/distributed-systems/dist-frangipani.png)](/assets/notes/distributed-systems/dist-frangipani.png)

Frangipani 文件服务器执行文件系统操作并维护本地缓存；分布式锁服务管理适用的访问资格；Petal 提供共享、复制的虚拟磁盘。这里的缓存是文件系统层缓存，不是 CPU cache line 与主内存之间的硬件缓存协议。

本章的 write-back 指文件数据和元数据的延迟写回。缓存一致性由文件服务器与锁服务共同维护，CPU 缓存行协议属于另外的硬件层次。[Frangipani 论文 §2—5](https://rcs.uwaterloo.ca/papers/frangipani.pdf)

## 2. Sticky Locks：保留缓存锁，冲突时撤回 {#_2-缓存锁为什么有-busy-与-idle}

本地操作结束后，服务器可以保留缓存的锁与相关数据，无需在每次系统调用结束时都向远端释放锁。busy 表示正在使用，idle 表示本地暂未使用、但仍持有远端资格；进入 idle 状态并不意味着其他节点可以随意修改同一数据。

这种在没有冲突时继续保留锁的策略称为 Sticky Locks（粘性锁）。这里用 busy、idle 标记本地使用情况。锁可以服务后续本地操作，直到其他服务器申请冲突权限时才需要交接。

其他服务器需要冲突资格时，锁服务发起撤回。旧持有者处理撤回、等待适用操作结束，按下面的读写锁规则归还或降级。busy 时可以记录撤回需求，不是完全看不到 revoke。

### 锁服务与 Clerk 如何配合

论文最终采用多个锁服务器，以及嵌入每个 Frangipani 文件服务器的 Clerk（锁服务客户端模块）。Clerk 发出 Request、Release，锁服务器发出 Grant、Revoke；这些异步消息分别表达申请、释放、授权与撤回。Petal 数据读写走独立路径，不必由锁服务器转发。

锁服务用 Paxos 一致复制较少变化的全局状态：锁服务器列表、各服务器负责的锁集合，以及打开了各锁表且尚未关闭的 Clerk 列表。锁按组分配给服务器，单把锁的常规请求并不等于每次运行一次全局 Paxos；文件数据 I/O 也不经过这套全局状态共识。[Frangipani 1997 §6](https://rcs.uwaterloo.ca/papers/frangipani.pdf)

锁服务器故障后，相关锁组会重新分配；新的负责服务器联系打开了相应锁表的 Clerk，重建具体锁状态。这个过程与文件服务器故障后的元数据日志恢复各有职责：前者恢复锁服务状态，后者完成故障持有者留下的数据更新。

## 3. 交接顺序保护缓存一致性

读锁允许读取并缓存，写锁允许修改并暂存脏数据。不同冲突需要不同的交接动作：

| 原持有者 → 新请求 | 原持有者在同意交接前必须做什么       | 缓存能否保留     |
| ----------------- | ------------------------------------ | ---------------- |
| Read → Write      | 释放读锁前使相关缓存失效             | 不能保留有效缓存 |
| Write → Read      | 先将脏数据写回 Petal，再降级为读锁   | 降级后可保留缓存 |
| Write → Write     | 先写回脏数据，再释放写锁并使缓存失效 | 不能保留有效缓存 |

两个教学时序可以帮助区分：

```text
A 持有 Read，B 请求 Write
  → Lock Service 向 A 发 Revoke
  → A 停止相应使用、使缓存失效、Release
  → Lock Service 向 B 发 Grant(Write)
  → B 读取并修改

A 持有 Write 且缓存有脏数据，B 请求 Read
  → Lock Service 向 A 发 Revoke，要求消除冲突
  → A 保证必要元数据日志已持久化，将脏数据写回 Petal
  → A 同意降级为 Read，可继续保留缓存
  → Lock Service 向 B 发 Grant(Read)
  → B 从 Petal 读取已更新数据
```

![Frangipani 读写锁交接时序](/assets/notes/distributed-systems/dist-frangipani-lock-handoff.svg)

如果先授权 B，再等待 A 回写，B 就可能读到旧数据，A 的迟到回写也可能覆盖 B 的更新。锁记录与数据更新的顺序属于协议的一部分，不能仅凭“有锁”就认定数据一致。

## 4. 元数据日志与用户数据的保护范围 {#_4-日志针对元数据-不是所有用户数据}

论文使用 write-ahead redo logging 记录文件系统元数据更新；每个服务器的私有日志保存在 Petal，供其他服务器在它故障后接管恢复。不能将其扩大为所有用户文件内容都经过同样的事务日志保护。

元数据修改的日志先于对应永久位置更新；日志可先在内存组织，再按规定写到 Petal。调用返回与同步持久化之间仍有文件系统的具体语义，不能假定所有普通写调用返回都意味着任意故障下内容完整保留。

论文的具体安排是：先在本服务器内存日志追加更新记录，按请求顺序定期批量写到 Petal，日志写入后才允许更新对应元数据的永久位置（home location）。永久位置仍可延迟写回；需要回收旧日志空间时，必须先完成其保护的未落盘元数据更新。论文也提供同步日志写入选项，以额外延迟换取更好的故障语义。

以创建 `/data/a` 为教学例子，需要协调分配信息、inode 和目录项等元数据。可先组织描述这些变更的日志记录，在日志持久化后再将受保护的元数据写到永久位置；持锁期间缓存中可能暂有尚未写回的修改。这个例子表达写前日志约束，不规定论文的实际记录格式，也不把一次 `create` 等同于单条固定格式的日志。

元数据日志帮助恢复文件系统结构，不保证任意用户文件内容在崩溃后都符合应用的业务不变量。应用在合适的检查点调用 `fsync` 可获得更好的同步语义，但不能由此推导跨多个文件的任意业务操作自动成为原子事务。[日志顺序与保护范围：Frangipani 1997 §4](https://rcs.uwaterloo.ca/papers/frangipani.pdf)

## 5. 先恢复元数据，再释放故障者的锁 {#_5-恢复为什么要先于释放故障者的锁}

目录项和 inode 等元数据如果只改了一部分，直接释放锁会把不完整状态暴露给别人；永不释放又无法继续服务。恢复者取得故障服务器的日志与锁的相应管理权，重放尚未完成的适用更新，再释放。

日志序号帮助找有效边界，块版本帮助避免旧恢复覆盖后来的更新。恢复不是把整段旧日志无条件再写一次，也不是只凭某个 ready 文件是否存在决定所有资源可用。

按论文 §4、§6，可以把恢复过程展开为：

1. 锁服务在故障服务器的租约过期后，安排另一台机器上的 Clerk 执行恢复。受影响的锁暂不交给新业务使用者。
2. 恢复守护进程获得故障服务器日志的独占锁，确保同一时刻只有一个恢复者；恢复锁本身也受租约保护，恢复者再失败时可重新安排接管。
3. 定位循环日志的有效起止范围。每个 **512 字节日志块**带单调递增序号，序号比前一块小有助于识别日志结束；这是日志块序号，不是下面的元数据版本。
4. 按顺序扫描有效记录。对记录修改的每个元数据块，比较块上版本和记录的新版本：仅当块版本更小时应用该更新；否则跳过已完成的更新。元数据跨多个块时，各块分别带版本。
5. 将必要的待完成更新写到 Petal。日志处理完成后，释放故障者的锁并回收其日志，其他服务器才能继续；论文将释放锁和释放日志列为恢复后的收尾动作，不能先释放业务锁再回放日志。

![Frangipani 故障接管与版本化重放](/assets/notes/distributed-systems/dist-frangipani-recovery.svg)

例如教学记录要求把块版本推进到 8：当前为 7 则应用，为 8 或更高则跳过。这样即使恢复中再次崩溃，也不会无条件用旧记录覆盖已完成或更新的状态。论文还将释放的元数据块限制为继续用作元数据，避免它改存用户数据后丢失版本号，破坏旧日志的识别条件。

## 6. 租约检查与迟到写入的时间窗口 {#_6-论文自己保留了哪些限制}

客户端检查租约后，写到 Petal 前仍可能延迟。论文指出 Petal 当时不在每次写到达时验证租约，时间余量不能绝对排除迟到写，并讨论资源端验证方案。因此，其租约保证需要结合写入到达资源端之前的延迟条件理解。

具体风险可按时间线理解：A 检查租约有效 → A 或写请求发生长延迟 → 租约过期 → 其他机器完成 A 的日志恢复并释放其锁 → B 获得新资格并更新 → A 的旧写才到 Petal。由于 Petal 当时不校验写请求所依赖的租约，迟到写仍可能影响新持有者的数据。

论文在写入前检查租约还至少剩 `t_margin`，历史实现取 15 秒。这降低正常情况下的风险，但无法证明任意长暂停或网络延迟下都安全。论文 §6 将两类消除风险的方式作为后续方案讨论：写请求携带“生成请求时的租约过期时间减去 `t_margin`”，Petal 拒绝该时间早于当前时间的请求，要求两端时钟同步误差在 `t_margin` 内；或将锁服务与 Petal 更紧密集成，每次写携带租约 ID，由资源端拒绝过期 ID，无需这种时钟同步。它们不是论文当时已经实现的资源端拒绝机制。[租约迟到写与未来方案：Frangipani 1997 §6](https://rcs.uwaterloo.ca/papers/frangipani.pdf)

本章重点在于理解锁、缓存、日志与恢复之间的依赖关系；历史时间余量不应直接作为今天系统的安全证明。
