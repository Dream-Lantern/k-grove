# 第1章 AI Agent 基础与 Harness

AI Agent 围绕一个目标，反复执行“判断下一步、采取行动、读取反馈”的过程。例如，查找一项配置的使用方法时，它可以先搜索资料，再读取相关文档，最后根据找到的内容组织回答。

理解 Agent，可以先抓住三个组成部分：模型负责决策，上下文提供决策所需的信息，工具负责与外部环境交互。把这些部分组织成可持续运行的程序，就是本章要介绍的 Harness。

## 1.1 Agent 的基本组成 {#_1-1-现代-agent-是什么}

原书用 **Agent = LLM + 上下文 + 工具** 概括 Agent 的基本组成。

| 组成部分                                | 作用                   | 包含的内容或例子                                           |
| --------------------------------------- | ---------------------- | ---------------------------------------------------------- |
| LLM（Large Language Model，大语言模型） | 根据当前信息决定下一步 | 回答问题、选择工具、修正计划                               |
| Context（上下文）                       | 提供本轮决策所需的信息 | 用户目标、系统指令、任务状态、历史交互、工具结果           |
| Tools（工具）                           | 读取或改变外部环境     | 搜索、读取文件、查询数据库、调用 API、执行代码             |
| Harness（工程支架）                     | 组织运行过程并约束执行 | 驱动循环、维护状态、校验权限、处理错误、记录轨迹、管理退出 |

一次工具调用包含明确的分工：模型提出调用哪个工具、传入哪些参数；Harness 校验请求并执行工具，再把结果交给模型。工具是否执行成功，以实际返回结果和环境状态为依据。

API（Application Programming Interface，应用程序接口）是程序之间约定的调用方式。工具可以封装一个 API，让模型用约定的名称和参数请求执行某项操作。

### 用一个小任务串起四个部分

**教学任务：**“在给定的公开文档副本中，查找 DemoServe 1.0 的启动端口配置，告诉我默认端口、修改方式和来源；只读文档，不启动或修改服务。”DemoServe、下面的工具和文档内容均为合成教学材料，不对应真实项目或运行结果。

假设文档中写着：“默认端口为 9000，可用 `--port` 指定其他端口。”一次完整处理可以这样理解：

1. **Harness 准备输入。** 它把任务、只读范围，以及 `search_docs(query)`、`read_doc(path)` 两个工具的说明放入 Context。工具说明让模型知道有哪些操作、需要什么参数。
2. **LLM 选择搜索。** 模型输出 `search_docs(query="DemoServe 1.0 启动端口")` 这一调用请求。Harness 检查范围并执行，搜索工具返回文档路径和摘要。
3. **Context 加入搜索结果。** 下一次模型调用便能看到找到的路径。LLM 据此选择 `read_doc(path="demoserve-1.0/config.md")`，Harness 执行读取，把正文加入 Context。
4. **LLM 组织答案，Harness 检查后结束。** 模型根据文档说明默认端口与修改参数，并附上文档路径。执行侧核对版本、出处和答案是否得到正文支持，再返回结果。

这里，**Context 是传给模型的信息，LLM 提出下一步，Tools 实际读写环境，Harness 负责把它们接起来并管理执行。** 找到文档后，模型要再次收到对应内容才能据此回答；输出“读取文档”几个字本身不会打开文件。文档找不到时，系统应继续查找、追问或说明未完成，而不是把合成例子中的端口当作真实项目知识。

### Agent 与普通 Chatbot / Workflow 的区别

Chatbot（聊天机器人）、Workflow（工作流）与 Agent 可以从“下一步由谁决定”来理解；Autonomous Agent 指能在给定权限和预算内自行选择动作的自主智能体。

| 系统             | 决策与执行路径                                     | 适合的场景                           |
| ---------------- | -------------------------------------------------- | ------------------------------------ |
| 普通 Chatbot     | 主要根据输入生成文本                               | 问答、翻译、解释                     |
| Workflow         | 外层执行顺序由代码预先定义，模型参与其中的局部判断 | 审批、固定流程、确定性操作           |
| Autonomous Agent | 模型根据反馈选择下一步动作                         | 调研、代码修复、需要逐步探索的任务   |
| 混合系统         | 固定流程管理关键状态，模型处理其中的开放问题       | 同时需要灵活决策和执行约束的工程任务 |

选择时可以从任务的复杂度出发：一次模型调用能够完成的任务，保持单次调用即可；步骤固定的任务，适合 Workflow；需要根据中间结果调整动作的任务，再考虑 Agent 循环。

## 1.2 ReAct 循环与轨迹

**ReAct（Reasoning + Acting，推理与行动结合）是一种具体方法。** 原论文在提示示例中交错组织推理文本、动作和环境观察，让模型利用新信息调整后续行动；常见表达为 Thought（推理文本）、Action（动作）、Observation（观察）。这里的推理文本是可见的表达，不等于模型全部内部计算。[ReAct 原论文](https://arxiv.org/abs/2210.03629v3)

**一般工具调用循环是更宽的执行结构：读取上下文 → 选择动作 → 执行工具 → 写回结果 → 再次判断。** 它可以借鉴 ReAct，也可以直接使用结构化工具调用，不要求模型每轮都输出一段 Thought。看到多轮调用工具，还需要查看提示和消息组织方式，才能判断是否采用了原始 ReAct 方法。下面先按一般工具调用循环讲解，便于理解 Harness 的职责。

多轮中可观察的决策、调用和结果组成轨迹（Trajectory），用于还原任务经过。每一步的工具返回是环境观察，模型自己写的计划则仍是待执行的决定。

一轮执行可以拆成五步：

1. **准备上下文。** Harness 将用户目标、当前状态、可用工具和相关历史组织成模型输入。
2. **生成下一步动作。** 模型给出工具调用请求，或生成准备返回的答案。
3. **执行工具。** 对工具调用，Harness 校验参数、权限与执行条件，再调用对应工具。
4. **写入观察结果。** 工具的返回值、错误或状态变化进入上下文，成为下一轮决策的依据。
5. **判断继续或结束。** 根据结果、任务完成条件与剩余预算，继续执行、等待新输入，或结束任务并说明当前结果。

### 最小伪代码

下面的教学伪代码只保留工具调用循环和步数限制，便于对应前面的执行顺序：

```python
for step in range(MAX_STEPS):
    decision = llm(messages, tools=tool_catalog)
    if decision.is_final:
        return decision.answer
    request = validate_tool_call(decision.tool_call)
    authorize(request, user_context)
    result = dispatch_with_timeout(request)
    messages.extend([decision, result])
raise StepBudgetExceeded()
```

`messages` 保存模型当前可见的信息；`decision` 是本轮输出；工具执行后，调用请求和返回结果一同追加到 `messages`。达到 `MAX_STEPS` 仍未结束时，循环通过异常退出，避免无限运行。

这里的 `decision.is_final` 演示“返回答案”分支。配图中的完成条件校验、等待与拒绝，以及并行调用、幂等、事务、取消和重试竞态，需要在执行设计中进一步实现。工具输出较大时，也需要控制进入上下文的内容。

### 两轮工具调用怎样接到最终答案

继续使用第 1.1 节的合成任务。下面将模型输入和工具执行分开，**两次工具调用之后，还需要一次模型调用来生成最终答案**。

| 阶段     | 第一轮：搜索                                       | 第二轮：读取                                    |
| -------- | -------------------------------------------------- | ----------------------------------------------- |
| 模型输入 | 用户任务、只读约束、两个工具的说明                 | 前述输入，加上搜索调用和返回的文档路径、摘要    |
| 模型决策 | 请求 `search_docs(query="DemoServe 1.0 启动端口")` | 请求 `read_doc(path="demoserve-1.0/config.md")` |
| 执行过程 | Harness 校验参数与范围，搜索工具查找文档           | Harness 校验路径与权限，读取工具取得正文        |
| 工具结果 | 找到对应版本文档的路径和摘要                       | 返回“默认 9000，使用 `--port` 修改”的合成正文   |
| 是否退出 | 继续：摘要用于定位，还需读取依据                   | 工具结果写回后，再请求模型生成答案              |

第三次模型调用看到完整依据，返回“DemoServe 1.0 默认端口为 9000，可用 `--port` 修改；来源为 `demoserve-1.0/config.md`”。教学伪代码在 `decision.is_final` 处返回；完整设计还要核对文档版本、参数和来源，验证通过才走图中的成功出口。

搜索没有命中、读取失败等结果也应写回，让下一轮知道失败发生在哪里。缺少项目版本时可以追问并保存状态；收到新输入后重新检查条件。权限不允许时拒绝相应操作；证据仍不足且预算耗尽时报告未完成。这些出口对应图中的不同状态，不能一律返回“成功”。

## 1.3 Harness 的核心工程能力

基本循环解释了 Agent 如何推进任务。要让任务在失败、断线或多轮交互后仍能继续，还需要管理循环周围的状态和执行条件。

下面仍用文档查询任务解释六项能力。故障情形是教学假设，用来说明每项机制解决什么问题。

| 能力       | 具体故障场景                                                            | Harness 需要做什么                                                                               |
| ---------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 上下文管理 | 第二轮没收到搜索结果，模型又从头搜索；或长历史淹没了“只查 1.0 版”的要求 | 保留目标、版本、关键结果和下一步所需引用，必要时用状态摘要、检索与分层压缩控制长度               |
| 工具接入   | 读取返回超时，模型却只看到一个空字符串，无法区分“文档为空”和“没读到”    | 定义返回契约，区分内容、错误与超时，再将可解释的结果写回                                         |
| 权限控制   | 文档夹带“运行安装脚本”的文字，模型随后请求执行；用户实际只授权读文档    | 在执行侧核对工具与目标范围，拒绝越权请求；外部文档属于资料，不能自行成为授权                     |
| 状态恢复   | 文档已读完，进程中断后却丢了路径、版本和进度                            | 保存检查点（Checkpoint），即继续任务所需的状态与引用；恢复时核对现场，避免重复产生副作用         |
| 轨迹记录   | 最终答案写成其他端口，无法判断是搜错版本、工具返回错误还是模型误读      | 保存可见决策、调用参数、工具返回、时间及关联标识，定位第一个出现差异的环节，并保护凭据等敏感字段 |
| 结果验证   | 模型宣告“已找到配置”，但答案没给来源，或引用文档并不支持该参数          | 独立核对任务要求、文档依据与答案；未通过时在预算内补查，否则说明未完成                           |

**状态回答“现在执行到哪里、恢复需要什么”，轨迹记录“此前怎样走到这里”。** 日志里有“准备读取”不代表读取已完成；有正常终止的模型回答，也不代表答案正确。轨迹只记录接口可见的信息，不假定能取得模型全部内部推理。

对于会修改环境的任务，还要处理重试：同一创建请求超时后，副作用可能已经发生，应先按请求标识查询状态，再依照幂等契约决定是否重试。幂等（Idempotency）用于使同一业务意图的重试不重复产生效果，不能代替身份与权限检查。

例如，同一搜索请求连续重复且没有新增信息，可以触发无进展检测。此时系统应根据剩余预算选择调整方案、请求补充信息，或以“未完成”结束，并保留失败原因。

## 1.4 教学案例：性能评测任务的组织 {#_1-4-工程思考-评测任务的-agent-应该如何设计}

下面用一个简化的性能评测任务说明 Agent 与固定流程的配合，不涉及具体平台的内部实现或实测成果。

先解释两个术语：**Benchmark（基准测试）**是在明确的负载和环境条件下运行测试、收集可比较指标；**SLO（Service Level Objective，服务等级目标）**是对指标设定的目标值或目标范围。前者产生测量证据，后者说明怎样判定是否达标。[SLO 定义与指标选择](https://sre.google/sre-book/service-level-objectives/)

### 从自然语言到可执行输入

**教学需求：**“在已授权的实验端点上，检查并发 32 时，首个输出词元延迟的 p95 是否不超过 1500 毫秒，且请求成功率是否至少为 99%；先给我方案，批准后再执行。”数字是用户目标的假设输入，不是测得的性能或通用推荐值。

TTFT（Time to First Token，首个输出词元延迟）在本例约定为客户端发出请求至收到第一个输出词元的时间；Token（词元）是模型处理文本的基本单元。p95 指第 95 百分位数：将延迟从小到大排列，约 95% 的样本不超过该值；统计时需固定样本集合和计算方法。一次测试的方案至少要明确：

| 输入项     | 本例怎样约定                                                                                 |
| ---------- | -------------------------------------------------------------------------------------------- |
| 测试对象   | 已授权实验端点的标识、模型与推理服务版本                                                     |
| 工作负载   | 固定输入数据及其校验值、输入输出长度约束、生成参数；本例采用封闭式并发，即维持 32 个并发请求 |
| 测试窗口   | 预热与正式采样分开，事先约定持续时间、最少有效样本和超时；缺项时先补齐再批准                 |
| TTFT 口径  | 在正式窗口内成功且实际输出词元的请求上统计；失败与无词元请求单列，不能悄悄当作零延迟         |
| 成功率口径 | 正式窗口内成功请求数 ÷ 发起请求数；状态、截止时间和残留请求处理规则预先约定                  |
| 判定与权限 | TTFT p95 ≤ 1500 毫秒且成功率 ≥ 99%；记录用户批准的配置版本与可使用的端点范围                 |

任务可以按以下顺序组织：

**理解测试意图 → 生成方案 → 用户批准 → 冻结配置 → 执行 Benchmark → 分析证据 → 输出报告。**

在前半段，LLM 帮助理解用户描述、提出方案并解释选择。执行前，由固定流程完成配置校验、权限检查和用户确认，将批准后的配置保存下来。执行阶段调用评测工具，记录真实状态与结果；分析阶段再把这些结果交给模型，用于解释现象和组织报告。

这里的职责分界很重要：SLO 边界比较、配置校验、权限、任务状态变更和资产冻结由确定性服务处理。任务创建成功，应以数据库或工具返回的状态为依据；LLM 根据这些已确认的信息向用户说明进度。

“冻结配置”是把获准方案保存为确定版本，并关联输入、工具版本和结果，避免执行时偷偷换了模型或阈值。创建接口超时后，先按原请求标识查询任务，防止重复启动测试；轨迹同时保存方案版本、任务标识、调用与结果引用。

### 执行结束后怎样判定

下面是**教学判断规则，不含虚构的测量数据**。执行器按保存的阈值和比较符号检查结果，模型负责解释检查结论：

| 工具或校验器取得的证据                           | 应报告的结果                                                         |
| ------------------------------------------------ | -------------------------------------------------------------------- |
| 正式样本满足约定，两项指标都有有效值且均满足阈值 | 执行成功，本次测试点的 SLO 为 `PASS`                                 |
| 证据完整，其中一项指标超出目标                   | 执行成功，本次测试点的 SLO 为 `FAIL`；测试执行成功与性能达标是两件事 |
| 任务显示执行结束，但 TTFT 样本缺失               | 执行状态按实际记录报告，SLO 为 `UNKNOWN`，列出缺失证据               |
| 工具报错、超时或任务仍在运行                     | 报告对应执行状态；缺少足够测量证据时保持 `UNKNOWN`                   |

例如，工具只返回任务“已结束”，没有 TTFT 样本时，不能用“已结束”替代性能结论，应返回“缺少 TTFT 证据，当前无法判定”。这里也只检查并发 32 这一个测试点；SLO 边界搜索是进一步寻找满足目标的负载边界，需另有搜索范围、通过与失败两侧的证据及停止条件，不能由一个点推出最大容量。

## 1.5 从源码看懂一次 Agent 循环

理解前面的概念后，可以继续阅读原书配套仓库中的实现。本节引用固定提交 `dbc046eb896ac4e39aa19c7774c8bf49583b89a6`；教学图与伪代码用于说明执行设计，不表示该提交已经完整实现图中所有分支。本章也没有给出这些设计的实机验证结果。

| 阅读入口                    | 观察内容                                           |
| --------------------------- | -------------------------------------------------- |
| `chapter1/web-search-agent` | 一次调用如何形成轨迹，工具返回后如何进入下一步     |
| `chapter1/context`          | 提供给模型的消息发生变化后，模型能看到哪些任务信息 |

`web-search-agent` 的离线模式使用预写轨迹，适合对照调用、观察和结束的顺序。真实搜索能力与任务成功率需要另用实际模型、工具和任务验证。

读实际实现时还要检查结束条件：`execute_task()` 可在收到无工具调用的文本回复时结束，也处理带 `FINAL ANSWER:` 标记的工具调用轮次；迭代上限与异常有各自路径。正常返回中的 `completed` 表示取得非空终止文本，`success` 是其兼容别名，任务正确性仍需单独评分。源码入口见 [循环与返回语义](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter1/context/agent.py#L701-L960)。

### 上下文选择与源码节选

`ContextMode` 提供 `FULL / NO_HISTORY / NO_REASONING / NO_TOOL_CALLS / NO_TOOL_RESULTS` 五种配置，用来改变本轮发送给模型的消息。可以先看 `_prepare_messages_for_api()` 中的 `NO_HISTORY` 分支：它保留系统消息和最后一个用户任务，去掉该任务之后累积的交互记录。

这样，模型下一轮仍能看到任务目标，但看不到之前的工具结果。这个具体变化，有助于理解上下文如何连接多轮执行。

::: details 可选阅读：NO_HISTORY 源码节选

节选来自 [chapter1/context/agent.py](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter1/context/agent.py#L678-L692)，其上下文和依赖见原文件。

```python
messages = self.conversation_history
if self.context_mode != ContextMode.NO_HISTORY:
    return messages

# System prompt(s) are always kept as the static prefix.
windowed = [m for m in messages if m.get("role") == "system"]

# Anchor on the latest user task. Nothing after it is retained: those
# messages are precisely the previous-round history being ablated.
user_indices = [i for i, m in enumerate(messages) if m.get("role") == "user"]
if not user_indices:
    return windowed
last_user_idx = user_indices[-1]
windowed.append(messages[last_user_idx])
return windowed
```

### 上下文消融的对照方法 {#如何做一个有解释力的对照}

消融实验（Ablation Study）通过有控制地移除某类输入或能力，观察它对任务的影响。基线（Baseline）是用于比较的完整配置。下表区分**固定源码的处理方式**与**待实验检验的现象**，不把预测写成实测结论：

| 模式              | 这份实现实际改变什么                                                    | 可以观察什么，怎样解释                                                                   |
| ----------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `FULL`            | 保留累积消息并提供工具定义，正常结果写回                                | 作为基线，先确认工具可用、协议和任务能正常运行；完整输入不保证答对                       |
| `NO_HISTORY`      | 每轮请求只保留系统消息和最新用户任务                                    | 可能重复第一步，因为看不到上一轮结果；本地仍有轨迹，不等于已发送给模型                   |
| `NO_REASONING`    | 写回 assistant（模型回复）历史消息前移除其中的 `reasoning_content` 字段 | 可能观察到变化，也可能没有退化；它未关闭模型内部推理，接口不暴露该字段时应说明这一限制   |
| `NO_TOOL_CALLS`   | 调用模型接口时将 `tools`/`tool_choice` 参数设为 `None`，不提供工具定义  | 没有这条调用通道属于配置带来的结果；进一步观察模型是请求补充、停止还是给出缺乏依据的答案 |
| `NO_TOOL_RESULTS` | 正常执行工具并保存本地结果，写入模型消息的结果内容默认为空              | 可能重复调用、猜测或停止；要看模型实际收到的消息，而非仅看框架内的原始结果               |

对应实现分别位于 [字段过滤](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter1/context/agent.py#L534-L552)、[消息选择](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter1/context/agent.py#L660-L692)、[工具定义与请求参数](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter1/context/agent.py#L755-L785)和 [结果写回](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter1/context/agent.py#L842-L895)。`NO_TOOL_CALLS` 这个枚举名容易让人想到“删掉历史调用”，但这份实现主要移除的是工具定义；不要自行删除配对消息来模拟它，破坏工具协议造成的错误应与任务表现分开记录。

`NO_TOOL_RESULTS` 还需区分两种隐藏方式：`empty` 保留配对的 tool 消息（工具返回消息）但置空内容；`marker` 改为可见的隐藏提示，给模型增加了“内容被隐藏”的信号。二者属于不同实验设置。参数定义见 [专用实验脚本](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter1/context/run_experiment_1_1.py#L565-L605)。

### 按步骤完成一次对照

以下是供以后复现的步骤与命令，本次只核对源码和命令入口，未执行上游程序或调用模型。

1. **固定环境。** 获取上述固定提交，按对应 README 准备 Python 与依赖。记录模型服务商、明确的模型标识、工具、输入文件校验值、采样参数和迭代上限；密钥从环境变量读取，不写进笔记或日志。在线内容应固定快照。
2. **先读离线轨迹。** 在 `chapter1/web-search-agent` 执行 `python main.py --provider offline-demo --output demo.json`，对照 `trace` 与 `answer` 标记调用、观察和退出。这是预写数据回放，不能用于比较模型能力。
3. **跑通基线。** 在 `chapter1/context` 使用专用脚本先运行 `full`，核对实际发送的消息、工具参数、返回结果和最终答案。该脚本使用其自带的财务分析任务，不是前面的 DemoServe 例子。
4. **运行五组。** 保持同一任务、提供商、模型和预算，仅切换模式；每组重复多次、每次从干净会话开始。若某项服务不可用，记录该组未完成，不能以零分或零费用冒充有效测量。
5. **读证据再比较。** 保存每次输出目录中的 `evidence.json` 与校验值，检查 `api_turns`（实际请求与响应）、调用次数、重复动作、错误和答案依据，再按预先确定的任务标准判断正确性。区分“循环结束”“任务正确”和“答案有来源支持”。

专用脚本的命令模板如下，**需先将 `<PROVIDER>`、`<MODEL_ID>` 和输出目录替换为实际配置，再执行；调用在线服务可能产生费用**。两条命令分别用于基线和完整对照：

```text
python run_experiment_1_1.py --provider <PROVIDER> --model <MODEL_ID> --modes full --task guarded --hidden-result empty --max-iterations 5 --output-dir <BASELINE_OUTPUT_DIR>
python run_experiment_1_1.py --provider <PROVIDER> --model <MODEL_ID> --modes full no_history no_reasoning no_tool_calls no_tool_results --task guarded --hidden-result empty --max-iterations 5 --output-dir <COMPARISON_OUTPUT_DIR>
```

这里的 `--task guarded` 选择脚本内置的带约束任务，`--max-iterations 5` 是该对照采用的预算，不是实际完成轮数。`--hidden-result` 和 `--modes` 是这个专用脚本的参数；普通 `main.py` 的消融入口使用 `--mode ablation` 与 `--ablation-modes`，不能混用。每次重复应换用独立输出目录，并核对请求记录中的实际模型与后端。

移除 `reasoning_content` 后任务仍然成功，只能说明当前任务、模型与接口下没有观察到退化。没有退化和没有内部推理是不同判断；多个模式都报同样的鉴权或模型名错误，则应先修复环境，不能将其解释为消融效果。

完整的读码顺序可以串成：`ContextMode` → `_prepare_messages_for_api()` → `execute_task()` → 工具结果消息。做工程练习时，再依次补上预算管理、错误分支和结束验证。

## 本章要点 {#检查理解}

- Agent 通过模型、上下文和工具形成连续的决策与行动过程；Harness 负责组织这个过程。
- 模型输出工具调用请求后，由执行侧校验并执行，实际结果再进入下一轮上下文。
- 任务状态、授权和结果验证需要明确的执行机制；复杂工程任务适合把固定流程与模型决策结合起来。
- 运行过程应有预算、无进展检测和退出条件；等待、拒绝与未完成应分别说明。
