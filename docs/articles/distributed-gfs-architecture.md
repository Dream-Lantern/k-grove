# 第十六章 GFS 架构、Master 与元数据恢复

Google File System（GFS）把大文件拆成多个数据块，分散保存在一组存储节点上。Master 管理文件与数据块的对应关系，客户端先查询位置，再直接向存储节点读写数据。

理解这套架构，可以沿着两条线展开：正常访问时，客户端如何找到文件内容；故障恢复时，Master 如何重新获得文件目录和数据块的位置。

> 本章依据 2003 年 GFS 论文讨论历史设计，重点是工作负载、架构和恢复机制；当前 Google 存储产品的实现不在本文范围内。

## 1. 大文件工作负载与分块设计 {#_1-大文件工作负载为什么重要}

GFS 的设计背景是大量普通机器、巨大的文件，以及频繁发生的组件故障。文件访问以大范围顺序读取和追加为主。系统既要处理持续增长的数据，也要在部分机器或磁盘出故障后继续提供服务。

GFS 将文件划分为 chunk（数据块），论文选择的 chunk 大小为 **64 MB**。每个 chunk 有用于标识它的 handle，并在不同 Chunkserver 上保存副本。

大块设计与工作负载之间有直接联系：同样大小的文件，分块越大，需要管理的块越少，Master 保存的元数据也越少；客户端顺序访问较大范围时，可以在一段时间内持续使用同一个块的位置信息，减少查询。

这种选择也有代价。小文件或集中访问的少数 chunk 可能形成热点，负载分布仍然需要单独处理。因此，64 MB 应结合这篇论文的大文件访问模式理解。[GFS 论文 §2.1、§2.5](https://storage.googleapis.com/gweb-research2023-media/pubtools/4446.pdf)

**教学案例：150 MB 文件的读取。** 为与论文记法一致，以下都使用相同的 MB 单位计算，范围采用左闭右开区间：

| Chunk Index（块索引） | 文件范围      |
| --------------------- | ------------- |
| 0                     | [0, 64) MB    |
| 1                     | [64, 128) MB  |
| 2                     | [128, 150) MB |

读取偏移 70 MB 时，客户端计算 `floor(70/64)=1`，块内偏移为 `70−64=6 MB`。它以文件名和索引 1 查询 Master，例如得到 handle H101 及有效副本 S1、S2、S3；随后直接向合适副本发送 H101、块内偏移 6 MB 和读取长度。若读取范围跨过 128 MB，还要另行定位索引 2。这里的 H101 是教学标识，不是从索引 1 自动推导出的真实 handle。

## 2. 三类角色与客户端访问路径 {#_2-master-在什么路径上}

GFS 中的职责可以先分成三类：

| 角色                        | 主要职责                                        | 处理的信息                 |
| --------------------------- | ----------------------------------------------- | -------------------------- |
| Client（客户端）            | 代应用发起文件操作，查询元数据并访问存储节点    | 文件名、访问位置、数据内容 |
| Master（元数据管理节点）    | 管理命名空间、文件到 chunk 的映射、块位置和租约 | 文件目录与控制信息         |
| Chunkserver（数据存储节点） | 保存 chunk 副本，处理实际数据读取与写入         | 文件块内容                 |

**元数据描述“数据是什么、在哪里”，文件数据是实际存储的内容。** 这两个部分分别由 Master 和 Chunkserver 处理，客户端将它们连接起来。

以读取文件中的一段内容为例，访问过程是：

1. 客户端根据文件名和读取位置，确定目标 chunk。
2. 客户端向 Master 查询，获得对应的 chunk handle 和副本位置。
3. 客户端选择一个合适的 Chunkserver，携带 handle 和块内读取范围发出请求。
4. Chunkserver 将数据直接返回客户端。

客户端会缓存适用的元数据，后续访问可以复用有效的位置信息。这样，Master 负责查询与管理，文件内容的传输由客户端和 Chunkserver 直接完成。[GFS 论文 §2.3—§2.4](https://storage.googleapis.com/gweb-research2023-media/pubtools/4446.pdf)

[![GFS 架构总览：元数据查询、数据推送与写入控制](/assets/notes/distributed-systems/dist-gfs.png)](/assets/notes/distributed-systems/dist-gfs.png)

图中 Master 管理元数据，Chunkserver 保存文件内容；文件字节不经过 Master。写入的数据推送与 mutation 控制时序在下一章展开。

读取和写入对控制信息的要求有所不同：读取需要知道数据块的副本位置；写入还需要知道当前租约持有者 Primary 和参与写入的副本集合。Primary 是某个 chunk 在当前租约下承担写入排序职责的副本。

## 3. 元数据的组成与保存方式 {#_3-元数据不只有-handle-与版本号}

文件内容分散在 Chunkserver 上之后，Master 需要维护一份可查询的组织关系。学习时，可以把元数据分成两部分：文件与块的逻辑关系，以及块副本在当前集群中的实际位置。

| 元数据              | 回答的问题                        | 恢复依据                                 |
| ------------------- | --------------------------------- | ---------------------------------------- |
| 命名空间            | 有哪些目录、文件和 chunk          | 持久化操作日志与 checkpoint              |
| 文件到 chunk 的映射 | 一个文件由哪些 chunk 组成         | 持久化操作日志与 checkpoint              |
| chunk 副本位置      | 哪些 Chunkserver 当前保存了这个块 | 启动、节点加入时的报告，以及后续心跳交互 |

前两类描述文件系统的逻辑结构，需要可靠保存。位置信息随节点故障、重启和数据块变化而变化，Master 启动时向 Chunkserver 收集，并在运行过程中持续维护。

版本信息则用于识别落后的副本。例如，某个 Chunkserver 离线期间错过了写入，重新上线后需要结合版本检查，判断它持有的块是否仍适用。副本存在、位置已知和版本有效，分别对应不同的状态。

| 名称                    | 解决的问题                           | 教学例子                                            |
| ----------------------- | ------------------------------------ | --------------------------------------------------- |
| Chunk Index（块索引）   | 在一个文件中定位第几个块             | 偏移 70 MB 属于索引 1                               |
| Chunk Handle（块句柄）  | 标识具体 chunk，而非文件内的相对位置 | Master 分配的 H101；论文采用全局唯一的 64 位 handle |
| Chunk Version（块版本） | 区分同一 chunk 的有效与过期副本      | H101 的版本 8 与离线副本的版本 7                    |

一个块的各副本共享 handle，但它们的版本可能不同；不同文件中的索引 1 也不表示同一个块。[GFS §2.3、§4.5](https://storage.googleapis.com/gweb-research2023-media/pubtools/4446.pdf)

## 4. 操作日志与 checkpoint 的恢复过程 {#_4-操作日志与-checkpoint-如何配合}

Master 运行时需要快速查询元数据，也需要在进程崩溃后恢复这些状态。**操作日志记录关键元数据变更，checkpoint 保存某个时点的元数据状态。**

日志让恢复过程能够按顺序重现变更。如果从系统最初运行时的所有日志开始重放，随着运行时间增长，恢复所需的工作也会增加。checkpoint 提供一个较近的恢复起点，只需再处理它之后的适用日志。

从理解上，可以把恢复分成三部分：

1. **读取有效 checkpoint：** 恢复该时点的文件系统元数据状态。
2. **重放后续操作日志：** 将 checkpoint 之后已经持久化的变更按顺序补上。
3. **重建动态位置视图：** 向 Chunkserver 收集块信息，结合后续交互维护副本位置。

操作日志（Operation Log）记录关键元数据变更，例如命名空间、文件到块的映射及相关版本信息；它还定义并发元数据操作的逻辑顺序。先创建再删除与先删除再创建可能得到不同状态，因此恢复必须保留顺序。论文要求日志记录在本地及远程刷盘后才能向客户端确认；§5.1.3 更明确规定，本地和所有 Master 日志副本完成刷盘后才将该元数据变更视为提交，不是套用“多数日志副本确认”的 Raft 规则。Master 可批量刷盘来分摊成本。

检查点（Checkpoint）是一个可恢复的元数据状态快照，采用可直接映射内存的紧凑 B-tree 类格式。创建时 Master 切换到新日志文件，由独立线程生成覆盖切换点之前全部变更的 checkpoint；新的操作继续写入新日志。完成后 checkpoint 同样写到本地及远程。恢复只采用最新的**完整**检查点和后续日志；中途崩溃留下的不完整检查点会被检测并跳过，必要时退回更早的完整检查点及其后续日志。[GFS §2.6.3](https://storage.googleapis.com/gweb-research2023-media/pubtools/4446.pdf)

**教学案例：Master 崩溃后的时间线。** 目录状态仅用于展示逻辑重放，不表示真实日志编码：

```text
T0  完整 checkpoint：/data/a、/data/b
T1  已持久化日志 1：创建 /data/c
T2  已持久化日志 2：删除 /data/a
T3  已持久化日志 3：创建 /data/d
T4  Master 崩溃
T5  新 Master 进程启动，加载完整 checkpoint
T6  顺序重放 1、2、3：得到 /data/b、/data/c、/data/d
T7  联系 Chunkserver，收集实际 handle、版本和副本位置
T8  结合逻辑元数据与有效副本报告，重建可用元数据视图
```

删除的逻辑名字不必等于对应磁盘字节在 T2 立刻清空，物理清理由相应机制处理。恢复目录和映射也没有重新生成文件内容；内容仍保存在 Chunkserver。

[![GFS Master 的日志复制、Checkpoint、故障恢复与 Shadow Master](/assets/notes/distributed-systems/dist-gfs-master-recovery.png)](/assets/notes/distributed-systems/dist-gfs-master-recovery.png)

checkpoint 和日志恢复的是 Master 的元数据；文件内容仍由 Chunkserver 上的数据块副本提供。恢复设计也需要明确日志何时持久化、哪些变更可以对客户端确认，以及故障后从哪个位置继续。[GFS 论文 §2.6](https://storage.googleapis.com/gweb-research2023-media/pubtools/4446.pdf)

日志的作用包括记录变更顺序和确定恢复边界。分析它的 I/O 成本时，需要结合缓存、设备、刷盘和批处理；数据库同样可以使用日志和顺序写。

### Master Replication 与 Shadow Master

Master 复制（Master Replication）把操作日志和 checkpoint 保存在多台机器上。一个 Primary Master 负责元数据修改及垃圾回收等后台决策；进程故障可以重启，机器或磁盘故障时，由 **GFS 外部监控基础设施**在其他机器启动新 Master，使用复制日志恢复。客户端通过可调整的规范名称（论文以 DNS 别名说明）访问 Master。这是 GFS 2003 的接管机制，不是 Raft 自动选举。

影子 Master（Shadow Master）读取增长中的日志副本，按同样顺序更新自己的元数据结构；日志读取与应用进度使它可能稍微落后。它也在启动时向 Chunkserver 收集位置并持续交换状态信息，同时依赖 Primary 提供由其副本创建、删除决策导致的位置更新。Shadow 主要提供**只读访问**，可改善 Primary 不可用时的读取能力，适合容忍短暂元数据滞后的场景；不应把它当成自动接管全部写操作的 Leader。

Shadow 的滞后主要涉及目录、访问控制等元数据；文件内容仍直接来自 Chunkserver。元数据恢复与数据块丢失后的重复制属于两条路径：日志副本能重建目录，却不能凭空恢复已在所有 Chunkserver 上丢失的内容。[GFS §5.1.3 Master Replication](https://storage.googleapis.com/gweb-research2023-media/pubtools/4446.pdf)

## 5. 租约与版本管理的分工 {#_5-租约与版本管理解决什么}

多个副本保存同一个 chunk 时，写入还需要统一的执行次序。Master 通过租约，为该 chunk 选定一个承担写入排序职责的 Primary；其他参与副本按这个次序执行 mutation。

租约和版本管理分别处理两件事：

- **租约管理当前的排序资格。** 租约有有效期，重新授予时要遵循协议中的条件。暂时联系不上旧 Primary，只说明通信出现问题，仍需判断旧租约的有效状态。
- **版本帮助识别落后副本。** 新租约授予过程包含版本推进和副本确认，之后才能按协议向客户端提供相应信息。它有完整的操作顺序，不能只理解为切换 Primary 时修改一个计数器。

版本比较也要放回租约授予和故障恢复流程中理解：Master 需要结合自己的记录与副本状态，判断版本差异产生的原因。[GFS 论文 §3.1、§4.5](https://storage.googleapis.com/gweb-research2023-media/pubtools/4446.pdf)

按论文 §4.5，新租约涉及以下顺序：Master 推进 chunk version 并通知当前有效副本；**Master 与这些副本都先把新版本记录到持久状态，再通知客户端**，客户端之后才能开始相应写入。这里没有推断“Master 必须先于副本单独刷盘”之类论文未规定的内部先后。

例如 H101 从版本 7 推进到 8，S1、S2 参与并持久化，S3 离线而仍为 7。S3 重启报告 H101/7 时，Master 将其识别为过期副本（Stale Replica），查询响应不再把它作为有效副本返回，也不让它参与正常写入集合；后续由常规垃圾回收清理。客户端旧缓存仍可能暂时指向它，因此还要结合版本验证、缓存失效与重试理解。

若 Master 恢复时发现副本版本比自己记录的更高，论文把这解释为可能在授予租约期间故障，并把更高版本视为当前版本，不能反向把所有较高版本都降回自己的旧值。块版本用来识别错过租约时代的副本，不是每笔业务写入都递增的事务提交号。

## 6. 副本、校验与备份的作用 {#_6-重建副本不是备份恢复}

某个 Chunkserver 故障后，一些 chunk 的可用副本数会减少。通过把有效副本重新复制到其他节点，可以补回冗余，降低后续故障带来的风险。

学习容错时，还需要区分以下几类能力：

| 能力           | 主要作用                                   | 需要另外考虑的情况               |
| -------------- | ------------------------------------------ | -------------------------------- |
| 元数据恢复     | 从日志与 checkpoint 恢复文件系统的组织状态 | 故障后的服务接管与访问能力       |
| 数据副本与重建 | 在节点或磁盘失效后维持数据冗余             | 误删除、错误写入向副本传播       |
| 校验和         | 发现某些数据损坏                           | 数据来源的真实性与访问授权       |
| 独立备份       | 保留可用于恢复的历史数据                   | 备份覆盖范围、保留策略和恢复方法 |

删除延迟、校验和、版本检查与独立备份各有用途。复制恢复的是冗余数量；如果复制的内容已经发生逻辑错误，增加副本数量也会保留这个错误。

Master 的日志复制、恢复和备用读取角色，按 GFS 论文中的机制理解；Raft 选主属于另一套协议。元数据可恢复、数据块有副本和故障后能够接管服务，需要分别分析。

## 本章要点

- GFS 的大块设计服务于大文件、顺序读取和追加为主的工作负载。
- 客户端查询 Master 获取元数据，文件内容在客户端与 Chunkserver 之间直接传输。
- Master 通过日志与 checkpoint 恢复逻辑元数据，通过 Chunkserver 报告重建动态位置信息。
- 租约组织写入排序，版本帮助识别落后副本；副本重建、数据校验和备份分别承担不同职责。
