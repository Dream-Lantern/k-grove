# 第 22 章：容量、延迟与积压排查

> 版本基线：Kafka Broker 3.9、Java Client 3.9 与 librdkafka v2.8.0。
>
> 学习目标：用相同时间窗关联生产、复制、读取和业务处理，不把 lag、QPS 或 CPU 的单个数值当成根因。

## 1. 先确定慢在哪一段

生产者排队、网络确认、Broker 追加复制、事务可见性、Consumer 拉取、业务线程池和外部数据库都会贡献延迟。先界定症状是发送变慢、消费追不上，还是读取及时但业务完成晚。

同时明确测量口径：从创建事件到入队、到投递报告、到消费者收到、到外部效果完成，得到的是不同延迟。只测异步 send 函数返回时间，不能作为端到端消息延迟。

![分层观察积压](/assets/notes/kafka/kf-lag.svg)

| 观测点 | 事件                                 | 与前一观测点的关系                                                                                 |
| ------ | ------------------------------------ | -------------------------------------------------------------------------------------------------- |
| T0     | 业务创建事件                         | 以事件 ID 关联后续记录                                                                             |
| T1     | Producer 接受发送                    | T0→T1 包含应用序列化、等待与入队                                                                   |
| T2     | 应用收到 Delivery Report（投递报告） | T1→T2 包含批次等待、网络、适用的复制确认、重试和回调调度                                           |
| T3     | Consumer 取得记录                    | T3−T2 是有符号的观测差。回调服务延迟或确认策略可能使 T3 早于 T2。事务未提交也可能使 T3 显著晚于 T2 |
| T4     | 外部业务成功                         | T3→T4 包含 Worker 排队及数据库操作                                                                 |
| T5     | 安全位点提交得到确认                 | T4→T5 包含等待分区前沿、批次提交和请求往返                                                         |

同机耗时用单调时钟。跨机器只比较经过同步的时间戳，并记录时钟误差。异步路径可能重叠，不能把阶段分位数直接相加。成功投递与业务成功分别记录，业务成功与恢复位置提交也分别记录。

## 2. 结合可见性与业务进度解释 Lag {#_2-lag-是位置差-不总是消息条数}

常见组监控把日志末端与提交位置比较，但提交位置未必等于业务已完成位置；事务隔离下可见边界也未必等于物理末端。压缩、控制记录或过滤导致的 Offset 空洞，使差值不能总解释成未完成业务记录数。

应分别观察每个分区的读取与提交位置、业务在途量、最老未完成事件的年龄和处理成功率。即使总 lag 稳定，也可能是其他分区的积压下降，掩盖了某个热点分区的恶化。

取同一个 Topic-Partition 的教学快照：

| 指标                                  |   示例值 | 含义                                      |
| ------------------------------------- | -------: | ----------------------------------------- |
| Log End Offset（日志末端偏移量，LEO） |     1200 | Leader 日志的下一位置                     |
| Committed Offset（已提交恢复位置）    |     1000 | 组已提交的下一位置                        |
| Consumer Position（客户端读取位置）   |     1150 | 当前客户端的下一读取位置，以 API 契约为准 |
| 业务安全完成前沿                      |     1050 | 应用可以安全提交的下一位置                |
| 业务在途任务数                        | 单独计数 | 应用已经接收但尚未完成的任务数量          |

以 LEO 为末端时，提交 Lag 为 200，读取位置领先提交位置 150，末端领先读取位置 50。若监控工具取的是高水位 HW 或最后稳定偏移量 LSO，计算应使用它实际返回的末端。日志压缩可移除旧记录，事务控制记录不交付业务，`read_committed` 跳过已中止记录并受 LSO 限制。应用过滤和 Worker 乱序完成也会影响实际业务量。各差值都是 Offset 距离。

例如同一窗口里 P0 的 Lag 从 500 升到 900，P1 从 500 降到 100，总数仍为 1000。检查 P0 的输入速率、Key 分布与完成前沿，才能判断它是否正在形成热点。

## 3. 速率推演比盲目加实例更有帮助

教学例子：持续输入每秒 1000 条，消费业务只能完成 800 条，则积压持续增加。修复后完成能力到 1500 条，净追赶约 500 条/秒；若积压 30000 条，理想追赶约 60 秒。

这个纸面算例假定速率恒定、不再发生故障且没有热点，不代表实际 SLA。下游限流、Key 热点、重平衡和重试都可能改变速率。增加成员还会受到分区分配的限制，因此不能从实例翻倍直接推导出吞吐翻倍。

令输入速率为 λ，成功完成速率为 μ，两者以同一窗口内的实际业务记录计数。积压变化近似为 `(λ − μ) × 窗口秒数`，积压有存量且 μ 大于 λ 时，追赶时间约为 `存量 / (μ − λ)`。本例先以 200 条/秒累积，再以 500 条/秒追赶。速率相等时已有积压可能维持不变。突发结束后可用余量追赶，下游限流会压低持续 μ，Rebalance 则可能暂时降低 μ。热点分区必须独立满足追赶条件。成员多于可分配分区时，新成员可能空闲。计算应使用稳定可持续能力，Offset 差不能直接替代业务记录存量。

## 4. 从逻辑数据估算副本与恢复空间 {#_4-存储容量不能只算一份业务数据}

先用保留周期内的平均输入字节量估算逻辑数据，再考虑压缩效果、RF、索引、日志清理临时空间、重分配流量与安全余量。即使集群整体还有大量空闲空间，某个 Broker 或日志盘也可能先满。

监控离线分区、欠复制、低于 minISR、请求耗时与错误、网络磁盘利用、配额和客户端队列。不同指标反映不同风险，ISR 缩小不一定立刻离线，但可能已经减少可靠写入余量。

假设订单 Topic 用 Delete 策略，按时间保留 3 天，无 `retention.bytes` 上限。平均写入 1000 条/秒，每条压缩前业务数据 1024 字节。压缩后按原大小的 50% 估算，Replication Factor（副本因子，RF）为 3。用十进制 GB：

- 单副本载荷为 `1000 × 1024 × 86400 × 3 × 0.5 = 132.71 GB`，全副本约 398.13 GB。
- 日志批次头、Segment（日志段）和 Index（索引）等按载荷额外加 10% 估算，约 437.94 GB。此处未把网络协议开销当作磁盘占用。
- 另留 60 GB 给清理、滚动延迟和迁移期间的新旧副本重叠。若要求空闲占配置容量 20%，总配额约 `(437.94 + 60) / 0.8 = 622.43 GB`。

三台均衡 Broker 平均约 207.48 GB，但迁移峰值可能集中在单节点或日志盘，需按分区大小、当前副本位置和最坏迁移计划逐盘计算。时间保留按段回收，删除有延迟。若启用 `retention.bytes`，它按分区限制，实际保留窗可能缩短。Compact 的占用受 Key 基数、更新速率、墓碑和清理工作空间影响，应单独建模。

| 来源                              | 可检查的指标                                                                                                        | 诊断用途                                               |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Java Producer 客户端指标          | `record-send-rate`、`request-latency-avg`、`record-queue-time-avg`、`record-retry-rate`、`record-error-rate`        | 区分本地排队、网络请求和失败重试                       |
| C v2.8.0 Statistics               | `msg_cnt`、`msg_size`、`brokers[].rtt`、`brokers[].txretries`，另记 Delivery Report 成败                            | 观察本地积压、Broker 往返和内部重试                    |
| Kafka 3.9 Broker JMX              | `RequestQueueTimeMs`、`LocalTimeMs`、`RemoteTimeMs`，按 Produce/Fetch 请求拆分                                      | 比较 Broker 排队、处理和等待远端的时间                 |
| Kafka 3.9 Broker / Controller JMX | `UnderReplicatedPartitions`、`UnderMinIsrPartitionCount`、`OfflinePartitionsCount`                                  | 观察复制风险和可用性，结合节点角色及主机磁盘、网络指标 |
| Consumer 客户端与应用             | Java `records-lag-max`、`fetch-rate`、`rebalance-total`。C `consumer_lag`、`cgrp.rebalance_cnt`。提交错误由应用统计 | 客户端读取 Lag 与组提交 Lag 要分别查询，结合当前前沿   |
| 业务自定义指标                    | 队列条数、最老在途年龄、业务成功率、数据库等待及处理延迟                                                            | 区分读取正常与处理停滞                                 |

## 5. 调优一次回答一个假设

若怀疑批次过小，固定其他条件观察批次与吞吐、尾延迟；若怀疑下游慢，先看业务耗时和队列；若重平衡频繁，核对处理时长与成员存活，而非直接增加 Fetch。

记录版本、消息分布、可靠性设置、负载、观察时间与变化。历史硬盘或 QPS 数字按其测量环境理解；性能恢复应以持续处理能力、错误和业务结果验收，清空 Topic、跳过积压或重置位点会改变工作范围。本册没有运行压测或修改任何集群。

### 三组对照诊断

使用隔离的 Kafka Broker 和 Java Client 3.9，订单 Topic 三分区，固定 1 KiB 事件、RF、acks、提交周期与机器配置。每轮预热 30 秒、测量 120 秒，从同一输入速率开始，逐秒采集指标，分别做基线与变更轮。以下为实验设计。

| 场景                  | 仅改变的变量                                                               | 预期、观测与回退                                                                                                                        |
| --------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| A · Producer 批次等待 | 以每秒 100 条和均匀 Key 输入，把 `linger.ms` 从 0 调到 20                  | 批次可能变大，低流量尾延迟可能上升。看发送吞吐、队列、平均与 P95/P99、错误和重试。超过预先设置的延迟预算就恢复 0                        |
| B · 下游处理不足      | 固定每秒 1000 条及三个串行分区 Worker，将每条人工处理时间由 2 ms 调至 5 ms | 理想总能力从 1500 降至 600 条/秒。看 Lag、读取位置、完成前沿、队列及成功完成速率。队列触及上限或窗口结束后移除延迟并观测追赶            |
| C · 热点 Key          | 保持速率与处理时间，把均匀 Key 改为 90% 同一个 Key                         | 观察分区流量、分区 Lag 与每分区完成速率。固定热点分布再独立从 3 个成员增至 4 个，比较是否仅增加空闲成员。积压超预算就恢复原分布和成员数 |

P50、P95、P99 分别表示对应百分位的延迟。对比时保留相同采集边界、工作负载与时间窗，同时看吞吐、错误率、Lag 与业务成功率。低平均延迟可能来自错误提前返回，高 CPU 也可能只是正常工作负载。跨章节的业务验证见[订单故障推演](/articles/kafka-order-events.html)。

生成器可用定速循环发送固定长度记录。预先挑选能均匀落入三个分区的 Key，每条记录带序号和产生时间。Consumer 用每分区单一串行 Worker 模拟业务延迟，使用有界队列，在成功后记录前沿。用组 Describe 采样提交 Lag，采样期间不要重置组位点。每轮用独立的等价 Topic 或先排空前一轮，避免把旧积压误记成新变量的影响。
