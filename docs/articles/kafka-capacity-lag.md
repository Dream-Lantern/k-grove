# 第 22 章：容量、延迟与积压排查

> 版本导航：Broker3.9 / Java3.9与C2.8按参数区分。
>
> 学习目标：用相同时间窗关联生产、复制、读取和业务处理，不把 lag、QPS 或 CPU 的单个数值当成根因。

## 1. 先确定慢在哪一段

生产者排队、网络确认、Broker 追加复制、事务可见性、Consumer 拉取、业务线程池和外部数据库都会贡献延迟。先界定症状是发送变慢、消费追不上，还是读取及时但业务完成晚。

同时明确测量口径：从创建事件到入队、到投递报告、到消费者收到、到外部效果完成，得到的是不同延迟。只测异步 send 函数返回时间，不能作为端到端消息延迟。

![分层观察积压](/assets/notes/kafka/kf-lag.svg)

## 2. 结合可见性与业务进度解释 Lag {#_2-lag-是位置差-不总是消息条数}

常见组监控把日志末端与提交位置比较，但提交位置未必等于业务已完成位置；事务隔离下可见边界也未必等于物理末端。压缩、控制记录或过滤导致的 Offset 空洞，使差值不能总解释成未完成业务记录数。

应分别观察每个分区的读取与提交位置、业务在途量、最老未完成事件的年龄和处理成功率。即使总 lag 稳定，也可能是其他分区的积压下降，掩盖了某个热点分区的恶化。

## 3. 速率推演比盲目加实例更有帮助

教学例子：持续输入每秒 1000 条，消费业务只能完成 800 条，则积压持续增加。修复后完成能力到 1500 条，净追赶约 500 条/秒；若积压 30000 条，理想追赶约 60 秒。

这个纸面算例假定速率恒定、不再发生故障且没有热点，不代表实际 SLA。下游限流、Key 热点、重平衡和重试都可能改变速率。增加成员还会受到分区分配的限制，因此不能从实例翻倍直接推导出吞吐翻倍。

## 4. 从逻辑数据估算副本与恢复空间 {#_4-存储容量不能只算一份业务数据}

先用保留周期内的平均输入字节量估算逻辑数据，再考虑压缩效果、RF、索引、日志清理临时空间、重分配流量与安全余量。即使集群整体还有大量空闲空间，某个 Broker 或日志盘也可能先满。

监控离线分区、欠复制、低于 minISR、请求耗时与错误、网络磁盘利用、配额和客户端队列。不同指标反映不同风险，ISR 缩小不一定立刻离线，但可能已经减少可靠写入余量。

## 5. 调优一次回答一个假设

若怀疑批次过小，固定其他条件观察批次与吞吐、尾延迟；若怀疑下游慢，先看业务耗时和队列；若重平衡频繁，核对处理时长与成员存活，而非直接增加 Fetch。

记录版本、消息分布、可靠性设置、负载、观察时间与变化。历史硬盘或 QPS 数字按其测量环境理解；性能恢复应以持续处理能力、错误和业务结果验收，清空 Topic、跳过积压或重置位点会改变工作范围。本册没有运行压测或修改任何集群。
