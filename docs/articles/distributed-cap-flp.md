# 第五章 CAP、FLP 与最终一致性

> 阅读标签：通用协议/应用模型，具体前提见本章。

CAP 不是数据库选型中可随意勾选的三个特性，FLP 也不意味着“共识不可能实现”。理解这些结论，应先明确模型，再看哪些保证无法同时获得。忽略前提、只记口诀，容易将正常的安全拒绝误判为设计缺陷。

## 1. CAP 中的词要按模型解释

这里的一致性指适用读写对象的原子、线性一致语义，不是 ACID 中的业务约束；可用性要求每个非故障节点收到的请求最终得到满足服务规范的响应，单纯快速报错不能冒充完成读写。分区表示节点间消息可能无法送达。

当分区阻断了必要信息，又要求双方持续完成操作，就不能同时保留实时一致的单副本语义。它不是说网络健康时也必须永久丢掉某一项。[Gilbert 与 Lynch 的 CAP 讨论](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer2.pdf)

[![CAP：分区中的可用性与一致性边界](/assets/notes/distributed-systems/dist-cap.svg)](/assets/notes/distributed-systems/dist-cap.svg)

## 2. CP 不等于整个集群全部不可用

纸面推演：三个投票成员发生 2+1 分区，多数侧可能在协议允许时继续处理相关写入，孤立侧不能自行确认同等保证的写入。这里牺牲的是“所有非故障节点都能完成这类请求”的要求，不是宣布所有业务入口必须同时停机。

AP 路线若接受分区内的某些独立更新，就必须处理冲突、合并与恢复。库存扣减、购物车和只读推荐可以采用不同契约，不能用一个标签概括整个公司的系统。

## 3. FLP 限制的是无条件终止保证

在完全异步、确定性的消息传递模型里，即使只允许一个进程崩溃，也无法保证每一种合法执行都能终止并完成共识。这不表示每次运行都会失败，更不表示安全性无法维持。[Fischer、Lynch、Paterson 原论文](https://groups.csail.mit.edu/tds/papers/Lynch/jacm85.pdf)

工程协议会引入随机退避、故障怀疑和最终有利的时序条件来争取活性。超时用于推动尝试，不是获得了“对方已死亡”的逻辑证明；网络长期不满足条件时，进展仍可能停止。

## 4. BASE 是设计取向，不是自动收敛算法

原笔记用基本可用、软状态、最终一致描述允许中间差异的路线，可以保留作入门框架。但最终一致性必须说明：在不再有新更新且通信与修复持续完成等条件下，副本如何收敛、冲突如何处理。

异步复制没有自行解决所有冲突；最后写入获胜会丢掉某些并发意图；永久丢失的更新也不会因为“等得足够久”自行出现。需要明确复制、反熵、版本和业务合并规则。

## 5. ACID 的 C 与 CAP 的 C 不同

ACID 中的一致性侧重事务前后满足约束与不变量，隔离级别和应用校验共同影响业务正确性。一个数据库可以提供 ACID 事务，同时对只读副本允许旧读；也可以提供线性一致单键操作，却没有跨键事务。

学习时，应分别列出请求成功条件、允许观察的状态、分区期间拒绝请求的范围，以及恢复后的合并策略。明确这四项，比单纯讨论“选 CP 还是 AP”更有助于设计可执行的接口。
