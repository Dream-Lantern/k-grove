# 第五章 CAP、FLP 与最终一致性

> 阅读标签：通用协议/应用模型，具体前提见本章。

CAP 和 FLP 分别讨论特定模型下的保证范围。CAP 关注网络分区发生时的一致性与可用性，FLP 关注完全异步模型中共识的终止保证。学习时先明确节点、消息和故障假设，再观察协议保留哪些性质、在什么条件下取得进展。

## 1. CAP 中的词要按模型解释

CAP 分别表示一致性（Consistency）、可用性（Availability）和分区容错（Partition Tolerance）。讨论前先固定服务契约：本节分析一个初值为 0 的读写寄存器，`write(v)` 设置值并返回成功，`read()` 返回值；这些合法操作没有“任意拒绝即可完成”的分支。

| 概念 | 本节采用的含义 |
| --- | --- |
| C：一致性 | 读写满足第四章的线性一致性，即可解释为保留实时先后的单副本顺序；不是 ACID 的业务约束 |
| A：可用性 | 每个非故障节点收到的请求最终得到响应；理论定义没有指定业务超时上限或成功率百分比 |
| P：分区容错 | 在节点间消息可能丢失、分区双方不能通信的执行中仍讨论上述保证，而不是假设分区不会发生 |

理论中的“得到响应”要与操作规范一起理解。A 描述终止，C 描述响应是否符合所规定的对象语义。对本文这个必须完成读写的寄存器，快速返回“无法服务”没有实现原定读写契约，不能用它声称同时提供了 C 和 A。但若业务 API 明确允许“库存不足”等合法拒绝，该拒绝可以是完成操作的正常响应；不能脱离规范断言所有错误响应都不算可用。定义与读写对象的证明见 [Gilbert、Lynch 2002 原论文 §2](https://cs.nyu.edu/~apanda/classes/sp25/papers/gilbert02brewers.pdf)。

实际服务等级协议（Service Level Agreement，SLA）常统计一定时间窗口内的成功率、延迟与错误预算；这与“所有合法执行中请求最终响应”的理论要求不同。一次请求等到业务已失去意义时才返回，可能满足某种终止定义，却不满足业务 SLA。

网络分区（Network Partition）发生后，假设一侧已经完成 `write(1)`，另一侧才收到 `read()`。读节点收不到写入消息，无法区分“另一侧写过 1”和“根本没有写入”的历史。如果必须在持续分区中回答值，就不能在两种历史中都保证正确；若等待必要信息，则不能保证分区不恢复时仍完成请求。因此对这个对象无法同时保证线性一致性和可用性。CAP 不是任意“三选二”，而是在允许分区的模型中说明这两种保证的冲突；网络健康时系统可以同时提供二者。工程解释可联读 [Gilbert、Lynch 2012 回顾 §2](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer2.pdf)。

## 2. 分区期间不同节点的服务能力 {#_2-cp-不等于整个集群全部不可用}

教学推演：A、B、C 是同一复制组的三个投票成员，A、B 可通信，C 被隔离，形成 2+1 分区。下面用 CP 表示该操作在分区期间优先保持线性一致契约，用 AP 表示它允许以较弱契约在两侧处理请求；它们不是两套由 CAP 自动给出的算法。

| 操作契约 | A、B 多数侧 | C 少数侧 | 分区恢复后的工作 |
| --- | --- | --- | --- |
| 强一致库存扣减 | 在领导者有效、日志符合协议并获多数确认等条件下，可继续提交 | 不能作为独立领导者提交同等保证的写入；可重定向、拒绝或等待 | 让 C 追上已提交历史，处理客户端结果未知的请求 |
| 允许离线合并的购物车添加 | 记录本侧添加 | 记录本侧添加，即使暂时不知道另一侧更新 | 传播版本、发现并发更新，按业务规则合并并收敛 |

多数为 2，任意两个多数集合都有交集；配合选举、日志约束和持久化规则，协议才能防止相互矛盾的已提交决定。C 单独只有一个投票，不能在相同三成员多数规则下确认新写入。多数侧的普通本地读也不自动是最新读，仍需协议规定的领导权与应用进度检查，见 [Raft §5、§8](https://raft.github.io/raft.pdf)。因此 CP 不等于整个集群全部停机，而是某些节点不能完成原契约下的某些请求。

例如库存只剩 1 件时，两侧若都把“本地读到 1，扣 1 成功”当作全局预留成功，就会超卖；事后合并不能撤销已经对顾客作出的全部承诺。购物车的两次“添加”则可以先保留各自意图，恢复后合并；删除和数量修改仍需单独设计规则。这些是教学契约，不意味着库存永远只能采用一种方案：预先分配各地区可用额度可以支持部分本地扣减，但需要额外的额度不变量与转移协议。

**CP/AP 描述的是特定请求、操作及分区期间的行为。** 一个系统可以对库存预留要求强一致，对购物车接受合并，对推荐读取允许陈旧值；不能把整个数据库或公司系统永久贴成一个标签。图中的两个示例也不是把所有请求简化为“等待”与“返回旧值”二选一。

## 3. FLP 限制的是无条件终止保证

FLP 是 Fischer–Lynch–Paterson 不可能性结果。其关键前提是完全异步消息传递模型：不假定消息延迟或进程执行速度存在固定上界；合法执行中，非故障进程持续获得执行机会，发往它们的消息最终送达，但可以被延迟任意久。算法是确定性的，并且至多一个进程可能发生崩溃。

在这些前提下，不存在既满足共识安全要求、又对所有合法执行都保证终止的算法。即使没有实际节点崩溃，也可能存在一直无法决定的合法调度。这限制的是无条件终止保证，不是说系统每次都会失败。安全性（Safety）要求不作出冲突决定；活性（Liveness）要求最终取得进展，二者必须分开判断。[Fischer、Lynch、Paterson 原论文 §2～3](https://groups.csail.mit.edu/tds/papers/Lynch/jacm85.pdf)

工程系统通过改变假设或终止要求争取进展，需要分清四件事：

| 方法或模型 | 改变了什么 | 边界 |
| --- | --- | --- |
| 随机化共识（Randomized Consensus） | 在共识算法及证明中引入随机选择，在规定故障和调度假设下可证明概率 1 终止 | 不是对每一条随机选择序列都保证终止，也不等于给普通重试加随机等待 |
| 部分同步（Partial Synchrony） | 在同步与完全异步之间增加时序约束，例如时延上界存在但事先未知 | 需按具体模型与协议证明进展 |
| 最终同步（Eventual Synchrony） | 部分同步的一种常用表述：某个未知时刻后，消息和处理延迟满足适用上界 | 稳定前可以停滞；多数节点等其他条件仍需满足 |
| 故障检测与超时 | 用长时间无响应形成怀疑，触发选举或重试 | 在完全异步模型中不能区分慢节点与已崩溃节点；检测器若提供更强性质，也是在增加假设 |

随机化共识的例子见 [Ben-Or 1983](https://cs.nyu.edu/~apanda/classes/sp25/papers/benor83.pdf)；部分同步模型见 [Dwork、Lynch、Stockmeyer 1988](https://groups.csail.mit.edu/tds/papers/Lynch/jacm88.pdf)。随机退避可以减少竞争，却不能单独证明共识算法满足上述终止性质。

Raft 用随机选举超时降低候选人反复撞车的机会；取得活性还依赖足够节点可通信、时延相对选举超时足够小等条件。[Raft §5.2、§5.6](https://raft.github.io/raft.pdf) 给出了相应说明。Paxos 的进展需要一个能够稳定推进提案的领导者及足够响应的参与者，见 [Paxos Made Simple §2.4](https://lamport.azurewebsites.net/pubs/paxos-simple.pdf)。这类协议不承诺在无限恶劣的异步调度中也必然结束；超时始终只是故障怀疑，不能证明远端进程已经死亡。

## 4. BASE 与最终一致性的收敛条件 {#_4-base-是设计取向-不是自动收敛算法}

BASE 是基本可用（Basically Available）、软状态（Soft State）和最终一致（Eventually Consistent）的组合，描述一种允许中间差异的设计取向：

- 基本可用：故障时争取保留约定的核心服务，可能降级或暂时提供较弱结果；它不是 CAP 理论可用性的同义词。
- 软状态：即使没有新的用户请求，后台传播、过期与修复也可能改变节点状态；“软”不代表数据可以随意丢失。
- 最终一致：在指定收敛条件下，保存同一逻辑数据的副本最终达到一致，而不是保证任意时刻都相同。

术语说明可参照 [AWS 的 ACID 与 BASE 对照](https://aws.amazon.com/compare/the-difference-between-acid-and-base-database/)。真正的收敛还要有机制：对所讨论数据不再产生新更新，相关副本最终可通信，需要保留的更新仍有持久副本，传播与修复能持续完成，并且各节点使用兼容、可收敛的冲突解决规则。持续写入时，不承诺任意时刻所有副本完全相同。

| 机制 | 解决的问题 |
| --- | --- |
| 副本传播 | 把新更新传给其他副本 |
| 反熵修复（Anti-Entropy） | 比较副本的状态或摘要，发现并补传漏掉的版本 |
| 冲突解决 | 对并发版本决定保留、合并或交给业务处理，避免各节点各选一个结果 |

教学示例：三个副本的购物车初始只有“书”；分区时 A 添加“笔”，B 添加“灯”，C 没收到这两个更新。连接恢复后，版本信息识别出 A、B 的并发修改；若契约仅包含“添加”，合并为 `{书, 笔, 灯}`，再传播给三者；反熵可以发现 C 漏掉的版本并补齐。涉及删除时，简单集合并集会把被删商品加回来，因此需要额外的删除语义。

异步复制不会自行解决所有冲突；“最后写入获胜”可能舍弃某次并发意图；如果一个更新在传播前已永久丢失，等待不会把它恢复出来。版本与反熵机制的具体系统实例见 [Dynamo 2007 §4.4、§4.7](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)，本例不是对其购物车实现的逐行复述。

## 5. ACID 的 C 与 CAP 的 C 不同

事务的 ACID 分别是原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）和持久性（Durability）。其中 C 关注事务前后满足约束与不变量，需要数据库约束、隔离机制与正确的事务逻辑共同配合；CAP 的 C 则关注不同客户端观察到的操作历史是否线性一致。一个约束业务状态，一个约束可见顺序，二者不能互相替代。

教学示例：主库用一次正确的转账事务把两个账户从 `100、100` 改成 `90、110`，总额约束仍为 200，转账已提交；异步只读副本尚未重放这次事务，随后开始的查询仍读到 `100、100`。旧快照仍满足总额约束，但这个读取没有满足“在已完成写入后看到其效果”的实时要求。异步副本可能返回旧数据的产品依据见 [PostgreSQL 17 的同步与异步复制说明](https://www.postgresql.org/docs/17/warm-standby.html#SYNCHRONOUS-REPLICATION)。

反过来，线性一致的两个单键接口也不自动提供跨键原子事务，正如第四章的转账例子。选择事务隔离级别和选择副本读取策略，是需要分别声明的两组保证。

学习时，应分别列出请求成功条件、允许观察的状态、分区期间拒绝请求的范围，以及恢复后的合并策略。明确这四项，比单纯讨论“选 CP 还是 AP”更有助于设计可执行的接口。
