# 第八章 竞争条件、原子操作与锁

> 阅读标签：通用并发模型 / C11与Linux锁条件。

多个执行流访问同一份可变数据时，需要同步机制保护共享状态。可以先在抽象模型中观察“读取—计算—写回”如何交错，再理解互斥锁和原子操作怎样约束这些步骤。将模型落到 C11 程序时，还要遵守语言对数据竞争与内存顺序的规定。

## 1. 从丢失更新看临界区

纸面推演：初值 0，A 读到 0，B 也读到 0，两者分别写回 1，最终为 1。关键是“读取—修改—写回”不能被另一个相冲突操作拆开。

这是一条顺序交错的抽象历史，不是合法可运行的C程序结果清单。C11中，未同步的冲突非原子访问若构成data race，其行为未定义，不能说只可能得到1或2；反复运行没有观察到错误也不是正确性证明。应使用互斥或标准原子API。[WG14 N1570 §5.1.2.4 ¶25](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

即使用原子fetch_add使一次加法不可分割，复合的“余额足够才扣减”也不会自动整体原子；检查与更新仍需共同的锁、CAS循环或其他正确协议。这里限定C11规则，不把所有语言的内存模型混为一谈。

[![volatile 与线程同步：职责不同](/assets/notes/operating-systems/os-lock.svg)](/assets/notes/operating-systems/os-lock.svg)

临界区是受保护的代码区域。互斥需要覆盖访问同一共享状态的所有相关路径，而不只是调用“同一函数名称”的线程。如果只有写者加锁，读者仍随意读取，也未必满足程序语言和业务要求。

## 2. 原子指令的操作与内存顺序 {#_2-原子指令不等于普通赋值的伪代码}

Test-and-set、compare-and-swap 等指令提供相应不可分割的状态操作。用 C 写成“读旧值；写 true；返回旧值”的三行，仅表示规格，不实现硬件原子性。

原子操作还涉及内存顺序。需要在锁保护下发布的数据，必须对随后获得资格的线程正确可见；volatile 通常不提供跨线程互斥或完整同步保证。具体语言应使用相应标准原子与同步 API。[OSTEP Locks](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-locks.pdf)

## 3. 关中断只能处理一部分并发

单 CPU 的特定内核场景可通过屏蔽本地中断，防止相关中断路径插入；多个 CPU 上，别的 CPU 仍能访问同一数据。因此，本地 cli 的保护范围只覆盖相应 CPU 的中断路径。

还要避免在关中断或持有不允许睡眠的锁时等待可能阻塞的操作。长临界区会抬高中断与调度延迟，不能把一切 I/O 都放进去。[Linux 6.6 锁说明](https://docs.kernel.org/6.6/locking/spinlocks.html)

## 4. 自旋与睡眠等待

自旋锁等待者持续尝试，适合受限上下文中的短持有；睡眠锁在竞争时可让出 CPU，但需要可调度上下文。持锁者若被长时间暂停，自旋者会浪费 CPU；睡眠锁也有唤醒与调度成本。

内核版本、抢占模式及 PREEMPT_RT 会改变某些锁的具体语义，不能将某一教学内核规则直接写成所有现代配置的定律。

## 5. 互斥、公平与死锁的分别检查 {#_5-互斥不自动保证公平或无死锁}

一个实现可能保证同一时刻只有一个持有者，却让某线程长期得不到机会；也可能因嵌套锁顺序不一致形成死锁。有界等待是额外性质，不因函数名为 mutex 就当然满足。

检查时应明确：谁会访问共享状态、哪个锁保护哪些字段、能否睡眠、是否存在逆序加锁，以及退出和错误路径是否释放锁。缺少这些约束，增加锁反而可能引入新故障。
