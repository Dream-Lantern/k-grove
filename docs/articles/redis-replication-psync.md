# 第二十一章 复制、PSYNC 与读写分离

[返回本册目录](/collections/redis/)

复制让副本跟随主节点的数据变化。首次建立关系或历史无法接续时使用全量同步，短暂中断后则尝试部分重同步。它为恢复与读扩展提供数据基础，客户端主节点发现和一致性要求由相应机制进一步处理。

Master（主节点）接收业务写入，Replica（副本）跟随复制流。本章以 Redis Open Source 7.2.0 为参照；PSYNC（Partial Resynchronization，部分重同步）自 2.8.0 提供，后续历史标识机制按 7.2.0 说明。所有命令、偏移数字和故障时间线都是教学示例，未在实例上执行。

![复制重连的两条路径](/assets/notes/redis/redis-study-replication.svg)

## 1. 异步复制下的写入确认与副本进度 {#_1-写入回复与复制进度不同步}

默认异步复制下，主节点完成相应操作并回复客户端，不需要先等待所有副本完成。因此在主节点刚写入后读取副本，可能读到旧值；主节点故障时，也可能丢失已向客户端确认但未被可用副本保留的写入。

“复制延迟通常不高”是观测，不是“小于一秒”的协议保证。网络停顿、重命令、加载快照和资源不足，都可能扩大滞后。[复制官方说明](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

## 2. 全量同步与部分重同步

首次同步或无法接续历史时，通常需要全量同步：主节点形成可用快照，传给副本，副本加载，再追赶期间产生的新变化。磁盘或无盘传输路径依版本与配置不同；副本加载阶段对请求的影响也要单独评估。

```text
副本连接 → 握手与能力协商 → 请求按复制历史续传
                             └─ 无法续传：主节点生成 RDB 快照
                                → 传输快照 → 副本加载
                                → 追赶快照期间积累的新写入
                                → 持续复制
```

RDB（Redis Database，数据库快照）让副本先得到某个时点的完整数据集。主节点在快照传输期间仍接收写入，并保留待发送复制流，快照完成后副本再接续这些变化；不是只复制快照就宣布最新。按 7.2.0 配置，磁盘路径先写 RDB 再传输，无盘路径由子进程直接传输 RDB；无盘不等于没有 fork、内存或网络成本。[全量同步机制](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/) · [7.2.0 复制配置](https://raw.githubusercontent.com/redis/redis/7.2.0/redis.conf)

副本加载数据时，正常请求可能收到 LOADING（正在加载错误）；是否能在特定加载路径继续提供旧数据，取决于 `repl-diskless-load` 等配置，不能无条件保证可读。生成、传输和加载还会消耗 CPU（Central Processing Unit，中央处理器）、磁盘、网络和内存；成本见 [第 20 章 fork/COW](/articles/redis-fork-copy-on-write.html)，其中 COW（Copy-on-Write，写时复制）不会因为无盘传输而消失。

短暂断线后，PSYNC 可以根据复制历史标识与偏移尝试续传。复制 backlog 保存了有限的近期复制流；若所需区间仍在，就可能只补齐缺失部分，否则仍需全量同步。现代复制标识不能简单等同于进程 run_id；PSYNC2 还需考虑切换后的历史连续性。

Replication ID（复制历史标识）表示一条数据历史，Replication Offset（复制偏移量）表示这条历史中已处理的复制流字节位置；Replication Backlog（复制积压缓冲区）保留主节点有限的近期复制流。ID 和 offset 必须一起比较：相同 offset、不同历史不代表同一数据状态，ID 也不是服务器进程 run_id（运行实例标识）。

假设复制历史相符，当前已生成复制流的末尾为 12000，Backlog 保留以下范围；数字是教学假设：

```text
主节点当前 offset = 12000
Backlog 已保留字节 = 8001 ～ 12000，共 4000 字节

副本已处理到 10000 → 请求下一字节 10001 → 缺失 10001 ～ 12000 可续传
副本只处理到 5000  → 请求下一字节 5001  → 超出保留范围，通常需全量同步
```

“已处理到”和“请求下一字节”相差 1，不能混用边界；偏移是字节位置，不是命令条数。主节点切换后，新的主节点可以保存旧历史为第二复制 ID，并记录其有效偏移上限；只有历史、上限和 Backlog 都满足条件才可能续传，不能说切换后一定全量或一定续传。[复制 ID 与第二历史](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/) · [7.2.0 PSYNC 判断](https://raw.githubusercontent.com/redis/redis/7.2.0/src/replication.c)

7.2.0 的 `second_repl_offset` 按“请求的下一字节位置”记录允许上限：切换时若旧历史已到 12000，可记录边界 12001。因此它不能直接当作旧历史最后已处理字节的位置。

backlog 容量可以从“峰值复制字节速率 × 期望可覆盖断线时长”估算起步，再加入余量并实测。它不是按业务命令条数计算，也不是给每个副本都完整分配一份相同历史缓存。偏移差是字节差，不能不经测量直接当成秒数。

例如复制流峰值为 2 MiB/s，期望覆盖 30 秒断线：`2 MiB/s × 30 s = 60 MiB`。MiB（Mebibyte，兆比字节）为 2²⁰ 字节；60 MiB 只是理论起点，还要为突发、重连耗时和速率变化留余量并验证。应使用复制流字节速率，而不是业务 QPS（Queries Per Second，每秒请求数）；有限 Backlog 不是无限历史日志。

## 3. 用只读信息先建立关系图

以下是观察命令示例，不会自动建立复制关系：

```redis
INFO replication
ROLE
```

应确认当前角色、上游、链路状态、同步状态和偏移变化，再与主节点观察结果比对。单看 `master_link_status:up` 不足以证明业务读到最新值。

下表均按 Redis Open Source 7.2.0 的 INFO replication 核对；某些字段依角色或状态输出，不能把不同版本、主副本角色的结果硬套成一份固定回复：

| 观察对象 | 字段                                              | 含义                                    |
| -------- | ------------------------------------------------- | --------------------------------------- |
| 主节点   | connected_slaves、master_repl_offset              | 当前连接副本数、复制流末尾字节位置      |
| 副本     | master_link_status、master_sync_in_progress       | 上游连接状态、是否正全量同步            |
| 历史     | master_replid、master_replid2、second_repl_offset | 当前及第二历史 ID，第二历史可接续的边界 |
| Backlog  | repl_backlog_size                                 | 配置的缓冲容量目标，不等于有效历史长度  |
| Backlog  | repl_backlog_first_byte_offset                    | 当前保留的第一个字节位置                |
| Backlog  | repl_backlog_histlen                              | 当前有效历史字节数                      |

有效历史非空时，区间末尾为 `first_byte_offset + histlen - 1`。应连续观察同步状态和偏移变化；链路 up 只是一个条件，偏移差也不能直接除以 QPS 推出秒数，因为单位不同且速率会变化。[7.2.0 INFO 输出](https://raw.githubusercontent.com/redis/redis/7.2.0/src/server.c) · [INFO 字段说明](https://redis.io/docs/latest/commands/info/)

教学部署中常见的 REPLICAOF 会改变实例关系，可能触发数据同步；不能把它作为线上排查的只读命令。复制关系的运行时设置与重启后的配置持久性，也要分别确认。

## 4. 按业务新鲜度要求选择读取路径 {#_4-读写分离要承认陈旧读}

统计、推荐等能容忍延迟的读取可以交给副本，但登录状态、余额或写入后需立即展示的结果，往往有更严格的要求。常见策略包括让关键读取走主节点、在写后一定范围内保持主读，以及使用业务版本校验；无论采用哪种策略，都需要结合失败场景分析，不能作无条件保证。

```text
假设副本仍是旧状态：order:42 = pending
客户端在主节点执行 SET order:42 paid → 主节点回复成功
客户端立即在副本 GET order:42 → 副本尚未追平 → 仍可能读到 pending
```

| 策略             | 作用                       | 局限                                 |
| ---------------- | -------------------------- | ------------------------------------ |
| 关键读取走主节点 | 减少因副本滞后造成的旧读   | 增加主节点负载，切换和路由仍需处理   |
| 写后短时间主读   | 改善写后读体验             | 时间阈值需测量，不能保证所有故障场景 |
| 业务版本校验     | 识别读取内容过旧           | 需要版本传递及补偿逻辑               |
| 等待复制确认     | 增强特定写入的复制进度保障 | 不保证任意后续读取都强一致           |

副本执行大查询也可能影响复制追赶，不能认为“只读就不会干扰”。副本内存不足、磁盘缓慢或带宽开销过高，同样可能使高可用链路失效。

## 5. WAIT 的复制确认与 WAITAOF 的持久化确认 {#_5-wait-与-waitaof-分别在等什么}

WAIT 自 Redis Open Source 3.0.0 提供，可等待当前连接之前的写入获得一定数量副本确认；必须检查实际返回数量，超时不等于撤销写入。它增强某些故障下的数据安全性，但不能将异步复制变成严格的强一致系统。[WAIT](https://redis.io/docs/latest/commands/wait/)

以下两行在同一连接、向学习环境的主节点顺序发送，未执行：

```redis
SET demo:replication:order paid
WAIT 1 1000
```

1000 是毫秒；WAIT 返回实际确认副本数，可能达到或超过目标，也可能超时只返回 `0`。返回 `0` 不能理解为 SET 回滚；返回大于等于 `1` 也不是副本已经 fsync 的证明。连接池若把 WAIT 放到另一条连接，它就不再针对原连接的这次写入。

Redis Open Source 7.2.0 起的 WAITAOF 进一步针对 AOF（Append Only File，只追加文件）的 fsync（文件同步到存储的系统调用）确认，是否可用依赖部署和配置。复制处理确认、数据在内存中执行、日志刷盘，是不同保证，应用不能混用。[WAITAOF](https://redis.io/docs/latest/commands/waitaof/)

以下是另一组独立教学调用，必须在同一连接上向主节点执行，且需要本地与目标副本都启用、正常写入和同步 AOF；副本还需支持相应确认协议。未实际执行：

```redis
SET demo:replication:order paid
WAITAOF 1 1 1000
```

目标是本地 1、副本至少 1，在 1000 毫秒等待期限内检查之前写入的同步进度。返回数组如 `[1,1]` 表示达到该目标，`[1,0]` 只达到本地目标；这些仅为结果示意，不能伪装成实际回复。

新增参数和返回对照，不执行写入或阻塞等待：

| 命令模板                             | 等待对象                         | 返回值                           |
| ------------------------------------ | -------------------------------- | -------------------------------- |
| WAIT numreplicas timeout             | 当前连接之前写入的副本确认       | 整数：已确认的副本数             |
| WAITAOF numlocal numreplicas timeout | 当前连接之前写入的适用 AOF fsync | 两个整数：本地完成数、副本完成数 |

两者 timeout 都是毫秒，0 表示不设等待超时。超时返回不是回滚，实际确认数也可能不足目标，必须检查返回。WAITAOF 的 numlocal 只能为 0 或 1；numlocal=1 必须启用本地 AOF，numlocal=0 可只要求副本 AOF 确认。在 7.2.0 中，无论 numlocal 为多少，WAITAOF 都拒绝在副本实例上调用；WAIT 也拒绝副本实例。MULTI 或脚本等不允许阻塞的上下文中，二者立即报告当时完成数，不按普通等待流程阻塞。[7.2.0 WAIT/WAITAOF 角色与阻塞判断](https://raw.githubusercontent.com/redis/redis/7.2.0/src/replication.c)

例如目标为本地 1、副本 1，返回 `[1,0]` 只满足本地，不满足该副本目标；业务端自己又发生读取超时，则连这个结果也可能未知。模块或脚本选择性传播还可能影响保证，必须遵守命令的具体限制。这些确认不自动构成强一致提交。

若主节点不持久化，重启后空数据再成为复制源，可能造成严重后果。需要结合启动隔离、角色发现和恢复流程处理，而不是用“副本总有数据”替代恢复设计。

```text
假设：主节点关闭持久化，副本仍保存旧数据
主节点故障 → 以空数据自动重启并继续担任主节点
           → 副本重新全量同步空主节点 → 副本原有数据可能被覆盖
```

这是部署和恢复风险，不是每次重启必然发生的结果。需要结合启动角色隔离、故障发现、持久化和恢复方案防范；不能先让空主节点接回副本，再假定副本一定替自己保住数据。[主节点关闭持久化的风险](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

| 能力                | 主要解决的问题             | 不保证什么                     |
| ------------------- | -------------------------- | ------------------------------ |
| Replication（复制） | 多份近实时副本和读扩展基础 | 不保证零数据丢失或可靠历史备份 |
| RDB                 | 时间点快照恢复             | 不保证近期全部写入             |
| AOF                 | 记录写入并支持恢复         | 不保证所有故障下零损失         |
| WAIT                | 等待副本复制确认           | 不保证故障转移一定保留该写入   |
| WAITAOF             | 等待适用 AOF 同步确认      | 不自动构成共识提交协议         |

Availability（可用性）关心能否继续服务，Durability（持久性）关心故障后写入能否保留，Consistency（一致性）关心各读写结果是否满足约定。它们不能互相替代：恢复材料见 [第 19 章 RDB/AOF](/articles/redis-rdb-aof.html)，角色发现与自动切换继续见 [第 22 章 Sentinel](/articles/redis-sentinel.html)。
