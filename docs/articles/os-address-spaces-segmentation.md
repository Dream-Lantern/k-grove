# 第十三章 地址空间、重定位与分段

> 阅读标签：简化重定位模型、历史 x86 32 位保护模式，与现代 Linux 地址空间对照。

同一个程序装进不同的内存位置，为什么还能访问自己的变量？关键是保留程序内部的地址关系，再由适用的装载和硬件机制联系实际位置。虚拟地址使程序能够按自身的地址关系运行，物理内存由系统组织和共享；教学模型、历史 x86 分段和现代平坦模型各有适用背景。

## 1. 编译、装载与运行期重定位

先用**没有分页、忽略权限和溢出的单一基址教学模型**：程序访问逻辑偏移 `0x1234`，硬件把它加上本次装入的物理基址。

| 装入情况 | 基址      | 相同偏移 | 模型中的物理地址 |
| -------- | --------- | -------- | ---------------- |
| 第一次   | `0x10000` | `0x1234` | `0x11234`        |
| 第二次   | `0x30000` | `0x1234` | `0x31234`        |

改变基址不改变变量相对程序起点的位置，程序因而不必绑定某个物理起点。这个例子解释设计动机，**不表示所有现代程序都按“物理地址 = 基址 + 偏移”访问内存**。

| 阶段             | 处理什么                                                               | 与其他阶段的区别                                   |
| ---------------- | ---------------------------------------------------------------------- | -------------------------------------------------- |
| 编译与链接       | 生成代码、组织节、解析符号，按目标格式处理适用的相对地址与重定位项     | 尚未等于建立真实物理页映射                         |
| 装载及动态链接   | 建立虚拟映射，处理适用的装载重定位或动态符号绑定                       | 可以修改需要修正的位置，但不是每次访存都执行链接器 |
| 运行中的硬件转换 | 中央处理器（CPU，Central Processing Unit）按当前模式转换地址并检查访问 | 不等于反复执行链接器重定位                         |

真实程序可能使用相对寻址、位置无关代码与动态链接；“编译时只能固定位置”“载入后映射不能改变”只适用于特定简化模型。位置无关可执行文件（PIE，Position-Independent Executable）有利于程序在不同虚拟位置装载，地址空间布局随机化（ASLR，Address Space Layout Randomization）可随机安排适用区域；两者都不意味着程序直接获得物理地址。可执行与可链接格式（ELF，Executable and Linkable Format）中的节、程序头与重定位项各有用途。[elf(5)](https://man7.org/linux/man-pages/man5/elf.5.html)

## 2. 分段表达逻辑区域与访问权限 {#_2-分段要表达什么}

抽象分段按代码、数据、栈等逻辑区域组织空间，可以分别设置基址、界限和权限。下面固定为**历史 x86 32 位保护模式，普通向上扩展数据段，一次读取 1 字节**，不讨论栈段或门的完整规则。

逻辑地址（Logical Address）由段选择信息和段内偏移构成。段寄存器保存段选择子（Segment Selector）；选择子的索引字段定位描述符，表指示位选择全局描述符表（GDT，Global Descriptor Table）或局部描述符表（LDT，Local Descriptor Table）。GDT 是系统级表，LDT 是由系统配置的另一类描述符表，不是每个现代进程都必须拥有一张。

例如选择子 `0x23`：索引 `0x23 >> 3 = 4`，表指示位为 0，选择 GDT 第 4 项；低两位为请求特权级 3。这是人为指定的描述符配置，不是所有 Linux 系统的固定选择子含义。设该描述符给出：

| 属性         | 本例设置                                             |
| ------------ | ---------------------------------------------------- |
| 基址         | `0x00400000`                                         |
| 原始界限字段 | `0x0000FFFF`                                         |
| 粒度 G       | 0，按字节解释界限                                    |
| 类型         | 存在、可读写、向上扩展的普通数据段                   |
| 权限假设     | 描述符特权级 3，当前与请求特权级均为 3，访问类型允许 |

1. 装载段选择子时，CPU 按规则检查表范围、描述符类型、存在性及权限，并把适用描述符信息缓存在段寄存器的隐藏部分；不是每次读一个字节都重新遍历 GDT。
2. 段内访存还要满足访问类型和界限等条件。本例合法偏移为 `0x00000000～0x0000FFFF`，上界包含在内。
3. 偏移 `0x00001234` 合法，形成线性地址 `0x00400000 + 0x00001234 = 0x00401234`。
4. 改为 `0x00010000`，越过本例界限，进入相应保护异常路径，不能把加法结果当作合法访问继续。
5. 若分页启用，合法线性地址还要经适用页表转换与检查，才联系物理地址；分页关闭时走该模式规定的非分页路径。

[![32 位保护模式中选择描述符、检查段界限、形成线性地址并进入分页](/assets/notes/operating-systems/os-address.svg)](/assets/notes/operating-systems/os-address.svg)

这里使用的是**有效界限**：G=0 时等于原始界限；G=1 时为 `(原始界限 << 12) | 0xFFF`。这只是粒度换算，不是所有段的统一合法偏移规则。向下扩展数据段的界限解释不同；多字节访问还必须检查末字节是否越界，栈段、代码段和门也各有检查条件。不能只做一次 base+offset 加法就跳过保护。[Intel 软件开发手册 Volume 3A，保护模式内存管理与保护章节](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)

### 逻辑、线性和物理地址的语境

| 地址                         | 在上述 x86 模型中的含义                                                |
| ---------------------------- | ---------------------------------------------------------------------- |
| 逻辑地址                     | 段选择信息 + 偏移，例如本例 `0x23:0x1234`                              |
| 线性地址（Linear Address）   | 分段处理后的 `0x00401234`，分页开启时作为分页输入                      |
| 物理地址（Physical Address） | 经过适用分页等转换后联系物理内存的地址；不能仅从上述逻辑地址给出其数值 |

现代 x86-64 长模式中的 **64 位子模式**，普通 CS/DS/ES/SS 的基址按平坦语义处理，传统段界限不按本例方式限制普通访存；仍有其他特权与地址合法性检查。FS/GS 基址有特定用途，例如 FS 常用于线程局部存储（TLS，Thread Local Storage）。长模式还包含兼容子模式，不能把“64 位子模式”的结论不加区分地套给所有情况。现代 Linux 的主要地址隔离依赖虚拟映射、页级保护等机制，不能解释成“每个进程各用 LDT 隔离全部内存”。[Linux FS/GS 文档](https://docs.kernel.org/arch/x86/x86_64/fsgs.html)

## 3. 软件区域与硬件段并不相同

| 概念                                           | 所属层次                                                  | 职责                                           |
| ---------------------------------------------- | --------------------------------------------------------- | ---------------------------------------------- |
| x86 硬件段                                     | CPU 架构机制                                              | 在适用执行模式下参与地址生成、类型与权限检查   |
| ELF 程序段（Program Segment）                  | 可执行与可链接格式（ELF，Executable and Linkable Format） | 程序头描述装载区域等信息，PT_LOAD 表示可装载段 |
| Linux 虚拟内存区域（VMA，Virtual Memory Area） | 内核虚拟内存管理                                          | 记录虚拟连续范围、权限与文件/匿名后备关系      |
| 页表映射                                       | 硬件转换及内核管理                                        | 建立虚拟页到物理页框等关系，并携带适用属性     |

一个 ELF 装载段不等于一个独立的 x86 硬件段；VMA 也不是段描述符。ELF 的节（Section）偏重链接组织，程序段偏重装载视图，一个装载段可以涵盖多个节。页对齐、权限调整等还可能使装载区域与 VMA 不形成简单一一对应。

同一 VMA 可以覆盖许多页，其中有些页尚未建立驻留映射；因此有合法虚拟区域不等于其中每页都已经占用独立物理页。`/proc/<PID>/maps` 展示虚拟区域及权限，不是物理内存布局图。[Linux Process Addresses](https://docs.kernel.org/mm/process_addrs.html)、[proc_pid_maps(5)](https://man7.org/linux/man-pages/man5/proc_pid_maps.5.html)

## 4. 阅读分段汇编的前提 {#_4-原汇编片段的纠错}

阅读段内访问指令时，要分别确认段寄存器、偏移和传送方向。x86 常见段寄存器写作 ES，Intel 与 AT&T 汇编语法的源、目的操作数顺序不同。

本章用“段选择信息 + 偏移 → 经检查形成线性地址”表达访问含义。将它写成可运行汇编，需要先确定目标位宽、执行模式、汇编器语法和指令语义。不要在普通用户程序中尝试随意改写系统段表来验证纸面算例。

## 5. 地址空间中的隔离与受控共享 {#_5-隔离不是每进程独占物理-ram}

固定 4 KiB 页，下面页框号均为教学假设，不是读取当前主机得到的数据：

| 场景                   | 进程 A 的映射        | 进程 B 的映射        | 说明                           |
| ---------------------- | -------------------- | -------------------- | ------------------------------ |
| 相同虚拟地址，不同页框 | `0x400000` → 页框 10 | `0x400000` → 页框 25 | 各自地址空间的转换结果可以不同 |
| 不同虚拟地址，共享页框 | `0x500000` → 页框 30 | `0x700000` → 页框 30 | 受控共享可让不同地址引用同一页 |

[![两个进程的虚拟地址分别映射独立页框或共享页框](/assets/notes/operating-systems/os-address-sharing.svg)](/assets/notes/operating-systems/os-address-sharing.svg)

相同数值的指针不能脱离所属地址空间理解；把 A 的指针数字交给 B，并不会自动让 B 获得 A 的数据。共享也要建立适用映射和访问权限，而不是任意访问其他进程。共享库页、共享文件页或显式共享内存都可能形成共享关系，具体写入语义还要区分共享映射和写时复制。

没有配置交换空间（swap）仍可拥有虚拟内存，不能把虚拟地址的存在归因于不断交换磁盘。[Linux 内存概念](https://docs.kernel.org/6.6/admin-guide/mm/concepts.html)

### 只读观察：变量地址与自己的 maps

保存为 `observe.c`，在 Linux 上运行 `gcc -std=c11 -Wall -Wextra -Werror observe.c -o observe`，再执行 `./observe`。示例显式申请 20 字节并读取自身映射，不直接改写真实页表或修改系统配置：

```c
#include <stdio.h>
#include <stdlib.h>

static int global_value = 7;

int main(void)
{
    int local_value = 9;
    void *object = malloc(20);
    if (object == NULL) {
        perror("malloc");
        return EXIT_FAILURE;
    }
    printf("global=%p local=%p malloc(20)=%p\n",
           (void *)&global_value, (void *)&local_value, object);
    FILE *maps = fopen("/proc/self/maps", "r");
    if (maps == NULL) {
        perror("fopen maps");
        free(object);
        return EXIT_FAILURE;
    }
    char line[1024];
    while (fgets(line, sizeof line, maps) != NULL)
        fputs(line, stdout);
    int failed = ferror(maps);
    if (failed)
        perror("read maps");
    if (fclose(maps) != 0) {
        perror("fclose maps");
        failed = 1;
    }
    free(object);
    if (fflush(stdout) == EOF || ferror(stdout)) {
        perror("stdout");
        failed = 1;
    }
    return failed ? EXIT_FAILURE : EXIT_SUCCESS;
}
```

把第一行的三个地址分别放入后续 maps 的 `[起点, 终点)` 区间，观察对应权限与路径标签。局部变量通常在栈映射，动态对象常来自分配器管理的区域；不能把每次 malloc 都固定解释成新增一条 `[heap]` 映射。若直接执行 `cat /proc/self/maps`，self 是 cat 自己，不是此前已退出的 observe。

本轮在 WSL2/Linux x86_64 环境编译运行通过，并将三个地址逐一匹配到了程序打印的映射范围。地址是**虚拟地址**，具体数值受 ASLR、装载和运行环境影响，不提供伪造的固定地址输出；实验不展示完整物理页框映射，也不证明历史硬件分段过程。

## 本章小结与联读

程序的内部地址关系、装载位置与硬件转换是不同层次；硬件段、ELF 装载段、VMA 和页表也各司其职。下一章看程序如何[申请与释放内存](/articles/os-memory-allocation.html)，随后再计算[分页映射](/articles/os-paging-page-tables.html)。Linux 0.11 特有的段页布局留到[第十七章](/articles/os-linux011-copy-on-write.html)，避免将历史实现当成通用定义。
