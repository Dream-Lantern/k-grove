# 第 17 章 HAMi-core：显存限额、算力控制和安全边界

“容器里看到 3GB 显存”与“物理卡真的切出了独立 3GB 硬件分区”不同。HAMi-core 典型路径通过用户态 CUDA 调用拦截落实资源控制，应把它与 MIG 的资源边界分开说明。

## 1. 一次分配如何经过控制层

在受支持且已被正确注入的调用路径上，控制层检查并维护分配记录；超过相应配额时返回分配失败，允许时再调用真实驱动路径。多个进程需要共享和协调配额记录，不能只按一个 Python 进程的局部计数判断总用量。

这不是“应用独占整卡但用不满”，其他受管理任务仍可能共享物理设备。显存限额与硬件切片的机制不同，不应混用术语。[HAMi-core 项目说明](https://github.com/Project-HAMi/HAMi-core)

## 2. 算力限制不等于精确吞吐控制

典型软件控制可以通过调节提交节奏等方式影响资源使用；具体算法应以所审阅 tag 为准。原文中按 `grids × blocks` 估算、固定 sleep、固定超时和固定函数行数的描述，在没有源码版本证据时不能写成通用实现。

即使配额值为 50，也不能保证业务性能恰好是独占时的一半。kernel 长短、CUDA Graphs、并发提交和底层共享资源都可能影响控制效果与实际观测。也不能反过来断言限速“一定不改变功耗”；这需要测量，不能仅根据控制层位于软件中就作出判断。

## 3. 三种视图需要分别观察

| 视图                   | 可能看到什么               | 验证目的               |
| ---------------------- | -------------------------- | ---------------------- |
| 容器内 CUDA 查询       | 受管理的可见资源或配额     | 应用得到的契约是否一致 |
| 容器内 NVML/nvidia-smi | 受注入和工具路径影响的视图 | 工具是否正确关联该任务 |
| 宿主侧监控             | 物理卡及实体的状态         | 实际占用与全局剩余量   |

把相关行为简单叫“nvidia-smi 欺骗”不够专业。应记录“逻辑资源视图”和“物理资源视图”的差异，并检查容器里的工具是否确实使用了被拦截的库，不能保证任意二进制都呈现同一结果。

## 4. 软件控制层不是完整的对抗性安全边界

拦截覆盖面、动态库解析、静态调用路径、新 CUDA API、Graph 回放以及容器权限，都会影响控制是否生效。调度器分配了配额，并不自动证明应用无法绕过。对不可信租户，需要独立评估设备访问、特权、驱动和硬件隔离，不能以用户态 hook 替代安全审计。

## 5. 最小验收矩阵

分别验证单进程/多进程、分配/释放/失败、异步内存池、普通 launch/Graph、异常退出/进程重启，并对比宿主与容器视图。验收时应检查“超额时发生什么”和“退出后配额是否恢复”，不能只看某次查询显示的总量。未验证的 API 路径应明确列为限制，不用“理论上支持全部 CUDA”代替验证。

## 6. 记账设计要覆盖请求大小、预留与回滚

![配额记账的设计验收模型](/assets/notes/ai-infra/hami-allocation-ledger.svg)

这张图给出的是**应审查的并发记账模型**，不表示某个未知 HAMi-core commit 已按此实现，也不能据此认定现有库存在竞态。

仅检查 `used < limit` 不够：还要考虑本次 requested bytes。多进程同时准入时，检查与预留需形成一致的并发协议，避免每个进程都按同一份旧余额通过。调用真实分配失败，要撤销相应预留；成功后把状态转成已生效分配。实际实现可以采用不同的锁、记录与事务方式，关键在可验证的不变量。

| 不变量/事件                              | 验收问题                                     |
| ---------------------------------------- | -------------------------------------------- |
| `used + reserved + requested` 与限额关系 | 单位、溢出、粒度和并发准入如何处理           |
| 真实分配失败                             | 预留能否按原请求撤回，是否遗留占额           |
| free / async free                        | 按什么逻辑时点释放配额，和物理内存池是否分开 |
| 进程异常退出                             | 谁检测失效记录，如何防止误清其他进程         |
| VMM/Graph/新入口                         | 是支持、拒绝还是未观测，不可默认为已覆盖     |

查设备总量时，`cuDeviceTotalMem` 是独立 API；`cuDeviceGetAttribute` 是设备属性查询，不能造一个 TOTAL_MEMORY attribute 把二者混写。资源视图改写、实际指针分配和账本更新也须分开核对。[CUDA 12.8.1 Device Management](https://docs.nvidia.com/cuda/archive/12.8.1/cuda-driver-api/group__CUDA__DEVICE.html)
