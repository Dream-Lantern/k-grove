# 第十二章 文件描述符、文件系统与持久化

> 阅读标签：现代Linux普通文件API与持久化。

本章补充基础概念，串联原笔记中的系统调用、bread 和缺页文件读取。文件名、文件描述符、打开文件描述和实际存储对象属于不同层次，区分这些概念，才能解释 fork、缓存与数据持久化。

## 1. 路径与描述符

路径用于查找对象，open 成功返回进程中的文件描述符编号。描述符引用相应内核打开状态，后者再联系文件系统对象；一个文件可以被多次打开，也可以有多个引用。

![从路径到文件与持久数据](/assets/notes/operating-systems/os-file.svg)

关闭某个描述符只是释放这个引用，不能据此推导其他引用失效、文件立即删除或所有数据落盘。不同系统对象还可能有不同读写行为。

## 2. 共享偏移怎样出现？

dup 或 fork 继承的描述符可以指向同一个打开文件描述，因而共享适用偏移；分别 open 同一路径通常会创建不同打开状态。教学例子：两个引用交替 read，不一定各自从文件开头读取。

需要按位置访问时，可以考虑相应显式偏移接口，而不是先 lseek 再 read 却忽略另一线程可能改变共享偏移。接口的原子范围要按文档确定。[fork 的文件继承说明](https://man7.org/linux/man-pages/man2/fork.2.html)

## 3. read 与 write 的返回量

正返回值表示本次实际处理的字节数，不意味着已处理全部请求长度；read 返回 0 时有其 EOF 等语义；错误和中断也需分别处理。不能将短读、短写、阻塞或非阻塞行为一概解释为“磁盘坏了”。

新增教学循环只强调边界：记录已处理位置，根据返回量推进，遇到错误按 API 条件处理；不要用无限重试掩盖永久错误，也不要对已经完成的部分从头重复写入。

## 4. 缓存、设备完成与持久化

write 成功可能表示数据已被内核接受到缓存，不等于所有相关状态都满足断电恢复承诺。fsync/fdatasync 提供相应同步接口，但要检查返回错误，文件名变更所涉及的目录持久化也需要独立考虑。

仅对文件 fsync，不必然保证包含它的目录项已持久；这对“写临时文件再 rename 发布”尤其重要。这里给出设计边界，不提供覆盖用户文件的脚本。[fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)

## 5. 文件系统日志不等于应用事务

文件系统可采用日志或其他恢复技术，保护自身元数据与适用数据的一致性；不代表两个独立文件的业务更新自动成为一个 ACID 事务。原子 rename 的范围也不能无限扩大到跨文件系统、跨主机或任意多文件操作。

可以用一个问题检查理解：订单文件已写入，但索引尚未更新时发生崩溃，恢复时如何识别最后一个完整版本？这需要版本指针、应用日志或其他协议，不能因为底层使用“日志文件系统”就省略应用层设计。
