# 第十一章 Raft 持久化、快照、读与成员变更

> 阅读标签：Raft2014 / 恢复、安全读与成员。

长期运行的共识服务需要在重启后恢复协议状态，用快照控制历史规模，为读取确认安全边界，并在成员变化时维持统一配置。本章依次解释这四条路径如何与选举和日志复制衔接。

## 1. 重启恢复协议承诺与应用进度 {#_1-重启不能忘掉协议承诺}

经典模型把 currentTerm、votedFor 与日志列为需要稳定保存的状态。它们不仅用于恢复业务数据，也用于防止重启后重复投票或违背日志约束。具体存储实现要保证协议所需的写入顺序和原子性，不是调用了 write 就可一概认为抗掉电。

以下是 **Raft 2014 图 2** 的经典模型分类，不要求每个产品使用同样的文件或字段布局：

| 状态 | 类型 | 恢复时的职责 |
| --- | --- | --- |
| `currentTerm` | 持久化 | 不能忘记已知任期并回到过期权威 |
| `votedFor` | 持久化 | 不能重启后在同一任期投给另一个候选人 |
| `log` | 持久化 | 保存命令与任期，供日志匹配、选举和重放使用 |
| `commitIndex` | 易失 | 重建安全的提交认知，不能把所有本地条目直接当作提交 |
| `lastApplied` | 易失 | 与状态机及快照恢复边界协调，避免遗漏或重复应用 |
| `nextIndex` | Leader 易失 | 当选后为各 Follower 重建发送位置 |
| `matchIndex` | Leader 易失 | 重建已确认的复制进度，不能凭旧猜测计多数 |

稳定存储（Stable Storage）是协议对“崩溃重启后仍保留必要状态”的抽象要求。以 Linux 为例，普通 `write` 可能只把数据交给内核缓存；`fsync` 等接口用于请求将数据及必要元数据同步到存储设备。文件创建或替换还可能涉及目录持久化，设备及存储栈也必须履行其承诺，不能由函数名称直接推导任意掉电情形下都安全。接口边界见 [Linux fsync(2)](https://manpages.debian.org/trixie/manpages-dev/fsync.2.en.html)，这里不规定所有平台的具体落盘方案。

commitIndex、lastApplied 与应用快照的保存方式有实现差异，不能机械删掉它们的恢复关系。应用状态若已持久化，重复应用某条命令如何识别，也要与日志位置一起考虑。

教学恢复例子：快照和应用状态对应 index=5，剩余日志从 6 开始。重启先恢复快照，再获得安全的提交边界并按序重放；若应用数据库已单独持久保存到 8，就必须一致地恢复这个进度或提供可靠的重放去重，不能无条件再执行扣款 6～8。经典模型把某字段列为易失，不表示工程实现禁止持久化它。例如 [etcd v3.5.0 raft.go](https://raw.githubusercontent.com/etcd-io/etcd/v3.5.0/raft/raft.go) 的 `hardState` 包含 Commit，`Config.Applied` 用来在重启时避免向应用重新返回已应用条目；这是实现选择，不改写论文图 2 的分类。

## 2. 快照保存已应用边界并衔接日志 {#_2-快照压缩的是历史-不是任意状态拷贝}

![快照与日志边界](/assets/notes/distributed-systems/dist-raft-snapshot.svg)

快照对应已经应用的确定边界，带上 lastIncludedIndex、lastIncludedTerm 等元数据；恢复后再衔接后续日志。它不是普通业务命令中随便插入的一块内存，也不是先删除日志再慢慢复制目录。

快照（Snapshot）把已应用前缀的结果保存为状态机数据，同时保留协议接续所需的元数据：`lastIncludedIndex` 是覆盖到的索引，`lastIncludedTerm` 是该条目的任期，还需保存到这一边界为止的成员配置。客户端去重状态与必要响应缓存也要按应用恢复契约一致保存。[Raft §7～8](https://raft.github.io/raft.pdf)

教学示例，假设状态机已应用到 5：

```text
原日志 index   1  2  3  4  5  6  7  8
       term    1  1  2  2  3  3  4  4

快照：lastIncludedIndex=5，lastIncludedTerm=3
      状态机数据与成员/去重信息均对应边界 5

保留日志 index 6  7  8
         term  3  4  4
```

快照替代的是应用 1～5 后的结果，不必保存这五条命令的完整过程。6～8 的效果尚不在这份快照内，因此保留它们，之后只按提交状态决定是否应用。边界的 index/term 还用于 index=6 之前的前缀匹配；删掉前缀不等于这些逻辑位置从历史中消失。

先安全保存完整快照及其元数据，再回收被替代的日志；若先删日志、快照又未成功持久化，崩溃后可能两种恢复依据都没有。快照仍是当前运行副本的恢复材料，不会自动提供独立、保留历史且跨故障域的备份。

客户端去重表、配置和业务索引如果参与结果判定，也应按应用恢复契约纳入一致状态。否则重启后数据看似存在，同一请求却可能再次扣款。[Raft 扩展论文 §7—8](https://raft.github.io/raft.pdf)

## 3. 用 InstallSnapshot 恢复落后节点 {#_3-落后节点为什么需要-installsnapshot}

Follower 太落后，而 Leader 已经压缩掉它所需的旧日志时，单纯递减 nextIndex 无法找回被回收的内容。需要安装适用快照，再追赶后续日志。

教学案例：Leader 的快照覆盖到 100，只保留日志 101～120；Follower 的最后日志才到 40。Leader 已没有 41～100 可供普通 `AppendEntries` 发送，因此使用安装快照请求 `InstallSnapshot`，使 Follower 获得边界 100 的状态，再接续后面的日志。

对一个任期有效、范围适用的快照，日志保留有两种分支：

| 分支 | 日志处理 |
| --- | --- |
| 本地存在相同 `lastIncludedIndex`、相同 `lastIncludedTerm` 的条目 | 该边界能证明前缀匹配，保留边界之后的有效日志后缀；不要因重传就丢掉它 |
| 没有相同 index/term 的边界条目 | 不能证明原后缀可接续；按经典快照规则丢弃不匹配的旧日志，以快照为基准再接收后续条目 |

前述落后到 40 的节点没有 index=100，属于第二种情况。第一种则可能发生在收到覆盖本地已有前缀的快照时。两分支讨论日志保留；状态机是否需要重新装载还要结合已应用位置，不能用旧快照把更先进的已应用状态回退。依据见 [Raft §7、Figure 13](https://raft.github.io/raft.pdf)。

接收方必须检查任期与快照边界，防止旧快照覆盖更先进的已应用状态；需要保留哪些日志，也取决于边界是否匹配。文件接收完成、快照安全生效和状态机开始提供服务，是三个不同步骤。

论文支持按 `offset`、`data`、`done` 分块传输：最后一块到达之前，接收文件还不是可安装的完整快照。中断、重试与重复块必须按偏移和传输状态处理，不能将半份文件公布为有效恢复点。图 13 是算法概要，具体原子文件替换、接收缓存和恢复流程由实现完成，不能直接当作可部署的文件复制脚本。

## 4. 读取前确认领导权并等待应用进度 {#_4-leader-本地读为何可能读旧}

被隔离的旧 Leader 可能尚未得知新任期，不能仅凭自己的角色变量服务实时一致读。基于多数确认的安全读路线需要三个条件，缺一不可：

1. **建立当前任期的提交前提。** 新 Leader 先提交一条本任期日志，以确定自己掌握的已提交前缀。论文在任期开始时提交 no-op；一条正常业务命令也可提供这一前提，不是每次读都必须追加 no-op。
2. **为这次读确认领导权并取得读边界。** 通过与该次读关联的多数确认等协议排除已被替换的旧主，取得安全读取边界。随意复用很久以前的心跳成功，不能保护任意后来的读。
3. **等状态机追上。** 等待本地 lastApplied 达到读边界，再从状态机读取。日志已提交，但状态机尚未应用时，立即读仍可能返回旧状态。

纸面推演：新 Leader 有旧任期条目 index=8，但刚上任时未必已知其提交边界。它先提交本任期 index=9，再对一次读确认多数，得到读边界9。若 lastApplied=7，仍须先应用8、9，不能只因角色是 Leader 就返回状态。[Raft 2014 扩展论文 §8](https://raft.github.io/raft.pdf)

把这个读取时刻写成字段就是 `commitIndex=9、ReadIndex=9、lastApplied=7`。提交进度达到读边界，不代表应用进度已经达到；必须等 8、9 应用完才能按该边界读取。读取还应使用与状态机更新协调的视图，避免把查询拆成互相矛盾的中间状态。

租约读是另一种经证明的优化路线，依赖时钟偏差、时序与租约协议等额外假设；不应当成基础多数确认读的无条件替代。

反例：A 与多数失联，B 已在新任期提交 x=2；A 本地还保存 x=1。如果 A 在 B 写成功之后仍立即返回 1，就违反这一对象的线性一致读取要求。租约优化不能反过来改写成“基础 Raft 天生允许 Leader 永远不联系多数”。

产品 API 还可能提供显式旧读选项。例如 etcd v3.5 区分默认的线性一致读取与较弱的 serializable 读取；该产品术语不能直接等同 SQL 事务的 Serializable 隔离级别。[etcd v3.5 API 保证](https://etcd.io/docs/v3.5/learning/api_guarantees/)

| 路线或术语 | 作用与条件 |
| --- | --- |
| 读索引（ReadIndex） | 获得本次请求可依赖的安全日志边界；基于多数确认的路线通常关联读取上下文与心跳确认，不需要每次读取都写一条日志，仍须等待应用 |
| 租约读（Lease Read） | 在有效租约内减少反复多数确认，安全性依赖经过证明的时钟与时序假设；过去一次心跳成功不能无限期作为租约 |
| etcd v3.5 的 Serializable Read | 显式允许相对集群最新状态的旧读，减少实时共识依赖；不是 SQL Serializable 事务隔离的同义词 |

实现定位采用 **etcd v3.5.0** 的 [raft.go：MsgReadIndex、committedEntryInCurrentTerm、sendMsgReadIndexResponse](https://raw.githubusercontent.com/etcd-io/etcd/v3.5.0/raft/raft.go)。其中基于多数的 `ReadOnlySafe` 与依赖租约的 `ReadOnlyLeaseBased` 是两条路径，后者还要求相应的 `CheckQuorum` 条件；这些选项名是该实现的术语，不是论文规定的通用 API。

## 5. 成员变更中的配置一致性 {#_5-成员变化为什么也是共识问题}

旧配置 {A,B,C} 与新配置 {C,D,E} 可以各自形成没有交集的多数，不能让大家独立改配置文件后自行生效。论文的联合共识在过渡阶段同时满足新旧配置的多数，以避免两个独立权威。

联合共识（Joint Consensus）让配置作为日志条目复制，按 `C_old → C_old,new → C_new` 过渡。本节严格采用 **2014 论文 §6** 的生效规则：节点一旦把配置条目加入本地日志，就用日志中最新配置作后续协议决策，**不等该条目提交**；这不等于一次追加已完成整个成员变更。

| 阶段 | 复制、提交与生效的区别 |
| --- | --- |
| 旧配置 `C_old={A,B,C}` | 旧多数为 2；新节点可先以非投票成员追赶，尚不改变投票门槛 |
| Leader 追加并复制联合配置 `C_old,new` | 存有该条目的节点立即按联合配置决策；Leader 用旧多数和新多数同时满足的规则提交联合条目。尚未收到该条目的节点可能仍按旧配置运行 |
| 联合配置已提交 | 后续合法 Leader 必须包含它；没有新配置条目前，选举与提交都要求旧、新各自多数。只有此时才开始提出 `C_new` 条目 |
| Leader 追加并复制 `C_new={C,D,E}` | 存有该条目的节点立即用新配置决策；按新配置的多数提交此条目，其他节点可能暂时仍处于联合配置 |
| 新配置已提交 | 变更完成，旧配置独有成员 A、B 可退出；若 Leader 不在新配置中，也须按论文规则在此时退下 |

以上时点依据 [Raft §6、Figure 11](https://raft.github.io/raft.pdf)。配置暂时不同的节点仍受日志、选举和这两个阶段的约束，不是让旧、新两个配置独立作决定。

联合阶段的成功集合 Q 必须同时满足 `|Q ∩ {A,B,C}| ≥ 2` 与 `|Q ∩ {C,D,E}| ≥ 2`。例如 `{A,C,D}` 同时有旧侧 A、C 和新侧 C、D，满足双多数；而 `{A,B,D}` 虽是五个联合成员中的三人，却只有一个新成员 D，不满足。反过来 `{C,D}` 是新配置多数，但不是旧配置多数。C 可以同时计入两个配置各自的计数，不能把双多数改成联合集合的一次普通多数。

![Raft 2014 配置条目追加即参与决策、联合双多数及新配置提交的阶段关系](/assets/notes/distributed-systems/dist-raft-joint-consensus.svg)

不同实现的成员变更协议与操作接口并不完全相同，不能统一采用“停掉旧节点、启动同名新节点”的替换步骤。还需处理身份、数据追赶、持久化配置与恢复流程。

学习者或非投票成员（Learner）可以先同步日志，达到要求后再通过配置变更获得投票资格；它不计入此前的投票多数。etcd v3.5 文档介绍了添加 Learner 与显式晋升的工程流程，见 [etcd Learner Design](https://etcd.io/docs/v3.5/learning/design-learner/)。论文的非投票追赶、联合配置，与具体实现采用的单节点变更、应用配置条目或操作 API 要分别理解；本章联合配置图不用于推导 etcd 的全部配置生效细节。

## 6. 持久化成本与实际吞吐 {#_6-不用固定磁盘数字推导系统上限}

HDD 10 ms、SSD 0.1 ms 只能作为某环境中的示意延迟。批处理、流水线、日志组提交、网络和数据大小都会影响吞吐，不能由某一次写时延倒数直接声称整个 Raft 服务只有 100 QPS。

实际实践必须固定实现版本，独立验证断电与故障切换路径。

本章沿共识日志讨论恢复、读取和配置安全。下一章换一个问题视角：一些数据服务允许故障期间在不同可达副本接收更新，因而需要版本因果、冲突合并和副本修复。Dynamo 的这些机制与 Raft 所解决的操作契约和假设不同，不能仅用“强、弱一致”两个标签替代具体分析。
