# 第二十九章 慢查询、延迟与热点大键

[返回本册目录](/collections/redis/)

客户端超时可能发生在连接池、应用事件循环、网络、服务端排队、命令执行或持久化竞争等阶段。排查时先拆分时间，再选择对应证据；Slowlog 用于观察命令执行，端到端等待还需结合客户端与系统指标。

![延迟的四层来源](/assets/notes/redis/redis-study-latency.svg)

## 1. Slowlog 的执行时间与其他等待 {#_1-slowlog-看不到所有等待}

Slowlog 记录符合阈值的命令执行耗时，不包括与客户端通信的全部时间。阈值和结果中的耗时使用微秒，不能把 1000 微秒误读成 1000 毫秒。

```redis
SLOWLOG LEN
SLOWLOG GET 10
INFO commandstats
```

Slowlog 为空，仍可能存在服务端排队、网络拥塞或客户端自身停顿。commandstats 的调用数和累计耗时也不是 P99；需要结合采样窗口计算变化，并与应用监控对应。[SLOWLOG GET](https://redis.io/docs/latest/commands/slowlog-get/)

慢日志可能包含键名、参数和客户端信息，导出时应脱敏，避免将真实业务标识直接贴到公开博客。降低阈值或增加日志长度，也会改变采集开销，不能认为任意强度的采集都没有成本。

## 2. 按对象规模与访问集中度区分大键和热键 {#_2-大键与热键不是同一种问题}

大键是尺寸或元素规模过大；热键是访问集中。一个很小的计数器可以极热，一个很大的归档对象也可能很冷。它们会通过不同路径造成 CPU、网络、内存、复制或迁移压力。

检测大键时，需要区分命令统计的是字符串字节、集合元素数，还是内存估算。`redis-cli --bigkeys` 的结果不能统一读成内存字节；适用版本的内存扫描功能也有采样与运行成本。

默认检查不应包括全库 KEYS、直接全量读取巨大集合，或对生产库执行无约束扫描。SCAN 虽可分步执行，但仍需控制总工作量、返回值尺寸和扫描节奏。

## 3. 删除和读取都可能产生尖峰

大对象的成本不只出现在删除时。一次 HGETALL 或 LRANGE 取回大量结果，同样会占用执行时间、输出缓冲、网络和客户端解码资源。应先检查数据模型与访问范围，再考虑分页、拆分或只读取必要字段。

UNLINK 可让适用对象的内存回收走异步路径，但不是零开销删除，也不能让所有大键操作都变轻。对象删除后的 RSS 不立即下降，也不证明删除失败。

## 4. 带宽、吞吐与排队要分开算

1 Gbit/s 的理论字节速率约为 125 MB/s，实际还要扣除协议和链路开销；不是 128 KB/s。大回复即使计算很快，也可能使网络先达到瓶颈。

若 1 ms 是客户端端到端响应时间，不能直接取倒数当作服务器吞吐上限。若明确限定为单个串行执行路径，每条命令实际占用该路径 1 ms，忽略其他开销时，理论容量约为 1000 条/秒；增加客户端并发或 Pipeline 不消除这部分执行成本。

混合负载应按命令执行时间和比例估算服务需求，再考虑其他瓶颈。这是带假设的纸面模型，不是压测结果。[第 17 章 Pipeline](/articles/redis-pipeline.html) 主要摊薄通信等待，不让占用同一串行路径的 CPU 工作凭空并行。

## 5. 压测不是诊断的第一动作

先保存版本、数据规模、实际命令分布与时间窗，再提出假设。需要实验时，在隔离环境控制并发、连接、值大小和 Pipeline。redis-benchmark 中 `-p` 是端口，`-P` 是 Pipeline 数量，大小写不能混淆。

redis-cli 的 `--raw` 倾向原始输出，`--no-raw` 倾向便于阅读的格式。工具输出本身不能证明生产性能；本次没有执行扫描、基准测试或配置变更。
