# 第六章 分片、一致性哈希与数据迁移

> 阅读标签：通用协议/应用模型，具体前提见本章。

分片（Sharding）决定不同键的数据由哪些分片负责，用于分担容量与访问负载；复制（Replication）决定同一分片保留多少份数据，用于冗余和适用的读扩展。二者常一起实现，却不能互相替代。一致性哈希（Consistent Hashing）主要减少成员变化对路由映射的影响，这里的“一致性”不表示副本自动满足第四章的一致性模型。

## 1. 从简单取模的问题开始

假设使用 `hash(key) mod N` 选择编号为 0 到 N−1 的节点。教学示例：12 个键每个占 1 MiB，哈希结果恰好为 0～11，总计 12 MiB；暂不考虑副本及元数据开销。三个节点时每个承载四个键，扩成四个节点时每个承载三个键：

| 哈希值 | 原节点：mod 3 | 新节点：mod 4 | 是否重新映射 |
| --- | --- | --- | --- |
| 0、1、2 | 0、1、2 | 0、1、2 | 否 |
| 3、4、5 | 0、1、2 | 3、0、1 | 是，三个键都变化 |
| 6、7、8 | 0、1、2 | 2、3、0 | 是，三个键都变化 |
| 9、10、11 | 0、1、2 | 1、2、3 | 是，三个键都变化 |

扩容只增加了一个节点，但这里 9/12 的键、共 9 MiB 需要重新映射，且不只是旧节点向新节点移动。原因是除数从 3 变成 4，整个余数规则随之改变。这个算例不是实测迁移量，也不是任意键分布下的固定比例；实际搬多少字节取决于键的大小、分布和迁移方案。

范围分片（Range Sharding）按键的连续区间分配数据，范围查询容易定位到少量分片；若订单 ID 随时间单调递增，新写入会集中到当前最大 ID 所在的尾部分片，扩出其他范围也不会自动分担这个写入点。哈希分片（Hash Sharding）按哈希值分配，哈希分布良好时更容易分散不同键，但原始键相邻不再意味着位置相邻，范围查询可能需要访问多个分片。产品实例可参照 [MongoDB 8.0 范围分片](https://www.mongodb.com/docs/v8.0/core/ranged-sharding/)与[哈希分片](https://www.mongodb.com/docs/v8.0/core/hashed-sharding/)。没有一种分片键同时优化所有访问模式。

## 2. 一致性哈希环的归属与成员变化 {#_2-一致性哈希环怎样工作}

先把哈希值空间想象成一个首尾相接的有序环：真实系统可以使用很大的整数范围，教学中缩成 0～99，顺时针数值递增，99 后回到 0。

1. 把节点标识哈希到环上，得到它的一个位置，也称令牌（Token）。
2. 把数据键哈希到同一个空间。
3. 从键的位置顺时针查找第一个节点位置，将它作为该键的所有者；超过最大位置就绕回第一个位置。

“顺时针第一个”是这里采用的确定性分配规则，不是数据本身必须这样存储的自然规律。它让某位置 p 负责 `(前驱位置, p]`：新增 q 只需拆分其后继原有的区间；移除 p 则把该区间交给仍在环上的后继。未被拆分的区间仍指向原所有者，所以不必像改变取模除数一样重算全部归属。该方法的最少扰动思想见 [Karger 等人 1997 原论文 §4](https://people.csail.mit.edu/karger/Papers/web.pdf)。这只解释所有权变化，实际搬数据、复制和切换仍需协议。

### 多个虚拟节点分担区间

若一台机器只有一个随机位置，区间长短可能很不均匀，且扩容时负载可能集中由某一台旧机器转出。虚拟节点（Virtual Nodes，vnodes）让一台物理机器在环上有多个位置，承载分散的区间，从而改善统计上的均衡；容量大的机器还可以分配更多令牌或更大权重。这仍依赖位置选择、数据大小和流量分布，不保证每台机器的实际负载相等。设计依据见 [Dynamo 2007 §4.2](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)。

虚拟节点是分配单位，不是真实副本。A1、A2 即使是两个环位置，只要都在物理机器 A 上，A 故障就会一起失效；选择多个数据副本时要额外跨越不同物理机器及故障域。

### 三台物理机器扩为四台的教学推演

设物理机器 A、B、C 各有两个虚拟位置：A1=10、A2=70；B1=30、B2=85；C1=50、C2=95。新增 D 时加入 D1=40、D2=80，旧位置不变。本例只展示单份数据的主归属，不把令牌数当作副本数。

| 数据键与哈希位置 | 扩容前的归属 | 扩容后的归属 | 是否迁移 |
| --- | --- | --- | --- |
| k05：5 | A1=10 | A1=10 | 否 |
| k20：20 | B1=30 | B1=30 | 否 |
| k35：35 | C1=50 | D1=40 | 是，C → D |
| k45：45 | C1=50 | C1=50 | 否 |
| k60：60 | A2=70 | A2=70 | 否 |
| k75：75 | B2=85 | D2=80 | 是，B → D |
| k90：90 | C2=95 | C2=95 | 否 |
| k98：98 | 绕回 A1=10 | 绕回 A1=10 | 否 |

D1 接管 `(30,40]`，D2 接管 `(70,80]`，所以示例中的八个键只有 k35、k75 改变所有者。环上没有画出的键，只要落在这两个区间，也都需要按新归属迁移。移除 D 时，这两段分别还给后继 C1=50、B2=85；如果 D 是突然故障且没有其他数据副本，环能算出新归属，却无法凭空恢复 D 上丢失的数据。

## 3. 键分布、热点与实际负载 {#_3-均匀键数不等于均匀负载}

教学例子：100 万个商品平均分在四个分片，但一次促销的单商品占到大部分访问。即使每片键数相近，该商品仍只在一个所有权范围里；增加虚拟节点不自动拆开它的写入瓶颈。

需要分别观察字节数、访问次数、热点对象和跨分片事务比例。业务拆键、缓存、读副本或专门的聚合协议，解决的是不同瓶颈。

## 4. 从存量复制到增量追赶与路由切换 {#_4-扩容不是改完路由就结束}

![数据复制与路由切换的协作](/assets/notes/distributed-systems/dist-sharding.svg)

[打开迁移流程原图](/assets/notes/distributed-systems/dist-sharding.svg)。图示采用“单一写入所有者 + 快照 + 增量日志 + 短暂停写切换”的教学方案；其他系统也可选择转发、双写或不同复制方式。

教学中要把某个范围从旧节点 S 搬到新节点 T，可以按以下过程组织；假设元数据能原子更新所有权、写入能持久记录有序增量，且存储会校验所有权版本。这些是方案前提，不是哈希环自带的功能。

| 步骤 | 动作与确认条件 |
| --- | --- |
| 1. 确定所有权与版本 | 记录该范围当前由 S、代际 e 负责；为迁移建立唯一标识，T 暂不直接接受业务写入 |
| 2. 复制存量 | 在可恢复边界 b0 取得一致快照；开始复制前就保留边界后的增量，避免复制与日志捕获之间出现缺口 |
| 3. 捕获增量 | S 继续负责业务写入，将 b0 后的新增、修改、删除持久记录并重放到 T；重放需按序且可去重 |
| 4. 追赶并确认边界 | 暂停该范围旧写入，排空在途写，确定最后提交位置 b1；确认 T 已应用到 b1，失败时先不切换 |
| 5. 切换路由 | 在旧资格已被隔离、T 已就绪的条件下，将权威所有权发布为 T、代际 e+1，再开放 T 写入 |
| 6. 处理旧客户端 | 旧路由请求在 S 被拒绝或有限转发，客户端刷新版本；写入端与底层资源校验新代际，阻止旧执行者继续写 |
| 7. 观察后回收 | 确认新数据、恢复能力及旧请求处理符合要求后，再回收 S 的旧数据；切换和删除分开执行 |

单纯复制存量可能遗漏复制期间的新写，也可能被迟到的旧值覆盖。快照边界、可靠增量和最终排空共同回答“哪些数据已经包含在 T 中”。作为产品对照，[MongoDB 8.0 的范围迁移过程](https://www.mongodb.com/docs/v8.0/core/sharding-balancer-administration/#range-migration-procedure) 也包含源端接写、复制及追赶、短暂停写、元数据切换和后续清理；本表是教学设计，不声称所有产品采用相同协议。

### 双写与旧请求的失败边界

双写是另一种选择，但“同时向两处写”不提供天然原子性。教学推演：S 写入成功、T 写入失败，如果仍向业务返回成功，就要把待补传记录和 S 的变更可靠关联，之后按同一操作 ID 修复；如果返回失败，S 上的成功也不能当作从未发生。反过来只有 T 成功时，同样需要约定谁是权威、如何查询和消除分歧。还要防止两个目标以不同顺序应用更新；幂等、顺序与补传状态都属于协议。

所有权版本（Ownership Version）、代际编号（Epoch）或隔离令牌（Fencing Token）用来区分新旧写入资格。例如元数据已经是 e+1，暂停后恢复的 e 代执行者不能继续向资源写入；令牌必须在实际写入端被校验，仅在客户端缓存一个版本号并不够。若采用转发，旧节点也不能先本地写成功再任意转发，且应有跳转次数与截止时间，避免重定向循环。

切换后，T 可能已接受 b1 之后的新更新。此时直接把 S 的旧快照覆盖回去，或简单把路由改回 S，会丢掉这些新数据。回退需要重新确定权威、补齐反向增量或合并版本，再以更新的代际切换；保留旧数据只是回退条件之一，不是现成的安全回滚方案。

## 5. 复制位置与成员视图也是协议状态

为每个键沿环选择多个副本时，要保证它们符合故障域策略。成员列表传播有延迟，两个客户端可能暂时看到不同路由；实际系统需要权威配置、代际编号或适用的冲突协议，不是只要画好圆环就消除了分歧。

验证时应检查：扩容期间是否遗漏读写、重复迁移是否安全、失败后能否恢复、何时可回收旧节点，以及回退是否会覆盖切换后的新数据。本册仅整理分析流程，不执行迁移。
