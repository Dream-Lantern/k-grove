# 第六章 分片、一致性哈希与数据迁移

> 阅读标签：通用协议/应用模型，具体前提见本章。

分片决定各部分数据由谁负责，复制决定同一数据保留多少份。二者常一起实现，却不能互相替代。一致性哈希主要减少成员变化对路由映射的影响，并不负责使数据自动保持一致。

## 1. 从简单取模的问题开始

假设使用 hash(key) mod N 选择节点。N 从 3 改成 4 时，许多键的映射都会改变；即使旧节点仍在线，也需要迁移大量数据。这个方案实现简单，但扩容方式必须与路由规则共同设计。

范围分片可以支持局部范围查询，却可能因单调增长的键形成尾部热点；哈希分片通常有助于分散键，却不天然支持相邻键局部扫描。没有一种分片键同时优化所有访问模式。

## 2. 一致性哈希环的归属与成员变化 {#_2-一致性哈希环怎样工作}

把节点和键映射到同一个有序环，键归属顺时针遇到的第一个适用节点。新增节点主要接管前驱与自身之间的一段键空间；移除节点则由后继接管。这是基本环模型，不代表真实系统只做一次单副本移动。

虚拟节点让一台物理机器承载多个位置，可以改善平衡与异构容量分配，但需要考虑同一物理故障域，不能把同一台机器的多个位置当成多个独立副本。[Dynamo 的分区与虚拟节点设计](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)

## 3. 键分布、热点与实际负载 {#_3-均匀键数不等于均匀负载}

教学例子：100 万个商品平均分在四个分片，但一次促销的单商品占到大部分访问。即使每片键数相近，该商品仍只在一个所有权范围里；增加虚拟节点不自动拆开它的写入瓶颈。

需要分别观察字节数、访问次数、热点对象和跨分片事务比例。业务拆键、缓存、读副本或专门的聚合协议，解决的是不同瓶颈。

## 4. 从存量复制到增量追赶与路由切换 {#_4-扩容不是改完路由就结束}

![数据复制与路由切换的协作](/assets/notes/distributed-systems/dist-sharding.svg)

教学中的迁移过程可以按以下顺序组织：先固定所有权版本；复制存量期间记录增量；达到允许的追赶边界后切换；处理旧客户端和在途请求；最后才清理旧数据。若没有停写或可靠增量机制，初始复制后的新写可能被遗漏。

双写同样需要处理失败。当两个目标一方成功、一方失败时，必须明确以谁为准、如何补偿，以及能否安全重试。切换期间的重定向还需避免循环与无限重试。

## 5. 复制位置与成员视图也是协议状态

为每个键沿环选择多个副本时，要保证它们符合故障域策略。成员列表传播有延迟，两个客户端可能暂时看到不同路由；实际系统需要权威配置、代际编号或适用的冲突协议，不是只要画好圆环就消除了分歧。

验证时应检查：扩容期间是否遗漏读写、重复迁移是否安全、失败后能否恢复、何时可回收旧节点，以及回退是否会覆盖切换后的新数据。本册仅整理分析流程，不执行迁移。
