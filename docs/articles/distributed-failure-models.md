# 第一章 全景架构、问题与故障模型

> 阅读标签：通用协议/应用模型，具体前提见本章。

分布式系统由多个通过网络协作的进程组成。一项业务经过计算、通信和持久化的多个环节，各环节可能独立成功或失败。学习这类系统，可以先确定数据归属、成功条件和恢复依据，再分析分片、复制与协调机制。

## 1. 用分片扩展工作，用复制保留冗余 {#_1-为什么需要分布式}

分片（Sharding）按照键（Key，例如商品 ID）把数据分配给不同分片，让不同节点分担存储容量与访问负载。复制（Replication）则把同一分片的数据保存多份，用于容错，并在读取规则允许时分担读请求。两者可以一起使用。产品实例可参照 [MongoDB 的分片说明](https://www.mongodb.com/docs/manual/sharding/)，这里不展开其路由算法。

教学示例：商品目录按商品 ID 分为三个分片，每片保存三份副本，总计 `3 × 3 = 9` 个副本实例。假设采用主从复制，每片的三份**包含一份主副本和两份跟随副本**。这是三个逻辑数据集，不是九份完全相同的完整数据库。某一分片失去可写能力，仍可能只影响部分商品；如果订单必须同时访问多个分片，故障范围又会扩大。

复制不等于备份：误删除也可能被同步到其他副本；备份需要独立保留可恢复的历史状态。备份方法可参照 [PostgreSQL 17 的备份与恢复文档](https://www.postgresql.org/docs/17/backup.html)。复制也不能自动拆散一个热 Key：若某热门商品的写入都由同一主副本处理，增加跟随副本仍不能分担这个写入点，反而增加复制工作。能否分担读取，则取决于一致性要求与读路由。

## 2. 从全景图分清职责

[打开架构原图](/assets/notes/distributed-systems/dist-overview.svg)。小屏幕可打开原图放大查看。

入口决定请求路由，不负责证明数据库已经提交；业务服务维护订单、库存等约束；数据层决定分片、复制和恢复；协调服务提供适用的成员、配置与资格信息。观测系统帮助重建事实，但日志里的一句“开始提交”不是提交证明。

这些是逻辑职责，不意味着每一部分都需部署为独立产品。小系统可能只需一个有备份的数据库；拆分出更多服务，会增加跨边界通信和恢复协议，并不一定更可靠。

图中实线表示入口到业务层、业务层到数据层的请求；虚线表示协调与配置对业务层、数据层的控制关系；点线表示多个组件把指标、日志和追踪送入观测系统。协调与观测不是每次业务请求必须串行经过的下游。

## 3. 故障不只有进程退出

下表均为订单系统的教学示例，不是故障实测记录。

| 故障类型                     | 订单系统示例                          | 观察边界                 |
| ------------------------ | ------------------------------- | -------------------- |
| 崩溃故障（Crash Failure）      | 订单进程在提交前退出，连接断开                 | 进程停止不代表磁盘上的已提交状态丢失   |
| 网络分区（Network Partition）  | 订单服务与库存服务之间链路中断，双方仍在运行          | 互相超时不代表对方停止执行        |
| 进程暂停（Process Pause）      | 库存工作进程因垃圾回收（GC）或调度暂停而很久不回复，随后恢复 | 旧锁持有者仍可能继续写入         |
| 存储故障（Storage Failure）    | 订单数据库磁盘返回 I/O 错误、数据损坏或写入长时间阻塞   | 更多副本不能自动覆盖所有相关故障     |
| 拜占庭故障（Byzantine Failure） | 有缺陷或被入侵的节点向不同节点声称同一订单有不同扣款金额    | 这是任意错误或恶意行为，超出普通崩溃模型 |

**节点没有响应，不代表节点已经死亡。** 网络延迟、GC 和调度暂停都可能让活着的进程错过超时。教学推演：旧工作进程获得库存操作资格后暂停，协调方判定其超时并把工作交给新进程；旧进程恢复时，内存中的执行位置仍在“写库存”之前。如果数据层不检查资格是否过期，它可能继续执行旧操作。因此接管还需要防止过期写入，后续租约与隔离令牌章节会展开。

[Raft 2014 扩展论文 §2](https://raft.github.io/raft.pdf) 的故障假设包括非拜占庭故障及消息延迟、丢失等；它不保证处理任意造假或恶意行为。[PBFT 原论文的系统模型](https://www.usenix.org/legacy/publications/library/proceedings/osdi99/full_papers/castro/castro_html/node2.html) 则讨论拜占庭故障，并有自己的身份与故障数量前提。

讨论容错数量前，协议应先声明能够处理的故障类型。多个实例若共用机架、电源，或受同一误删除脚本影响，就可能出现相关故障，不能按独立失效的概率计算。

## 4. 安全性约束结果，活性约束进展 {#_4-安全性和活性分别是什么}

安全性（Safety）约束“不能发生什么”，例如一个订单不能重复扣款、同一日志位置不能提交两个不同值。活性（Liveness）描述“满足约定条件后，系统最终如何继续推进”，例如网络恢复、必要节点可用且调度公平后，待处理订单最终能得到结果。系统失去多数时拒绝写入，可能是在守住安全性；持续失去多数时则无法保证完成写入。共识中的安全性与进展条件见 [Raft §2、§5.6](https://raft.github.io/raft.pdf)。

反过来，只要还有一个节点就接受所有写入，可能提高某些请求的成功率，却需要承担冲突与合并责任。“返回了 200”与“满足了业务一致性”是两个指标。

## 5. 用不变量贯穿后面的章节

不变量（Invariant）是在系统允许的状态转换中始终应成立的约束。本册使用虚构的订单教学案例：

- 同一订单的同一笔支付最多产生一笔有效扣款。
- 可用库存始终大于或等于零，并发预留也要守住这一点。
- 在约定的故障范围内，已确认的关键状态必须保留足够的持久化依据以便恢复。

这些约束可用于检查安全性与持久性。恢复依据不能丢失是约束；故障条件解除后最终完成恢复，则还涉及活性。算法与产品是实现这些约束的工具。

各章沿着请求的执行阶段、可恢复记录与继续执行资格展开。本章时序仅用于推演，没有部署实例或制造故障；历史系统的前提在案例章单独标明。
