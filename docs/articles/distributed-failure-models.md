# 第一章 全景架构、问题与故障模型

> 阅读标签：通用协议/应用模型，具体前提见本章。

分布式系统不只是“把一个服务部署三份”。一项业务经过多个进程、网络和持久化介质时，可能出现局部成功、响应丢失和视图不同步。学习时应先明确数据由谁负责、什么算成功、失败后如何判断事实，再考虑中间件选型。

## 1. 为什么需要分布式？

原笔记中的分片与复制，分别回应两类需求。分片把不同数据或工作分给不同节点，争取容量与并行；复制为同一份逻辑状态保留多份副本，争取容错与适用的读扩展。分片不自动提供冗余，复制也不会自动拆开单个热键。

教学例子：商品目录按商品 ID 分为三个分片，每片有三个副本。这是三个逻辑数据集、九个副本实例，不是九份完全相同的完整数据库。某一分片失去可写能力，仍可能只影响部分商品；如果订单必须同时访问多个分片，故障范围又会扩大。

## 2. 从全景图分清职责

![请求、计算、数据、协调与观测](/assets/notes/distributed-systems/dist-overview.svg)

入口决定请求路由，不负责证明数据库已经提交；业务服务维护订单、库存等约束；数据层决定分片、复制和恢复；协调服务提供适用的成员、配置与资格信息。观测系统帮助重建事实，但日志里的一句“开始提交”不是提交证明。

这些是逻辑职责，不意味着每一部分都需部署为独立产品。小系统可能只需一个有备份的数据库；拆分出更多服务，会增加跨边界通信和恢复协议，并不一定更可靠。

## 3. 故障不只有进程退出

| 情况             | 观察到的现象           | 不能直接推断的结论             |
| ---------------- | ---------------------- | ------------------------------ |
| 进程停止         | 心跳消失、请求失败     | 磁盘上的状态已经丢失           |
| 网络分区或长延迟 | 双方互相超时           | 对方停止执行、可以随意接管     |
| 进程暂停         | 长时间无回复，随后恢复 | 旧锁持有者不会再写入           |
| 存储故障         | I/O 错误、损坏或延迟   | 多放一份副本就必然覆盖所有风险 |
| 错误或恶意行为   | 不同接收方得到矛盾消息 | 适用崩溃模型的 Raft 足以处理   |

讨论容错数量前，协议应先声明能够处理的故障类型。多个实例若共用机架、电源，或受同一误删除脚本影响，就可能出现相关故障，不能按独立失效的概率计算。

## 4. 安全性和活性分别是什么？

安全性要求不发生禁止的结果，例如同一日志位置不会提交两个不同值；活性要求在约定条件下能继续取得进展。系统失去多数时拒绝写入，可能是在守住安全性，而不是共识算法“已经错误”。

反过来，只要还有一个节点就接受所有写入，可能提高某些请求的成功率，却需要承担冲突与合并责任。“返回了 200”与“满足了业务一致性”是两个指标。

## 5. 用不变量贯穿后面的章节

本册新增一个虚构的订单案例：订单不能重复扣款；库存不能因并发预留而变为负数；已确认的关键状态应在约定故障范围内可恢复。这些是不变量，算法与产品是实现它们的工具。

各章会追问请求可能停在哪一步、有哪些可恢复记录、谁有权继续执行。所有时序与伪代码仅用于推演，没有部署实例或制造故障。经典复制模型可参照 [Raft 扩展论文 §2](https://raft.github.io/raft.pdf)；历史系统的前提在案例章单独标明。
