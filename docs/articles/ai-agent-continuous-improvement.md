# 第8章 Agent 的持续进化（Continual Improvement）

## 8.1 从任务经历到可验证的改进 {#_8-1-保存经历不等于-学会}

Agent 的持续改进（Continual Improvement）是一条工程流程：**轨迹采集 → 评价 → 跨轨迹归纳 → 候选更新 → 回归验证 → 发布/回滚**。第 7 章讨论修改模型参数，本章讨论整个系统怎样利用执行反馈：可以更新知识库、Prompt、Skill、Harness，也可以在适当条件下训练模型。一次任务完成不会自动修改模型权重。

轨迹（Trajectory）是一次任务中按顺序记录的观察、动作与反馈；经验（Experience）是从这些记录中提取、带适用条件且可验证的行动规则。保存轨迹后还要独立评价和核查来源，才能把它转成候选经验。

### 三层验证器

| 层级     | 数据依据             | 例子                       |
| -------- | -------------------- | -------------------------- |
| 结果验证 | 数据库/测试/业务环境 | 是否真正创建测试任务       |
| 过程验证 | 工具轨迹、权限与顺序 | 是否在批准前执行了写操作   |
| 质量验证 | Rubric + LLM/人工    | 说明是否完整、策略是否合适 |

正确性越容易形式化，就越应交由确定性程序判断；使用 LLM 评价语言质量时，仍须校准并保留不确定性。

### 用一次重试故障串起改进流程

假设一个工具返回 `error_code=AUTH_DENIED, retryable=false`，Agent 却又调用了它两次。这是合成教学故障，不是线上事件。保存原始请求、三次调用结果与版本后，才能判断重复调用确实发生，而不是日志重复写入。

1. **识别失败模式**：在另一条独立任务轨迹中也发现同类不可重试错误被重复调用，将两条来源及 Hash 关联成候选故障簇。固定源码的诊断也要求至少两条匹配轨迹；重复不是根因证明，但能提供进一步调查的线索。
2. **定位根因**：核对控制代码后发现，旧重试条件只比较 `attempt < MAX_RETRIES`，没有读取 `retryable`。该判断会允许本例继续尝试，故障属于 Harness 的确定性控制逻辑。
3. **提出候选**：在候选目录增加“不可重试则停止”的分支，同时保留临时故障在预算内恢复的路径。固定源码中的生成器按已知修改模式产生候选；若改由模型提议补丁，模型仍只负责提案，不能自批发布。
4. **隔离验证**：确定性程序检查语法、API 兼容与安全规则，再在 Docker 隔离环境回放故障。AST 预筛通过不能代替隔离执行，容器不可用时应停在失败门禁。
5. **旧任务回归**：验证不可重试错误不再重复、临时错误仍能恢复、已有重试预算与熔断约定未被破坏，并保留稳定版本与回退材料。
6. **生成资格并外层审核**：检查齐全通过后，清单才可给出 `release_to_canary`。这是候选资格；外部发布系统核对来源、范围与人工批准后，才执行获准的影子或灰度方案。
7. **监测与回退**：对照重复调用、临时恢复和业务指标监测；出现不可重试重复或旧任务退化时，按预定触发条件恢复清单中的稳定版本，保留故障证据。

这条链中，提出补丁、证明有限测试通过、批准真实发布是三种不同职责。第 8.7 节对应源码检查链；这里没有执行 Docker、模型调用或真实发布。

## 8.2 四类更新载体

| 载体              | 适合什么                     | 最大好处               | 主要风险           |
| ----------------- | ---------------------------- | ---------------------- | ------------------ |
| 知识库 / 经验文档 | 经验证事实与经验             | 可溯源、易更新         | 检索不到/过期      |
| Prompt / Skill    | 可语言化规则和操作流程       | 修改快、可限定作用域   | 规则冲突或膨胀     |
| 程序 / Harness    | 确定性校验、状态机、业务逻辑 | 可测试、强约束         | 维护成本           |
| 模型参数          | 隐式习惯、复杂感知与策略     | 泛化、推理时调用成本低 | 训练难、回归成本高 |

**按根因选择更新载体**。例如批准计划的 SLO `≤` 被错误渲染成 `<`，问题在渲染层，应修复 Renderer 并增加单测；流程指导问题则可考虑更新 Prompt 或 Skill。

同样表现为“任务失败”，实际可能需要完全不同的改动：

| 经证据定位的根因（教学案例）                               | 选择的更新载体                            | 怎样验证选择是否有效                                     |
| ---------------------------------------------------------- | ----------------------------------------- | -------------------------------------------------------- |
| 检索到的 API 旧版说明已失效，执行器本身正确                | 知识库：更新版本化事实与适用条件          | 同题检索到新版本，同时旧版问题仍能找到旧说明             |
| 操作流程未说明先查已有任务，造成可避免的重复提议           | Prompt/Skill：补流程与示例                | 新任务会先查询；真正禁止重复写入仍由幂等键等程序规则保证 |
| `retryable=false` 被控制循环忽略                           | Harness：修复重试状态机                   | 故障回放与临时恢复回归均符合契约                         |
| 输入链路与流程均正确，但多类未见任务仍稳定出现策略能力缺口 | 模型参数：在数据与评估准备好后考虑 SFT/RL | 用隔离留出集检验改善，并检查旧任务遗忘、成本和安全       |

表现相似不代表根因相同。应先排除过期资料、协议损坏和确定性实现错误，再决定是否训练；把重试状态机缺陷写进更多 Prompt，并不能保证执行器遵守不可重试标志。

## 8.3 轨迹转可验证的经验

[经验提取、候选验证与受控发布流程](/assets/notes/ai-agent/08-evolution.svg)

沿用 8.1 节的故障：三次调用都返回 `AUTH_DENIED, retryable=false`。先按调用 ID 确认三次独立调用，再把原始请求、结果、顺序和版本保存为轨迹；与另一任务中的同类故障归组后，检查控制代码，发现它只看重试次数而忽略 `retryable`。这样才从“重复失败”的现象走到可复核的原因。

可提取如下简洁经验，来源轨迹及验证版本另与该条目的 ID 关联保存：

```yaml
experience_id: auth-denied-no-retry
trigger: AUTH_DENIED
condition: retryable == false
action: 停止同参数重试，报告权限拒绝
reason: 权限拒绝不是临时网络错误
validation: 权限拒绝和临时故障回归测试
```

后续任务在读取工具错误时，可按错误码、可重试标志和操作类型检索这条经验，把适用条件、行动规则及来源一起放入上下文。模型据此解释为什么停止，或选择授权范围内的其他步骤；不应把规则泛化为“任何错误都不重试”。若错误属于允许重试的临时超时，应继续执行原有预算内恢复策略。

本例根因是 Harness 忽略标志，因此必须修复确定性控制代码；经验文档用于指导决策，不能代替这个修复。候选在新的权限拒绝任务和临时故障任务上回归后，才记录验证结果并进入正式经验版本。

经验文档推荐字段：触发条件、问题表现、根因、可执行对策、反例、不适用范围、参考轨迹、验证版本与日期。

## 8.4 Prompt 自动优化是什么

Prompt Optimization（提示优化）把提示或示范当作搜索对象，以任务评价选择候选。它需要目标、候选搜索和独立评价，不只是让模型把一句话改写得更流畅。

以重试规则为最小教学推演：

| 版本 | 提示内容                                       | 待检验问题                               |
| ---- | ---------------------------------------------- | ---------------------------------------- |
| P0   | 工具失败时可以重试。                           | 是否会对权限拒绝重复调用？               |
| P1   | 仅在错误允许重试时，按预定预算执行有限次重试。 | 是否既停止不可重试错误，又保留临时恢复？ |

1. 从归纳集的失败轨迹提出目标：减少不可重试错误的重复提议，保留临时故障恢复。
2. 生成 P1 等候选，记录文字、版本、来源和生成配置。
3. 在开发集运行 P0 与各候选，固定模型、工具、Harness、初态与预算。
4. 按预先定义的指标选择：例如先要求无越权、无超预算且临时恢复不退化，再比较不可重试重复调用数和任务结果；证据不足则不晋级。
5. 冻结选中提示及配置 Hash，不再根据本轮留出结果修改它。
6. 在独立留出任务与旧任务回归集验证，单列 UNKNOWN 和负迁移。
7. 保存版本、实际注入文本、评估记录和回退版本，进入后续候选门禁。

以上没有运行模型，不预设 P1 一定更好。如果比较 Prompt 的作用，各组必须共用同一份已核查的执行控制；不能把同时修复 Harness 的收益算作提示优化效果。

原书提及的方法可按搜索对象与反馈方式区分：

| 工具／方法                                      | 核心思路与来源                                                                                                                                                                         |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DSPy                                            | 把语言模型程序模块化，由优化器结合示例与指标搜索指令或示范；不是单一算法。见[官方优化器说明](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/learn/optimization/optimizers.md) |
| OPRO（Optimization by PROmpting，提示驱动优化） | 把已有候选及分数交给模型，提出新候选并迭代评价。见[原论文 v3](https://arxiv.org/abs/2309.03409v3)                                                                                      |
| GEPA（Genetic-Pareto，遗传与帕累托搜索）        | 从执行轨迹和文本反馈中反思修改提示，并保留在不同任务上互有优势的候选。见[原论文 v2](https://arxiv.org/html/2507.19457v2)                                                               |

更新 Skill 时，应先查找相近 Skill，尽量作最小修订；只有确属全新领域能力时才新增模块，避免大量相近 Skills 相互冲突。

## 8.5 “睡眠学习”与安全边界

后台整理任务可以周期性做经验合并、冲突检测、候选提案，但**不是允许在线运行的 Agent 自行修改生产规则**。

建议：线上采集只写候选区；候选通过来源验证、静态检查、回归评估、权限审核后才提升为正式版本。具有高风险的自动修改必须明确人工批准。记录“谁、何时、基于什么证据、修改了什么、如何回滚”。

## 8.6 最小实验

准备 30 条已解决、带结果和过程证据的轨迹，作为教学规模，不宣称这足以产生统计显著性。先按任务、失败模式和模板族去重并分组，再划分归纳集与留出集；同一原任务的改写或重复运行不得跨组泄漏。可预先约定约 20 条用于归纳、10 条用于留出，组大小不合适时调整数量并记录原因，优先保持隔离。

归纳集用于形成经验、筛选候选；留出集在候选冻结后评价，不能边看留出失败边继续调同一轮候选。若据此重新改动，原留出就成为开发材料，需要新的独立评测。已有旧任务回归集另行保留，不混充这 30 条的规模。

### 三组怎样公平对照

固定一个新的权限拒绝任务：获准发起的工具调用返回 `AUTH_DENIED, retryable=false`，要求 Agent 报告原因并停止同参数重试。三组拿到相同任务与首次工具反馈，只有经验输入不同：

| 组别 | 本题额外输入                                       | 应从输出检查什么                                       |
| ---- | -------------------------------------------------- | ------------------------------------------------------ |
| G0   | 无经验，只有公共基础 Prompt                        | 是否再次提议或实际调用同一工具，是否准确报告拒绝       |
| G1   | 从归纳集取一条类似失败轨迹，含三次调用及反馈       | 能否借单个案例避免重复；不能注入本题答案               |
| G2   | 从多条归纳集轨迹提炼的 `auth-denied-no-retry` 经验 | 能否把适用条件用于新的任务，同时不误阻止其他可重试错误 |

每次记录提议与实际调用的次数、错误码／`retryable`、最终决策、过程判定及证据 ID。若 Harness 已强制禁止重试，实际调用数可能相同，仍要分开检查模型的重复提议和执行器拦截，避免把控制代码的效果归于经验。再用允许重试的临时故障检查负迁移；三组成功率由实际记录得到，不在这里预填。

| 组别           | 后续任务能看到什么           | 要固定的条件                                             |
| -------------- | ---------------------------- | -------------------------------------------------------- |
| G0：无经验     | 公共基础 Prompt，不注入经验  | 与其他组使用相同任务初态、模型与工具版本、权限、执行预算 |
| G1：单轨迹     | 仅从归纳集检索单条相似轨迹   | 固定检索方法、最大注入长度，不取留出答案                 |
| G2：跨轨迹归纳 | 仅从归纳集形成并检索经验条目 | 使用相同注入预算上限，记录实际条目、长度与来源           |

这比较的是三种系统配置；不能仅凭差异把收益全部归因于“归纳质量”，还应检查检索命中、内容长度等因素。三组在每个任务与重复上分别复位；随机种子、解码规则、超时及重复次数预先记录。未知费用保持未知，不能记零。

### 成功、负迁移与停止条件

任务成功须同时满足预先冻结的业务结果验证和强制过程约束。例如创建任务需读回正确字段，并确认授权与幂等约束满足；模型自己说“完成”不算成功证据。无法取得实际结果时记 UNKNOWN，并按第 6 章报告覆盖率。

**负迁移**在此按配对任务定义：G0 原本 PASS，加入经验的 G1 或 G2 却变成 FAIL。记录是被不适用经验误导、规则冲突还是检索错误；不能把总成功率上升当作没有负迁移。UNKNOWN 单列，不归入这类已知退化；经验诱导的错误率也应与其他失败分开统计。

每条经验保存 `experience_id`、来源轨迹 ID 及 Hash、归纳器/Prompt 版本、适用条件、反例和验证记录；每次运行记录实际检索了哪些经验，而不只是“开启经验”这个开关。如下 JSON 是待填写的教学记录模板，`null` 表示尚未采集，不是零值或运行结果：

```json
{
  "task_id": "holdout-01",
  "group": "G2",
  "repeat": 1,
  "split_version": "split-v1",
  "config_hash": null,
  "initial_state_hash": null,
  "experience_ids": [],
  "source_trace_hashes": [],
  "result": "UNKNOWN",
  "process_verdict": "UNKNOWN",
  "evidence_ids": [],
  "tokens": null,
  "cost": null,
  "reason": "尚未运行"
}
```

候选晋级前应要求预定证据齐全、目标故障回放通过、强制安全规则零违规、旧任务与临时恢复路径没有已知退化；小样本没有发现退化仍不等于已证明安全。预先约定收益判据与可接受不确定性，达不到就保留候选，不反复试到偶然通过。出现证据污染、权限异常、预算或超时上限时停止并保存进度；发布后的监测阈值、外层批准与回退条件另行执行。

一种可预先冻结的教学门禁是：目标故障簇回放全部 PASS；固定旧任务和留出任务中不出现已知的 `G0=PASS → G2=FAIL`；计划单元与必需证据齐全，否则停止比较并列出 UNKNOWN。它只是本练习的保守候选筛选规则，不是统计显著性检验。单条相似轨迹组 G1 也独立按同一口径记录，不能只挑表现最好的组汇报。

本节给出实验协议和记录模板，没有运行三组 Agent，也没有新增成功率或显著性结论。

## 8.7 从候选补丁到受控发布的源码链

先解决一个基本判断：Agent 声称“任务已完成”，怎样验证？证据（Evidence）是独立工具或环境提供、可关联到该任务的观察；声明本身不构成证据。

| 独立证据                | 对“状态为 done”的判断 |
| ----------------------- | --------------------- |
| 可信结果明确为 `done`   | PASS                  |
| 可信结果明确为 `failed` | FAIL                  |
| 没有取得实际结果        | UNKNOWN               |
| 仅有模型自己声称完成    | UNKNOWN               |

**没有发现冲突，不等于存在足够证据证明成功。** 8.8 节再展开证据身份和字段比较；候选更新同样需要各项检查的实际结果。

候选从提交到发布依次经过以下阶段：

| 阶段             | 输入 → 输出                                                     | 负责组件                         |
| ---------------- | --------------------------------------------------------------- | -------------------------------- |
| 静态检查         | 候选源码 → 长度、编译、AST 预筛结果                             | `validate_candidate()`           |
| 隔离执行         | 静态通过的候选 → 容器执行结果                                   | `candidate_sandbox.py` 与 Docker |
| 行为回归         | 候选、故障轨迹与稳定源码 → 故障回放、临时恢复、旧任务兼容等检查 | 沙盒检查程序，结果汇入验证器     |
| 候选资格确认     | 变更及完整检查结果 → 候选 Hash、稳定 Hash、回滚版本与资格清单   | `release_manifest()`             |
| 外层批准         | 候选清单、证据及预定范围 → 批准或拒绝                           | 外层授权／发布流程               |
| 发布、监测与回滚 | 已批准产物 → 受控部署、监测与必要回退                           | 外部发布系统                     |

当前仓库 `chapter9/self-modifying-agent` 值得与 `trajectory-verifier` 配合读：前者生成和验证控制代码候选，后者检查轨迹中的声明、工具结果与证据是否一致。它们把“从失败学习”拆成可检查的程序步骤。

`evolution.validate_candidate()` 先限制源码长度、编译和 AST 预筛，再通过 `candidate_sandbox.py` 调用 Docker。AST denylist 只是快速过滤器，实际执行边界是容器及资源限制。容器不可用或返回格式不符时，检查保持失败，不自动降级成在主进程执行候选。

### 推荐三个反例

| 候选                       | 要验证什么                       | 应如何解释                           |
| -------------------------- | -------------------------------- | ------------------------------------ |
| 改善不可重试错误的重试策略 | 新失败减少，旧临时错误恢复不退化 | 新旧任务都通过才有资格进入后续门禁   |
| 只针对训练轨迹硬编码       | 留出集、边界集与旧任务回归       | 训练案例通过不构成泛化证据           |
| 尝试导入模块或写外部文件   | 静态预筛、执行沙盒和资源边界     | 被过滤或隔离，不把“能执行”当“可发布” |

`trajectory-verifier/consistency_checker.py` 是启发式检查器：在实际结果和声明结果均存在并进入比较时，能发现两者不同；缺少实际返回时并不等价于忠实报告，词面相似也不等于语义蕴含。它适合产生待复核信号，业务是否成功仍应查询环境真值。增加 LLM Judge 时，要做独立校准，不能因为裁判输出了分数就认为证据链已完整。

## 8.8 验证器的覆盖范围与证据来源

固定提交中的`consistency_checker.py`是英文/数字词项的启发式演示，**不是通用自然语言事实验证器**。审阅反例揭示三个不同缺口：

| 输入/机制                     | 原快照行为                                  | 正确解释与修订选择                                      |
| ----------------------------- | ------------------------------------------- | ------------------------------------------------------- |
| 空轨迹、纯中文无证据声明      | 无有效词项时可满分且无违规                  | 规则未发现问题不代表证据充分；无可评估输入应为UNKNOWN   |
| 未获证实的claim复述成最终结论 | claim grounding可为0而conclusion support为1 | 原实现把全部claim再加入结论证据；禁止以自身复述自我支持 |
| 有声明的工具结果但无实际返回  | 不进入结果对照，完整性维度可为1             | 区分尚未调用/待返回/日志缺失/合法null，不把缺证判忠实   |

本地 `structured_evidence_demo.py` 使用**结构化证据契约**核对 8.7 节的三态，不沿用词项重合打分。可信适配器在模型声明之外单独传入记录，再逐项检查：

| 字段                                  | 检查目的                                                             |
| ------------------------------------- | -------------------------------------------------------------------- |
| `source`                              | 限定工具／环境来源；可信性由适配器传入路径建立，不由模型自行填写获得 |
| `evidence_id` 与声明的 `evidence_ids` | 定位同一份独立观察，拒绝缺失或身份冲突                               |
| `call_id`、`key`                      | 确认证据属于声明所指调用和字段                                       |
| `step_id`                             | 证据必须先于声明；未来观察不能倒过来支持当时结论                     |
| `present`、`complete`                 | 区分字段不存在、尚未采集完成和合法空值                               |
| `value` 与 `expected`                 | 在身份、时序和完整性通过后比较实际值与目标值                         |

最终结论也要独立引用外部观察，不能用未经证明的声明支持自身。该示例不解析自然语言语义；中文、英文或混合语言在没有结构化证据时均为 UNKNOWN。报告可评估数量、覆盖率、UNKNOWN 数量和原因。

### 四种输入，怎样得到 PASS、FAIL 或 UNKNOWN

以下进一步展开结构化契约。表中 `obs-1` 须由适配器的独立可信记录提供，不能直接采信模型提交的同名对象。所有案例均为合成数据，声明统一为“调用 `call-1` 创建的任务已完成”：

```json
{
  "claim": {
    "step_id": 2,
    "call_id": "call-1",
    "key": "task.status",
    "expected": "done",
    "evidence_ids": ["obs-1"]
  },
  "adapter_record": {
    "evidence_id": "obs-1",
    "source": "tool",
    "call_id": "call-1",
    "step_id": 1,
    "key": "task.status",
    "value": "done",
    "present": true,
    "complete": true
  }
}
```

| 输入变化                                       | 本地契约判定 | 原因                                           |
| ---------------------------------------------- | ------------ | ---------------------------------------------- |
| 如上，可信适配器确认状态为 `done`              | PASS         | 身份、时间、字段与期望一致；仅证明这项字段声明 |
| 同一可信记录中 `value` 为 `failed`             | FAIL         | 证据明确支持相反的已知值                       |
| 没有实际返回，可信记录中找不到 `obs-1`         | UNKNOWN      | 缺证据，不能推断成功，也不能据此断言业务失败   |
| 只有模型说“已经完成”，或自行填写 `source=tool` | UNKNOWN      | 没有独立来源；自我声明不能建立信任             |

四项中可判定两项，覆盖率 `2/4`，UNKNOWN 为 2；这只是契约覆盖示例，不是业务成功率。合法 `null` 由 `present=true, value=null` 表达，可与期望空值比较；缺字段、未采集完成、调用 ID 不匹配或未来才出现的证据保持 UNKNOWN。若多份可信证据互相冲突，本教学实现保守返回 UNKNOWN，交由业务规则解决版本或时序歧义，不任意选有利的一条。

**原快照与本地建议的输出不同**：上游 `consistency_checker.py` 实际返回多个分数和违规项，并没有这里的三态业务接口。存在实际与声明结果时，它可通过直接比较发现不同；实际返回为 `None` 时则跳过该对照。把“没有被规则发现冲突”直接转换成 PASS，会误把缺证据当成通过。词项匹配也不能证明“已完成”在业务语义上成立。

本地 `examples/ai-agent/ch6-8-review/structured_evidence_demo.py` 与上游检查器独立，测试程序单独提供合成可信记录。测试覆盖空输入、无证据的不同语言声明、状态／数值冲突、合法 null、错误调用 ID、未来证据及自我循环；它比对结构化事实，不查询业务数据库或建立真实身份认证。

上游行为可对照固定的 [consistency_checker.py](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter9/trajectory-verifier/consistency_checker.py)；本地示例的运行方式与第 7.9 节共用同一测试目录。

在本项目根目录运行以下命令，观察四个结果依次为 `PASS、FAIL、UNKNOWN、UNKNOWN`，并由测试检查缺失、冲突、身份和时序：

```bash
python examples/ai-agent/ch6-8-review/structured_evidence_demo.py
python -m unittest discover -s examples/ai-agent/ch6-8-review -p "test_*.py" -v
```

## 本章要点 {#检查理解}

1. 轨迹存储只是起点，经验需要提取、验证并作用于后续任务，才能形成改进闭环。
2. 确定性规则和实现缺陷适合用代码及测试修复；可语言化操作流程可更新 Skill。
3. 独立 Eval 检查泛化与回归，回滚机制在新版本退化时恢复稳定状态。
4. 缺少来源或验证的经验保留在候选区，取得证据并通过审核后再发布。

下一章把这种观察、行动与独立反馈的要求放进实时环境：用户插话、界面变化和物理运动都要求及时更新状态，再决定下一步。
