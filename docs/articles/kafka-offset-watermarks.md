# 第 11 章：消费位点、提交与连续完成水位

> 版本基线：Kafka Broker 3.9、Java Client 3.9 与 librdkafka v2.8.0。
>
> 学习目标：区分已拉取、已交给应用、业务已完成、本地已保存和 Broker 已提交的位置，正确解释提交值中的“下一位置”。

## 1. 按 Topic-Partition 分别管理进度 {#_1-位点不是全组一个数字}

每个 Topic-Partition 都有自己的位置。客户端可能已预先拉取一批记录到本地，应用却只处理了其中一部分，外部数据库完成的部分还可能更少。因此，网络读取进度、应用读取进度和业务完成进度不能混用。

提交给组的恢复位点通常采用下一读取位置口径。例如已安全完成 Offset 100，希望恢复时从 101 继续，则提交 101，而不是 100。若直接调用接受消息对象的提交 API，要先确认它是否已经内部加一，不能再人为加一次。

| 进度                                    | 谁推进它                                  | 读数表示什么                                                                                                                                        |
| --------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fetch Position（拉取位置）              | 客户端内部拉取流程                        | 后续 Fetch 请求从哪里读。预取或缓存的记录可能尚未交给应用                                                                                           |
| Consumer Position（客户端消费位置）     | Java 客户端随 `poll()` 交付及扫描日志推进 | `position(tp)` 表示下一读取位置，可以越过不可见记录。librdkafka 2.8.0 的 `rd_kafka_position()` 查询最近交付的消息 Offset 加一，不能拿来查询预取进度 |
| Processing Frontier（业务连续完成前沿） | 应用根据 Worker 结果推进                  | 当前可安全提交的下一位置                                                                                                                            |
| Offset Store（本地位点存储）            | librdkafka 自动存储或应用显式写入         | 待提交位置。进程退出可能丢失                                                                                                                        |
| Committed Offset（已提交位点）          | 组协调器处理提交请求                      | 该组该分区的恢复位置。应用收到成功结果后才确认此次提交已生效                                                                                        |

## 2. 并行消费需要连续完成前沿

[![异步消费：只提交连续完成的下一位置](/assets/notes/kafka/kf-frontier.png)](/assets/notes/kafka/kf-frontier.png)

假设 100、101、102 都存在，100 和 102 完成，101 仍在执行。安全提交值只能推进到 101。提交 103 会让崩溃恢复跳过尚未完成的 101。等 101 也完成，再推进到 103。

实现时通常维护分区内交给业务的记录顺序、完成标记和最前方未完成记录。不要死等每一个数学整数 Offset：compact、事务控制记录或可见性过滤可能造成应用记录的空洞，应按实际交付的记录序列及客户端位置语义推进。

教学推演使用订单 Topic `review-orders` 的 P0。假设这批交付的三条记录从 100 开始，期间没有别的记录进入处理队列：

| 时刻 | 已完成        | 未完成        | 安全提交位置 |
| ---- | ------------- | ------------- | ------------ |
| T0   | 无            | 100、101、102 | 100          |
| T1   | 100           | 101、102      | 101          |
| T2   | 100、102      | 101           | 101          |
| T3   | 100、101、102 | 无            | 103          |

每个 Topic-Partition 的日志独立编号。不同分区的 Offset 没有共同的顺序，必须分别推进。以下伪代码由 Poll 线程运行，队列按交付顺序维护。初始状态等待首次交付，提交映射只包含已计算出安全位置的分区。

```text
poll 返回一批记录:
    按分区将整批追加到对应队列，每项标为未完成
    登记完成后再向 Worker 派发

收到 Worker 成功结果(partition, ownership, offset):
    如果 ownership 不是该分区的当前所有权标记，忽略结果
    标记对应项为完成
    while 队首存在且已完成:
        last = 移除队首
        safe = last.offset + 1

计算分区的安全位置:
    如果队列非空，返回队首 offset
    否则返回 safe（若已初始化）

提交:
    只提交仍持有的分区已计算出的安全位置
```

例如实际交付 100、104，100 完成而 104 未完成时，队首 104 可以作为恢复位置。客户端按当前读取和隔离条件已跨过中间空洞。队列排空后使用最后移除的记录加一，即使这个位置没有可见记录，客户端也能向后读取。算法假设同一次所有权内按分区顺序交付，应用主动 Seek 后需清理并重建进度，不能沿用旧任务表。失败项继续阻挡前沿。待完成和已完成但仍被挡住的项共享容量上限，达到上限就暂停取数并继续 poll。撤销时停止派发，在仍持有分区的条件下提交已知前沿，失去所有权后隔离迟到结果并允许新实例重放。Kafka 不会替应用记录 Worker 的完成状态。

## 3. Auto Store 保存本地位置，Auto Commit 提交恢复位置 {#_3-auto-store-与-auto-commit-不是一回事}

librdkafka 的本地 Offset Store 记录下一次可提交的位置；Commit 才把恢复位置提交到 Broker。`enable.auto.offset.store` 与 `enable.auto.commit` 是两个开关。

对于耗时较长或异步执行的处理，若记录一交付给应用就自动 Store，后台 Commit 就可能早于实际业务完成。可以关闭 Auto Store，在完成前沿推进后保存安全位置，再由后台提交；也可以关闭自动提交，由应用明确提交各分区的安全位点。两种做法都需要检查错误，不能只关闭一个开关就认为已经可靠。

| 操作                     | Java 3.9                                                                                                                      | librdkafka 2.8.0                                                                                                       |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 按分区显式提交           | `commitSync(map)` 等待结果，`commitAsync(map, callback)` 异步报告结果。Map 的值为 `OffsetAndMetadata`，其中 Offset 传下一位置 | `rd_kafka_commit(rk, offsets, async)` 的列表也直接填下一位置。异步调用返回成功只表示请求已排队，提交结果另行检查       |
| 用客户端已记录的位置提交 | 无 Map 的 `commitSync()` / `commitAsync()` 使用消费位置，可能超过 Worker 完成前沿                                             | `rd_kafka_commit(rk, NULL, async)` 使用当前分配的本地存储位置                                                          |
| 只更新本地待提交位置     | 异步业务前沿由应用持有                                                                                                        | 关闭 `enable.auto.offset.store` 后，`rd_kafka_offsets_store()` 原样保存列表中填写的位置，检查逐分区结果                |
| 直接传消息对象           | 应用构造分区提交 Map                                                                                                          | `rd_kafka_commit_message()` 提交消息 Offset 加一，`rd_kafka_offset_store_message()` 存消息 Offset 加一。传原始消息即可 |

消息对象接口只有在该消息及其之前交付的同分区任务均已完成时，才适合用来推进安全位置。自动提交关闭后，显式提交仍可使用。

## 4. 无有效起点或位置越界时的重置规则 {#_4-earliest-与-latest-什么时候生效}

`auto.offset.reset` 一般处理没有有效初始提交位置或请求位置越界的情况，不是每次启动都覆盖已有有效位点。`earliest` 指向当前保留范围的早端，不承诺从 Topic 创建时的第一条历史开始；`latest` 从当时末端继续，不会自动补回已过期数据。

值名也依客户端：Java 的异常路线用 `none`，本册固定的 librdkafka 使用 `error` 等受支持值，不能直接互抄。显式 seek 则是另一种位置控制，仍必须考虑保留范围和待处理任务。

| 起点条件                                   | 客户端如何处理                                                                                              |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| 存在有效提交位点，且应用未显式 Seek        | 从该位置读，忽略重置策略                                                                                    |
| 没有提交位点，或请求位置已超出有效范围     | `earliest` 从当前日志起点读，`latest` 从重置时末端读。Java `none` 抛异常，librdkafka `error` 向应用报告错误 |
| 位置在范围内，但该 Offset 没有应用可见记录 | 继续向后寻找可见记录。日志压缩可能移除旧记录，事务控制记录不会交给应用，`read_committed` 还会过滤已中止事务 |

## 5. 提交失败与重放窗口

业务完成后提交失败，恢复时可能重放已经完成的业务，因此需要幂等。提交成功后才处理业务，崩溃则可能永久跳过未完成工作。同步提交只是等待提交结果，不会把外部业务和位点自动放进同一个事务。

异步提交还要考虑旧结果回调延迟到达，以及失败重试与新位点交错的情况。比起设计复杂逻辑来重试每次历史提交，更安全的起点是明确维护当前安全前沿和分区所有权，再按客户端契约制定单调推进与恢复策略。

以下用 P0 的 100 和 101 表示故障前后的恢复位置，假设记录仍在有效范围内。

| 故障点                          | Broker 的恢复位置                                              | 恢复效果和应用责任                                                                                  |
| ------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 100 已写库，提交 101 被明确拒绝 | 仍为 100                                                       | 重放可能重复写库，用订单事件 ID 去重，并在仍有权时决定是否再提交                                    |
| 101 已提交，100 尚未执行业务    | 101                                                            | 重启跳过 100，业务漏处理。应先完成业务再推进前沿                                                    |
| 100 写库后进程在提交前崩溃      | 100                                                            | 100 重放。若崩溃时提交已发出但未收到响应，Broker 可能仍为 100，也可能已经是 101，以实际恢复位置为准 |
| 异步回调延迟，应用误重试历史值  | 可能已为更新的 102，随后被错误的旧提交回退到 101               | 多重放一条。重试取当前安全前沿，丢弃失效所有权的重试                                                |
| 旧实例失去分区后尝试提交        | 旧组世代或成员身份的提交可能被拒绝，恢复以协调器保存的位置为准 | 新成员可能重放。旧实例应停止提交该分区，外部请求仍须去重或隔离                                      |
| 重启时 101 是有效提交位置       | 101                                                            | 从 101 继续，跳过已完成的 100。若 101 已过期，按重置策略处理                                        |

Java 3.9 同一 Consumer 的异步提交发送顺序和回调调用顺序与 API 调用顺序一致，随后调用同步提交可等待先前异步提交完成。风险来自应用把结果转交给并发执行器、延迟重试旧值，或跨所有权把旧回调当成当前进度。同步提交的成功只确认 Kafka 位点，外部数据库事务仍单独完成。

### 实践：让 102 先于 101 完成

以下为 Java 3.9 Classic 实验伪代码。用独立空 Topic 建一个分区，用生产者写入 103 条普通记录并确认最后三条的实际 Offset 为 100、101、102。每次实验使用新的组，关闭自动提交。手动分配该分区，初始化阶段显式提交 100 作为实验恢复点，再 Seek 到 100。正常重启阶段只分配分区，从组位点恢复。

单 Broker 环境仍需满足[内部位点 Topic 的创建条件](/articles/kafka-log-model.html)，即使消费者使用手动分配。

1. 反复 Poll，按交付顺序登记 100、101、102，登记齐后再派发。一次 Poll 可能只返回其中一部分。Worker A 顺序处理 100、102。Worker B 处理 101，先在闩锁上等待，直到 Poll 线程记录 T2 检查结果。
2. 让 100 完成后显式同步提交 101。等 102 完成，检查前沿和已提交位置都为 101，再释放 101 的闩锁。三个任务都完成后，前沿应为 103。
3. 第一轮在提交 103 之前强制退出，重启预期重放 101 和 102。第二轮使用新组重复步骤，等待同步提交 103 成功后退出。重启时读取 `position(tp)`，预期是 103，原三条记录均不再交付。
