# 第6章 Agent 的评估与可观测性

## 6.1 评估的目标

Agent 评估通过可复现任务和独立证据，判断**模型、提示词、工具或架构变更对产品的影响**。一个完整的评估流程包含四个彼此相连的要素：

1. 可复现的环境：工具、数据、权限和初始状态可控。
2. 代表性任务：真实需求、边缘情况、失败场景、防止评估数据污染。
3. 独立验证器：优先从环境真值判断成功，无法形式化时再用 Rubric/LLM Judge。
4. 反馈闭环：轨迹诊断 → 提出改进 → 受控实验 → 回归发布。

对比实验要控制变量；消融实验固定其余条件，仅关闭某一组件，以衡量它的贡献。

### 从创建任务开始

用户要求“创建标题为周报、负责人为 `u7` 的任务”。评估先保存这个目标，再在隔离的测试环境执行 Agent，最后由独立验证器按新任务 ID 读回状态。第 6.7 节用同一份教学 Trace 展示完整记录：模型生成的参数却是 `owner=u8`，创建接口返回 HTTP 200 和 `task_id=42`，数据库读回也确认为 `u8`。

这份记录把两个问题分开：请求是否执行，以及用户要求是否实现。读回结果证实“创建了任务”，同时证实“负责人错误”。据此才能进一步定位模型决策、参数映射或工具执行中的故障。

## 6.2 评估分为结果、过程、效率、安全四层

| 层级        | 指标示例                                   | 主要回答               |
| ----------- | ------------------------------------------ | ---------------------- |
| 结果正确性  | 任务成功率、真实环境状态、一致性           | 事情最终做成了吗？     |
| 过程正确性  | 工具调用正确率、步骤合法率、路径冗余       | 是否按允许的方式完成？ |
| 效率与成本  | 总 Token、LLM 延迟、工具调用费、端到端耗时 | 代价是否合理？         |
| 安全/稳定性 | 越权率、注入成功率、回归率、重试可靠性     | 会不会伤害系统或退化？ |

“API 请求成功率”不等于“Agent 任务完成率”；即使 Agent 的全部调用都返回 200 OK，也可能没有完成业务目标。

### 用同一条 Trace 判断四个层次

下面继续使用第 6.7 节的 `t1`，所有数据均为教学假设：

| 检查层次 | 沿证据怎么判断                                            | 本例结论                                                                                                            |
| -------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 结果     | 将用户目标 `owner=u7` 与 `e-read` 的 `owner=u8` 比较      | FAIL；HTTP 200 不能改变业务判定                                                                                     |
| 过程     | 核对模型决策 `s-model`、创建输入 `e-create` 与工具 Schema | `u8` 即使符合字段类型，也不符合本次用户要求；错误在创建前已出现。具体由模型还是参数映射造成，仍需对照二者的输入输出 |
| 效率     | 汇总模型、创建和读回的次数、耗时与用量                    | 当前表只显示一次创建和一次读回，没有 Token 与耗时数据；不能给出成本或速度优劣结论                                   |
| 安全     | 对照身份、授权范围与写操作审计                            | 若另有可信策略证据证明只准分配给 `u7`，还应判授权违规；只有负责人不符的记录，尚不足以认定越权                       |

状态读回是必要的验证开销，不宜直接算作冗余调用。结果失败也不意味着其他维度自动都是失败；每个维度都要列出自己的证据与未知项。

## 6.3 Pass@k、Pass^k、Best@k

对固定的一道任务，假设单次成功的概率为 `p`，每次尝试**独立同分布**（简化假设）：

- `Pass@1 = p`：单次成功率。
- `Pass@k = 1-(1-p)^k`：k 次尝试中至少一次成功的概率；体现通过多次尝试能否找到解。
- `Pass^k = p^k`：k 次尝试都成功的概率；体现连续稳定性。
- `Best@k`：必须说明是用真值做oracle最优选择，还是由实际selector挑一个；后者的选择错误与费用要计入系统结果。

例：`p=0.6, k=5`：`Pass@5 ≈ 98.976%`，`Pass^5 = 7.776%`。

**注意**：现实执行之间可能因相同样本、共享环境、随机种子和工具状态而相关，上述公式不是无需前提的通式。正式报告应说明抽样方法、k、独立性假设及重复次数；某些 Benchmark 的 `pass@k` 是特殊的有限样本无偏估计，不可随意混用。

### 从两次尝试看概率怎样变化

仍取 `p=0.6`。一次失败的概率是 `0.4`；在独立同分布假设下，两次都失败的概率为 `0.4 × 0.4 = 0.16`，因此两次至少成功一次为 `1 - 0.16 = 0.84`。两次都成功则为 `0.6 × 0.6 = 0.36`。尝试次数增加，会让“至少找到一次解”更容易，让“每次都成功”更难。

| 使用场景                                 | 较相关的量 | 还需要什么条件                               |
| ---------------------------------------- | ---------- | -------------------------------------------- |
| 离线生成多个代码候选，再用测试寻找可用解 | Pass@k     | 测试与选择机制可靠，且把多次生成成本计入预算 |
| 同一种任务在重复执行中保持可靠           | Pass^k     | 每次初态与抽样规则明确，相关性得到处理       |

代码候选可以在沙盒中试错；真实转账、发消息等有副作用的任务不能直接在生产环境重放 k 次。Pass@k 也不保证实际选择器一定挑到那次成功结果。

### 先逐题计算，再按声明权重汇总

不同任务有不同`p_i`。在每题内部重复独立的前提下，等权宏平均为：

```text
macro Pass@k = mean_i[1 - (1-p_i)^k]
macro Pass^k = mean_i[p_i^k]
```

两题的成功概率分别为1和0，平均单次成功率为0.5，但按题平均的Pass@5与Pass^5都为0.5。把平均概率0.5直接代入非线性公式，却会得到96.875%和3.125%，不代表该数据集。抽样权重不等时改用预先声明的权重。

HumanEval式有限样本估计：每题采样`n≥k`次，其中`c`次成功，`pass@k_hat = 1 - C(n-c,k)/C(n,k)`；`n-c<k`时取1，再跨题汇总。这依赖相应采样设置；有状态Agent仍需每次环境复位并检查相关性。依据：[HumanEval论文§2.1与附录A](https://arxiv.org/html/2107.03374v2)。

### 有限样本估计的手算

假设一道 HumanEval 题生成了 `n=5` 个候选，其中 `c=2` 个通过测试，想估计 `k=2` 的表现。从这五个已采样候选中等可能选两个，共有 `C(5,2)=10` 种组合；三个失败候选组成的全失败对有 `C(3,2)=3` 种。因此估计值为 `1 - 3/10 = 0.7`。

这里“不放回选两个”解释的是估计器如何利用已有候选池，并不是要求模型生成时不放回采样。若把样本比例 `2/5` 直接当真实概率代入概率式，会得到 `1-(1-0.4)^2=0.64`；它是另一种代入估计，不能替换 HumanEval 的有限样本估计器。上述 0.7 只属于这一题；数据集结果仍需先逐题计算，再按前述权重汇总。

## 6.4 评估数据集和验证器

- **任务代表性**：覆盖常见、边界、长链、失败恢复、注入攻击。
- **初始环境一致**：每条测试用例执行前能复位数据库/沙盒/网页状态。
- **防污染**：Eval 用例与训练样本隔离，动态参数避免硬编码答案。
- **环境真值优先**：创建任务后读数据库、测订单后查真实订单，而不是让模型口头自评。
- **LLM-as-a-Judge**：给出 Rubric、参考答案或证据、评分等级，进行人工校准；尽量不让同一个模型既当唯一选手又当唯一裁判。

## 6.5 统计显著性与置信区间

成功率 `p̂ = successes/n`，独立伯努利近似下 `SE ≈ sqrt(p̂(1-p̂)/n)`。若 `n=100, p̂=0.7`，`SE ≈ 4.58%`，粗略 95% 区间可估计为 `70% ± 9.2 个百分点`。

这里每次试验的结果只有成功或失败。标准误（SE）估计的是：按相同抽样规则反复收集大小为 `n` 的样本时，**样本成功率**会有多大波动，而不是某一次执行的成败。在正态近似成立时，标准正态分布约 95% 的概率落在均值两侧 `1.96` 个标准差内，所以区间半宽取约 `1.96 × SE`，粗略写作两倍 SE。

95% 置信区间描述的是构造区间的方法：若反复抽样并用同一方法计算区间，长期约 95% 的区间会覆盖真实成功率。它不表示这次得到的固定区间有 95% 的概率包含某个固定参数，也不保证下一次任务有 95% 的成功概率。比例区间及近似条件见 [NIST §7.2.4.1](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)，覆盖率含义见 [NIST §1.3.5.2](https://www.itl.nist.gov/div898/handbook/eda/section3/eda352.htm)。

**注意**：这只是便于解释的正态近似；样本量小、成功率接近 0/1 时可使用 Wilson 区间或二项精确方法。对**相同任务**比较 A/B 两个模型，建议配对统计（例如 McNemar 检验或配对 Bootstrap），而不是把两批结果当独立样本。

下面是假设的教学数据，并非实测：A、B 对每题分别从相同初始状态运行一次，每次只记录一个二元结果。

| 任务 | A    | B    |
| ---- | ---- | ---- |
| T1   | 成功 | 成功 |
| T2   | 成功 | 成功 |
| T3   | 成功 | 失败 |
| T4   | 失败 | 成功 |
| T5   | 失败 | 成功 |
| T6   | 失败 | 失败 |

配对汇总得到：双方成功 2 题、仅 A 成功 1 题、仅 B 成功 2 题、双方失败 1 题。A 的成功率为 `3/6`，B 为 `4/6`，相差约 16.7 个百分点；这个差值只是点估计。McNemar 检验关注两类**不一致配对**，这里是 1 与 2，判断两种变化方向是否有系统性差异。只看总成功率会丢掉哪些题从成功变失败、哪些题从失败变成功的信息，无法据此完成配对检验。检验输入与定义见 [statsmodels 0.14.4 的 McNemar 文档](https://www.statsmodels.org/v0.14.4/generated/statsmodels.stats.contingency_tables.mcnemar.html)。这里不计算 p 值，也不据这六题断言模型改进成立。

另一个随机来源是同一任务重复运行时的生成随机性。应分别说明“任务样本抽样误差”和“重复执行随机波动”，不能用一个误差条笼统表示。

上例的配对单位是任务，每题每个模型只有一次结果。若每题重复多次，应另行声明统计单位及同题重复之间的相关性处理；例如以任务为单位做配对 Bootstrap 时，每次重抽一个任务，要同时保留该题 A/B 的全部重复记录，不能把这些记录当作互不相关的新任务。

## 6.6 LLM 性能指标与 Agent 端到端指标

| 指标             | 定义                                                    | 注意                                               |
| ---------------- | ------------------------------------------------------- | -------------------------------------------------- |
| TTFT             | Time to First Token，首 Token 延迟                      | 通常只用于流式输出，包含不同服务侧与客户端延迟口径 |
| TPOT             | Time Per Output Token，输出 Token 平均间隔/耗时相关指标 | 不等于所有系统的 ITL 指标定义；要核对具体采集口径  |
| ITL              | Inter-Token Latency，Token 间延迟                       | 可以看每相邻 Token 间分布，需注明是否包含首 Token  |
| E2E latency      | 从请求到最后结果的总延迟                                | Agent 端到端还包含检索、工具、重试及队列           |
| RPS              | Request Throughput，每秒成功/完成请求等定义             | 必须说明是发起速率还是完成速率                     |
| Token throughput | 每秒输入/输出/总 Token                                  | 需声明哪种吞吐，避免混用                           |

Agent 任务的完整时间可以粗分：模型推理、工具执行、网络、排队、框架处理。优化模型 TTFT 不一定改善最终 Agent 任务成功率或总耗时。

### 一次请求的合成时间线

以下时间戳是合成教学数据，假设客户端能逐个观察输出 Token，并将最后一个 Token 到达视为本次请求结束：

```text
请求发出       Token 1       Token 2       Token 3       Token 4 / 结束
0 ms           400 ms        460 ms        550 ms        700 ms
               └── 60 ms ──┘└── 90 ms ──┘└── 150 ms ─┘
```

- TTFT：`400 - 0 = 400 ms`。
- 相邻 Token 的 ITL：`60、90、150 ms`，不是把首 Token 等待也算成一个相邻间隔。
- 本例选择的 TPOT：`(700 - 400) / (4 - 1) = 100 ms/Token`，即首 Token 之后三个间隔的均值；只有一个输出 Token 时这个口径未定义。
- 本例模型请求 E2E：`700 - 0 = 700 ms`。若还要等结束事件或后处理，应另行记录真正完成时间。

这只是明确的一种 TPOT 计算约定。使用压测工具时，应核对其是否扣除 TTFT、采用什么分母，以及记录的是 Token 还是包含多个 Token 的网络块；不能把块间隔直接当 Token 间隔。

若完整 Agent 串行经历检索 `0.2 s`、第一次模型请求 `0.7 s`、工具调用 `1.1 s`、第二次模型请求 `0.5 s`、框架处理 `0.1 s`，任务总耗时为 `2.6 s`。其中 `0.7 s` 只是一个模型请求。存在并行时要按实际时间线的关键路径计算，不能把有重叠的 Span 耗时直接相加。

### 性能压测示例

比较两个推理 Endpoint 时，要冻结模型/Tokenizer、Dataset/采样、并发、输出约束、预热、重复次数和 SLO 统计口径；否则看到的速度差异可能来自测试工作负载变化，而非部署优化。

对于 SLO 边界测试，故意探索到失败点是正常的；不能按 Grid 的“所有点都 PASS”规则判断边界搜索是否完成。要独立报告：执行状态、搜索结果、证据是否完整、已验证通过/失败两侧。

## 6.7 可观测性：Trace—Span—Evidence

一次任务对应 Trace，即把相关操作关联起来的执行记录；模型调用、工具、检索和数据库操作各自形成 Span，即具有起止时间的工作单元。同一 Trace 内的 Span 共享 `trace_id`，各有不同的 `span_id`；子 Span 记录父 Span 的 ID，表示它由哪个操作发起。根 Span 没有父 Span，其下可以嵌套调用，也可以有并列的子操作。这样既能看操作耗时，也能沿调用关系定位问题。

跨服务调用时，调用方需要把追踪上下文注入请求，接收方提取上下文后再创建关联的子 Span；否则不同服务的记录可能无法连成同一次任务。机制见 [OpenTelemetry Trace 概念](https://opentelemetry.io/docs/concepts/signals/traces/)与[上下文传播](https://opentelemetry.io/docs/concepts/context-propagation/)（概念文档，不限定具体 SDK 版本）。

每个 Span 建议包含：`trace_id/span_id`、父 Span ID、时间、工具/模型版本、输入规模、输出规模、错误、重试、成本、证据引用。注意对 Prompt 和外部结果脱敏。

沿用“创建任务后读回验证”的场景，下面是假设的教学记录，并非运行证据。为便于阅读，ID 使用简写；证据引用字段是应用自己的约定，不是 OpenTelemetry 强制字段。

| 操作                     | trace_id | span_id | 父 span_id | 输入、输出与证据引用                                                                    |
| ------------------------ | -------- | ------- | ---------- | --------------------------------------------------------------------------------------- |
| 根操作：完成创建任务请求 | t1       | s1      | 无         | 目标：创建标题为“周报”、负责人为 `u7` 的任务                                            |
| 模型决策：生成调用参数   | t1       | s-model | s1         | 将目标转换为创建参数，但输出了 `owner=u8`；供排查参数生成与映射边界                     |
| 工具调用：创建任务       | t1       | s2      | s1         | 输入为 `title=周报, owner=u8`；返回 HTTP 200、`task_id=42`；保存请求与响应为 `e-create` |
| 独立状态读回             | t1       | s3      | s1         | 按 `task_id=42` 查数据库；返回 `title=周报, owner=u8`；保存为 `e-read`                  |

表中按执行先后阅读：根操作先生成调用参数，再发起创建调用，获得 ID 后发起状态读回，因此 `s-model`、`s2` 与 `s3` 是同一根操作下顺序执行的三个子 Span。Eval 比较根操作的目标与 `e-read`：虽然请求成功且任务存在，负责人却不符，应判业务任务失败。再沿 Trace 查 `s2` 的 `e-create`，可以发现创建输入已经是 `u8`，从而把下一步排查收敛到调用前的参数生成或映射，而非仅凭 HTTP 200 判成功。

Trace 负责“发生了什么”，Eval 负责“是否达到目标”，二者联动才能构成改进循环。

## 6.8 从评估到决策

```text
线上观察异常
→ 按任务标签分组定位失败
→ 提出单因素改进假设
→ 同样的评估集、配对实验、重复运行
→ 质量/延迟/成本/安全综合决策
→ 小范围发布并监控
→ 回归集沉淀新的失败案例
```

评估报告应说明**测试条件、相对收益、不确定性和新增风险**，为版本选择提供依据。

## 6.9 检索指标的主定义与源码口径

当前仓库的评估源码位于 `chapter7`。`user-memory-system-evaluation/experiment.py` 的 `retrieval_metrics()` 固定看前5个块，并分别返回单查询Hit@5、Recall@5和RR@5；第三个返回值不是跨查询MRR。这段代码能把容易混用的指标拆开。

源码节选（上下文依赖见原文件）：[chapter7/user-memory-system-evaluation/experiment.py](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter7/user-memory-system-evaluation/experiment.py#L824-L833)。

```python
def retrieval_metrics(retrieved: Sequence[Chunk], relevant_ids: Sequence[str]) -> Tuple[float, float, float]:
    relevant = set(relevant_ids)
    ids = [chunk.chunk_id for chunk in retrieved[:5]]
    hits = [idx for idx, chunk_id in enumerate(ids, 1) if chunk_id in relevant]
    return (
        1.0 if hits else 0.0,
        len(set(ids) & relevant) / len(relevant) if relevant else 0.0,
        1.0 / min(hits) if hits else 0.0,
    )

```

先固定查询集合、相关标注、候选去重和截断k。下面是唯一主定义，其他章节只保留场景例子：

| 指标             | 单查询q的计算                                              | 聚合层级                               |
| ---------------- | ---------------------------------------------------------- | -------------------------------------- |
| 首次相关排名 r_q | 前k个结果中第一条相关结果的1起始位置                       | 未命中时不伪造排名                     |
| Hit@k(q)         | 至少命中一个相关ID取1，否则0                               | 可按查询平均成命中率                   |
| Recall@k(q)      | `cardinality(topk ∩ relevant_q) / cardinality(relevant_q)` | 分母是该查询全部相关文档数；先逐题算   |
| RR@k(q)          | 若`r_q≤k`，取`1/r_q`；未命中取0                            | 一条查询的标量                         |
| MRR@k            | 查询集合上RR@k的平均                                       | 需同时报告有效查询数、排除/UNKNOWN策略 |

空相关集合的查询应按任务单列，不能无条件算成功或漏召回。本地修订示例将其标为UNKNOWN并从MRR分母排除，同时报告覆盖率；这只是明确的约定，不是所有基准的统一规则。[TorchMetrics官方文档](https://lightning.ai/docs/torchmetrics/stable/retrieval/mrr.html)也将query分组、聚合与空标注策略分开。

例如相关集合为 `{A, B}`，返回 `[X, A, Y]`：Hit@5 为 1，Recall@5 为 1/2，RR@5 为 1/2；如果前5名重复出现 A，召回不应因重复而增加。空相关标注在该实现中 Recall 取 0，这是一种实现约定；真实报告中应单列“无答案”任务，避免与漏召回混为一组。

**Hit 与 Recall 的区别**：包含证据的查询比例属于 query-level Hit/Success 指标；集合 Recall 的分母是该查询的全部相关文档数。只有每题恰好一个相关文档等特定设置下，两者才可能数值相同。

## 6.10 完整性、覆盖与UNKNOWN

记录单元以`task × variant × repeat`标识；A/B对每个任务与重复分别从同一初始状态启动。先逐查询计算，再按任务/变体汇总。缺运行、证据缺失、未计价用量不是0；它们应分别计数并限定哪些结论可判定。可报告已有组件指标，但不能把不完整campaign写成完整的质量/成本优劣比较。

### 12 个预期运行单元，为什么会有三个分母

设任务为 T1、T2，变体为 A、B，每个组合重复三次，共预期 `2 × 2 × 3 = 12` 个运行单元。每个 `(task, repeat)` 构成一对，A、B 分别从相同初态运行。下面是合成教学数据，PASS/FAIL 均指已有可信证据的结果判断：

| 任务与重复 | A               | B                             |
| ---------- | --------------- | ----------------------------- |
| T1，1      | PASS            | PASS                          |
| T1，2      | FAIL            | UNKNOWN：已运行，读回证据缺失 |
| T1，3      | PASS            | PASS                          |
| T2，1      | PASS            | FAIL                          |
| T2，2      | FAIL            | PASS                          |
| T2，3      | MISSING：未运行 | MISSING：未运行               |

运行状态和结果判断应分开保存：MISSING 表示未执行；UNKNOWN 表示目前不能判定结果。在面向全部计划单元的结果汇总里，两个未运行单元也没有已知结果，因此总共有三个结果未知单元，但仍要分别列出缺运行 2 个、已运行缺证据 1 个。

| 报告项                   | 计算             | 分母含义                 |
| ------------------------ | ---------------- | ------------------------ |
| 运行覆盖率               | `10/12 ≈ 83.33%` | 全部计划运行单元         |
| 有效结果证据覆盖率       | `9/12 = 75%`     | 全部计划运行单元         |
| 已运行单元内的证据覆盖率 | `9/10 = 90%`     | 实际执行单元，需带限定语 |
| A 的可判定单元成功率     | `3/5 = 60%`      | A 的五个已知结果         |
| B 的可判定单元成功率     | `3/4 = 75%`      | B 的四个已知结果         |

最后两行可以作为局部描述，但分母不同，而且缺失未必随机，不能据此宣称 B 在完整评测中优于 A。UNKNOWN 不计为成功或失败，覆盖率的 12 个计划单元却一个也不能抹掉。这里的 60%/75% 也是已知运行的描述性比例，不是直接代入 Pass@k 的真实单题概率。

做配对比较时，只能使用双方都有已知结果的 T1-1、T1-3、T2-1、T2-2，共四对；原计划六对，配对覆盖率为 `4/6`。这四对里 A、B 均成功三次。T1-2 的 A 结果仍可保留在单侧描述中，但不能用它与未知的 B 配对，也不能把 B 补成失败。同题重复仍有关联，统计推断沿用第 6.5 节的任务级处理原则；四对相同成功率不构成等效性证明。

这张表没有费用、Token 和安全审计记录，因而不能汇总对应指标。若已有部分用量记录，也应分别给出其覆盖率，未知价格不能记成零费用。

声明检查器也要报语言覆盖、可评估声明数、证据覆盖和UNKNOWN数量，而非只有总分。空轨迹或没有术语覆盖时没有可靠的满分解释；第8章讲证据门禁，第10章讲术语指标。课程中的20条任务只是练习规模，不保证统计显著性或充分功效。

## 本章要点 {#检查理解}

1. Pass@k 衡量多次尝试至少成功一次，Pass^k 衡量连续成功，后者更能反映重复执行的稳定性。
2. HTTP 状态描述请求处理，任务完成需要业务环境中的证据，例如创建后的任务记录与字段读回。
3. 相同任务的 A/B 结果有关联，配对分析利用这一对应关系评价差异。
4. 检索、生成、成本和安全分别评价，并报告缺运行、缺证据与未计价用量。
5. 吞吐比较需固定工作负载、模型、采样与统计口径；不同 Dataset 的差异可能来自输入输出长度变化。
