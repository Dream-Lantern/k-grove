# 第二十章 mmap、页缓存与 I/O 路径

> 阅读标签：现代Linux普通文件read/mmap/msync。

文件读取与内存访问并非完全独立。普通文件 I/O 与文件映射可能使用同一页缓存；mmap 先建立虚拟地址关系，后续访问再触发实际的页面处理。本章用于串联原 bread 与缺页章节。

## 1. read 的典型缓冲路径

应用传入用户缓冲，内核在相应文件状态与权限下读取数据；可能命中页缓存，也可能请求设备并等待，再将适用内容提供给用户缓冲。预读、异步与文件系统实现会改变具体路径。

不是每次 read 都发磁盘命令，也不是所有 I/O 都通过同一个缓存。Direct I/O、设备映射和 DAX 等另有条件，不从普通文件模型外推。

## 2. mmap 先建立什么？

![映射、访问与后续同步](/assets/notes/operating-systems/os-mmap.svg)

mmap 组织一段进程虚拟地址与文件或匿名后备的关系，涉及长度、偏移、保护与标志。调用成功不等于整份文件已读入物理内存；首次访问可能缺页，也可能已有可用缓存。[mmap(2)](https://man7.org/linux/man-pages/man2/mmap.2.html)

例如，映射大文件后若只访问其中一小段，就不能根据映射长度判断 RSS 会立即增加相同大小。后续驻留情况还受访问模式、预读和回收影响。

## 3. MAP_PRIVATE 与 MAP_SHARED

私有映射的修改按适用写时复制语义，不用于修改底层文件；共享映射则按 API 与后备对象语义共享更新。共享不等于多线程复合更新自动原子，也不意味着每条存储指令完成时已经达到持久化介质。

如果文件同时被截断，某些范围访问可能引起 SIGBUS 等错误；映射生命周期、文件变化和线程并发需要共同管理，不能认为 fd 关闭后所有相关风险都消失。

### 普通文件的同步与映射生命周期

对普通文件MAP_SHARED映射，`msync(...,MS_SYNC)`请求同步所指定映射范围并等待完成；`MS_ASYNC`的接口语义是安排同步后返回。Linux自2.6.19起，MS_ASYNC实际上为no-op，因为内核已跟踪脏页并按需写回；这不等于它提供MS_SYNC的等待保证。调用可能失败，必须检查返回值。[msync(2)](https://man7.org/linux/man-pages/man2/msync.2.html)

纸面时间线是“修改缓存页→请求同步→同步成功返回→按需要munmap”。`munmap`和`close(fd)`都不能替代应用的持久化屏障；关闭fd也不等于解除已经建立的映射。成功同步不使两个字段成为业务原子事务，不覆盖所有设备映射/DAX；新文件发布的目录项持久化还需联系[文件与fsync](/articles/os-file-descriptors-persistence.html)。

## 4. mmap 为什么不是免费零拷贝？

它可以减少某些用户缓冲复制，但还有缺页、页表、TLB、回收和同步成本。大量随机访问、内存压力或页错误会影响尾延迟，不能直接承诺所有负载比 read 快。

讨论零拷贝时，必须说明省略了哪一段复制、是否仍涉及 DMA、内核与设备传输，以及目标接口有哪些限制。性能数据还需注明版本、大小、缓存热度和硬件条件，本册不提供虚构数值。

## 5. 映射不等于应用事务

两个字段依次写入映射，其他执行者可能观察中间状态；崩溃持久化也可能不满足业务原子性。需要相应锁、版本、日志或持久化协议，不能把共享文件直接当成自动事务数据库。

学习时可画出“用户地址、页表、物理缓存页、文件与设备”的关系，再问每一步是建立映射、修改缓存还是同步持久。这样能把原笔记中“页”和“磁盘块”混用的问题拆开。
