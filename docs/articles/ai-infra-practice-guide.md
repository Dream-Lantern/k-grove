# 附录 B 两个贯穿案例与验收表

以下为新增教学设计，未在用户设备运行，也不伪装成原始实验记录。

## 案例一：向量加法从正确到优化

先使用第 04 章完整示例，确认所有输出为 3；扩大规模时检查索引溢出和边界覆盖。再建立一条端到端基线：从申请显存、把数据拷进设备、执行 kernel，到把结果拷回主机，整段计时；这条基线要和只计 kernel 执行的那一段分开记录。

逐步尝试复用分配、分块、多 stream 或 Graph，每次使用相同输入并校验结果。如果速度变快却漏算了尾部数据，应判定实验失败；如果单次 kernel 变快而总时间变长，应结合时间线分析额外成本。

| 实验项 | 预期证据                 | 失败时检查                        |
| ------ | ------------------------ | --------------------------------- |
| 正确性 | 全元素校验与错误码       | 越界、漏算、同步、生命周期        |
| 流水化 | 独立分块的依赖与时间线   | pageable 内存、隐式屏障、资源竞争 |
| Graph  | 构建成本与多次回放总成本 | 捕获限制、输入地址、形状变化      |
| 观测层 | 无拦截/有拦截结果一致    | 错误吞掉、符号覆盖、递归日志      |

固定设备、驱动、Toolkit、编译参数和向量长度。先跑单流全元素校验，再换用 pinned host buffer（页锁定内存，不会被系统换出到磁盘，GPU 可以直接从它异步搬运）把数据切成两块，分别交给两个 Stream，按[第 6 章](/articles/ai-infra-streams-events.html)用 Event 表达依赖。分别记录 Graph 捕获成本与预热后重放的耗时，再按[第 12 章](/articles/ai-infra-performance-profiling.html)短时采集时间线，核对拷贝与 kernel 是否实际重叠。GPU 时间与端到端时间分列。任何 CUDA 错误或输出偏差均判失败。

## 案例二：一个 7B 级模型的容量评估

先固定具体模型 revision、格式、量化方式、引擎与硬件，不把 7B 当作完整规格。先用第 20 章公式算出权重本身至少占多少显存（只是下限，还没算别的），再从日志和运行观察补上 KV、工作区、Graph、通信和框架这几项。

分别测量短输入短输出、长输入、长输出、混合并发四类负载；逐步增加到达率，记录吞吐、TTFT/TPOT 分位数、错误和峰值显存。所有容量结论都应注明质量门槛和超时统计口径。

如果需要共享，先测一份“一台卡只跑这一个任务”的独占基线，再测试目标 MIG/MPS/HAMi 策略；第一次试验只改一项，量化、设备分区和引擎分开验证。隔离验证由单独测试负责，吞吐结果说明不了安全性。

先算 BF16 权重约 13.04 GiB 或理想 W4 约 3.26 GiB，再列 scale、零点、未量化张量和加载峰值。按第 19、20 章分开估算逻辑 KV 与预留池，另计激活、Graph、通信与余量。按第 23 章固定负载和 Tokenizer，记录 TTFT、ITL、TPOT、吞吐、超时、设备峰值和质量。100 秒内若有 800 个请求满足预先定义的质量与时延条件，Goodput 为 8 req/s。按[第 24 章](/articles/ai-infra-capacity-troubleshooting.html)仅接受队列稳定且通过质量、错误预算和显存余量约束的档位。

## 交付前应保存的记录

1. 模型制品、镜像和软件版本清单。
2. 请求分布、并发、到达率、预热及计时定义。
3. 正确性与质量结果，包含失败和超时。
4. 无 profiler 的业务基线，以及短时诊断报告。
5. 峰值内存与余量、资源共享边界及恢复步骤。

这里不预填吞吐、显存或成功结果，待实际运行后再依据证据记录。

可选的隔离实验参考[第 25 章](/articles/ai-infra-gpu-checkpoint-restore.html)。先确认从完整快照恢复后输出仍然正确、各 Rank 之间还能正常通信；再比较增量保存写了多少字节、训练停了多久、恢复后第一个请求多快返回。分别记录各 Rank 阶段结果和应用就绪。以上均为 NOT TESTED。
