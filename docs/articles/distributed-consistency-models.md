# 第四章 线性一致性、顺序一致性与会话保证

> 阅读标签：通用协议/应用模型，具体前提见本章。

一致性模型规定客户端能够观察到哪些结果。可以把请求的调用时间、返回时间与返回值放在同一条历史中，再判断能否按模型解释。线性一致性、顺序一致性、会话保证与事务各有定义，需要分别理解它们约束的对象和顺序。

## 1. 用单个寄存器理解线性一致性

假设对象 x 的顺序语义是：写入改变值，读取返回最近的值。线性一致要求能把每次完成的操作安排在其调用与返回之间的某个点，形成合法顺序；若 A 已返回、B 才开始，则这个顺序必须把 A 放在 B 前面。[Herlihy 与 Wing 原论文](https://cs.brown.edu/~mph/HerlihyW90/p463-herlihy.pdf)

![公共时间轴上重叠的W1/R1与随后R2](/assets/notes/distributed-systems/dist-linear-history.svg)

这个定义不要求每个副本在每个瞬间字节都相同。副本可以暂时落后，只要对外服务方式满足约定的调用历史。

## 2. 用重叠读写理解合法结果 {#_2-并发读可以看到什么}

纸面历史，初值 x=0：

| 操作       | 调用区间 | 结果                          |
| ---------- | -------- | ----------------------------- |
| W1：写 x=1 | 1—4      | 成功                          |
| R1：读 x   | 2—3      | 可以是 0 或 1，取决于合法排序 |
| R2：读 x   | 5—6      | 没有其他写时应为 1            |

R1 与 W1 重叠，可以排序在写之前或之后，但这不意味着“客户端随意选择输出”：全部读写必须能共同构成一个合法顺序。例如，一次读取返回 1，之后才开始的读取却返回 0，在没有其他写入时就无法解释。

正在进行的写也可能已经在调用区间内线性化，并被并发读观察到；超时写同样可能生效。分析历史时，需要把这些尚未明确返回状态的操作纳入判断。

## 3. 顺序一致性保留客户端程序顺序 {#_3-顺序一致性少了哪项约束}

顺序一致性也要求存在符合单客户端程序顺序的全局合法顺序，但不额外保留不同客户端操作间所有实时先后关系。线性一致性保留的实时约束更强。

“每个客户端自己的请求按顺序处理”还不能单独证明顺序一致性，因为不同客户端看到的结果也必须能放进同一个合法顺序。不要把某一条客户端 FIFO 规则当成整个服务的完整模型。

## 4. 读己之写与单调读 {#_4-会话保证解决什么问题}

读己之写使同一会话在成功写入后不再读到该写之前的状态；单调读避免同一会话观察到的状态回退。它们有明确使用价值，但不等价于跨客户端实时最新。

ZooKeeper 的普通读可能来自所连节点，同时提供自身文档规定的会话与更新顺序保证；不能把它写成“ZooKeeper 所有读都线性一致”。同一会话重连与创建新会话也是不同情形。[ZooKeeper 3.9.3 一致性说明](https://zookeeper.apache.org/doc/r3.9.3/zookeeperProgrammers.html#ch_zkGuarantees)

## 5. 对象操作与数据库事务 {#_5-和数据库事务怎样区分}

线性一致性常用于描述对象操作；可串行化描述多个操作组成的事务能否等价于串行执行。严格可串行化还要求保留事务之间的实时顺序。单个键读写很强，不意味着跨多个键自动获得原子事务。

阅读系统设计时，依次标明操作对象、事务边界、是否允许副本旧读和调用是否重叠，再选择对应模型分析。这样能将抽象的一致性要求落到具体请求与结果上。
