# 第四章 线性一致性、顺序一致性与会话保证

> 阅读标签：通用协议/应用模型，具体前提见本章。

一致性模型规定客户端能够观察到哪些结果。可以把请求的调用时间、返回时间与返回值放在同一条历史中，再判断能否按模型解释。线性一致性、顺序一致性、会话保证与事务各有定义，需要分别理解它们约束的对象和顺序。

## 1. 用单个寄存器理解线性一致性

假设对象 x 是一个寄存器，顺序语义是：写入改变值，读取返回顺序中最近一次写入的值。线性一致性（Linearizability）要求整个调用历史能解释为一个合法的顺序执行，而且保留不重叠操作的实时先后：若操作 A 已返回、操作 B 才开始，就必须把 A 排在 B 前面。[Herlihy 与 Wing 原论文 §2.2](https://www.cs.columbia.edu/~wing/publications/HerlihyWing90.pdf)

一次完成操作有三个需要区分的时间：

- 调用时间：客户端发起操作。
- 返回时间：客户端收到该操作的结果。
- 线性化时间：在调用与返回之间，为解释其效果选定的一个时刻，称为线性化点（Linearization Point）。

操作内部可能经过排队、复制和提交等多个步骤；只要所有可见结果都能解释为在某一瞬间生效，就可以使用这个抽象。线性化点是正确性推理中的位置，不要求客户端能从日志中直接读出它，也不一定是发送响应的时刻。必须为整段历史共同选择这些点，不能为每个读操作分别编造互相矛盾的顺序。

![公共时间轴上重叠的W1/R1与随后R2](/assets/notes/distributed-systems/dist-linear-history.svg)

[打开读写历史原图](/assets/notes/distributed-systems/dist-linear-history.svg)。两种面板代表不同返回结果下的合法解释，不是同一操作发生两次。

这个定义不要求每个副本在每个瞬间字节都相同。副本可以暂时落后，只要对外服务方式满足约定的调用历史。

## 2. 用重叠读写理解合法结果 {#_2-并发读可以看到什么}

教学历史，初值 x=0，W1 由客户端 A 调用，R1、R2 由客户端 B 按此顺序调用；没有其他写入，时间数字仅用于推演：

| 操作       | 调用区间 | 结果                          |
| ---------- | -------- | ----------------------------- |
| W1：写 x=1 | 1—4      | 成功                          |
| R1：读 x   | 2—3      | 可以是 0 或 1，取决于合法排序 |
| R2：读 x   | 5—6      | 没有其他写时应为 1            |

R1 与 W1 重叠，因此没有“W1 已完成、R1 才开始”的限制。可以用两组点解释不同的合法结果：

| 历史 | 一组可行的线性化点 | 全局顺序与结论 |
| --- | --- | --- |
| R1=0，R2=1 | R1 在 2.25，W1 在 2.5，R2 在 5.5 | `R1 → W1 → R2`，合法 |
| R1=1，R2=1 | W1 在 2.5，R1 在 2.75，R2 在 5.5 | `W1 → R1 → R2`，合法 |
| R1=0，R2=0 | 无法为所有操作选择合法的点 | W1 在 4 已完成，R2 在 5 才开始，必须在 W1 之后读到 1，因此非法 |

并发允许不同合法排序，不表示客户端可以随意选择输出。所有结果必须共同构成同一个合法顺序。例如，某次读取返回 1，之后才开始的读取却返回 0，在没有其他写入时就无法解释为线性一致历史。

正在进行的写也可能已经线性化，并被并发读观察到。形式化判断允许为部分待完成操作补上响应，再检查完成部分能否形成合法顺序；其余待完成调用可以不纳入该顺序。如果一个读已经看到该写的值，就不能简单删掉这个写来解释历史，见 [Herlihy 与 Wing §2.2 的历史补全定义](https://www.cs.columbia.edu/~wing/publications/HerlihyWing90.pdf)。

超时只结束调用方的等待，服务端写入未必取消。分析时要区分客户端的超时结果与服务端操作的最终结果，保留“写入可能生效”的分支；查询或重试应沿用第二章的业务操作 ID。

## 3. 顺序一致性保留客户端程序顺序 {#_3-顺序一致性少了哪项约束}

顺序一致性（Sequential Consistency）要求存在一个全局合法顺序，保留每个客户端的程序顺序，但不要求保留不同客户端操作之间的实时先后。这里的客户端指顺序执行操作的逻辑进程；同一连接上并发发出的多个请求，还需要声明程序顺序如何定义。定义源于 [Lamport 1979 的顺序一致性论文](https://lamport.azurewebsites.net/pubs/multi.pdf)。

沿用上面的 A、B 与操作区间，可以比较同一组结果：

| R1、R2 的返回值 | 顺序一致性 | 线性一致性 |
| --- | --- | --- |
| 0、1 | 可排为 `R1 → W1 → R2` | 合法，符合重叠与实时边界 |
| 1、1 | 可排为 `W1 → R1 → R2` | 合法 |
| 0、0 | 可排为 `R1 → R2 → W1`，保留 B 的程序顺序 | 非法，违反 W1 完成早于 R2 调用的实时约束 |
| 1、0 | 没有合法顺序：读到 1 后又读到 0，且没有其他写入 | 非法 |

顺序一致性中的顺序是对结果的抽象解释，不要求把操作放回各自物理调用区间；表中 `R2 → W1` 正是两种模型的区别。如果增加跨客户端的消息同步并要求系统保留相应因果关系，还要明确这个更强的契约，不能直接沿用本例的独立客户端假设。

“每个客户端自己的请求按顺序处理”还不能单独证明顺序一致性，因为不同客户端看到的结果也必须能放进同一个合法顺序。不要把某一条客户端的先进先出（First In, First Out，FIFO）规则当成整个服务的完整模型。

## 4. 读己之写与单调读 {#_4-会话保证解决什么问题}

读己之写（Read Your Writes，RYW）让同一会话的后续读取包含自己已成功写入的效果，或看到在其后的合法更新。例如修改个人资料后刷新，不应因被路由到落后副本而又显示修改前的状态；其他客户端后来覆盖资料则是另一回事。

单调读（Monotonic Reads，MR）避免同一会话观察到的版本进度回退。例如先读到订单“已付款”的版本，再切换副本时，不应退回更早的“待付款”版本。它约束的是版本或可见历史，不是字段数值只能增加；订单后续进入“已退款”可以是更晚的状态。会话保证的正式讨论见 [Terry 等人的 Session Guarantees 原论文](https://www.cs.cornell.edu/courses/cs734/2000FA/cached%20papers/SessionGuaranteesPDIS_1.html)。

这些保证面向一个会话，不要求其他会话立刻看到该写入，也不要求本会话每次都读到所有客户端的实时最新值，因此不等于全局线性一致性。

以 **ZooKeeper 3.9.3** 为例，更新由服务端协议排序，同一客户端发出的更新按发送顺序应用。普通读取由所连服务器提供，该服务器的已应用进度可能落后于其他客户端已完成的写入。同一会话已见的进度不会因切换服务器而倒退；使用旧会话重连与创建新会话是不同情形。这里要分别判断写入排序、会话可见性和跨客户端最新读取，不能把文档中的更新顺序保证扩写成“所有读都线性一致”。依据见 [Programmer's Guide：Consistency Guarantees](https://zookeeper.apache.org/doc/r3.9.3/zookeeperProgrammers.html#ch_zkGuarantees)。

官方文档给出这样的例子：A 成功把 `/a` 从 0 改成 1，再通过外部消息通知 B；B 在落后服务器上普通读取，仍可能得到 0。文档建议 B 在读取前调用 `sync()`。应用应等待同步接口成功返回，或异步接口的回调报告成功，再发起同一会话中的读取，以便同步所连服务器的进度；两种接口见 [3.9.3 Java API](https://zookeeper.apache.org/doc/r3.9.3/apidocs/zookeeper-server/org/apache/zookeeper/ZooKeeper.html)。这个同步步骤不冻结其他客户端写入，也不为多个键建立事务快照；不能把一次 `sync()` 当作后续所有读取永久获得全局最新值的开关。涉及连接错误、领导者切换等情况还需按 API 结果重试或重新同步，本节不把该模式泛化为任意故障历史下所有读都线性一致。

## 5. 对象操作与数据库事务 {#_5-和数据库事务怎样区分}

| 性质 | 约束的单位 | 顺序要求 |
| --- | --- | --- |
| 线性一致性（Linearizability） | 约定对象的一次操作 | 等价于合法顺序，保留不重叠操作的实时先后 |
| 可串行化（Serializability） | 包含多次读写的事务 | 已提交事务的结果等价于某个串行执行，不额外要求跨事务实时顺序 |
| 严格可串行化（Strict Serializability） | 事务 | 在可串行化基础上，事务 A 完成后 B 才开始，则串行顺序必须 A 在 B 前 |

上述区分见 [Herlihy 与 Wing §3.1 的事务比较](https://www.cs.columbia.edu/~wing/publications/HerlihyWing90.pdf)。讨论失败时的全有或全无，还需明确事务的原子提交与恢复保证，不能只靠一个顺序名称推导。

教学示例：余额 `x=100、y=100`，一次转账要把 x 减到 90、y 加到 110。如果只是调用两个各自线性一致的单键写入，另一个客户端可以在两次写入之间读到 `x=90、y=100`；每个键都合法，但转账尚未作为整体完成。两个单键接口不会自动组成跨键事务；同样，两次独立读取也不会自动成为一个一致快照。

若转账和读取分别封装为事务，并由系统提供覆盖这两个键的可串行化保证，读取事务就应能解释为在完整转账之前或之后执行。严格可串行化再约束实时关系：转账事务已成功提交后才开始的读取事务，在没有其他更新时必须排在转账后，看到 `90、110`；不能仅以“可以排在转账前”解释旧快照。

阅读系统设计时，依次标明操作对象、事务边界、是否允许副本旧读和调用是否重叠，再选择对应模型分析。这样能将抽象的一致性要求落到具体请求与结果上。
