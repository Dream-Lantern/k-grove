# 第 14 章 MIG 操作复盘：查询、规划、变更和恢复

## 1. 变更前记录布局、身份与工作负载 {#_1-变更前必须保存哪些证据}

记录 GPU UUID、型号、驱动、MIG 模式、现有 GI/CI、profile 和 placement，以及容器/Pod 与设备的对应。确认维护窗口、业务退出和调度侧摘除方式。不能默认把所有占用进程 `kill -9` 作为准备步骤。

[![MIG：受控变更与联合验收](/assets/notes/ai-infra/mig-change.png)](/assets/notes/ai-infra/mig-change.png)

只读查询示例，未执行；目标命令是否支持以本机 `--help` 为准：

```bash
nvidia-smi -L
nvidia-smi -i 0 -q
nvidia-smi mig -i 0 -lgip
nvidia-smi mig -i 0 -lgipp
nvidia-smi mig -i 0 -lgi
nvidia-smi mig -i 0 -lci
```

| 清点项     | 保存的证据与验收条件                                                                                                                       |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 硬件与软件 | `-L` 对照物理 GPU 和 MIG UUID。`-q` 核对型号、驱动、MIG 当前/待生效状态。按支持表确认目标卡                                                |
| 当前资源   | `-lgip` 查看 GI Profile、规格和可用数，`-lgipp` 查看候选放置位置，`-lgi` 记录实际起点、跨度和 GI ID，`-lci` 记录父 GI、CI Profile 和 CI ID |
| 工作负载   | 对齐宿主进程、容器、Pod、设备插件分配与 GPU UUID。摘流并等在途请求结束，确认监控和管理进程是否仍持有设备                                   |
| 维护条件   | 指定负责人和授权范围，保存原模式、可复现布局、调度与监控配置。约定变更窗口、回滚门槛和恢复验收                                             |

命令中的 `0` 仅用于初次只读定位。执行变更前用实际物理 GPU UUID 锁定设备。Kubernetes 上先禁止新工作进入，按工作负载约束摘除并确认占用已清空。仅 cordon 不会驱逐已运行的 Pod，某些控制器也有自己的重建行为。保存 Node 资源和设备插件配置，恢复时先核对资源上报，再解除隔离。

## 2. 创建顺序与位置限制

典型流程是启用 MIG 模式 → 查询 GI profile → 创建 GI → 查询该 GI 的 CI profile → 创建 CI → 读取新 UUID → 启动受控测试。`-C` 在支持的创建方式中可以一起创建默认 CI，但不代表所有组合都适合业务。

即使总剩余容量足够，也可能无法创建目标实例，因为 profile 对 placement 有限制。

在 A100 40GB 的官方 3-2-1-1 混合布局例中，先列出 `19,19,14,9` 可能前三个创建成功、最后一个报 `Insufficient Resources`。文档记录该组合的已知 API 顺序要求，改为 `9,19,14,19` 后可得到合法布局，例如 `3g.20gb` 在 `4:4`，`2g.10gb` 在 `2:2`，两个 `1g.5gb` 在 `0:1` 与 `1:1`。这是官方示例，实例 ID 和实际位置仍须查询。失败后的 GPU 可能已发生部分变更。先读 `-lgi`、`-lci` 和 `-lgipp`，核对切片范围、引擎和顺序，再按批准的计划处理已创建的对象。[A100 混合布局](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/getting-started-with-mig.html#instance-geometry)

## 3. MIG 查询与变更命令示例 {#_3-mig常用命令}

**以下为维护操作语法。仅在授权、维护窗口和业务排空均已确认后，替换占位符并逐项执行。删除或关闭模式可中断服务，先保留原布局和恢复方案。**

```text
nvidia-smi -i <GPU_UUID> -mig 1
nvidia-smi mig -i <GPU_UUID> -cgi <GI_PROFILE_ID> -C
nvidia-smi mig -i <GPU_UUID> -dci -gi <GI_ID> -ci <CI_ID>
nvidia-smi mig -i <GPU_UUID> -dgi -gi <GI_ID>
nvidia-smi -i <GPU_UUID> -mig 0
```

销毁时通常先处理 CI，再处理 GI；日常示例不应使用未限定设备和实例范围的批量销毁命令。恢复需要按已记录的布局重建、重新获取标识并重新分配工作。

逐步核对以下状态。A100 40GB 的教学目标是创建一个 `3g.20gb` GI，并在其中建立一个 CI。所有写命令仅用于已获授权且已排空的维护窗口。本章未执行这些操作。

| 阶段     | 操作与验收                                                                                                                                                                                           | 失败时                                                                              |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 启用模式 | 仅当目标模式尚未启用时执行 `nvidia-smi -i <GPU_UUID> -mig 1`，随后确认 Current 为 Enabled                                                                                                            | Ampere 可能因进程持有设备或平台禁止复位而保持 Pending。保持摘除，检查驱动与平台策略 |
| 创建 GI  | 用 `-lgip`、`-lgipp` 核对 `3g.20gb` 及位置，执行 `nvidia-smi mig -i <GPU_UUID> -cgi 3g.20gb` 后用 `-lgi` 读取实际 GI ID                                                                              | 保留失败日志并重新枚举，检查放置冲突和部分创建                                      |
| 创建 CI  | `nvidia-smi mig -i <GPU_UUID> -gi <GI_ID> -lcip` 查询支持项，确认 CI Profile 后执行 `nvidia-smi mig -i <GPU_UUID> -gi <GI_ID> -cci <CI_PROFILE_ID>`                                                  | 检查父 GI、剩余计算资源及实例权限，避免重复盲试                                     |
| 联合验收 | 用 `-lci`、`-L` 获取新身份，用 `CUDA_VISIBLE_DEVICES=<MIG_UUID> ./vector_add` 运行[第 4 章](/articles/ai-infra-cuda-memory.html)程序。再用真实调度路径分配受控容器/Pod，并确认监控实体与工作负载一致 | 实例能列出但程序或调度失败时保持隔离，优先检查 UUID、设备注入、驱动及插件资源       |

默认 CI 也可用上面的 `-C` 路径一次创建。GI/CI 管理与读查询的权限不同。MIG 模式切换需具备相应的管理权限，NVIDIA 文档列出 `CAP_SYS_ADMIN` 条件。Linux 上可按驱动暴露的 `mig-config` capability 授权受限用户管理实例，核对 `/dev/nvidia-caps` 设备节点及访问控制。它不自动授予模式切换、任意容器内管理或复位权限。操作前核查目标驱动、节点安全策略和现行授权。[MIG Device Capabilities](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/device-nodes-and-capabilities.html)

## 4. 分别核对模式保留与布局恢复 {#_4-模式持久性与布局持久性不是一回事}

Ampere 与 Hopper+ 启用模式时的 reset、模式跨重启保留行为不同。当前文档说明 Hopper+ 的 MIG 模式随驱动驻留，不跨系统重启持久；而“模式仍启用”也不等于 GI/CI 布局自动恢复。[MIG Getting Started](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/getting-started-with-mig.html)

变更后应验证设备枚举、CUDA 最小任务、调度层可分配资源和监控实体；重启后再按设计核对一次。如果业务无法发现设备，应暂停重新切分，先检查布局与旧标识引用，避免扩大影响。

| 架构                                    | 启用时的复位                                                | 模式持久性                                                                             | GI/CI 布局                                         |
| --------------------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Ampere A100/A30                         | 通常需要 GPU Reset 使模式生效，受进程占用、虚拟化和权限影响 | InfoROM 模式位持久，显式更改前跨驱动卸载、GPU Reset 与系统重启保留                     | 复位或重启后按目标状态重新创建并验收               |
| Hopper H100/H200 及指南所述后续支持型号 | 启用 MIG 无需 GPU Reset                                     | 仅在驱动驻留期间持有，卸载驱动或重启会丢失。不要用无驱动卸载的单次设备复位推导其他场景 | 随模式或设备状态变化重新发现，缺失时由配置管理重建 |

模式和实例布局可由节点配置流程分别恢复。例如 NVIDIA 开源 `mig-parted`（例如 v0.15.1）的 systemd 集成可在启动时应用声明式几何。接入时固定实际使用的 release、GPU 选择器和配置，并先在实验节点验证重启、恢复、幂等与失败状态。[NVIDIA MIG Partition Editor](https://github.com/NVIDIA/mig-parted/releases/tag/v0.15.1)

## 5. 把恢复拆成四份状态

| 状态           | 要保存什么                      | 变更或重启后由谁核对   |
| -------------- | ------------------------------- | ---------------------- |
| MIG 模式       | 原模式、GPU UUID、目标驱动      | 节点维护流程或配置管理 |
| GI/CI 布局     | profile、placement、包含关系    | 布局重建流程           |
| 当前设备身份   | 新枚举结果及 UUID 映射          | 应用启动/设备发现流程  |
| 调度与监控映射 | Pod 配置、设备上报和指标 entity | 插件、调度及监控验收   |

Ampere 的模式位持久性不替这些流程保存业务状态。恢复前仍须退出使用者，按保存布局重建后验证。

## 6. 失败时保持隔离并按原布局恢复

| 失败阶段               | 下一步                                                                          |
| ---------------------- | ------------------------------------------------------------------------------- |
| 模式启用失败或 Pending | 检查占用进程、平台复位能力与权限，记录 Current/Pending。未生效时停止创建        |
| GI 创建失败            | 查询是否部分创建，核对 Profile、放置、顺序。只处理计划内对象                    |
| CI 创建失败            | 核对父 GI 和 CI Profile，检查现存 CI。维持摘除直至布局一致                      |
| 实例存在但业务不可用   | 对照新 UUID、CUDA 可见性、容器权限和实际计算结果                                |
| 重启后布局缺失         | 分别核对模式与布局，按保存的配置重建并重新发现身份                              |
| 插件未上报或指标缺失   | 核对插件策略、Node allocatable、Exporter 实体和字段支持，刷新映射并观察有效样本 |

回滚的目标是恢复原模式和原几何。仍保持节点隔离，停止使用待回滚实例的工作，按范围先移除 CI 再移除 GI，随后按已保存的 Profile、放置与父子关系恢复。只有原状态为整卡模式时，才按批准的流程考虑关闭 MIG。重建无法保证得到旧 UUID 或实例 ID，应更新服务、调度和监控映射。

验收顺序为设备发现 → CUDA 结果正确 → 容器/Pod 实际分配 → 监控实体与指标正常 → 服务冒烟 → 分批恢复流量。任何一项失败或未知都保持不可调度，修复或回滚后重新走联合验收。图中的“驱动重新发现”指重新枚举与核对，是否需要重新加载驱动由平台和实际失败原因决定。

| 记录字段       | 填写内容                                                 |
| -------------- | -------------------------------------------------------- |
| 设备与窗口     | GPU UUID、型号、Driver、维护窗口、授权与负责人           |
| 原布局与新布局 | 模式、GI/CI Profile、Placement、实例 ID 与 UUID 映射     |
| 联合验收       | CUDA、调度、监控、服务分别记录通过 / 失败 / 未运行及证据 |
| 回滚状态       | 原布局恢复结果、重新发现与验收结论、是否已恢复调度       |
