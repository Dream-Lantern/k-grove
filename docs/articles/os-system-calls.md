# 第三章 系统调用、特权级与异常入口

> 阅读标签：通用系统调用 / 现代Linux ABI对照。

文本编辑器要保存文件，却不能自行控制磁盘、绕过权限读取别人的数据。**系统调用（System Call）**为这种请求提供受控入口：程序说明要做什么，内核检查后代表它访问资源。普通函数调用通常仍在原有特权级执行；系统调用还涉及由硬件和内核共同规定的权限边界。

一次请求通常涉及三个层次：运行库提供应用接口，体系结构定义进入内核的指令与参数约定，内核检查参数并处理请求。POSIX（Portable Operating System Interface，可移植操作系统接口）主要规定接口与行为，具体机器级约定由 ABI（Application Binary Interface，应用二进制接口）决定。

## 1. 从 printf 到底层写接口 {#_1-printf-不等于每次立即-write}

`printf()` 是 C 标准库函数，在用户态进行格式化，并可能把结果先留在标准 I/O 流的缓冲区。`write()` 是 POSIX 写接口，在 Linux 上通常由 C 运行库包装对应的系统调用：它接收文件描述符、缓冲区地址和字节数，不负责解释 `%d` 这样的格式字符串。

一次 `printf()` 可能不立即触发 `write`，多次输出也可能合并为一次系统调用。`fflush(stdout)` 显式请求将标准输出流的缓冲数据交给底层写接口；它不是磁盘持久化保证，也不能等同于 `fsync()`。缓冲策略和刷新时机见 [stdio(3)](https://man7.org/linux/man-pages/man3/stdio.3.html)与 [fflush(3)](https://man7.org/linux/man-pages/man3/fflush.3.html)。

[![运行库、体系结构入口与内核处理](/assets/notes/operating-systems/os-syscall.svg)](/assets/notes/operating-systems/os-syscall.svg)

图中只有需要等待的分支才进入等待与调度流程。格式化、用户态缓冲、内核接收和设备完成各有位置；不能把它们合并成固定的“printf → int 0x80 → write”通用流程。

## 2. x86 的 0 和 3 是特定架构的级别编号

假如普通应用能够随意关闭中断、改写地址映射或直接控制设备，一个程序的错误就可能影响整台机器。x86 使用硬件特权级限制这些操作，常见 Linux 路线用 ring 0 执行内核，用 ring 3 执行用户代码；数值越小表示特权越高。这里的 ring 是 x86 的编号习惯，不应直接套给其他架构。

| 名称                                            | 含义                             | 用途                                     |
| ----------------------------------------------- | -------------------------------- | ---------------------------------------- |
| CPL（Current Privilege Level，当前特权级）      | 当前代码的执行特权级             | 参与指令、段和门等权限检查               |
| DPL（Descriptor Privilege Level，描述符特权级） | 段描述符或门描述符中记录的特权级 | 与目标类型、访问方式一起确定是否允许访问 |
| RPL（Requestor Privilege Level，请求特权级）    | 段选择子中的请求级别             | 在适用检查中限制请求，不能任意提升权限   |

权限检查依目标段、门、指令与分页规则而异，不能把 DPL≥CPL、DPL≥RPL 写成所有跳转和访问的通用充分条件。普通应用也不能通过给某个变量赋 0，就获得内核权限。

例如，Linux 0.11 通过 DPL 为 3 的 `0x80` 门允许用户程序主动请求服务，但该门指向的是内核预先设置的入口。允许使用入口不等于允许调用者任意选择内核地址。现代 x86-64 的原生 `syscall` 路径也不是通过这个 IDT 门进入；段、门与分页检查的适用规则可查 [Intel 架构手册](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html) Volume 3A 的 Protection、Interrupt and Exception Handling。

## 3. 受控入口的处理顺序 {#_3-受控入口做了什么}

假设现代原生 x86-64 Linux 上，`fd` 是已经打开、允许写入的描述符，用户缓冲区包含 100 字节。执行 `write(fd, buf, 100)` 的主线如下；具体入口代码以 Linux 6.12 为对照。

1. **用户代码与运行库**：C 代码先按普通函数约定调用 `write()` 包装函数。包装层按系统调用 ABI 将调用号放入 `rax`，前三个参数放入 `rdi`、`rsi`、`rdx`，再执行 `syscall`。参数和调用号不是由 CPU 猜出来的。
2. **CPU 硬件**：`SYSCALL` 保存用户返回指令地址到 `rcx`，保存返回所需标志到 `r11`，按内核预设的寄存器配置转入内核入口和特权状态，并屏蔽相应标志位。它本身不向栈压入完整现场，**也不自动切换 RSP 到内核栈**。
3. **内核入口汇编**：保存用户栈指针，切换到内核使用的栈，保存通用寄存器并组织供后续代码使用的现场，再进入 C 层分派。与页表隔离等有关的附加步骤由内核配置决定，不能全部算成 CPU 自动操作。
4. **内核服务**：检查调用号、描述符、写权限、长度和用户缓冲区访问条件，交给相应文件或设备的写实现。传入的是用户地址，不代表可以不经保护地解引用；复制过程仍可能失败或触发缺页处理。不同内核版本的检查位置并不相同。
5. **立即完成或等待**：若本次请求可以处理，返回实际写入量；若需要等待管道空间或其他资源，任务可能阻塞。等待结束且重新获得 CPU 后，从内核中先前的执行位置继续，而不是从头调用用户程序。
6. **返回原任务**：内核完成必要的信号、调度等返回前工作，恢复现场，经适用的 `sysretq` 或 `iretq` 路径回到用户态；栈指针的恢复同样需要软件配合。运行库解释原始返回值，遇到错误通常返回 `-1` 并设置 `errno`。

内核接受写入不代表外设已经完成，更不代表数据已经持久化。普通文件写入可能先进入内核缓存；终端、管道、套接字有各自的完成与等待条件。

### 进阶：不要混抄两条 x86 入口

| 责任             | Linux 0.11 的 x86-32 `int 0x80`                                                             | Linux 6.12 的原生 x86-64 `syscall`                                         |
| ---------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 用户侧参数约定   | 调用号在 `eax`；`write` 三参数在 `ebx/ecx/edx`                                              | 调用号在 `rax`；前三参数在 `rdi/rsi/rdx`                                   |
| 硬件控制转移     | 经 IDT 门检查；从用户态进入内核态时，从 TSS 取得内核栈并保存旧 `SS/ESP`、`EFLAGS`、`CS/EIP` | 根据预配置的专用寄存器进入；返回地址与标志存入 `rcx/r11`，RSP 不变         |
| 入口汇编补充工作 | `_system_call` 保存段寄存器与参数寄存器，设置适用段，再调用系统调用表中的函数               | `entry_SYSCALL_64` 保存用户 RSP、切换栈并构造寄存器现场，再调用 C 分派函数 |
| 正常返回         | 汇编恢复保存的寄存器，`iret` 恢复跨特权级返回现场                                           | 软件恢复现场和栈，按返回条件选择 `sysretq` 或 `iretq` 路径                 |

TSS（Task State Segment，任务状态段）是此处 x86 硬件取得特权栈信息的结构，不能据此推导所有系统调用都由硬件切栈。这张表描述指定模式下的两条路径，现代 32 位程序还有其他入口，不能把 `int 0x80` 当作全部现代 Linux 的统一实现。

历史实现可在 [Linux 0.11 源码包](https://www.kernel.org/pub/linux/kernel/Historic/old-versions/linux-0.11.tar.gz)中核对 `include/unistd.h` 的 `_syscall3`、`kernel/sched.c` 的 `sched_init()`、`kernel/system_call.s` 的 `_system_call` 与 `ret_from_sys_call`。现代对照为 [Linux 6.12 entry_64.S](https://github.com/torvalds/linux/blob/v6.12/arch/x86/entry/entry_64.S) 的 `entry_SYSCALL_64`；不同架构的入口指令和参数表见 [syscall(2)](https://man7.org/linux/man-pages/man2/syscall.2.html)。例如 AArch64 使用 `svc`，不能把 x86 的寄存器约定直接搬过去。

## 4. 中断、异常和系统调用

| 类型                           | 触发来源                               | 执行过程与典型场景                                                       |
| ------------------------------ | -------------------------------------- | ------------------------------------------------------------------------ |
| 硬件中断（Hardware Interrupt） | 与当前指令通常无直接因果关系的外部事件 | 设备报告完成或时钟到期，CPU 经相应入口进入处理程序；不表示每次都切换任务 |
| 异常（Exception）              | 当前指令的执行引发处理器检测           | 缺页可能由内核补充映射后重试；除零等错误可能转为给进程的信号             |
| 系统调用                       | 程序主动请求服务                       | 按 ABI 进入、检查并处理请求，再按调用语义返回                            |

它们可能共用部分低层入口设施，例如 Linux 0.11 的软件 `int` 入口也使用 IDT；现代原生 x86-64 `syscall` 则有独立入口配置。共用处理代码不意味着三者的语义相同。

**案例 A：管道有足够空闲容量。** 假设读端仍打开，任务 P 写入一条小消息，内核能接收全部数据且没有其他必须调度的条件。P 从用户态进入内核，完成复制后直接返回，仍是同一个任务在执行。

**案例 B：阻塞式管道已满。** 假设读端仍打开，P 的写请求需要等待读者腾出空间。P 进入等待，调度器可让读任务 Q 运行；Q 取走数据后使等待条件满足并唤醒 P。P 后续重新获调度，在内核中继续写入，再返回用户态。如果设置非阻塞模式，则可能得到 `EAGAIN`，不沿用这个等待分支。

因此，**进入内核态**改变执行权限；**任务上下文切换**把 CPU 交给另一个任务；**进程地址空间切换**改变所用的地址环境。这是不同的动作：同一进程的两个线程切换可以继续共享地址空间，内核因隔离措施切换页表也不代表更换了任务。即使请求本身不阻塞，其他抢占或返回前调度条件仍可能引发切换，不能把案例 A 理解为永不调度的保证。[pipe(7)](https://man7.org/linux/man-pages/man7/pipe.7.html) 给出管道的阻塞与非阻塞语义。

## 5. 错误应按 API 解释

运行库常将底层错误转换为 -1 与 errno，但具体接口有各自返回规则。不能把所有返回 0 都理解成“成功写入全部内容”，例如 read 返回 0 往往表示到达文件末尾，write 还可能短写。

以纸面流程为例：请求写入 100 字节，返回 `40` 表示**本次成功写入 40 字节**，这是短写，不是“失败 60 字节”的错误码。若业务与目标接口允许继续，下一次应从 `buf + 40` 请求剩余 60 字节，而不能重发前 100 字节导致重复。

| 返回情况                           | 应如何理解                                                     |
| ---------------------------------- | -------------------------------------------------------------- |
| `n > 0`                            | 已取得进展；记录这 `n` 字节，再按接口与业务决定是否继续        |
| `-1` 且 `errno == EINTR`           | 本次在写入任何数据前被信号打断；可按信号处理策略决定是否重试   |
| `-1` 且为 `EAGAIN` / `EWOULDBLOCK` | 非阻塞请求暂时不能推进；按接口等待可写事件等，避免无休止忙重试 |
| 其他错误                           | 报错或执行适用恢复策略，不能统一当作临时错误重试               |

对正长度请求，若没有取得进展，也不能让重试循环永远空转。上述处理只是字节流写入的教学思路；消息边界、管道原子性、信号、超时与其他描述符语义需要另外考虑，不是适用于所有设备的完整实现。依据为 [write(2)](https://man7.org/linux/man-pages/man2/write.2.html) 的返回值、短写和错误说明。此例未执行实际设备操作。

## 6. 用 strace 观察缓冲与系统调用

推荐在有 GCC 和 strace 的 Linux 环境中运行以下实验；终端显示和系统调用跟踪是不同的观察结果。将代码保存为 `demo.c`：

```c
#include <stdio.h>
#include <unistd.h>

int main(void) {
    if (printf("Hello, ") < 0 || printf("OS!") < 0) {
        return 1;
    }
    if (fflush(stdout) == EOF) {
        return 1;
    }
    if (write(STDOUT_FILENO, "\n", 1) != 1) {
        return 1;
    }
    return 0;
}
```

这段小程序遇到输出失败即退出，用于观察调用边界，不实现通用写入重试策略。在普通工作目录中执行：

```bash
gcc -Wall -Wextra -O0 demo.c -o demo
strace -e trace=write -o trace.log ./demo
cat trace.log
```

两次 `printf()` 都不含换行，常见缓冲策略下数据可先留在用户态缓冲区，直到 `fflush()` 才交给一次底层写入。常见环境中的**预期输出示例，非本轮实测结果**为：

```text
write(1, "Hello, OS!", 10) = 10
write(1, "\n", 1)         = 1
+++ exited with 0 +++
```

关注 `write` 的次数、请求字节数与返回值，而不是要求输出逐字相同。运行库、缓冲配置、描述符目标和跟踪能力会影响结果；有的实现还可能使用 `writev`，只跟踪 `write` 并不能覆盖全部底层写入方式。可再把命令改为 `strace -e trace=write,writev -o trace.log ./demo` 作对照。strace 的参数含义见 [strace(1)](https://man7.org/linux/man-pages/man1/strace.1.html)。

若在 `printf` 中加入换行后观察到更早的写入，应结合行缓冲解释；把标准输出重定向到文件又可能改变策略。因此“两个 printf 必然等于一个 write”同样不成立。本轮仅作代码静态复核，未在 Linux 上编译、运行该实验。

## 本章小结

- 系统调用提供受控内核服务，普通运行库函数调用不一定立即进入内核。
- ABI 规定调用号和参数；CPU 与入口代码共同完成受控转移、现场保存与恢复。
- x86-64 的 `SYSCALL` 本身不自动切换内核栈，不能套用 x86-32 `int 0x80` 的全部行为。
- 系统调用不必切换任务，返回值也不保证请求一次全部完成。
- strace 能观察调用边界，具体调用次数需要结合运行库缓冲与环境解释。
