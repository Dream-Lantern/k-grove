# 第三十一章 安全、备份、多实例与维护边界

[返回本册目录](/collections/redis/)

开发沙箱可以简化，但简化步骤必须有边界。本册不把原笔记中的内网地址、账号或部署清单改写成公共教程；也不把关闭保护、开放所有接口的旧步骤推荐给新环境。

## 1. 网络、认证、授权、加密各管一层

监听地址和防火墙限制谁能到达服务；认证识别客户端；ACL 限制可以执行的命令与访问的键；TLS 保护适用链路的传输。仅配置 AUTH 不代表传输已经加密，仅修改默认端口也不构成有效访问控制。

Redis 应放在受控网络内，由可信应用访问，不直接暴露给不可信终端。不要为解决一次连接失败，就默认关闭 protected mode 或允许公网无认证访问。[Redis 安全模型](https://redis.io/docs/latest/operate/oss_and_stack/management/security/)

Redis 6.0+ 提供 ACL。应按业务需要授予最小命令和键空间权限，区分应用、运维、复制与 Sentinel 等用途；升级时重新检查命令类别变化，而不是永久沿用过宽账号。[ACL](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/)

键范围与 PubSub 频道范围是不同规则：`~demo:*` 描述键权限；Redis 6.2+ 的 `&demo:*` 描述适用频道权限。允许访问同名键，不等于频道已经隔离，仍需对应的命令权限。

PUBLISH/SUBSCRIBE 的频道名可按允许频道模式匹配；PSUBSCRIBE 的订阅模式则有与允许模式进行字面匹配的规则，不能简单按“两个 glob 看起来包含”推导。allchannels 等宽权限又会改变整体结果。设计后分别测试允许/拒绝的键、发布、订阅路径，不用管理员账号证明最小权限正确。

普通键级 ACL 也不会自动对一个 Hash 中的不同 field 做独立授权。若权限边界需要分别控制字段，应重新评估拆键或在可信应用层授权，关联第 2、4 章的数据模型选择。本节没有修改任何账号。

## 2. 凭据不要出现在命令历史与文章中

示例使用虚构的 `demo:` 命名空间和占位参数。真实口令、证书、内部地址、客户标识不应被提交到博客仓库。命令行参数、进程列表、Slowlog、终端截图与复制日志都可能泄露信息。

轮换凭据时，还需同步考虑连接池、自动任务、复制和监控。变更认证设置前，应先确认恢复通道，避免正常维护导致集体断连。

## 3. 多实例隔离不只有端口

同机部署多个实例时，需要分别管理各自的配置、数据目录、日志、进程身份、端口和持久化文件，防止文件相互覆盖。现代 AOF 目录也属于实例资源，不能只修改 dbfilename 就认为已经完成隔离。

CPU、内存、磁盘、网络和故障域仍然共享。多个实例 maxmemory 相加小于主机内存，不代表加上 COW 与缓冲后一定安全；同机主副本也不能抵御主机故障。

## 4. 备份验收必须包含隔离恢复

![从文件到恢复能力](/assets/notes/redis/redis-study-backup.svg)

备份清单要说明版本、数据文件集合、配置、函数或扩展依赖、加密及访问权限。多部分 AOF 应取得一致的完整文件集，模块数据还要核对兼容版本。

还应确认启动实际加载哪一组文件：RDB 与 AOF 同时启用时，正常启动优先使用 AOF，不能因目录里有 dump.rdb 就把它当成恢复来源。AOF 损坏也不代表自动回退旧 RDB；单文件 AOF、多部分 AOF 与故障分支见 [第 19 章](/articles/redis-rdb-aof.html)。

恢复演练应在不接收真实写入的隔离环境中进行。除确认能够启动外，还应抽查类型、TTL、关键关系与业务不变量，并记录恢复点和总耗时。如果备份与源盘处于同一故障域，备份的保护价值就会降低。

## 5. 把操作按影响分级

INFO、ROLE 等通常用于观察；修改配置、重写日志、断开连接、复制关系变更、故障转移和迁槽都可能影响业务。FLUSHDB/FLUSHALL、破坏性文件修复或覆盖恢复更不能作为排查中的“试一下”。

维护前应有明确对象、授权、恢复点、窗口和验收标准。本文是笔记整理，不是对任何实例的操作授权。本次没有安装插件、执行数据命令、修改服务或连接真实 Redis。
