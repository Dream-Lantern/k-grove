# 附录 B：贯穿案例与纸面验证

以下均为新增的虚构教学材料，尚无执行结果。订单 o-42、操作 op-42 和事件 e-42 用于串联不同章节，不对应真实项目。先明确状态，再选择技术，有助于避免堆叠缩写、却无法解释架构如何工作。

## 1. 最小业务状态

```text
订单：CREATED → RESERVED → PAID → CONFIRMED
失败路径：RESERVED → CANCELLED，释放相应预留
未知路径：支付调用超时 → PAYMENT_UNKNOWN → 查询/对账
```

这只是示例状态机。真实业务可能不支持取消付款，也可能采用先授权、后扣款的流程，不能直接将这里的顺序用于生产接口。PAYMENT_UNKNOWN 不意味着失败，也不允许在无条件再次扣款的同时立即返还全部资源。

## 2. 每章对应的问题

| 学习段   | 用订单案例问什么？                             | 纸面验收                           |
| -------- | ---------------------------------------------- | ---------------------------------- |
| 1—3 章   | 哪份状态权威？同一操作怎样识别？时间能否比较？ | op-42 不因回复丢失变成新扣款       |
| 4—5 章   | 写后读要多新？分区时允许哪些请求继续？         | 拒绝范围和旧读边界明确             |
| 6—7 章   | 订单怎样分片？复制后哪些故障仍可能传播？       | 路由变化不遗漏新写；有独立恢复点   |
| 8—12 章  | 谁能确定顺序？什么算提交？                     | 不能只数 ACK，必须满足完整协议条件 |
| 13—15 章 | 配置、会话和锁怎样恢复？                       | 迟到旧执行者不能覆盖新资格结果     |
| 16—18 章 | 文件与对象存储提供哪种写入保证？               | 重复追加和未提交版本可识别         |
| 19—21 章 | 本地恢复与跨资源决定在哪里？                   | Prepared 未知时不能猜测中止        |

## 3. 线性一致历史练习

初始 x=0。W1 调用区间为 1—4、写入 1；R1 为 2—3；R2 为 5—6。分别给 R1 安排 0 和 1，尝试寻找合法线性化顺序。R2 在没有其他写时应返回 1；R1 与写入重叠，可以分别尝试排在写之前或之后，并检查整个历史能否共同构成合法顺序。

再增加 W2，调用 2、返回 7、写入 2。不能再仅按“已完成写入 W1”确定所有重叠读取；需要为整个历史寻找一致顺序。这个练习没有生成随机测试或运行线性一致检查器。

## 4. Raft 的状态表练习

分别记录每个节点的 currentTerm、votedFor、日志、commitIndex、lastApplied。对一次选举和一次回复丢失，写清哪些数据已持久化、哪些只是内存视图。加入快照后，数组位置与绝对日志索引怎样转换？

验收不能只看“最终三份是否一样”，还应确认整个过程中没有应用未提交的冲突命令，重启后也没有违反此前的投票承诺。

## 5. 事务故障练习

在协调者持久化 COMMIT 后、只通知了库存参与者时停止协调者。支付参与者已 Prepared 但未知决定，应查询权威记录或等待恢复；仅凭超时中止会与已存在的提交决定冲突。恢复后依据事务 ID 和已保存状态识别重复通知。

再把流程改为 Outbox：业务事务已提交，事件已发出但发布进度未保存。重复传递 e-42 时，消费者的去重与业务更新应该在哪里原子完成？跨外部支付又多了什么限制？

## 6. 真正实践前的边界

开展实验时，先在独立环境中固定版本、拓扑、数据范围与恢复点，再逐项引入故障，保存调用历史与业务状态。伪代码用于纸面理解，实际运行仍需对应实现和验收。

## 7. 故障反例与参考结论 {#_7-复核后的反例集}

| 输入/历史                                  | 必须说清的结论                                                     |
| ------------------------------------------ | ------------------------------------------------------------------ |
| 新Raft Leader有旧日志，但本任期尚未提交    | 不能只凭角色或旧心跳立即提供安全读；补本任期前提、读确认与应用屏障 |
| PBFT四副本，重复收到同一发送者三份commit   | 不等于三个不同副本；prepared条件也不能省略                         |
| 42已发放但资源仅见过41                     | 单凭maxSeenToken可能仍接受41；与资源建立42后拒旧的历史分开         |
| /counter被删除重建，version又为0           | 旧setData(...,0)可能命中新对象；路径/数据版本不是永久世代          |
| E2(version2)先发、E1(version1)后发，ID不同 | 同Key不修复错误发布顺序；event_id去重不修复版本逆序                |

这些是纸面协议检查，不是已运行的故障注入结果。
