# 附录 B：贯穿案例与纸面验证

以下均为新增的虚构教学材料，尚无执行结果。订单 o-42、操作 op-42 和事件 e-42 用于串联不同章节，不对应真实项目。先明确状态，再选择技术，有助于避免堆叠缩写、却无法解释架构如何工作。

| 示例标识 | 表示什么                         | 关系与边界                                                                   |
| -------- | -------------------------------- | ---------------------------------------------------------------------------- |
| `o-42`   | Order ID，订单标识               | 同一订单可以有创建、付款、退款等多个业务操作，不把它当作所有请求共用的幂等键 |
| `op-42`  | Operation ID，某次业务操作的标识 | 在约定作用域内用作幂等键，同一操作重试复用；退款等新意图使用另一个键         |
| `e-42`   | Event ID，某条事件的标识         | 一个业务操作可产生多条不同事件；事件投递去重不等于业务操作去重               |

## 1. 最小业务状态

```text
订单履约：CREATED → RESERVED → CONFIRMED
取消路径：RESERVED → CANCELLING → CANCELLED

本地支付状态：NOT_STARTED → PENDING → SUCCEEDED / FAILED
结果未知：PENDING → PAYMENT_UNKNOWN → 查询/对账
退款路径：SUCCEEDED → REFUND_PENDING → REFUNDED
```

这只是两组相互协调的示例状态。`PAYMENT_UNKNOWN` 表示本地尚不能判断支付结果，不是支付端确定失败；查询后仍可能待处理，也可能确定成功或失败。订单取消表示不再履约，不证明已经退款；已扣款而取消履约时，要另行推进退款并记录补偿进度。

结果未知时，按业务约定的期限保留库存预留或转入待对账状态，不无条件再次扣款。若决定超期释放库存，则迟到的支付成功不能再沿原路径直接确认订单，应进入退款或人工处理。对账、重试和补偿共同使两组状态收敛，失败步骤仍需可查询与恢复。真实业务也可能采用先授权、后扣款的流程，不能直接把本例当作生产支付接口。[支付未知与幂等](/articles/distributed-rpc-retries-idempotency.html)、[Saga 补偿](/articles/distributed-saga-tcc-outbox.html)

## 3. 线性一致历史练习

初始 x=0。W1 调用区间为 1—4、写入 1；R1 为 2—3；R2 为 5—6。分别给 R1 安排 0 和 1，尝试寻找合法线性化顺序。R2 在没有其他写时应返回 1；R1 与写入重叠，可以分别尝试排在写之前或之后，并检查整个历史能否共同构成合法顺序。

再增加 W2，调用 2、返回 7、写入 2。不能再仅按“已完成写入 W1”确定所有重叠读取；需要为整个历史寻找一致顺序。这个练习没有生成随机测试或运行线性一致检查器。

参考答案假设只有列出的操作、写均成功，且不同客户端允许这些区间重叠。第一组的两种结果分别可用 `R1 → W1 → R2`（R1=0）和 `W1 → R1 → R2`（R1=1）解释，R2 均为 1。

第二组中，R1 与 W2 重叠，所以 R1 **可以为 2**。全部合法读值组合及一个共同线性化顺序如下；不能为两次读分别挑选互不相容的历史：

| `(R1,R2)` | 一个合法顺序      |
| --------- | ----------------- |
| `(0,1)`   | R1 → W1 → R2 → W2 |
| `(0,2)`   | R1 → W1 → W2 → R2 |
| `(1,1)`   | W1 → R1 → R2 → W2 |
| `(1,2)`   | W1 → R1 → W2 → R2 |
| `(2,1)`   | W2 → R1 → W1 → R2 |
| `(2,2)`   | W1 → W2 → R1 → R2 |

共同的实时约束是 W1、R1 都先于 R2，W2 可在三个操作之间选择合法位置。R2 不能为 0，因为 W1 已在 R2 开始前完成，且后续写只可能给出 2。`(2,1)` 也不矛盾：W2 先线性化、W1 后线性化，虽 W2 最晚返回，其生效点仍可位于调用区间前部。定义和更多推演见[第 4 章](/articles/distributed-consistency-models.html)。

## 4. Raft 的状态表练习

分别记录每个节点的 currentTerm、votedFor、日志、commitIndex、lastApplied。对一次选举和一次回复丢失，写清哪些数据已持久化、哪些只是内存视图。加入快照后，数组位置与绝对日志索引怎样转换？

验收不能只看“最终三份是否一样”，还应确认整个过程中没有应用未提交的冲突命令，重启后也没有违反此前的投票承诺。

按经典 Raft 论文图 2，参考分类为：

| 状态                               | 分类与恢复含义                                                            |
| ---------------------------------- | ------------------------------------------------------------------------- |
| `currentTerm`、`votedFor`、`log[]` | 所有节点的持久化状态；按协议在回复所依赖的 RPC 前写入稳定存储             |
| `commitIndex`、`lastApplied`       | 图 2 中所有节点的易失状态，分别是已知提交和已应用进度                     |
| `nextIndex[]`、`matchIndex[]`      | Leader 专属的易失状态，当选时重新初始化，分别跟踪发送位置和已确认匹配进度 |

快照保存状态机已应用前缀，以及 `lastIncludedIndex`、`lastIncludedTerm`（最后包含条目的绝对索引与任期）和适用的成员配置。业务去重状态也要与状态机恢复边界一致。若快照包含到 100，且内存数组只保存 101 起的后缀，则 index 101 对应数组下标 0，换算是 `index - lastIncludedIndex - 1`；若实现保留哨兵条目，公式相应不同。

这是经典论文的分类，不要求所有工程实现只按易失字段处理应用进度。持久化状态机、应用位置与快照必须协调恢复，不能重复应用或漏掉业务效果。详见[第 9 章](/articles/distributed-raft-election.html)、[第 10 章](/articles/distributed-raft-log-replication.html)及[第 11 章](/articles/distributed-raft-snapshots-membership.html)。

## 5. 事务故障练习

在协调者持久化 COMMIT 后、只通知了库存参与者时停止协调者。支付参与者已 Prepared 但未知决定，应查询权威记录或等待恢复；仅凭超时中止会与已存在的提交决定冲突。恢复后依据事务 ID 和已保存状态识别重复通知。

参考结论：参与者不知道决定，不等于全局还没有决定。协调者恢复后必须读取已有 COMMIT 并继续传播，不能重新选择 ABORT；参与者对同一事务的重复 COMMIT 幂等完成。若 Prepared 参与者无法获得权威决定，经典 2PC 可能阻塞；超时只触发查询与恢复，不授予自行中止的权利。[第 21 章的决定与恢复](/articles/distributed-two-phase-commit.html)

再把流程改为 Outbox：业务事务已提交，事件已发出但发布进度未保存。重复传递 e-42 时，消费者的去重与业务更新应该在哪里原子完成？跨外部支付又多了什么限制？

参考结论：消费端以 `event_id=e-42` 的唯一约束等控制并发，在**同一个本地数据库事务**中保存去重记录并更新业务，提交后才确认消费。若先独立提交去重，随后业务更新前崩溃，重投会被跳过而丢失效果。

第三方支付不属于这个本地事务。应另用稳定的支付操作幂等键（如支付意图 `op-42`）调用并查询对端，重投事件仍复用它；退款等新操作另设幂等键。外部成功、本地保存结果前崩溃时，通过同键重试或对账恢复，不因换了执行尝试就再扣一次。事件顺序另按聚合版本处理，Event ID 去重不能阻止不同事件的旧版本覆盖新状态。[第 22 章的 Outbox 边界](/articles/distributed-saga-tcc-outbox.html)
