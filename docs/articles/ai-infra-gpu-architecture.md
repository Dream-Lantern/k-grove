# 第 2 章 GPU 架构：SM、Tensor Core 与资源瓶颈

显卡标称的 CUDA Core 数量很多，小任务却未必能充分利用它们。核心数量只是硬件条件的一部分；任务还需要足够的并行度，以及能让这些单元持续工作所需的数据、指令和可用资源。

## 1. 不要把 CUDA 线程直接等同于物理核心

SM（Streaming Multiprocessor，流式多处理器）是理解执行资源的重要单位。一个 SM 包含指令调度与执行单元，并拥有寄存器、共享内存等资源。CUDA 线程是程序抽象；硬件以 warp 等粒度推进指令，并不是启动多少线程就独占多少个 CUDA Core。

![GPU 资源关系示意](/assets/notes/ai-infra/gpu-resources.svg)

这张图只表示概念关系，不仿造某款 GPU 的精确芯片框图。GPC、TPC、SM、复制引擎、视频单元、L2 和显存的数量及组织会随芯片和产品 SKU 改变。完整芯片的设计数量也不等于实际产品启用数量。

## 2. 三类资源分别解决什么问题

| 资源                   | 主要作用                       | 容易混淆的地方                 |
| ---------------------- | ------------------------------ | ------------------------------ |
| 常规计算执行单元       | 执行相应整数、浮点等指令       | 不同精度和指令的吞吐不同       |
| Tensor Core            | 加速所支持的数据类型和矩阵运算 | 不会自动加速所有代码           |
| Copy Engine            | 在支持的路径上搬运数据         | 不能代替算术单元做模型计算     |
| L2 / 显存              | 缓存、存储与供给数据           | 容量大不代表带宽或延迟一定更好 |
| 寄存器 / shared memory | 保存线程、线程块局部工作数据   | 用量过大可能限制常驻线程块     |

原文把 Tensor Core 的首次引入放到了 Pascal；应修正为 Volta。另一方面，产品系列可能共用架构名称却面向不同市场，不能据此认定每一款 Ampere 卡都有 RT Core 或相同的视频编解码单元。[NVIDIA Volta 架构](https://www.nvidia.com/en-us/data-center/volta-gpu-architecture/)

## 3. 计算密集、带宽密集和提交受限

一次大型矩阵乘法可能主要受矩阵运算吞吐约束；逐元素读取大量数据而只做少量计算，往往更依赖访存带宽。大量很短的 kernel 还可能受 CPU 提交开销影响。这些是待测假设，必须结合时间线和计数器确认。

判断瓶颈时，先确认时间是否真的花在 GPU 上。如果 GPU 正在等待 CPU 预处理，换更快的 GPU 未必有效。如果耗时主要发生在 GPU 内，再检查数据供给、指令效率及并行度，不要盲目增加 block 数。

## 4. 比较硬件要使用相同口径

比较峰值性能必须写明 FP32、TF32、FP16、BF16 等数据类型，以及是否采用结构化稀疏。FLOPs 通常表示浮点运算次数，FLOP/s 才是每秒运算率；厂商表中的“倍数”还依赖基线和工作负载。

本册不保留“某代产品一律快几十倍”“MIG 在两个任务时一定更快”等泛化结论。选型记录至少需要 GPU 型号、显存、功耗约束、互连、软件版本、输入形状和业务指标。只有固定这些条件，结果才有可比较性。

## 5. 架构名称、芯片设计、产品 SKU 分列

可以先记住两项历史事实：Pascal P100 没有 Tensor Core，Volta V100 引入 Tensor Core。TensorRT 则属于软件，不应列入“芯片新增硬件单元”。即使架构名称相同，数据中心卡与图形产品也未必具有相同的 RT 或媒体引擎。

读架构图时按“架构 → 芯片完整设计 → 实际 SKU 启用配置”逐层核对。本册的 GPU 资源图刻意不写 GA100 数量，也不复用带 Three Video Encoders 的旧图；这是避免把概念图伪装成 A100 规格，而不是声称所有 GPU 都没有编码器。需要采购或精确容量时另查目标 SKU 白皮书，不能依据抽象图计算单元数量。
