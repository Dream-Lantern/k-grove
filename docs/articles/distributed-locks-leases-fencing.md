# 第十五章 分布式锁、租约与 fencing

> 阅读标签：应用资格协议 / ZooKeeper3.9.3锁recipe。

分布式锁为执行者分配访问共享资源的资格。完整路径包括申请资格、持有期间操作、资格交接，以及资源端处理迟到请求。锁记录与业务执行存在网络和调度边界，因此还需要 fencing 等机制把资格检查落实到实际写入端。

## 1. ZooKeeper 排队锁的主线

在锁父路径下创建临时顺序子节点，读取子节点列表。序号最小的适用节点取得资格，其余客户端观察紧邻前驱，而不是所有人同时观察同一个锁文件，减少释放时的大规模惊群。

教学伪代码，不是完整客户端实现：

```text
创建带本次申请身份的 ephemeral sequential 节点
循环：
    读取同一锁目录下的参与节点，定位自己
    如果自己已不存在：停止使用旧资格并进入恢复
    如果自己为最小序号：进入受保护逻辑
    否则对紧邻前驱 exists 并注册 Watch
    若前驱已不存在：立即重新列举；否则等待变化后重新判断
```

create 回复丢失时，应按申请身份恢复自己可能已经创建的节点，不能盲目重复创建。顺序后缀有范围与实现边界，不应无条件当成跨系统、永不回退的 fencing token。[ZooKeeper 3.9.3 锁 recipe](https://zookeeper.apache.org/doc/r3.9.3/recipes.html#sc_recipes_Locks)

教学队列中，假设目录只包含本协议的申请节点，暂省略用于恢复的 GUID 前缀：

```text
/locks/order/
    lock-0000000010    Client A：最小，持有资格
    lock-0000000011    Client B：只观察 A 的节点
    lock-0000000012    Client C：只观察 B 的节点
```

惊群效应（Herd Effect）是某次变化同时唤醒大量竞争者，而大多数只能再次等待。若大家都 Watch 父节点的子列表，A 退出可能唤醒所有申请者；观察紧邻前驱使 A 删除时主要通知 B，C 仍等 B。B 被唤醒后还须重新列举并确认自己最小；C 不能因为 A 删除就进入临界区。

![三个申请者分别监听紧邻前驱，以及通知后重新核对资格](/assets/notes/distributed-systems/dist-zk-lock-queue.svg)

把恢复和等待细节补入状态机，可得到以下教学流程，API 语义依据 **ZooKeeper 3.9.3 Recipes**，不指定生产客户端库：

1. 为本次申请生成 GUID（Globally Unique Identifier，全局唯一标识符），作为申请身份；以 `guid-lock-` 为前缀创建临时顺序节点。GUID 用来找回申请，不负责大小排序。
2. 保存 create 返回的实际路径。读取 `getChildren(parent, watch=false)`，筛选本锁协议的节点并按顺序后缀排序；GUID 前缀不同，不能直接按整个名称字典序决定资格。
3. 若自己不在列表中，停止使用该申请并进入恢复；若自己最小，才取得 ZooKeeper 队列资格。要保护外部写入，还须完成本章后述资源屏障。
4. 否则调用 `exists(predecessor, watch=true)`。若返回不存在，立即重新列举；这覆盖“列举后、注册前前驱恰好删除”的竞态。
5. 前驱存在则等待通知或连接状态变化。通知后重新列举、重新判断；一次通知不是一次授权，传统 Watch 的重读规则见[第十四章](/articles/distributed-zookeeper-watch.html#_2-收到通知之后怎样处理)。
6. 释放时只删除自己当前有效申请的实际路径，核对会话及申请身份；不删除前驱、别人节点或仅凭推测拼出的路径。取消及释放结果未知时同样需要恢复处理。

若 create 已在服务端成功，但返回路径前连接丢失，旧会话中的临时节点可能仍在。重连且确认还是同一有效会话后，用 `getChildren` 查找本次 GUID，核对实际节点及 `ephemeralOwner`，找回路径再继续。如果出现多个匹配或无法确认结果，应进入有界的恢复与清理流程，不能无限重建顺序节点。可靠确认不存在后才可按协议重试申请。会话过期则旧申请身份失效，不能继续等待旧前驱或沿用旧资格；新会话应使用新申请身份。[3.9.3 Recoverable Errors and the GUID](https://zookeeper.apache.org/doc/r3.9.3/recipes.html#sc_recipes_Locks)

## 2. 暂停恢复后的迟到写入 {#_2-失去锁为何还能写}

[![最高已见令牌：资源观察新代际后才拒旧](/assets/notes/distributed-systems/dist-fencing.png)](/assets/notes/distributed-systems/dist-fencing.png)

纸面推演：A 获锁后暂停很久；会话过期，B 获得新锁并完成更新；A 恢复，继续执行暂停前的代码。协调服务可能正确地交接了锁，但外部存储仍同时收到 A、B 的请求。

因此，“同一时刻只有一条有效锁记录”与“只有一个业务执行者在运行”是不同的不变量。即使 A 在每次写入前检查锁，检查完成到下游实际写入之间，仍存在竞态窗口。

把时间线拆开：A 得到资格和 token=41，执行前暂停；它无法续持会话，服务端最终判定过期并删除节点。B 重新判断为队首，得到新资格 token=42，开始业务。A 此后恢复，仍可能执行已经在栈中的数据库调用。服务端删除 znode 无法撤销数据库连接、终止 A 的 CPU 线程或收回已发出的网络请求；所以外部资源还必须参与资格隔离。

## 3. fencing 必须由资源端执行

一个常用设计是让新资格携带单调增大的令牌，下游以原子方式比较并记录已接受的最高令牌，拒绝旧资格。这个机制要求令牌发放可靠、范围正确，而且所有受保护路径都不能绕过校验。

同一个令牌的重复请求仍需操作级幂等；如果操作要跨多个外部系统，每个系统都要有相容的协议。只有一个数字、一次客户端判断，或把 token 打进日志，不能产生隔离效果。

隔离令牌（Fencing Token）代表某个受保护范围的一代资格，新的合法资格必须获得更大的可比较值。每条受保护写请求携带 token，资源端维护该范围的持久 `maxSeenToken`。例如已记录 42 时，A 发来的 41 被拒绝；B 的 42 还须满足权限、operation_id 和业务条件，不能因为令牌相等就无条件重复扣款。令牌用于隔离过时请求，仍需可信的发放及认证，不能允许任意客户端伪造更大数字。[fencing 的原始论述与示例](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)

一个教学资源协议如下，`atomic` 要由资源自身的事务、串行化服务或等价机制实现：

```text
apply(scope, token, operation_id, command):
    atomic（覆盖 scope 的并发请求）：
        验证请求及令牌来源，读取持久 maxSeenToken
        若 token < maxSeenToken：拒绝，不产生业务修改
        若 operation_id 已完成且参数一致：按协议返回已存结果
        校验业务前提
        记录 maxSeenToken = max(maxSeenToken, token)
        修改业务数据，并保存 operation_id 与结果
    持久提交后返回结果
```

上述伪代码把令牌更新、业务修改与幂等记录放在共同原子边界；重复请求若被较新代际拒绝，可用独立的结果查询协议判断原操作结局。**同 token 不等于同操作**，一个持有者可以执行多个不同 operation_id；同一操作的重试才应消除重复效果。

若先校验 token、释放原子边界，稍后才执行数据写入，A 可以先通过 41 检查，在 B 建立 42 后才把旧写落地，隔离便失效。若先单独持久推进到 42，业务写入随后失败，42 仍可作为已生效屏障，但不能报告业务已成功；B 应查询或按幂等协议重试。若二者属于一个事务并整体失败，则两者一起回滚，不能假设资源已经建立 42。资源恢复时也不能把最高令牌重置为较小值，否则旧请求可能重新通过。

### 资源观察新代际之前与之后 {#资源尚未看到新令牌时会怎样}

以资源端保存 `maxSeenToken` 的协议推演：

| 历史                            | 资源端当前最大令牌 | A携带41的迟到写                    |
| ------------------------------- | -----------------: | ---------------------------------- |
| B取得42，并已在资源端建立42代际 |                 42 | 拒绝41                             |
| 协调服务仅发放42，B尚未访问资源 |                 41 | 单凭最高已见令牌规则，仍可能接受41 |

因此它是**资源观察到新代际后的隔离**，不是协调服务交接瞬间的实时撤销广播。如果业务要求“资格切换完成后所有旧写立即无效”，需要先在资源端建立并确认新代际屏障，再把切换视为完成，或采用另一种与资源访问协调的验证协议。

比较token、更新maxSeenToken与受保护写入必须处于资源端共同的原子边界。若先检查、稍后才写，旧请求仍可穿过窗口。此表用于推演本章的应用协议；Frangipani 论文中的租约设计在下一节按其历史背景讨论。

场景 B 必须单独考虑：B 仅仅从协调服务拿到 42 时，资源仍是 41，A 的 41 可以满足“不得小于最高已见值”的条件。即使 B 已在客户端宣布自己持锁，资源也未必得知交接。

若要求“宣布交接完成后，所有旧资格请求都不能产生新的写入效果”，应先由 B 在资源端执行原子 `advanceFence(42)`，使其与所有受保护写入按同一边界排序；等屏障持久确认后，再宣布交接完成并开始新代际业务。已经在屏障前完成的旧写仍属于历史，不会自动回滚。跨多个独立资源则要分别建立屏障并设计交接失败的恢复规则，一个资源确认不代表其他资源也完成隔离。

### 令牌来源及比较范围

| 候选值 | 能提供什么 | 用于 fencing 前必须满足的条件 |
| --- | --- | --- |
| Sequential 后缀 | 同一父 znode 生命周期内的顺序命名 | 资格发放与令牌顺序绑定；固定父节点和资源作用域；在计数溢出前迁移；重建时用更高、可靠的外层代际衔接 |
| znode `version` | 同一对象的数据修改版本 | 删除重建会复位，且有计数边界；不能直接充当跨生命周期永久单调代际 |
| UUID / GUID | 区分申请身份 | 随机唯一性不提供严格递增的资格顺序 |
| zxid | 同一 ZooKeeper 历史中的事务顺序 | 明确提取哪个事务、如何绑定本次资格、完整比较范围，以及集群恢复/替换后如何保持资源令牌不回退 |

顺序计数器的父作用域和有符号整数溢出边界见[第十三章的数据模型](/articles/distributed-zookeeper-zab.html#_2-znode-是有路径的协调对象)。对于每次新建的申请节点，`czxid` 可以标记创建事务，但采用它发令牌仍需证明创建次序、授予资格顺序和下游比较相容；仅说“它是 zxid”还不够。已有资源的最高令牌、快照与恢复流程必须保持一致，不能在协调服务重建或资源恢复备份后悄悄复用旧代际。

## 4. 租约依赖明确的时间假设

租约赋予有限时间内的资格，续约只是协议动作，不保证业务线程永远持有资格。服务器端 TTL、客户端计时、暂停与时钟误差必须一起分析。

历史 Frangipani 论文讨论了客户端检查租约与 Petal 收到写入之间的延迟风险，并提出资源端进一步验证的路线。安全余量是否足够，取决于时钟和延迟假设。[Frangipani 论文 §5～6](https://rcs.uwaterloo.ca/papers/frangipani.pdf)

租约（Lease）把资格限制在一个有效期内，时间假设至少涉及以下几层：

| 因素 | 影响 |
| --- | --- |
| 服务端 TTL 与续期 | 服务端决定何时失效；续期请求发出不等于已经成功 |
| 客户端单调时钟 | 适合计算本地经过时间，避免墙钟校准导致倒退；它不直接等于服务器时钟 |
| 网络延迟 | 消耗申请、续期与业务请求的有效窗口，迟到包可能在过期后到达 |
| 进程或机器暂停 | 检查通过后仍可能暂停很久，恢复时资格已经失效 |
| 时钟偏差、漂移与计时行为 | 涉及时钟租约证明的误差界；不同平台的休眠计时行为也须核对 |
| ZooKeeper 会话过期 | 由 ZooKeeper 服务端管理会话与临时节点，不是客户端本地倒计时到点就直接获得全局失效结论 |

Frangipani 原论文 §5 介绍同步与缓存一致性，§6 的锁服务部分进一步讨论租约、故障恢复和存储竞态：历史实现先检查租约并预留余量，但 Petal 不验证收到的写是否仍有资格；足够长的延迟仍可能让过期写落地。论文讨论的改进包括资源端检查带到期时间的请求，以及与锁服务结合检查租约标识。前者需要相应时钟误差界，后者需要资源知道租约权威状态；都不能只靠客户端“多留一点余量”。这是历史系统的设计与改进讨论，不是 ZooKeeper 3.9.3 的实现说明。[Frangipani §5～6](https://rcs.uwaterloo.ca/papers/frangipani.pdf)

## 5. 持锁操作的中断与业务恢复 {#_5-锁不等于事务}

持有者若在一系列修改中途崩溃，新持有者可能接手部分完成的结果。自动释放锁只是允许其他执行者继续，并不会自动回滚库存、撤销付款或修复文件；恢复仍需日志、幂等步骤、事务或可恢复状态机。

因此设计清单至少包含：锁范围、资格有效性、资源端隔离、重入与取消、超时后行为、恢复记录及补偿。Redis SET NX、ZooKeeper 临时节点、租约和数据库行锁有不同边界，不宜只凭 API 名字互相替换。

教学案例：订单 O100 需要扣减库存并改为“已确认”。A 已将库存从 10 改为 9，却在更新订单前崩溃。锁随后释放，B 获得资格并建立新屏障；若 B 无条件重跑，又会把库存从 9 扣到 8。

恢复协议应为 O100 保留稳定 operation_id 与执行记录。若两个修改在同一数据库，可用适当事务将库存、订单和幂等记录一起提交；若跨系统，则由新工作者检查库存扣减结果与订单状态，从已完成步骤继续，或根据业务规则补偿。结果未知时先查询与核对记录。释放锁不会替代这套恢复流程，fencing 也不会撤销先前已经提交的库存修改。

| 机制 | 管理的内容 | 仍需其他机制处理的部分 |
| --- | --- | --- |
| 锁（Lock） | 竞争者访问资源的资格 | 外部旧线程、部分完成的业务 |
| 租约（Lease） | 资格有效期与续期 | 暂停后的迟到请求与资源验证 |
| 隔离（Fencing） | 资源端拒绝不再适用的旧代际效果 | 业务回滚和多系统原子提交 |
| 幂等（Idempotency） | 同一操作重试的重复效果 | 不同操作的旧资格问题 |
| 事务（Transaction） | 适用原子边界内多项修改的一致提交与恢复 | 边界之外的系统及访问资格 |

这几层可以组合：协调服务分配资格，资源端验证代际，业务记录支撑重试与恢复。单个数据库实现 fencing，不代表库存、支付和消息系统自动形成同一个事务。
