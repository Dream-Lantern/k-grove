# 第二章 RPC、超时、重试与业务幂等

> 阅读标签：通用协议/应用模型，具体前提见本章。

远程过程调用（RPC）把调用包装得像本地函数，却不能消除网络边界。调用者没有收到结果时，服务端可能没有执行，也可能已经完成，只是回复没有到达。这种“结果未知”是后续事务、锁与消息问题的共同起点。

## 1. 一次超时对应哪些历史？

假设客户端要求为订单 o-42 扣款。下面三种历史都可能表现为客户端超时：请求没有到达；服务端开始处理但尚未提交；服务端已提交而回复丢失。仅依据异常类型，通常无法区分它们。

![超时后的判定与恢复](/assets/notes/distributed-systems/dist-rpc.svg)

因此，超时后不能直接判定“扣款失败”并重新发起一笔扣款。新请求如果更换业务标识，服务端可能将其视为另一笔操作。

## 2. 幂等键保护的是业务操作身份

教学伪代码，展示设计意图，不是完整实现：

```text
请求携带 operation_id 和参数摘要
在一个受约束的事务或状态机中：
    如果 operation_id 已有最终结果：校验参数一致后返回该结果
    如果相同 ID 对应不同参数：拒绝冲突
    否则执行业务变更，并原子保存 ID、参数摘要与结果
结果未知时：查询同一 ID，或以同一 ID 有界重试
```

关键在于“业务效果”与“去重记录”是否处于同一原子边界。如果先扣款，再到另一个存储中记录已处理，两步之间崩溃仍可能导致重复扣款。副作用若发生在外部支付系统，则需要对方支持稳定操作标识，或提供可查询、可对账的状态协议。

同一个 ID 不能无限期保护所有未来重放。去重记录保留多久、客户端最晚会重试多久、历史是否可能恢复到旧版本，都要纳入约束。[AWS 的幂等 API 设计说明](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## 3. 不要把 exactly-once 当成传输属性

最多一次尝试可能丢失工作；至少一次尝试可能重复执行。业务上接近“效果一次”，依赖稳定身份、持久化结果和原子更新，并不意味着网络只投递过一次。

例如消息消费成功后、确认前崩溃，消息可能再次出现。用消息 ID 去重只有在去重状态与业务提交相容时才有意义；“先把消息 ID 写入 Redis，再修改另一个数据库”仍有两个独立提交点。

## 4. 重试也会制造故障

服务已经过载时，每层都立即重试会放大流量。若三层调用各尝试三次，极端情况下底层可能接到 27 次尝试，而不是三次。这个算例假定每次都触发完整下游尝试，不是压测结果。

设计中应明确总截止时间、单次超时、重试次数、退避与抖动，并确定由哪一层负责重试，避免逐层放大流量。即使业务请求已超过截止时间，也不能保证服务端会自动取消已接受的变更。

## 5. 学习验证要检查什么？

纸面检查至少覆盖：首次成功但回复丢失；重复 ID 参数改变；处理中崩溃；成功记录被清理后迟到重试。验收目标不是“没有重复日志”，而是同一业务操作只产生允许的持久效果，且未知状态可以查询或人工对账。
