# 第2章 上下文工程（Context Engineering）

上一章的工具循环需要不断接收新信息。本章从一个问题展开：工具已经查到文档后，下一轮模型怎样知道查到了什么、还有哪些步骤没完成？

全文使用同一条**合成教学任务**：“查询 DemoServe 1.0 的启动端口配置，只读取给定文档，回答默认端口、修改参数和来源。”假设示例文档说明“默认 9000，使用 `--port` 修改”。项目、工具结果和路径均用于推演，不对应真实框架或本地实测。

## 2.1 一次模型调用的上下文 {#_2-1-上下文究竟包括什么}

**Context 是本次模型调用能够使用的信息集合**，聊天记录是其中一部分。常见内容包含：系统/开发者指令、工具定义、用户消息、先前模型调用意图、工具结果、任务状态、按需检索出的知识与记忆。不同 API 对 reasoning 是否可见/如何保留可能不同，不能假定所有模型都会暴露完整内部思考。

有状态 Agent 的关键是：**LLM 请求常可视为一次无状态计算，而 Agent 需要显式维护跨轮任务状态**。模型不会自动继承你没有再次提供或通过 API 状态机制引用的信息。

LLM（Large Language Model，大语言模型）根据当前输入作决策；API（Application Programming Interface，应用程序接口）规定调用与返回方式。Agent 状态则由运行程序维护，例如当前阶段、已读文档和未解决问题。状态中需要参与决策的部分，必须被写入当前 Context，或通过接口支持的状态引用提供。

### 两轮请求中的信息传递

下面的 `search_docs` 和 `read_doc` 都是合成工具。表中列的是逻辑内容，实际接口还需遵守消息角色和工具调用标识等协议。

| 时点       | 模型实际收到的 Context                                           | 决策、执行与状态变化                                                               |
| ---------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 第一次调用 | 只读规则、用户任务、工具说明；状态为“尚未查找”                   | 模型请求搜索；执行侧检查权限并调用工具，获得 `demoserve-1.0/config.md` 和摘要      |
| 第二次调用 | 前述内容，加上搜索调用、对应工具结果；状态为“已定位，待读取正文” | 模型请求读该文件；工具返回版本、默认端口、参数与出处，状态改为“已读取，待核对答案” |
| 第三次调用 | 加上读取请求、文档正文和当前状态                                 | 模型组织答案；执行侧按任务要求核对后结束，或在证据不足时继续查找                   |

**工具取得结果、程序保存状态、模型收到这些信息，是三个独立步骤。** 即使日志中保存了搜索路径，如果第二次请求没包含它，模型也无法据此选择读取。反过来，模型说“已经读完”也不能替代实际工具记录。下面讨论的布局、Skill 和压缩，都是在管理这条传递链。

### 推荐上下文布局

```text
稳定前缀（尽量固定）
  ├── 系统角色 / 安全边界
  ├── 工具 Schema 与稳定规则
动态部分（按需追加或引用）
  ├── 当前用户目标和约束
  ├── 当前任务状态 / 下一步
  ├── 最近几轮交互
  ├── 检索到的相关知识、记忆
  └── 工具结果或摘要
```

**顺序的价值**：频繁修改很靠前的内容可能使后续缓存前缀无法复用；把易变信息放在后面一般更利于前缀缓存。但缓存命中规则依赖具体模型服务商的实现，不能把某个 API 的行为当作通用保证。

## 2.2 KV Cache、Prompt Cache 的区别

| 维度     | KV Cache                                            | Prompt Cache                            |
| -------- | --------------------------------------------------- | --------------------------------------- |
| 是什么   | Transformer 注意力计算中的 Key/Value 中间张量       | 产品/服务层对公共输入前缀的缓存复用能力 |
| 发生位置 | 推理引擎内                                          | 推理服务或 API 的缓存管理层             |
| 解决问题 | 减少自回归生成时对历史 token 的重复计算             | 降低相同前缀再次推理的计算、延迟或费用  |
| 关系     | Prompt Cache 通常依赖底层可复用的 KV 表示或等价机制 | 不代表任意文本重排后仍能命中            |

**注意**：一些系统会把 Prefix Cache、Prompt Cache、KV Cache 互换使用。做设计时要问清楚缓存键、作用范围、过期、跨请求隔离和实际命中统计口径。

### 从一次生成推演到下一次请求

**KV Cache（Key–Value Cache，键值缓存）**中的 Key/Value 是注意力计算产生的中间张量，不是 Redis 那样的业务键值对。以普通因果自注意力生成过程为例，模型已处理输入词元 A、B、C 后，生成下一位置时可复用它们在各层的 K/V，并加入新位置的 K/V，避免重新计算历史位置的这些量；新位置仍需利用历史信息进行注意力计算。[Hugging Face：缓存原理](https://huggingface.co/docs/transformers/main/en/cache_explanation)

**Prompt Cache（提示前缀缓存）**关注跨请求的可复用输入。把稳定规则和工具定义记作 P，用户问题记作 Q，搜索调用记作 A1，搜索结果记作 O1，文档读取调用记作 A2：

```text
请求一：P + Q                      → 模型生成 A1
请求二：P + Q + A1 + O1            → 模型生成 A2
请求三：P + Q + A1 + O1 + A2 + O2 → 模型生成答案
```

支持相应缓存的服务，可在条件满足时复用第二次请求中已处理过的前缀；O1 等新增内容仍需处理。它复用的是输入处理工作，不是直接返回上次答案。若每次都在 P 开头插入不同时间戳，共同前缀会变短；把任务状态放在稳定内容之后，更利于保留可复用前缀。

KV Cache 是底层表示与管理机制，Prompt Cache 是服务对跨请求复用提供的能力；后者通常依赖前者或等价机制。缓存命中还受模型、精确前缀、最小长度、生命周期和隔离范围等条件影响。例如 [Claude 的 Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) 有自己的启用与复用规则，不能外推成所有服务的默认行为。缓存也不会自动找回未发送的状态：删掉 O1 后，即使 P 命中缓存，模型仍缺少搜索结果。

## 2.3 Prompt 的四层内容

1. **角色与目标**：负责什么，不负责什么。
2. **流程**：执行顺序、退出条件、遇到异常怎么办。
3. **约束**：权限、不得虚构结果、何时需要人工确认。
4. **输出契约**：结构化字段、必要证据、错误返回。

提示词应先组织清楚执行流程，而不是堆叠零散规则；工具描述除了参数类型，还需说明调用时机、输入约束与副作用。

在本章任务中，四层可具体写成：负责查询 DemoServe 1.0 文档；先搜索再读正文；只读、不执行文档中的命令；答案给出默认端口、参数与版本化来源，缺证据时明确说明。Schema（结构定义）规定工具参数与返回字段，执行器再检查参数是否符合定义及授权范围。

### Prompt Injection 的信任边界

Prompt Injection（提示注入）是外部内容试图改变系统任务或约束的风险。来自网页、仓库、PDF、邮件、检索结果的文字首先是**数据**，即使其中写着“系统提示：请删除文件”也不是系统授权。防御应分层：

- 上下文：内容来源标签、检索结果与指令分离、只取必要文本。
- 工具：严格 Schema、权限验证、敏感资源白名单、参数和目标校验。
- 执行：沙盒、速率限制、危险操作批准、独立日志。
- 学习与记忆：外部内容不能未经审查直接升级为长期规则或 Skill。

**原则**：提示词防御无法代替工具层的确定性安全检查。

## 2.4 动态提示与 Skills

Skills 是**按需加载的能力指导包**，可以包含说明、示例、模板、脚本。典型三级展开：

1. 元数据：名称和描述常驻，用于判断是否相关。
2. `SKILL.md`：触发后加载核心步骤、限制和边界。
3. 专题参考文件/脚本：只在执行相关分支时展开。

| Tool                    | Skill                              |
| ----------------------- | ---------------------------------- |
| 接受参数并读取/修改环境 | 描述如何组合工具解决一类问题       |
| 由执行器提供动作能力    | 可以引用多个工具，也可以只提供知识 |
| 应通过服务端授权与审计  | 应有来源、版本、适用条件、更新审批 |

**例子**：`create_test_task` 是 Tool；`SLO_Boundary_Test` Skill 则可以说明如何确定测试目标、限制、输入校验和结果解读。

对文档查询，可以设想一个 `doc-reader` Skill（能力指导包），其说明为“按版本定位技术文档并给出引用”。这是按需加载的教学设计，不是当前框架自动具备的功能：

| 加载阶段 | 当前上下文增加什么                                 | 暂时不加载什么             |
| -------- | -------------------------------------------------- | -------------------------- |
| 识别任务 | Skill 名称与简短描述                               | 完整操作说明与全部技术资料 |
| 决定使用 | `SKILL.md` 中“确认版本→搜索→读正文→核对引用”的步骤 | 与本次任务无关的专题参考   |
| 需要细节 | 当前版本的参考说明和目标文档片段                   | 其他版本、长日志与无关示例 |

因此第二轮调用可能比第一轮多了指导步骤和搜索结果。按需加载减少初始无关内容，但仍有发现与读取成本；加载的 Skill 不能扩大原有的只读权限。若目标仅是查端口，也不必把所有部署教程都加入请求。

## 2.5 Agent 状态栏与时间预算

状态栏是供模型定期读取的**当前局面摘要**，把运行中的任务状态组织成便于决策的信息：任务剩余时间、当前步骤、已消耗预算、关键约束、上一个失败原因、下一步动作候选。

示例：

```yaml
task_status:
  goal: "完成方案校验"
  phase: "VALIDATING"
  elapsed_seconds: 132
  remaining_budget_seconds: 48
  completed: ["解析输入", "校验 Endpoint"]
  blockers: ["Dataset Binding 尚未 READY"]
  next_action: "等待状态变化或超时退出"
```

状态栏只是摘要，不是最终事实来源；原始状态应以数据库和工具结果为依据。尤其不能将不可信网页内容直接写成可信的状态字段。

回到文档例子，一份可继续执行的状态至少包含：`target_version=1.0`、`phase=FOUND_DOC`、已确认路径、未完成的“读取正文”、剩余工具次数，以及“只读”的约束。下一轮把这些字段与搜索结果引用放进 Context。预算由运行时更新，收到新输入或从检查点（Checkpoint，可恢复的任务状态）继续时重新检查；不能让模型自行延长截止时间。

## 2.6 上下文压缩的动机与方法 {#_2-6-上下文压缩-不是只有窗口满了才需要}

上下文压缩有两个动机：**成本/窗口约束**和**信息质量约束（Context Rot）**。模型即使装得下长历史，也可能丢失关键事实，反复寻找已知结果。

| 方案          | 保留                         | 可丢弃       | 风险                   |
| ------------- | ---------------------------- | ------------ | ---------------------- |
| 原始轨迹      | 每条工具调用/返回            | 无           | Token 消耗和注意力分散 |
| 滑动窗口      | 最近 N 轮                    | 久远的对话   | 丢失早期关键约束       |
| 结构化摘要    | 目标、决策、约束、状态、引用 | 冗长重复过程 | 摘要失真或遗漏         |
| 工具结果压缩  | 关键字段/引用                | 大量原始输出 | 关键异常被裁掉         |
| 子 Agent 隔离 | 主 Agent 只收结构化结果      | 子任务细节   | 交接上下文不足         |

### 压缩检查点建议

压缩检查点需要保留可继续执行任务的信息，而非仅概括对话主题。至少包括：

```yaml
handoff:
  user_goal: "..."
  accepted_constraints: []
  frozen_decisions: []
  completed_steps: []
  active_work: []
  errors_and_evidence: []
  file_or_artifact_refs: []
  next_action: "..."
  unknowns: []
```

- 对可以重读的原始日志、文件，保留引用/Hash，不必把全文塞进上下文。
- 对批准的不可变约束与关键错误，不应只保留含糊摘要。
- 压缩会改变后续上下文前缀，可能牺牲部分缓存命中；频繁压缩和过晚压缩都不好。
- **独立任务可优先隔离上下文**：不必把全部中间日志返回主 Agent；但须保留交接所需证据。隔离和压缩解决不同层面的问题，不能一概比较优劣。

### 按信息价值决定压缩方式 {#压缩风险不能只按消息角色排序}

工具结果中的唯一事务ID、真实写入状态、版本和关键错误栈可能是后续决策的唯一证据，不能因为它属于 Tool Result 就优先截断。重复大日志在原文可读、来源和版本固定时更适合摘要。批准阈值若已冻结到状态库并由执行器直接读取，模型上下文可以只保留摘要和引用。判断依据是内容重要性、可恢复性、时效与确定性约束，而非“工具消息比用户约束更不重要”。

### 压缩前后应保留什么

假设多轮查询产生了重复摘要、无关文档和一次读取超时。下面是人工编写的对照，不是模型摘要结果：

| 材料       | 原始记录                               | 可用于继续任务的结构化摘要                                                 |
| ---------- | -------------------------------------- | -------------------------------------------------------------------------- |
| 目标与权限 | 用户要求只查 1.0 版，只读              | 目标版本和只读约束完整保留                                                 |
| 搜索与读取 | 多条重复命中；一次超时，重试后读到正文 | 保留成功读取的文档标识、版本、可重读引用和实际结果；失败仍作为状态证据保存 |
| 关键事实   | 该合成文档中的默认端口和 `--port` 说明 | 保留具体值、参数及对应段落，避免仅写“找到了配置”                           |
| 剩余工作   | 尚未核对答案出处                       | 明确下一步为核对引用，不能摘要成“任务已完成”                               |

压缩可以外置重复正文，但引用必须能够按原版本重读。摘要“端口配置已找到”丢失了值、版本和出处，即使字数减少，也无法支撑最终回答。Hash（内容哈希）帮助识别文件版本，本身不提供读取权限。

## 2.7 最小实验

给同一 Agent 三组输入：原始 40 条工具日志、截断最近 10 条、结构化摘要+原始日志引用；固定模型和问题，比较任务成功率、找回关键约束的准确率、输入 Token、延迟。若压缩后节省 Token 却忘记必需约束，不应视为有效优化。

可把文档任务做成固定样本：包含命中的 1.0 文档、容易混淆的其他版本、重复日志和一次失败，再预先标注正确版本、端口、参数及出处。Token（词元）是模型输入输出的计量单元，不等于字符数。

1. **保存基准材料。** 固定文档快照与哈希、任务、工具返回和只读约束，避免在线搜索变化；预先写好答案检查项。
2. **构造三组输入。** 原始 40 条、最近 10 条、结构化摘要加可读引用。将关键版本说明安排在容易被截掉的位置，保留位置记录；这是人为设计的压力样例。
3. **先检查信息，再请求模型。** 核对实际请求是否包含关键事实或可用引用；没有引用读取能力时，不把一个文件名当成可恢复证据。
4. **固定条件重复运行。** 保持主模型、摘要模型、生成参数和预算一致，每次独立初始化；三组采用同一问题和检查标准。
5. **分别评价正确性与成本。** 记录版本/参数/引用正确率、关键约束保留、重复工具调用、失败与超时、主模型和摘要模型的总词元及总延迟。TTFT（Time to First Token，首词元延迟）只衡量开始输出的时间，不能替代整个任务耗时。

**判断标准：**先满足答案依据、权限和状态保真，再比较成本与延迟。预期结构化摘要能减少无关信息，但这需要实验支持；原始长上下文也可能表现更好。下面的源码检查只验证截断范围，不代表完成了三组模型实验。

## 2.8 从源码区分“压缩策略”与“实验结果”

`context-compression` 实现六种策略：不压缩、逐页摘要、合并摘要、任务感知摘要、带引用摘要、窗口化历史。窗口化不是任意删旧消息，而是尽量保留最新工具结果，压缩较早内容，并防止重复压缩。

`ContextCompressor.compress_for_history()` 的正常与失败路径决定了哪些原始内容会进入后续请求：摘要请求失败时，代码回退为截取前 2,000 字符；正常摘要的输入也仅限前 10,000 字符。因此，即使摘要读起来流畅，也不代表尾部事实曾进入压缩器；具备回退路径，同样不保证关键事实得到了保留。

源码节选（上下文依赖见原文件）：[chapter2/context-compression/compression_strategies.py](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter2/context-compression/compression_strategies.py#L219-L228)。

```python
except Exception as e:
    logger.error(f"Error compressing for history: {str(e)}")
    # Fallback to truncation
    truncated = content[:2000] + "\n\n[Content truncated for history...]"
    return CompressedContent(
        original_length=original_length,
        compressed_length=len(truncated),
        content=truncated,
        strategy=CompressionStrategy.WINDOWED_CONTEXT
    )
```

可以增加一个反例：将必需的文件路径、批准阈值或来源放在第 10,000 字符之后，再检查压缩后能否正确回答相关追问。原始日志可外置，摘要只保存任务所需信息和可重读引用；不能丢失的业务约束则用结构化字段和校验器保护。不能将每次截断都自动计为压缩成功。

### 从两个切片推导遗漏风险

固定提交的 [摘要输入与回退](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter2/context-compression/compression_strategies.py#L133-L228) 中，`content[:10000]` 只把原内容索引 0～9999 的字符放进摘要提示；查询和其他提示文字另行组成请求。这里限制的是这一段原内容，不是整个模型请求的总长度，更不是 10,000 个 token。

设一份合成文档在前面介绍通用参数，**从索引 10050 才开始写“1.0 版请使用 `--port`”**。这个版本条件没有进入上述摘要输入，摘要器就无法从这次输入得知它。若用截断后的摘要替换原文且不留可读取来源，下一轮便可能失去关键依据。

异常路径使用 `content[:2000]`，再附加截断标记。位于索引 2100 的事实可进入正常摘要输入，却进不了异常回退正文；位于索引 10050 的事实两条路径都进不去。返回的 `compressed_length` 包括标记长度，所以并非固定等于 2000。应在外层保留执行结果和来源，检测回退与信息缺失，而非把所有返回都计为语义压缩成功。

### 两个值得分开做的实验

| 实验                    | 控制变量                               | 主要观察                                         | 不足以证明什么                     |
| ----------------------- | -------------------------------------- | ------------------------------------------------ | ---------------------------------- |
| 六策略压缩对照          | 同一研究问题、搜索结果快照、模型和步数 | 事实保留、引用、溢出次数、主模型与摘要模型总用量 | 仅凭字符缩短不能证明成本或质量提升 |
| `kv-cache` 六种消息布局 | 同一文件任务与模型服务                 | `cached_tokens`、逐轮 TTFT、总输入和完成率       | 稳定前缀不保证服务实际命中缓存     |

在 `context-compression` 先运行 `python experiment.py --list-strategies`，再选 `-s context_aware` 或 `-s windowed` 做单策略验证。批量前固定搜索快照；在线搜索随时间变化，会破坏对照。缓存实验还应控制冷/热请求、工具顺序、时间戳位置和服务 TTL；不支持缓存统计的接口应记“不可观测”，不要填 0 当成真实未命中。

TTL（Time to Live，存活时间）影响缓存是否仍可复用。以下命令从固定提交的 `chapter2/context-compression` 运行，需先按该目录 README 准备依赖和模型服务；这是后续复现步骤，本轮未启动在线实验：

```text
python experiment.py --list-strategies
python experiment.py -s context_aware -o results/context-aware.json
python experiment.py -s windowed -o results/windowed.json
```

该入口使用仓库自带研究任务，并不自动接受本章的 DemoServe 样本；若要做第 2.7 节的对照，需另接固定输入和评分器。[命令参数](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter2/context-compression/experiment.py#L283-L327)与 [依赖文件](https://github.com/bojieli/ai-agent-book/blob/dbc046eb896ac4e39aa19c7774c8bf49583b89a6/chapter2/context-compression/requirements.txt)可用于准备环境；后者的 `-e ../..` 还引用仓库根包。程序打印的预期性总结也需要对照保存的原始记录，不能直接作为本地实验结论。

本轮仅对 `compress_for_history()` 的非流式路径做隔离检查：以合成内容和测试替身替代模型客户端，检查传入摘要的字符串，并故意触发异常观察回退。它验证切片及回退行为，不验证摘要质量、真实缓存命中或模型任务成功率。

## 本章要点 {#检查理解}

1. 上下文工程负责选择、排序和维护本次决策需要的信息；扩大窗口只增加容量，仍需管理信息质量。
2. KV Cache 复用减少重复计算，任务成功率衡量目标达成，优化时应分别观察。
3. 稳定目标与硬约束适合常驻；具体任务的操作指导可组织为按需加载的 Skill。
4. 网页属于外部数据，危险动作的最终权限检查由工具层和执行器落实。
5. 唯一事务状态、批准条件和关键错误需要保真；可重读日志可外置，摘要保留引用与恢复执行所需字段。
