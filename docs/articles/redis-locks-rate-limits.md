# 第二十八章 锁、限流与业务幂等

[返回本册目录](/collections/redis/)

本章是新增教学补充。它连接了原笔记中的原子命令、事务和缓存设计，但不宣称任何单段示例足以保证所有分布式业务安全。

## 1. 带期限的锁更像租约

SET NX PX 可以表达“键不存在时写入，并附带期限”。锁值使用本次获取的唯一标识，释放时应在同一原子操作中比较标识后再删除，防止旧持有者误删别人后来获得的锁。

```lua
-- 教学解锁逻辑：KEYS[1] 是锁键，ARGV[1] 是本次持有标识
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

先 GET、在应用中比较、再 DEL 不是原子解锁：比较后、删除前锁可能已经到期并被另一请求获得。上面脚本解决这项竞态，但并不解决全部锁问题。[官方分布式锁讨论](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

## 2. 锁过期不会让旧进程停止

![旧持有者恢复后的风险](/assets/notes/redis/redis-study-lease.svg)

请求 A 暂停超过租期后，B 可以获得新锁。A 恢复时仍可能继续向数据库或对象存储写入。唯一锁值只能帮助识别释放资格，不能让外部系统自动拒绝 A 的旧写。

若需要更强的约束，可以让下游校验单调递增的 fencing token 或实体版本，拒绝使用旧资格的操作；前提是令牌生成、比较与下游写入确实构成可靠协议。仅生成递增数而不让下游校验，并不能起到隔离作用。

续租需要核对所有权，并处理暂停和网络失败。异步复制故障切换还可能影响锁状态，因此不应把一个 SET NX 示例直接包装成强一致分布式互斥服务。

## 3. 限流先定义窗口和失败策略

固定窗口计数器简单，但窗口交界可能产生突发；滑动窗口、令牌桶和漏桶各有成本与行为区别。实现前应写清楚按用户、接口还是租户计数，窗口多长，超出如何拒绝，Redis 不可用时放行还是收紧。

把 INCR 和 EXPIRE 分开发送，可能在中间失败后留下无期限计数键。应使用适用的单命令或有限 Lua/Functions 将必要步骤组合起来，并核对集群同槽约束。

超时重试还可能重复扣减配额。若限流与业务请求要求精确对应，需要请求去重设计；近似限流则应明确允许的误差，而不是声称有原子计数就能精确一次。

## 4. 幂等是业务结果约束

为请求附上唯一 ID，还不足以保证幂等。系统需要原子地决定由谁执行，记录处理中与完成状态，并设计好处理进程崩溃、记录过期、结果查询失败和跨系统提交时的应对方式。

例如数据库已经成功提交，去重键却因 Redis 故障丢失，再次请求仍可能重复扣款。关键财务或唯一业务状态应利用权威系统的唯一约束、事务或专门协议，不将可淘汰缓存作为唯一防线。

学习时可以逐一画出故障点：获取资格前、获取后未写、外部提交后未确认，以及确认后回复丢失。相比“加锁就安全”，解释清楚每个故障点如何恢复，才更接近完整设计。
