# 第二十八章 锁、限流与业务幂等

[返回本册目录](/collections/redis/)

原子命令可以作为锁、限流与幂等协议的构件。这三类需求分别关注访问资格、请求预算和业务结果，实际设计还要考虑期限、并发与失败恢复。本章用教学流程说明它们如何组合使用。

## 1. 带期限的锁更像租约

租约（Lease）是有期限的访问资格。TTL（Time To Live，存活时间）让持有者崩溃后锁能到期释放，但不会终止持有者的业务进程。下面是 Redis 命令，不是 Shell（命令解释环境）或客户端方法；本章命令和预期返回均为教学示例。基础示例适用于 Redis Open Source 7.2.0，新命令另标版本，不推断 Redis Software 或 Redis Cloud 的能力。

```redis
SET lock:order:1001 unique-token NX PX 30000
```

`lock:order:1001` 是订单 1001 的锁键（Key）；值 `unique-token` 是本次获取的唯一标识，占位值必须换成每次获取新生成的随机值，不能由所有客户端固定共用。`NX` 只在键不存在时写入，`PX 30000` 同时设置 30000 毫秒租期。成功预期返回 `OK`，键已存在时预期返回 `nil`；网络超时则无法据此判断是否写入成功。获取与设期限在一条命令内完成，见 [SET](https://redis.io/docs/latest/commands/set/)。

续租需要核对所有权。原子性（Atomicity）在这里表示比较和修改期间不会插入其他客户端命令；先 GET、再单独 PEXPIRE 仍有竞态。下面是 Lua 服务端脚本正文，`KEYS[1]` 为锁键，`ARGV[1]` 为本次标识，`ARGV[2]` 为新的正整数毫秒租期：

```lua
local ttl = tonumber(ARGV[2])
if not ttl or ttl <= 0 or ttl ~= math.floor(ttl) or ttl > 300000 then
    return redis.error_reply('invalid lease milliseconds')
end
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('PEXPIRE', KEYS[1], ttl)
end
return 0
```

300000 是此教学脚本自定的租期上限，不是 Redis 限制。传入 `30000` 可续租 30 秒；返回 1 表示已续租，0 表示键不存在或标识不匹配。可用 `EVAL "脚本正文" 1 lock:order:1001 unique-token 30000` 调用，其中“脚本正文”需替换为上面完整代码，这一行是调用格式示意。参数验证放在写入前，续租命令参见 [PEXPIRE](https://redis.io/docs/latest/commands/pexpire/)。

续租返回 0、出错或超时后，业务不能继续假设持锁：停止发起新的外部副作用，尽可能取消未提交任务；已经提交但结果不明的操作应查询权威系统并对账。业务耗时超过租期也按失去资格处理，不能靠事后续租证明此前一直独占。重复续租还要设业务总时限。

释放时也应在同一原子操作中比较标识后再删除，防止旧持有者误删别人后来获得的锁。保留下面的 Lua 解锁逻辑：

```lua
-- 教学解锁逻辑：KEYS[1] 是锁键，ARGV[1] 是本次持有标识
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

先 GET、在应用中比较、再 DEL 不是原子解锁：比较后、删除前锁可能已经到期并被另一请求获得。上面脚本解决这项竞态，但并不解决全部锁问题。[官方分布式锁讨论](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

Redis Open Source 8.4.0 起可用 [DELEX](https://redis.io/docs/latest/commands/delex/) 原生执行条件删除，Redis Open Source 7.x 继续使用 Lua：

```redis
DELEX lock:order:1001 IFEQ unique-token
```

`IFEQ` 要求当前值等于本次标识。预期返回 1 表示已删除，0 表示键不存在或值不匹配；对非 String 键使用此条件会报类型错误。两种实现都必须比较本次标识。Lua 的 EVAL 自 Redis Open Source 2.6.0 提供，执行期间会阻塞其他命令，也不提供出错后的自动回滚；脚本应短小，详见 [第 18 章 Lua](/articles/redis-transactions-lua-functions.html) 和 [7.2.0 EVAL 定义](https://github.com/redis/redis/blob/7.2.0/src/commands/eval.json)。

## 2. 租约交接后的迟到操作与 Fencing {#_2-锁过期不会让旧进程停止}

![旧持有者恢复后的风险](/assets/notes/redis/redis-study-lease.svg)

请求 A 暂停超过租期后，B 可以获得新锁。A 恢复时仍可能继续向数据库或对象存储写入。唯一锁值只能帮助识别释放资格，不能让外部系统自动拒绝 A 的旧写。

Fencing Token（栅栏令牌）是为不同持有资格分配的有序递增令牌，下游资源依据顺序拒绝旧操作。教学推演如下，令牌生成服务是假定满足故障下单调性的独立机制，不是 SET 的返回值：

```text
A 获取租约，取得令牌 41 → A 暂停超过租期 → Redis 锁到期
B 获取新租约，取得令牌 42 → B 写数据库，数据库原子记录最大令牌 42
A 恢复，用令牌 41 写数据库 → 数据库比较 41 < 42，拒绝旧操作
```

唯一锁标识用于识别“是谁”，不代表资格的新旧顺序；Fencing Token 用于比较顺序，下游必须把令牌校验、最大值更新和业务写入原子地结合。令牌生成器还必须在目标故障模型下保持单调。Redis INCR 在单实例递增，并不自动构成完整的分布式令牌服务：如果异步复制故障转移丢失最新计数，新主节点可能重新发出旧值，不能宣称跨故障仍严格递增。

默认异步主从复制还存在另一条失败路径：

```text
t1：A 在主节点成功写入锁并收到成功回复
t2：锁尚未复制到副本
t3：主节点故障
t4：副本晋升为新主节点
t5：B 在新主节点成功获得同一把锁
t6：A 未停止业务，A、B 可能同时执行
```

主节点返回成功不代表副本已收到写入；简单的主从切换可能丢失最新锁状态。以下方案解决的问题不同，不能只按节点数量判断安全性：

| 方案             | 工作方式                       | 适用条件与边界                                   |
| ---------------- | ------------------------------ | ------------------------------------------------ |
| 单实例 SET NX PX | 一处管理有期限的资格           | 能接受实例故障、暂停等风险；业务须在有效期内完成 |
| 主从复制锁       | 增加副本与故障转移             | 接受异步复制丢写带来的互斥风险                   |
| Redlock          | 多个独立主节点，多数派获取租约 | 须评估租期、时钟漂移、网络延迟与进程暂停假设     |
| Fencing Token    | 下游拒绝旧令牌操作             | 下游支持原子校验，生成器在故障下仍保证顺序       |

Redlock 不把同一主节点的副本当作独立投票节点。例如 5 个独立主节点中至少 3 个获取成功，且总获取耗时小于租期，才认为成功；可用时间还要扣去获取耗时和时钟漂移余量。失败时应清理已经获得的局部锁。其安全性依赖时间与故障假设，对这些假设是否适合真实系统存在争议；它不是无条件的共识或外部写入保护。算法、续租与争议链接见 [官方锁文档](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。缓存重建中的适用取舍见 [第 27 章](/articles/redis-cache-patterns.html)。

## 3. 限流先定义窗口和失败策略

限流管理请求预算。实现前先写清楚按用户、接口还是租户计数，窗口多长，超出如何拒绝，Redis 不可用时放行还是收紧。

| 算法                                     | 工作方式                     | 取舍                             |
| ---------------------------------------- | ---------------------------- | -------------------------------- |
| Fixed Window（固定窗口）                 | 每个固定时间段独立计数       | 简单，边界可能突发               |
| Sliding Window Log（滑动窗口日志）       | 保存请求时间，剔除窗口外记录 | 时间判断精确，请求多时存储成本高 |
| Sliding Window Counter（滑动窗口计数器） | 按时间比例组合前后窗口计数   | 成本较低，存在近似误差           |
| Token Bucket（令牌桶）                   | 按速率补充令牌，请求消耗令牌 | 桶容量允许一定突发               |
| Leaky Bucket（漏桶）                     | 请求入队，按固定速率处理     | 平滑输出，须限制队列与等待时间   |

例如每秒最多 10 次，00:00:00.990 的 10 次与 00:00:01.010 的 10 次分别属于两个固定窗口，20 毫秒内仍可能通过 20 次。这是教学假设；选择算法前先确认业务是否允许这种边界突发。

INCR 负责计数，EXPIRE 负责清理过期窗口；分开发送可能在递增后进程崩溃，留下无期限键。Redis Open Source 7.2.0 可用以下事务，四条命令必须在同一连接执行：

```redis
MULTI
INCR rate:user:1001:minute:123
EXPIRE rate:user:1001:minute:123 120
EXEC
```

`123` 是教学窗口编号，实际由应用根据当前时间计算分钟编号，再组成键名，不是 Redis 自动替换的变量。EXEC 执行这组命令时不插入其他客户端命令；应用读取返回数组中的计数决定是否超过预算。每次命中都刷新 120 秒 TTL，这只是旧桶的清理期限，逻辑窗口仍由键中的分钟编号决定，并非“120 秒限流窗口”。

事务适合步骤已确定的组合；若希望“仅第一次递增时设期限”，可用 Lua 在服务端根据结果判断。下面是脚本正文，调用格式为 `EVAL "脚本正文" 1 rate:user:1001:minute:123 120`，需将占位正文替换为代码：

```lua
local ttl = tonumber(ARGV[1])
if not ttl or ttl <= 0 or ttl ~= math.floor(ttl) or ttl > 86400 then
    return redis.error_reply('invalid window seconds')
end
local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('EXPIRE', KEYS[1], ttl)
end
return count
```

86400 是教学参数上限。Lua 避免其他命令在递增与设期限之间插入，但事务和 Lua 都不提供传统数据库式的自动回滚：执行期出错时，先前写入可能已生效。因此先校验参数、约束键类型并检查返回结果。已有的无期限旧计数键也不会被此脚本自动修复。参见 [INCR 限流示例](https://redis.io/docs/latest/commands/incr/) 与 [事务错误语义](https://redis.io/docs/latest/develop/using-commands/transactions/)。Redis Cluster 中，多 Key 脚本访问的键必须在同一哈希槽；将键通过 KEYS 显式传入，不能把任意跨槽业务塞进一个脚本。

Redis Open Source 8.8.0 起，[INCREX](https://redis.io/docs/latest/commands/increx/) 可以在单条命令中组合递增、数值边界和过期控制：

```redis
INCREX rate:user:1001:second-demo BYINT 1 UBOUND 10 EX 1 ENX
```

`UBOUND 10` 允许结果等于 10；默认超出上界时跳过整个更新，而不是把值截断。`EX 1` 指定一秒期限；`ENX` 表示仅在键当前没有过期时间时设置期限，已有 TTL 时仍可递增，但不刷新期限，并非“只允许新建键”。ENX 必须与 EX/PX/EXAT/PXAT 一类到期参数配合使用。

整数模式返回二元素数组 `[新值, 实际增量]`，第二项不是成功布尔值。在同一秒租期内，从不存在开始前十次的预期返回为 `[1,1]` 至 `[10,1]`，后续为 `[10,0]`，应用据实际增量为 0 拒绝请求；跳过更新也不修改 TTL。这里是从首次请求开始的一秒计数周期，不等同于按整秒对齐的固定窗口。定义与边界已对照 [8.8.0 t_string.c](https://github.com/redis/redis/blob/8.8.0/src/t_string.c)；需要旧版本兼容时保留 Lua 方案，勿将此命令发往 Redis Open Source 7.x。各版本能力与升级检查方法见 [第 32 章](/articles/redis-upgrade-validation.html)。

超时重试还可能重复扣减配额。若限流与业务请求要求精确对应，需要请求去重设计；近似限流则应明确允许的误差，而不是声称有原子计数就能精确一次。

## 4. 幂等是业务结果约束

为请求附上唯一编号，还不足以保证幂等。系统需要原子地决定由谁执行，记录处理中与完成状态，并设计好处理进程崩溃、记录过期、结果查询失败和跨系统提交时的应对方式。

Idempotency Key（幂等键）标识一次逻辑业务请求，作用域应包含租户或用户、接口与请求编号，并保存请求内容摘要。同一键带来不同金额或不同商品时应拒绝复用，不能直接返回另一份请求的结果。以下是业务协议的教学状态机，不是 Redis 内置状态：

```text
请求 → 检查幂等键及请求摘要
  已成功：返回原结果；处理中：等待或查询；内容冲突：拒绝
  不存在：原子创建 PENDING → 执行业务 → 保存结果 → 标记 SUCCEEDED
  明确失败：FAILED；提交结果不明：UNKNOWN → 查询权威系统后恢复状态
```

| 状态                | 含义                     | 重试处理                             |
| ------------------- | ------------------------ | ------------------------------------ |
| PENDING（处理中）   | 已有执行者，结果尚未确定 | 等待、查询；不能因等待超时就并行重做 |
| SUCCEEDED（已成功） | 已确认业务提交并保存结果 | 返回原结果                           |
| FAILED（已失败）    | 已确认失败               | 按业务规则决定能否重新尝试           |
| UNKNOWN（结果未知） | 无法判断是否提交         | 查权威系统，避免盲目重试             |

例如用户 42 重复提交同一订单：幂等作用域为“用户 42 + 创建订单接口 + 请求编号”，摘要包含商品与金额；数据库对该业务请求设唯一约束，在事务内创建订单并保存请求对应关系。若数据库已提交、Redis 状态尚未更新就崩溃，恢复者先按唯一请求编号查订单，回填结果，不再生成第二张订单。跨系统通知可用事务发件箱（Transactional Outbox，在数据库同一事务内记录待发事件）等可靠协议衔接，不能把缓存写成功当作数据库提交证明。

例如数据库已经成功提交，去重键却因 Redis 故障丢失，再次请求仍可能重复扣款。关键财务或唯一业务状态应利用权威系统的唯一约束、事务或专门协议，不将可淘汰缓存作为唯一防线。

去重记录 TTL 至少应覆盖约定的重试、补偿和消息重投周期；过期或淘汰意味着 Redis 可能遗忘请求，权威系统仍须阻止重复副作用。幂等允许多次尝试产生可控、可恢复且不重复提交的业务效果，不等于 Exactly-once（恰好一次执行）。消息认领和重投也会触发这一问题，见 [第 12 章 Streams](/articles/redis-streams.html)。

三者可组合：订单接口先限流控制预算，再用租约减少并发竞争，最终由幂等协议与数据库约束控制订单结果。锁不能替代幂等，限流也不能识别重复订单。锁键、计数键的访问权限应限制到业务所需范围，见 [第 31 章安全边界](/articles/redis-security-maintenance.html)。

学习时可沿获取资格前、获取后未写、外部提交后未确认、确认后回复丢失四个阶段，分别记录权威状态与可采取的恢复动作。这样可以将锁的资格管理和业务的效果管理联系起来。
