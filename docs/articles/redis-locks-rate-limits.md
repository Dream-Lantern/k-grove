# 第二十八章 锁、限流与业务幂等

[返回本册目录](/collections/redis/)

单条原子命令可以直接当积木，拼出三类东西：锁管的是“这一刻谁有资格操作”，限流管的是“一段时间内允许进来多少次”，幂等管的是“同一件事重复提交也只生效一次”。三者解决的不是同一个问题，实际设计还要各自考虑期限、并发和失败后怎么恢复。本章用教学流程说明它们如何组合使用。

## 1. 带期限的锁更像租约

租约（Lease）是有期限的访问资格。TTL（Time To Live，存活时间）让持有者崩溃后锁能到期释放，但不会终止持有者的业务进程。下面是 Redis 命令，与 Shell（命令解释环境）或客户端方法不同；本章命令和预期返回均为教学示例。基础示例适用于 Redis Open Source 7.2.0，新命令另标版本，Redis Software 或 Redis Cloud 的能力另行确认。

```redis
# 仅当键 lock:order:1001 不存在时写入 unique-token；NX 不满足时返回 nil，成功返回 OK
# PX 30000 设置键的 TTL，单位毫秒；unique-token 应替换为本次持有者唯一标识
SET lock:order:1001 unique-token NX PX 30000
```

`lock:order:1001` 是订单 1001 的锁键（Key）；值 `unique-token` 是本次获取的唯一标识，占位值必须换成每次获取新生成的随机值；所有客户端共用同一个值，会让持有者身份失去区分度。`NX` 只在键不存在时写入，`PX 30000` 同时设置 30000 毫秒租期。成功预期返回 `OK`，键已存在时预期返回 `nil`；网络超时后写入结果未知。获取与设期限在一条命令内完成，见 [SET](https://redis.io/docs/latest/commands/set/)。

续租需要核对所有权。原子性（Atomicity）在这里表示比较和修改期间不会插入其他客户端命令；先 GET、再单独 PEXPIRE 仍有竞态。下面是 Lua 服务端脚本正文，`KEYS[1]` 为锁键，`ARGV[1]` 为本次标识，`ARGV[2]` 为新的正整数毫秒租期：

```lua
-- KEYS[1] 为锁键；ARGV[1] 为本次持有标识；ARGV[2] 为续租毫秒数。
local ttl = tonumber(ARGV[2])
if not ttl or ttl <= 0 or ttl ~= math.floor(ttl) or ttl > 300000 then
    return redis.error_reply('invalid lease milliseconds')
end
-- GET 读取锁持有标识；只有匹配才用 PEXPIRE 更新该键的 TTL，单位毫秒。
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('PEXPIRE', KEYS[1], ttl)
end
return 0
```

300000 是此教学脚本自定的租期上限，Redis 本身没有这个限制。传入 `30000` 可续租 30 秒；返回 1 表示已续租，0 表示键不存在或标识不匹配。可用 `EVAL "脚本正文" 1 lock:order:1001 unique-token 30000` 调用，其中“脚本正文”需替换为上面完整代码，这一行是调用格式示意。参数验证放在写入前，续租命令参见 [PEXPIRE](https://redis.io/docs/latest/commands/pexpire/)。

续租返回 0、出错或超时后，业务应立即按失锁处理：停止发起新的外部副作用，尽可能取消未提交任务；已经提交但结果不明的操作应查询权威系统并对账。业务耗时超过租期同样按失去资格处理，事后补续租也补不回已经失去的独占资格。重复续租还要设业务总时限。

释放时也应在同一原子操作中比较标识后再删除，防止旧持有者误删别人后来获得的锁。保留下面的 Lua 解锁逻辑：

```lua
-- 教学解锁逻辑：KEYS[1] 是锁键，ARGV[1] 是本次持有标识
if redis.call('GET', KEYS[1]) == ARGV[1] then
    -- DEL 删除匹配的锁键；返回删除数，未匹配则走下面的 return 0。
    return redis.call('DEL', KEYS[1])
end
return 0
```

先 GET、在应用中比较、再 DEL 存在竞态：比较后、删除前锁可能已经到期并被另一请求获得。上面脚本解决这项竞态，其他锁问题仍需另行处理。[官方分布式锁讨论](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

Redis Open Source 8.4.0 起可用 [DELEX](https://redis.io/docs/latest/commands/delex/) 原生执行条件删除，Redis Open Source 7.x 继续使用 Lua：

```redis
# 仅当锁键 lock:order:1001 的值等于 unique-token 时删除；IFEQ 指定相等条件，unique-token 是本次持有标识（Redis 8.4+）
DELEX lock:order:1001 IFEQ unique-token
```

`IFEQ` 要求当前值等于本次标识。预期返回 1 表示已删除，0 表示键不存在或值不匹配；对非 String 键使用此条件会报类型错误。两种实现都必须比较本次标识。Lua 的 EVAL 自 Redis Open Source 2.6.0 提供，执行期间会阻塞其他命令，出错后也没有自动回滚；脚本应短小，详见 [第 18 章 Lua](/articles/redis-transactions-lua-functions.html) 和 [7.2.0 EVAL 定义](https://github.com/redis/redis/blob/7.2.0/src/commands/eval.json)。

## 2. 租约交接后的迟到操作与 Fencing {#_2-锁过期不会让旧进程停止}

![旧持有者恢复后的风险](/assets/notes/redis/redis-study-lease.svg)

请求 A 暂停超过租期后，B 可以获得新锁。A 恢复时仍可能继续向数据库或对象存储写入。唯一锁值只解决释放资格的识别，外部系统拒绝 A 的旧写需要另加机制。

Fencing Token（栅栏令牌）是每次发放访问资格时附带的一个递增编号，比如 41、42、43。下游系统记住自己见过的最大编号，收到更小的编号就拒绝，于是暂停后恢复的旧持有者写不进去。教学推演如下，令牌生成服务是假定满足故障下单调性的独立机制，与 SET 的返回值无关：

```text
A 获取租约，取得令牌 41 → A 暂停超过租期 → Redis 锁到期
B 获取新租约，取得令牌 42 → B 写数据库，数据库原子记录最大令牌 42
A 恢复，用令牌 41 写数据库 → 数据库比较 41 < 42，拒绝旧操作
```

唯一锁标识用于识别“是谁”，与资格的新旧顺序无关；Fencing Token 用于比较顺序，下游必须把令牌校验、最大值更新和业务写入原子地结合。令牌生成器还必须在目标故障模型下保持单调。Redis INCR 在单实例递增，并不自动构成完整的分布式令牌服务：如果异步复制故障转移丢失最新计数，新主节点可能重新发出旧值，跨故障的严格递增没有保证。

默认异步主从复制还存在另一条失败路径：

```text
t1：A 在主节点成功写入锁并收到成功回复
t2：锁尚未复制到副本
t3：主节点故障
t4：副本晋升为新主节点
t5：B 在新主节点成功获得同一把锁
t6：A 未停止业务，A、B 可能同时执行
```

主节点返回成功只说明主节点写入完成，副本是否收到要看复制进度；简单的主从切换可能丢失最新锁状态。以下方案解决的问题不同，安全性不能只按节点数量判断：

| 方案             | 工作方式                       | 适用条件与边界                                   |
| ---------------- | ------------------------------ | ------------------------------------------------ |
| 单实例 SET NX PX | 一处管理有期限的资格           | 能接受实例故障、暂停等风险；业务须在有效期内完成 |
| 主从复制锁       | 增加副本与故障转移             | 接受异步复制丢写带来的互斥风险                   |
| Redlock          | 多个独立主节点，多数派获取租约 | 须评估租期、时钟漂移、网络延迟与进程暂停假设     |
| Fencing Token    | 下游拒绝旧令牌操作             | 下游支持原子校验，生成器在故障下仍保证顺序       |

Redlock 要求各主节点相互独立，同一主节点的副本不计入投票。例如 5 个独立主节点中至少 3 个获取成功，且总获取耗时小于租期，才认为成功；可用时间还要扣去获取耗时和时钟漂移余量。失败时应清理已经获得的局部锁。其安全性依赖时间与故障假设，这些假设是否适合真实系统存在争议；它提供的是租约互斥，共识与外部写入保护要另找机制。算法、续租与争议链接见 [官方锁文档](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。缓存重建中的适用取舍见 [第 27 章](/articles/redis-cache-patterns.html)。

## 3. 限流先定义窗口和失败策略

限流就是给请求数量定一个上限，超出就拦。动手之前先回答四个问题：按用户、接口还是租户计数；这个上限在多长的时间窗内算；超了是拒绝还是排队；Redis 本身不可用时，是放行还是收紧。

| 算法                                     | 工作方式                     | 取舍                             |
| ---------------------------------------- | ---------------------------- | -------------------------------- |
| Fixed Window（固定窗口）                 | 每个固定时间段独立计数       | 简单，边界可能突发               |
| Sliding Window Log（滑动窗口日志）       | 保存请求时间，剔除窗口外记录 | 时间判断精确，请求多时存储成本高 |
| Sliding Window Counter（滑动窗口计数器） | 按时间比例组合前后窗口计数   | 成本较低，存在近似误差           |
| Token Bucket（令牌桶）                   | 按速率补充令牌，请求消耗令牌 | 桶容量允许一定突发               |
| Leaky Bucket（漏桶）                     | 请求入队，按固定速率处理     | 平滑输出，须限制队列与等待时间   |

例如每秒最多 10 次，00:00:00.990 的 10 次与 00:00:01.010 的 10 次分别属于两个固定窗口，20 毫秒内仍可能通过 20 次。这是教学假设；选择算法前先确认业务是否允许这种边界突发。

INCR 负责计数，EXPIRE 负责清理过期窗口；分开发送可能在递增后进程崩溃，留下无期限键。Redis Open Source 7.2.0 可用以下事务，四条命令必须在同一连接执行：

```redis
# 开始当前连接的事务队列；无额外参数，后续命令先入队，等待 EXEC 执行
MULTI
# 将整数计数键 rate:user:1001:minute:123 增加 1；键不存在从 0 开始，返回计算后的值
INCR rate:user:1001:minute:123
# 为键 rate:user:1001:minute:123 设置 120 秒 TTL；从本次执行时刻计时，成功返回 1，键不存在返回 0
EXPIRE rate:user:1001:minute:123 120
# 执行当前连接中已入队的事务命令；无额外参数，返回逐条结果；WATCH 冲突时返回空结果，执行期错误不会回滚其他命令
EXEC
```

`123` 是教学窗口编号，实际由应用根据当前时间计算分钟编号，再组成键名；Redis 不会自动替换这个编号。EXEC 执行这组命令时不插入其他客户端命令；应用读取返回数组中的计数决定是否超过预算。每次命中都刷新 120 秒 TTL，这只是旧桶的清理期限，逻辑窗口仍由键中的分钟编号决定，与“120 秒限流窗口”不是一回事。

事务适合步骤已确定的组合；若希望“仅第一次递增时设期限”，可用 Lua 在服务端根据结果判断。下面是脚本正文，调用格式为 `EVAL "脚本正文" 1 rate:user:1001:minute:123 120`，需将占位正文替换为代码：

```lua
-- KEYS[1] 是计数键；ARGV[1] 是窗口 TTL，单位秒。
local ttl = tonumber(ARGV[1])
if not ttl or ttl <= 0 or ttl ~= math.floor(ttl) or ttl > 86400 then
    return redis.error_reply('invalid window seconds')
end
-- INCR 将计数加 1，键不存在从 0 开始；只有首次计数时用 EXPIRE 设置秒级期限。
local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('EXPIRE', KEYS[1], ttl)
end
return count
```

86400 是教学参数上限。Lua 避免其他命令在递增与设期限之间插入，事务和 Lua 都没有传统数据库式的自动回滚：执行期出错时，先前写入可能已生效。因此先校验参数、约束键类型并检查返回结果。已有的无期限旧计数键，此脚本也不会修复。参见 [INCR 限流示例](https://redis.io/docs/latest/commands/incr/) 与 [事务错误语义](https://redis.io/docs/latest/develop/using-commands/transactions/)。Redis Cluster 中，多 Key 脚本访问的键必须在同一哈希槽；将键通过 KEYS 显式传入；跨槽业务要拆到多个脚本或改用其他结构。

Redis Open Source 8.8.0 起，[INCREX](https://redis.io/docs/latest/commands/increx/) 可以在单条命令中组合递增、数值边界和过期控制：

```redis
# 原子增加整数计数键 rate:user:1001:second-demo；BYINT 1 加 1，UBOUND 10 限制结果不超过 10（Redis 8.8+）
# EX 1 指定秒数，ENX 仅在键无 TTL 时设置期限；返回 [新值, 实际增量]，超界默认返回 [当前值, 0]
INCREX rate:user:1001:second-demo BYINT 1 UBOUND 10 EX 1 ENX
```

`UBOUND 10` 允许结果等于 10；默认超出上界时跳过整个更新，值不会被截断。`EX 1` 指定一秒期限；`ENX` 表示仅在键当前没有过期时间时设置期限，已有 TTL 时仍可递增，但不刷新期限，与“只允许新建键”不是一回事。ENX 必须与 EX/PX/EXAT/PXAT 一类到期参数配合使用。

整数模式返回二元素数组 `[新值, 实际增量]`，第二项是实际增量，与成功布尔值不同。在同一秒租期内，从不存在开始前十次的预期返回为 `[1,1]` 至 `[10,1]`，后续为 `[10,0]`，应用据实际增量为 0 拒绝请求；跳过更新也不修改 TTL。这里是从首次请求开始的一秒计数周期，与按整秒对齐的固定窗口不同。定义与边界已对照 [8.8.0 t_string.c](https://github.com/redis/redis/blob/8.8.0/src/t_string.c)；需要旧版本兼容时保留 Lua 方案；Redis Open Source 7.x 没有此命令。各版本能力与升级检查方法见 [第 32 章](/articles/redis-upgrade-validation.html)。

超时重试还可能重复扣减配额。若限流与业务请求要求精确对应，需要请求去重设计；近似限流则应明确允许的误差，原子计数本身不等于精确一次。

## 4. 幂等是业务结果约束

为请求附上唯一编号，只是幂等的起点。系统需要原子地决定由谁执行，记录处理中与完成状态，并设计好处理进程崩溃、记录过期、结果查询失败和跨系统提交时的应对方式。

Idempotency Key（幂等键）是给“一次业务请求”发的编号：客户端重试时带同一个编号，服务端就能认出这是同一件事，而不是两件。键的作用域要包含租户或用户、接口和请求编号，并额外保存请求内容的摘要。同一键带来不同金额或不同商品时应拒绝复用，直接返回另一份请求的结果会造成串单。以下是业务协议的教学状态机，这套状态由应用维护，Redis 只提供存储原语：

```text
请求 → 检查幂等键及请求摘要
  已成功：返回原结果；处理中：等待或查询；内容冲突：拒绝
  不存在：原子创建 PENDING → 执行业务 → 保存结果 → 标记 SUCCEEDED
  明确失败：FAILED；提交结果不明：UNKNOWN → 查询权威系统后恢复状态
```

| 状态                | 含义                     | 重试处理                                         |
| ------------------- | ------------------------ | ------------------------------------------------ |
| PENDING（处理中）   | 已有执行者，结果尚未确定 | 等待、查询；等待超时后并行重做会产生第二个执行者 |
| SUCCEEDED（已成功） | 已确认业务提交并保存结果 | 返回原结果                                       |
| FAILED（已失败）    | 已确认失败               | 按业务规则决定能否重新尝试                       |
| UNKNOWN（结果未知） | 无法判断是否提交         | 查权威系统，避免盲目重试                         |

例如用户 42 重复提交同一订单：幂等作用域为“用户 42 + 创建订单接口 + 请求编号”，摘要包含商品与金额；数据库对该业务请求设唯一约束，在事务内创建订单并保存请求对应关系。若数据库已提交、Redis 状态尚未更新就崩溃，恢复者先按唯一请求编号查订单，回填结果，不再生成第二张订单。跨系统通知可用事务发件箱（Transactional Outbox，在数据库同一事务内记录待发事件）等可靠协议衔接，缓存写成功与数据库提交是两件事。

例如数据库已经成功提交，去重键却因 Redis 故障丢失，再次请求仍可能重复扣款。关键财务或唯一业务状态应利用权威系统的唯一约束、事务或专门协议，可淘汰缓存承担不了唯一防线的角色。

去重记录 TTL 至少应覆盖约定的重试、补偿和消息重投周期；过期或淘汰意味着 Redis 可能遗忘请求，权威系统仍须阻止重复副作用。幂等保证的是：同一个请求做多少次，业务结果都和做一次相同，但它不限制这件事实际被执行了几遍；Exactly-once（恰好一次执行）要求业务效果确实只发生一次。前者靠业务侧去重就能做到，后者需要更强的机制配合。消息认领和重投也会触发这一问题，见 [第 12 章 Streams](/articles/redis-streams.html)。

三者可组合：订单接口先限流控制预算，再用租约减少并发竞争，最终由幂等协议与数据库约束控制订单结果。锁解决互斥，幂等解决重复，限流识别不了重复订单。锁键、计数键的访问权限应限制到业务所需范围，见 [第 31 章安全边界](/articles/redis-security-maintenance.html)。

学习时可以按四个阶段分别问一遍“权威状态是什么、能做什么”：还没拿到资格时；拿到了但还没写外部系统时；外部系统已提交、本地还没确认时；确认已经做完、回复却丢了时。把每个阶段答清楚，锁的资格管理和业务效果管理才对得上。
