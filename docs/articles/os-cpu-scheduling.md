# 第七章 CPU 调度与 Linux 0.11 复盘

> 阅读标签：教学调度算法 / 0.11源码 / 现代Linux旁注。

调度是在当前可运行的实体中，选择由谁使用 CPU。评价算法需要先明确目标：交互响应、平均周转、公平、吞吐和截止期不一定能同时达到最优。“先来先服务很公平”并不足以评价所有工作负载。

## 1. 先定义三个时间指标

响应时间关心提交到首次得到服务的延迟；周转时间关心从提交到完成；等待时间关心处于可运行却未执行的时间。阻塞等待设备与等 CPU 不能无条件混成一个数。

![从可运行状态到策略选择](/assets/notes/operating-systems/os-schedule.svg)

纸面算例：两个同时到达、单 CPU、无 I/O 的任务，A 运行 8 单位，B 运行 2 单位。FCFS 先 A 后 B，平均周转为 (8+10)/2=9；若先 B 后 A，为 (2+10)/2=6。这个纸面模型解释短任务优先的目标，不是实测或通用上限。

## 2. FCFS、SJF 与 RR

FCFS 实现简单，但长任务可能延迟后续短任务；SJF 依赖运行时长估计，还需处理长任务饥饿；RR 通过时间片轮转改善首次响应，但时间片过短会增加切换成本，过长则接近 FCFS。

是否抢占、到达时间和 I/O 行为都会改变结果。不能由 RR 的名称推出所有请求的硬实时响应界，也不能说 SJF 天然等于公平。

## 3. 0.11 的 counter 怎样使用？

在已核对的 kernel/sched.c 中，从适用的 TASK_RUNNING 任务里选择 counter 最大者；当需要重新分配时，对存在的任务执行类似 counter=(counter>>1)+priority 的更新，再尝试选择。

counter 兼具剩余时间预算与历史调整的含义，不是每次 I/O 完成就直接执行固定加分。阻塞任务可能在重算时保留部分旧预算，这有助于解释某些交互倾向，但不意味着其优先级必然高于所有 CPU 密集任务。

配合`do_timer`看三条历史：用户态运行时counter耗尽，会沿该时钟路径调用schedule；内核态运行时耗尽，则因CPL检查返回，不在该处直接调度；内核等待I/O时可沿显式阻塞路径调度。因此预算耗尽与实际切换不是在所有上下文中同一个瞬间。这里讨论原版0.11，不代表现代所有抢占配置。

## 4. 原笔记伪代码为什么不能直接编译？

数组指针前移、空项检查、变量名称和循环边界都会影响程序行为。原笔记遗漏了部分指针移动，并混用了指针与成员访问，无法原样作为源码运行；新稿保留算法解释，不将这些不完整片段写成可运行程序。

```text
检查需要唤醒的任务
循环扫描可运行任务，寻找最大 counter
若存在可继续运行的预算，选择相应任务
否则按历史规则重算预算并再次扫描
切换到选择的任务；无普通可运行任务时处理空闲路径
```

## 5. 现代 Linux 不再沿用这一个公式

现代内核有多个调度类别、多核负载与资源控制。公平调度从 CFS 路线继续演进，Linux 6.6 起引入 EEVDF 相关变化；不能把 0.11、CFS 和所有最新版本合称同一种算法。[官方 EEVDF 说明](https://docs.kernel.org/scheduler/sched-eevdf.html)

新机制关注 eligibility、虚拟截止期等条件，但本册不把滚动文档的每个实现细节反推为用户当前内核参数。研究性能先记录实际版本、调度策略、核数、亲和性和负载，再解释运行队列与等待。
