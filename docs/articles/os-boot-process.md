# 第二章 从引导到首个进程

> 阅读标签：Linux0.11 / x86历史启动案例。

电脑刚开机时，还没有可供应用调用的文件系统和调度器。谁把内核放入内存，又是谁为它准备栈和地址环境？启动过程就是逐步建立这些条件，再把控制权交给下一阶段。本章沿 **Linux 0.11、80386 及兼容 PC BIOS 启动环境**追踪这条路线，现代 UEFI 平台另有启动协议。

## 1. 从初始环境到内核运行环境 {#_1-启动前-cpu-不是已经处在普通应用环境}

BIOS（Basic Input/Output System，基本输入输出系统）是此历史 PC 环境中的固件。它完成早期硬件准备，把启动扇区装入物理地址 `0x7c00`，并将控制权交给其中的 `bootsect`。此时只有很小的一段引导代码，完整内核还需要从启动介质装入。

[![Linux 0.11：从 bootsect 到 main](/assets/notes/operating-systems/os-boot.svg)](/assets/notes/operating-systems/os-boot.svg)

沿下面的状态表阅读代码，可以看出这些阶段为什么不能任意交换：

| 阶段                      | CPU 模式与分页状态          | 本阶段结果及下一跳                                               |
| ------------------------- | --------------------------- | ---------------------------------------------------------------- |
| BIOS → `boot/bootsect.s`  | 实模式；未启用分页          | 引导扇区已在内存，开始装载其余代码                               |
| `bootsect.s`              | 实模式；未启用分页          | 搬移自身、建立栈，装入 setup 和 system，远跳转到 setup           |
| `boot/setup.s`            | 实模式 → 保护模式；仍未分页 | 保存 BIOS 参数、搬移 system、准备描述符与硬件，远跳转到 `head.s` |
| `boot/head.s`             | 32 位保护模式；随后启用分页 | 建立早期栈、GDT、IDT 和页表，经 `ret` 进入 `_main`               |
| `init/main.c` 的 `main()` | 初始为内核态；分页已启用    | 初始化子系统，转入用户态，首次 fork 创建任务 1                   |

### 实模式、保护模式与分页解决不同问题

**实模式（Real Mode）**保留了早期 x86 的编程环境。在这里，常规地址由“段值 × 16 + 偏移”形成；传统 20 位地址空间为 1 MiB，A20 地址线状态还会影响高端地址是否回绕。它没有保护模式的分段特权隔离，也没有分页机制。Linux 0.11 在这个环境中利用 BIOS 服务读取磁盘和查询硬件，随后再建立自己的运行环境。

**保护模式（Protected Mode）**让处理器按照段描述符解释地址并检查权限，也支持本章所需的 32 位代码段。为了使用超过传统实模式范围的内存并建立受保护的任务环境，`setup.s` 准备好描述符后切入此模式。**分页（Paging）**则进一步把线性地址映射到物理地址，由页目录、页表及相关控制寄存器决定。进入保护模式不等于启用分页；本例直到 `head.s` 后半段才打开分页。

这些是特定启动路线的前提。C 代码需要满足编译目标的执行约定，例如可用栈与正确的地址环境，但不能由此得出“所有架构都必须先分页才能执行 C”。x86 模式、分段和分页可对照 [Intel 架构手册](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)的 Volume 3A：Protected-Mode Memory Management、Protection 和 Paging。

## 2. bootsect 与 setup 的装载和准备工作 {#_2-bootsect-与-setup-关注什么}

`bootsect.s` 先把自身从 `0x7c00` 搬到 `0x90000`，跳到搬移后的代码，设置段寄存器和栈。这样后续装载、搬移内核时就不容易覆盖仍在执行的引导代码。它通过 BIOS 磁盘服务把 4 个扇区的 setup 装到 `0x90200`，把 system 装到 `0x10000`，最后执行 `jmpi 0,SETUPSEG` 进入 setup。源码对某些读盘失败会复位并重试；因此“调用过读取”不代表一定能进入下一阶段。

这里的 system 是构建镜像中的内核主体，不是现代的 systemd。地址均为本例历史内存布局；实模式段值 `0x9020` 对应物理基址 `0x90200`，两者不能混写。

`setup.s` 接着完成以下依赖链：

1. 仍在实模式下调用 BIOS，取得内存、显示、硬盘等参数，保存在 `0x90000` 一带，留给内核读取。切换环境后不再沿用这套 BIOS 调用路径。
2. 执行 `cli` 禁止可屏蔽中断，在 `do_move` 循环中把 system 从 `0x10000` 一带向低地址搬移，使内核入口位于地址 `0`。
3. 装入早期 GDT；此时装入的 IDT 长度限制值为 `0`，不是可供正常异常处理中断使用的完整表。随后开启 A20 地址线，避免访问 `1 MiB` 以上地址时发生传统地址回绕，并重新编程、屏蔽 8259A 中断控制器。
4. 用 `lmsw ax` 设置 CR0 的 PE（Protection Enable，保护使能）位，再执行 `jmpi 0,8`。这里的 `8` 是代码段选择子，指向 GDT 中的代码段描述符；远跳转装入相应代码段状态，在地址 `0` 开始执行 32 位的 `startup_32`。

因此，**保护模式切换发生在 setup 的末尾，head 开始时已经处于保护模式**。A20 开启、保护模式切换和分页启用是三个不同操作。

本册不提供写启动扇区、修改固件或重装引导的命令。源码阅读中的“磁盘”“段地址”也不能直接对应用户电脑上的 C、D 盘分区。

## 3. head.s 为 C 入口建立执行条件 {#_3-head-s-为什么在-main-前}

`head.s` 的 `startup_32` 接过的是已经装入低地址的内核。它先设置数据段寄存器，并用 `lss _stack_start,%esp` 装入栈指针与栈段，使后面的 `call`、`push` 和返回操作有明确的存放位置。

| 结构                                            | 解决什么问题                           | Linux 0.11 此时做什么                                 |
| ----------------------------------------------- | -------------------------------------- | ----------------------------------------------------- |
| GDT（Global Descriptor Table，全局描述符表）    | 段从哪里开始、可访问多大范围、有何权限 | `setup_gdt` 装入内核使用的 GDT，替换 setup 的早期表   |
| IDT（Interrupt Descriptor Table，中断描述符表） | 中断或异常应进入哪个处理入口           | `setup_idt` 建立 256 个默认入口，先指向 `ignore_int`  |
| 栈（Stack）                                     | 函数返回地址、参数和临时状态放在哪里   | `_stack_start` 提供早期栈；不能误认为分页自动创建了栈 |
| 页目录与页表                                    | 开启分页后，线性地址如何找到物理内存   | `setup_paging` 建立初始映射，供 CPU 地址转换使用      |

默认 IDT 是过渡设施，不代表缺页、设备中断等专门处理程序已经安装完成。`main()` 后续的 `trap_init()` 会安装相应异常入口；设备初始化与 `sched_init()` 还会设置各自所需入口。

在检查 A20 和协处理器相关状态后，代码跳到 `after_page_tables`。此处先把参数占位、`main` 的返回地址 `L6` 以及 `_main` 的地址压栈，再跳入 `setup_paging`。后者：

1. 清空页目录与 4 张页表所用的 5 个页面。
2. 建立低 16 MiB 的恒等映射，即这段范围内线性地址与物理地址数值相同；这不表示机器一定有 16 MiB 实际内存。
3. 将页目录地址写入 CR3，并设置 CR0 的 PG（Paging，分页）位。
4. 执行 `ret`，弹出事先压入的 `_main` 地址，从而进入 C 函数 `main()`。这里不是直接写一条 `call main`；若 `main` 返回，就会落到 `L6` 的循环中。

早期入口与页目录还复用了地址 `0` 一带的空间，部分已执行过的初始化代码会被页表覆盖。`after_page_tables` 等后续代码位于保留区域，不能把源码中这种布局技巧理解为“任意覆盖正在运行的代码”。

学习时，可以为每一步记录它为后续代码建立了哪些前提，例如“下一段代码使用什么地址”“发生异常跳到哪里”“当前栈在哪里”。这比单纯记忆汇编标签更有效。

## 4. main 初始化子系统并启动用户任务 {#_4-main-之后不是整个系统停在一个死循环}

`main()` 从 setup 保存的信息中取得根设备、硬盘与内存参数，划定缓冲区和主内存范围，再依次调用 `mem_init()`、`trap_init()`、设备与终端初始化、`sched_init()`、`buffer_init()` 等。此时才逐渐形成可供任务使用的内核服务；不能把这些后续初始化都归到 `head.s`。

**任务 0 不是 `main()` 新 fork 出来的进程**。`kernel/sched.c` 已静态定义 `init_task`，并让 `current` 和 `task[0]` 指向它。`sched_init()` 配置它所需的任务状态段等结构，并安装系统调用入口。随后 `main()` 执行 `sti()` 开启可屏蔽中断，再用 `move_to_user_mode()` 构造返回现场并执行 `iret`，转到用户态继续执行。

接下来的源码控制流如下；为便于阅读省略初始化代码，保留原有关键语句：

```c
move_to_user_mode();
if (!fork()) {
    init();
}
for (;;) pause();
```

`fork()` 用于创建新任务：正常情况下，父任务得到子任务的 PID，子任务得到 `0`。首次成功 fork 创建任务 1，只有子任务满足 `!fork()` 而调用 `init()`。父任务 0 留在 `pause()` 循环中；如果首次 fork 失败，也不会凭空产生任务 1，原源码注释明确说这里依赖创建成功。

[![任务 0、任务 1 与两个 shell 阶段](/assets/notes/operating-systems/os-boot-tasks.svg)](/assets/notes/operating-systems/os-boot-tasks.svg)

图中 `init()` 是**定义在内核源码 `init/main.c`、但在这条启动路线中由任务 1 于用户态执行的函数**，不能因为源码位置就认为它始终运行在内核态。它调用 `setup()` 系统调用完成硬盘分区、根文件系统等设置，打开 `/dev/tty0`，并通过 `dup()` 建立标准输入、输出、错误描述符，然后：

1. 再 fork 一个子任务，让子任务将 `/etc/rc` 打开为标准输入，`execve("/bin/sh", ...)` 执行 shell，由 shell 读取启动脚本。`execve` 替换当前任务的程序映像，不是又创建一个任务；文件打开或执行失败会走退出分支。
2. 任务 1 等待这个子任务结束，然后循环创建面向终端的 shell 子任务。子任务通过 `setsid()` 建立会话、重新打开终端并执行 `/bin/sh`；任务 1 等待其退出、执行 `sync()`，随后重建 shell。

这里没有把任务 1 的初始 `init()` 直接替换为独立的 `/sbin/init` 或 systemd。现代 Linux 的 PID 1 通常是用户空间的 init 程序或服务管理器，不能把它们与此函数混为一谈。

任务 0 的 `pause()` 则是特殊的空闲行为。`schedule()` 找不到其他可运行任务时回到任务 0，而不要求它像普通等待任务一样必须先收到信号。循环仍在执行和让出调度机会，不等于 CPU 停止工作。为适应早期任务 0/1 的栈共享约束，该文件把 `fork`、`pause` 定义为内联系统调用；不能随意在父任务循环中加入普通函数调用。

## 5. 与现代启动的概念对照 {#_5-与现代启动怎样对照}

可以保留“固件/加载器 → 内核运行条件 → 内核初始化 → 用户空间管理程序”这组概念层次，但不能把 Linux 0.11 的文件名和布局照搬到现代系统。

| 路线                       | 简要控制流                                                     | 与本章的边界                                                                                                              |
| -------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 传统 BIOS 启动的现代 Linux | BIOS → 磁盘引导代码/加载器 → 内核                              | 加载器与镜像格式已经不同，不必逐个执行 0.11 的文件                                                                        |
| UEFI 启动                  | 固件启动管理器 → EFI 加载器，或带 EFI stub 的内核 → 内核初始化 | UEFI（Unified Extensible Firmware Interface，统一可扩展固件接口）定义不同的固件接口与装载协议，不等同于 BIOS 读取引导扇区 |

现代启动可能使用 initramfs（初始内存文件系统）作为早期根文件系统，再进入最终根文件系统与用户空间 init。它不是每种配置都必经的相同阶段。相关对照见 [Linux 6.12 x86 启动协议](https://docs.kernel.org/6.12/arch/x86/boot.html)与 [EFI Boot Stub](https://docs.kernel.org/6.12/admin-guide/efi-stub.html)。

具体 UEFI 配置、安全启动、initramfs 与系统管理器需要另外固定平台和版本。本文未验证这些现代启动细节，也未提供相应安装环境。

## 6. 只读源码追踪练习

使用 [kernel.org 的 Linux 0.11 原始源码包](https://www.kernel.org/pub/linux/kernel/Historic/old-versions/linux-0.11.tar.gz)，仅下载、解压到普通目录并用编辑器阅读即可。下面的路径相对于解压后的源码根目录；不需要编译旧内核或操作真实引导介质。

| 顺序 | 文件与定位词                                                                           | 要回答的问题                                                            |
| ---- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 1    | `boot/bootsect.s`：`start`、`load_setup`、`read_it`、`jmpi 0,SETUPSEG`                 | 自身、setup、system 分别装在哪里？读 setup 失败走哪条分支？             |
| 2    | `boot/setup.s`：`do_move`、`lgdt`、`lmsw`、`jmpi 0,8`                                  | 为什么先搬移内核并准备 GDT，再切换执行环境？哪条指令设置 PE？           |
| 3    | `boot/head.s`：`startup_32`、`setup_idt`、`setup_gdt`                                  | 哪条指令装入栈？早期 IDT 的各入口先指向哪里？                           |
| 4    | 同文件：`after_page_tables`、`setup_paging`                                            | `_main` 地址在哪里压栈？CR3 与 PG 位在哪里设置？`ret` 将进入哪里？      |
| 5    | `init/main.c`：`main`、`move_to_user_mode`、`init`                                     | 首次 fork 前处于什么特权状态？父子分支各执行什么？                      |
| 6    | `kernel/sched.c`：`init_task`、`schedule`；`include/asm/system.h`：`move_to_user_mode` | 任务 0 从哪里来？没有普通就绪任务时如何被选中？用户态返回现场如何构造？ |

最后写出两条状态线：一条标记 PE、PG 何时开启；另一条标记任务 0、任务 1、脚本 shell、交互 shell 的父子与等待关系。答案应能逐项指回源码标签，而不只复述流程图。本轮已核对上述原始源码，未编译或模拟启动 Linux 0.11。

## 本章小结

- bootsect 负责装载，setup 保存参数并切入保护模式，head 建立早期环境并启用分页。
- GDT 管段描述，IDT 管事件入口，页表管分页映射，栈保存调用与执行状态。
- 任务 0 是静态初始任务；首次成功 fork 创建任务 1，它在用户态执行源码中的 `init()`。
- 启动脚本和终端 shell 由任务 1 创建子任务并安排执行，任务 0 承担特殊空闲行为。
