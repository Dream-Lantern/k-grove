# 第十章 死锁条件、避免与恢复

> 阅读标签：通用死锁模型与教学算法。

死锁是相关活动相互等待、无法自行继续的状态；饥饿指某个活动长期得不到执行机会；活锁则表现为持续动作，却没有有效进展。三者现象可能相似，但处理方式不同。

## 1. 四个经典必要条件

在相应资源模型中，互斥、占有并等待、不可抢占、循环等待共同构成死锁的经典必要条件。描述“有两个线程等待”还不够，要明确它们各自持有什么、还需要什么。

[![死锁：资源分配图与循环等待](/assets/notes/operating-systems/os-deadlock.svg)](/assets/notes/operating-systems/os-deadlock.svg)

教学例子：A 持有 L1 请求 L2，B 持有 L2 请求 L1。两把锁各只有一个实例，且无法由外部安全解除，形成直接等待环。[OSTEP 并发问题](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-bugs.pdf)

## 2. 预防：事先破坏条件

统一加锁顺序可避免锁顺序形成环；一次申请全部资源可以避免部分占有后继续等待，但可能降低并发与利用率。不是所有资源都能安全抢占，也不是给锁加超时就自动修复已经做了一半的业务。

在复杂系统中，还需检查回调、异常和隐藏锁：函数表面上只获取 L1，但内部库若继续请求 L2，也可能与其他路径形成逆序加锁。

## 3. 避免：分配前检查安全序列 {#_3-避免-安全状态不是已发生死锁}

银行家类算法依赖已知最大需求，判断某次分配后是否仍存在让所有任务依次完成的安全序列。安全意味着在模型假设下有可完成的安排；不安全不意味着当下已经死锁，只是不能给出相应保证。

教学例子，单一资源总量 3：A、B 各持有 1，二者最大需求都是 2，剩余 1 可以让 A 完成再归还，从而让 B 完成。安全序列是一个证明，不是强制操作系统今后必须按 A→B 调度。

## 4. 检测：分析当前持有与请求关系 {#_4-检测与避免不是同一个算法调用}

检测关注当前请求、持有关系及能否推进。单实例资源的等待环可直接判定某类死锁；多实例资源有环并不总是充分条件，需要更细的资源分析。

银行家安全性检查依赖最大需求信息，适用于其资源模型；死锁检测则检查当前请求与持有关系。利用率低只能提供观察线索，没有负载或正常 I/O 等待也会产生这种现象。

## 5. 恢复：中止、回滚与受控重启 {#_5-恢复不能任意删除锁}

恢复时可考虑中止某个事务或任务、回滚到安全点，或受控重启，但前提是具备相应的清理与恢复能力。随意将共享锁变量改为未持有，可能使其他活动访问到损坏的中间数据。

选择受害者还要考虑已做工作、优先级、资源影响和反复被选的饥饿风险。真实内核与数据库可能采用不同机制，本章不对当前机器杀进程或强制解锁。
