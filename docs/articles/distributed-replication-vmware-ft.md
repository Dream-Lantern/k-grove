# 第七章 复制状态机与 VMware FT 历史设计

> 阅读标签：历史VMware FT / vSphere4.0时代论文。

复制通过传输状态、状态差异、日志或执行事件，让副本保有可用于继续服务的状态。快照常与日志配合：前者提供某个时点的状态，后者记录之后的变化。本章先区分状态复制与操作复制，再以历史 VMware FT 论文观察非确定性事件和外部输出的处理。

## 1. 状态复制与操作复制

状态传输可以发送完整快照，也可以只传变更，不局限于进程内存。操作复制让副本从相同初态处理相同有序操作；若状态转移是确定性的，才会得到相同结果。

| 机制 | 传递什么、如何追赶 | 本章中的位置 |
| --- | --- | --- |
| 状态传输（State Transfer） | 完整快照或状态增量，让备用节点获得某个边界的状态 | 可用于副本初始化与重建，之后仍可能需要日志追赶 |
| 确定性重放（Deterministic Replay） | 输入及必要的非确定性事件，让备用节点重现执行路径 | 历史 VMware FT 在主备（Primary/Backup）结构中复制 VM 执行 |
| 复制状态机（Replicated State Machine，RSM） | 从相同状态按同一命令顺序确定性执行；容错系统可用共识协议确定顺序 | Paxos/Raft 可维护命令选择或复制日志，再由副本应用命令 |

这三个概念并非互斥分类：状态机复制可结合快照传输，确定性重放也运用了状态机思想；它们强调的复制内容和实现层次不同。VMware FT 的日志通道（Logging Channel）传递 VM 输入、事件及重放所需信息，不是 Raft 的 `AppendEntries` 命令日志 RPC。机制对照依据见 [VMware FT §1～2](https://pdos.csail.mit.edu/6.824/papers/vm-ft.pdf) 与 [Paxos Made Simple §3](https://lamport.azurewebsites.net/pubs/paxos-simple.pdf)。

副本无需在同一物理时刻执行。只要按协议追赶，并且不以违反保证的旧状态对外服务，副本就可以暂时落后。这里要求的是相同的有效顺序与确定性解释，而非同一物理时刻执行。

## 2. 非确定性会改变重复执行的结果 {#_2-非确定性为什么需要处理}

教学例子：操作为“把当前时间写入订单”。若两个副本各自读取本机时间，它们收到相同请求也可能写出不同值。可以由权威端确定时间作为命令参数，或记录必要的非确定性结果，但不能让每个副本任意重算。

时间读取、定时器中断、I/O 完成时刻、网络输入和硬件相关的非确定性行为，都可能让相同请求走出不同路径。以定时器中断为例，不仅要知道“发生过中断”，还要在正确的执行位置注入它；任意改变位置可能影响之后的分支。虚拟机监控器（Hypervisor）控制 VM 的执行与输入，因此可以捕获并重放所需事件，见 [FT §2.1](https://pdos.csail.mit.edu/6.824/papers/vm-ft.pdf)。线程调度、随机数和系统调用结果在应用层复制中也需处理，不能只复制业务请求就假定整个 VM 执行一致。

## 3. VMware FT 论文的关键路线

[![VMware FT：Logging Channel与输出控制](/assets/notes/distributed-systems/dist-ft.png)](/assets/notes/distributed-systems/dist-ft.png)

本节只复盘 **VMware vSphere 4.0 时代的论文设计**。其停止型故障（Fail-stop Failure）模型假设故障服务器在产生错误的外部可见行为前能够被检测；这不等于抵御任意软件错误或拜占庭行为。论文发表时的生产版本仅支持单处理器 VM，多处理器的并发执行重放仍有挑战，不能据此描述现代 FT 全部版本。[FT §1](https://pdos.csail.mit.edu/6.824/papers/vm-ft.pdf)

正常工作与故障接管可按以下顺序理解：

1. Primary VM 接收外部输入，Hypervisor 记录必要输入、非确定性事件及相关执行位置。
2. 日志通过 Logging Channel 发送到 Backup，Backup 将它们放入接收缓冲区并返回确认（Acknowledgment，ACK）。
3. Primary 收到与某次输出关联的日志 ACK 后，才允许释放该外部输出；等待的是输出，不要求整个 VM 停止执行。
4. Backup 按日志重放，并在备用期间抑制外部输出；它可能已经确认日志，但还未执行到相应位置。
5. Primary 故障时，Backup 在取得接管资格的前提下继续消耗已接收、已确认但尚未重放的日志，追赶到最后的日志边界。
6. 重放完成后退出重放模式，作为新 Primary 正常对外执行；系统随后初始化新的 Backup，恢复冗余。

以上接收、缓冲与切换过程依据 [FT §2.2～2.3、§3.1](https://pdos.csail.mit.edu/6.824/papers/vm-ft.pdf)。

| 状态 | 含义 | 不能据此推断什么 |
| --- | --- | --- |
| 已接收 | 日志已进入 Backup 的缓冲区 | ACK 已到达 Primary，或该日志已执行 |
| 已确认 | Backup 发出相应 ACK；Primary 收到 ACK 后可推进对应输出 | Backup 已重放到输出点 |
| 已重放 | Backup 已按记录执行到相应位置 | 远端业务一定已经完成或客户端一定收到输出 |

这里的接收 ACK 针对 Backup 的日志缓冲区，不等于日志已经持久化到磁盘；不能把它与下一章 Acceptor 的稳定存储响应规则混为一谈。该历史故障切换还依赖可用的备用执行状态与存储，不意味着主备状态同时丢失也能继续服务。

### 输出要求与输出规则

输出要求（Output Requirement）是要达到的性质：Backup 接管后，必须继续到与 Primary 已经对外暴露的结果相容的执行状态。输出规则（Output Rule）是论文用于落实该性质的具体约束：Primary 释放外部输出前，Backup 必须已收到并确认关联日志及此前所需记录。[FT §2.2](https://pdos.csail.mit.edu/6.824/papers/vm-ft.pdf)

教学示例：Primary 即将发送“订单已创建”的网络响应。如果只把相关日志交给网络就立即释放响应，日志可能尚未到达 Backup，Primary 又故障；Backup 无从恢复已经向客户承诺的订单状态。因此必须等 Backup 的接收确认。ACK 不要求它已经执行到响应位置，只要求它保有所需记录，可以继续重放到与这个响应相容的状态。

## 4. 用仲裁确定故障接管资格 {#_4-超时探活不能单独决定接管}

Primary 与 Backup 失联，可能是主机故障，也可能只是它们之间的链路断开。若都认为自己有资格对外输出，就会脑裂。

教学推演：日志通道被分区，Primary 认为 Backup 已失效，准备退出记录模式正常执行；Backup 也认为 Primary 已失效，准备接管。心跳超时只能形成怀疑，不能证明另一方已死亡。

论文的具体方案是让双方在对外恢复正常执行前，竞争共享存储上的原子测试并设置（test-and-set）操作。只有成功方可继续；竞争失败的一方停止自身执行，避免两个 Primary 同时输出。若无法访问共享存储，则等待存储恢复可访问，不能自行假定获得资格。[FT §2.3](https://pdos.csail.mit.edu/6.824/papers/vm-ft.pdf)

这个共享存储还承载该设计中的虚拟磁盘，所以不可访问本来也会影响 VM 工作。这是原论文的仲裁实现，不是所有主备系统都必须使用的方式；它说明两个执行副本之外，还可能需要额外的权威与隔离机制。

## 5. 重复输出与业务幂等

旧主已经产生输出但新主无法判断客户端是否收到时，重复仍需处理。不能以“新主没有旧 TCP 连接，所以一定 reset”排除应用级重复：虚拟机故障切换可能保留网络状态，客户端也可能重试。

一次扣款可能跨越远程支付端，本地虚拟机状态复制并不自动覆盖对方效果。应回到第 2 章的稳定请求身份与结果查询，而不是由传输层替业务证明一次性。

### Exactly-once 的边界

论文明确说明：缺少外部输出边界上的事务协调时，故障切换不能保证所有输出恰好一次（Exactly-once）。Backup 无法仅凭本地记录区分 Primary 是在最后一次输出之前还是之后故障。[FT §2.2 末尾](https://pdos.csail.mit.edu/6.824/papers/vm-ft.pdf)

教学扣款历史：Primary 可能已经向支付系统发出请求，随即故障；日志足以让 Backup 重现 VM 执行，却不能单独证明支付端是否已扣款。切换后的输出重发或客户端重试，都可能再次触发同一业务意图。不能由此断言每次切换都会重复扣款，也不能宣称故障透明就绝不重复。

要分别看三层：VM 执行复制保护可恢复状态；TCP 等网络机制处理其覆盖范围内的丢包和重复包；业务恰好一次效果仍需要稳定的 `operation_id`、支付端幂等协议和结果查询或对账。传输层消除重复字节，不等于识别两次应用请求属于同一笔扣款。

## 6. 副本与独立恢复点 {#_6-副本不是备份}

复制也会传播误删除、错误命令和某些逻辑缺陷，运行相同软件的多个实例还可能具有相同缺陷。因此仍需独立恢复点、故障域和恢复验收。复制开销并非固定两到三倍，应结合副本数、日志、快照、网络和重建预算计算。
