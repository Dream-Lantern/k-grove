# 第七章 复制状态机与 VMware FT 历史设计

> 阅读标签：历史VMware FT / vSphere4.0时代论文。

复制通过传输状态、状态差异、日志或执行事件，让副本保有可用于继续服务的状态。快照常与日志配合：前者提供某个时点的状态，后者记录之后的变化。本章先区分状态复制与操作复制，再以历史 VMware FT 论文观察非确定性事件和外部输出的处理。

## 1. 状态复制与操作复制

状态传输可以发送完整快照，也可以只传变更，不局限于进程内存。操作复制让副本从相同初态处理相同有序操作；若状态转移是确定性的，才会得到相同结果。

副本无需在同一物理时刻执行。只要按协议追赶，并且不以违反保证的旧状态对外服务，副本就可以暂时落后。这里要求的是相同的有效顺序与确定性解释，而非同一物理时刻执行。

## 2. 非确定性会改变重复执行的结果 {#_2-非确定性为什么需要处理}

教学例子：操作为“把当前时间写入订单”。若两个副本各自读取本机时间，它们收到相同请求也可能写出不同值。可以由权威端确定时间作为命令参数，或记录必要的非确定性结果，但不能让每个副本任意重算。

线程调度、随机数、设备中断和系统调用结果也可能引入差异。复制状态机不是简单重放任意应用日志就能完成的。

## 3. VMware FT 论文的关键路线

[![VMware FT：Logging Channel与输出控制](/assets/notes/distributed-systems/dist-ft.png)](/assets/notes/distributed-systems/dist-ft.png)

本节复盘论文的 vSphere 4.0 时代方案：虚拟化层捕获使执行可重放的事件，经日志通道交给 Backup；Backup 抑制外部输出。Primary 的输出规则要求相关日志先得到 Backup 的确认，不是只要求转发了一个网络包。[VMware FT 原论文 §2](https://pdos.csail.mit.edu/6.824/papers/vm-ft.pdf)

确认收到日志，不等于 Backup 已执行完该请求；限制外部输出，是为了在主副本故障时，新主能够解释已经对外暴露的结果。这里不是现代 VMware 产品全部版本的实现说明。

## 4. 用仲裁确定故障接管资格 {#_4-超时探活不能单独决定接管}

Primary 与 Backup 失联，可能是主机故障，也可能只是它们之间的链路断开。若都认为自己有资格对外输出，就会脑裂。

论文通过共享存储上的原子 test-and-set 仲裁接管资格，不能写成“任意一方不回应，另一方直接上线”。这也说明两个数据副本之外，仍可能需要额外的权威与隔离机制。

## 5. 重复输出与业务幂等

旧主已经产生输出但新主无法判断客户端是否收到时，重复仍需处理。不能以“新主没有旧 TCP 连接，所以一定 reset”排除应用级重复：虚拟机故障切换可能保留网络状态，客户端也可能重试。

一次扣款可能跨越远程支付端，本地虚拟机状态复制并不自动覆盖对方效果。应回到第 2 章的稳定请求身份与结果查询，而不是由传输层替业务证明一次性。

## 6. 副本与独立恢复点 {#_6-副本不是备份}

复制也会传播误删除、错误命令和某些逻辑缺陷，运行相同软件的多个实例还可能具有相同缺陷。因此仍需独立恢复点、故障域和恢复验收。复制开销并非固定两到三倍，应结合副本数、日志、快照、网络和重建预算计算。
