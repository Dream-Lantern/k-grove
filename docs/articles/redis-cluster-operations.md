# 第二十四章 Cluster 扩缩容、故障恢复与迁移规划

[返回本册目录](/collections/redis/)

扩容不是“增加一个进程后数据自动均匀分布”。新节点加入、复制关系建立、槽分配、实际数据搬迁、客户端拓扑更新和业务验收，是不同工作。

![传统槽迁移的主要步骤](/assets/notes/redis/redis-study-reshard.svg)

## 1. 变更前先回答五个问题

第一，为什么扩容？是总内存不足、CPU 满、热点集中，还是恢复时间太长？如果瓶颈在一个不能拆分的热点键，平均迁槽不一定有效。

第二，目标节点与剩余节点是否能容纳变更峰值？要计算数据、复制缓冲、COW、临时文件和网络流量，不只看稳定态 used_memory。

第三，客户端是否正确支持重定向、地址发现与有界重试？迁移期间才首次发现客户端不能处理 ASK，风险很高。

第四，备份能否恢复，变更失败如何暂停、继续或回退？回退不是简单把元数据改回去，因为键可能已经分散在两端。

第五，所用 Redis、redis-cli、扩展和迁移工具是否匹配？原笔记的 redis-trib.rb、旧 Ruby 依赖与旧 RPM 安装步骤，应作为历史资料保留，不作为新环境默认路线。

## 2. 传统迁槽为什么需要中间状态

传统机制将源槽设为迁出、目标设为迁入，分批移动实际键。迁移中源节点仍可能保有部分键；不存在于源端的相关请求可能被 ASK 引导到目标。完成数据迁移后，再完成槽所有权传播与验证。

因此，不能把“槽归属变了”等同于“所有数据都安全到位”。迁移批次、键大小、网络和目标负载都会影响业务延迟。大键可能拖慢单次搬迁，也可能明显阻塞源节点与目标节点。[传统重分片说明](https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/)

迁移中途，不要随意通过删槽、强制归属、reset 或 fix 来“消除报错”。这些操作可能破坏原本尚可解释的数据状态。应先保存现场，再根据具体问题选择处置流程。

## 3. 缩容比清空节点复杂

缩容要迁出节点负责的全部槽，确认没有遗留键和迁移状态，再处理复制关系及节点退出。若节点是副本，也要评估退出后故障域和冗余是否仍满足要求。

同一台机器上的主副本并不能抵御整机故障。缩容时为省资源把主副本集中到同一主机，可能把容量优化变成可用性退化。

## 4. 故障恢复不能只追求 cluster_state:ok

验收至少包括槽覆盖、各方拓扑视图、副本追赶、客户端错误率、关键键与 TTL、热点分布以及持久化状态。集群状态正常，却因为重试导致业务重复扣减，仍然是一次失败的业务恢复。

节点地址也要从真实客户端所在网络验证。容器或 NAT 环境中，节点通告了不可达地址，会导致入口能连接、重定向后失败。总线端口默认常与数据端口相差 10000，但可配置，防火墙规则应以实际配置为准。

## 5. 8.4+ 的新能力单独看待

Redis 8.4 引入新的原子槽迁移能力；不能把它套用到原笔记的旧版本，也不能凭名称承诺业务零风险。新机制的版本条件、客户端兼容性、监控字段和异常恢复，需要按对应发布说明重新验证。[8.4 新特性](https://redis.io/docs/latest/develop/whats-new/8-4/)

本章提供变更分析框架，不提供默认可执行的脚本。实际迁移时，应先明确环境、维护窗口、恢复点与授权，再编写命令；此次没有连接或改变任何集群。
