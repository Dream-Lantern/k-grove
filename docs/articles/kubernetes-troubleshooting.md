# 第三十章 应用、网络与存储分层排障

> 新增实用章节，串联前面各层证据。以下是定位方法与命令模板，不是对某个真实故障的诊断记录。本次未连接集群、强删对象或重启组件。

## 1. 先给现象加上边界

“服务挂了”还不足以开始修复。先记录时间范围、影响用户、环境、命名空间、工作负载、相关 Pod UID 与最近变更。明确是提交失败、启动失败、间歇错误、延迟升高还是数据不一致。

故障范围同样是重要线索：影响的是一个副本、一台节点、一个命名空间，还是全局？只有外部访问失败，还是集群内也失败？对比这些情况，有助于确定接下来检查哪一层。

![API、调度、节点准备、应用和连接的分层排查](/assets/notes/kubernetes/k8s-troubleshooting-map.svg)

## 2. API 请求失败

核对当前上下文、API 地址、身份、权限和对象版本，再看服务端返回的错误。认证、授权、准入、字段校验和冲突不是同一个问题。

保存错误原文与时间，但应脱敏。不要在公开 issue 中附管理员 kubeconfig、Bearer token 或 Secret；也不要把403直接用管理员权限“修好”后认为问题已解释。

## 3. Pod 没有进入业务运行

| 观察             | 下一步证据                             | 不要直接做什么    |
| ---------------- | -------------------------------------- | ----------------- |
| 未分配节点       | 调度事件、requests、约束、污点、卷绑定 | 给所有节点去污点  |
| sandbox 准备失败 | kubelet/运行时事件、网络准备错误       | 删除所有 CNI 配置 |
| 镜像失败         | 引用、平台、网络、认证、证书           | 默认跳过 TLS      |
| 卷准备失败       | PVC/PV、供应、附加、挂载与权限         | 删除 PVC 重试     |
| 容器反复退出     | reason、exitCode、上次日志、探针       | 只调大超时或内存  |

`Pending` 包含多个阶段，不能一律归因于调度器。`ImagePullBackOff` 也不是“镜像一定不存在”，原始拉取错误才提供更具体的方向。

```bash
kubectl get pod POD_NAME -n NAMESPACE -o wide
kubectl describe pod POD_NAME -n NAMESPACE
kubectl logs POD_NAME -n NAMESPACE -c CONTAINER_NAME --previous
```

查询未执行。事件和日志可能已过期或轮转，缺少它们不代表从未发生故障；需要既有监控和审计补充。

## 4. 运行中但不能服务

先看应用是否监听正确地址和端口，再看配置、依赖、资源和探针。容器 Running 只说明某一运行状态；探针成功还受检查语义影响。

对于网络，把同一客户端的服务名、Service 地址、Pod 地址分开。先确定失败的是解析、连接、TLS、HTTP 路由还是业务响应；不要把所有超时叫成“DNS 问题”。

若只有跨节点失败，对比节点网络、封装或路由、MTU 和策略；若只有外部入口失败，再看负载均衡与 Ingress。ICMP 与业务协议的结果不能互相直接替代。

## 5. 存储与数据异常

PVC Bound 之后仍需看挂载、文件系统、身份权限和应用目录。Pod 可写一个临时目录，不证明持久卷写入成功；挂载路径被遮蔽也可能让配置或数据“看起来丢失”。

发现数据错误时，先保护现场，避免旧实例与替代实例同时写入。区分临时缓存与唯一数据源，保留应用事务和存储日志，再决定如何恢复。

本册的 etcd 备份与业务卷备份有不同边界。恢复集群对象不能自动恢复数据库内容；复制文件也不自动保证运行中数据库一致性。

## 6. 一次只验证一个假设

新增教学例子：假设修改发布模板后只有新副本 readiness 失败，旧副本正常。先对比镜像、配置和实际监听，必要时在授权环境针对一个实例验证；不要同时升级 CNI、重启 DNS 和调整资源。

记录“假设 → 需要的证据 → 观察结果 → 是否支持 → 下一步”。如果证据不支持，保留结果并换一个假设，不把猜测写成已确认根因。

修复前保存可用于恢复的配置，修复后同时验证对象状态、业务请求和数据一致性。观察窗口应覆盖原先触发故障的条件，不能仅凭一次成功就结束排查。

## 7. 排障记录的最小模板

```text
现象与时间：
影响范围：
环境与近期变更：
已收集证据（脱敏）：
假设及排除依据：
获批的变更与恢复步骤：
验证结果及观察窗口：
仍未确认的条件：
```

更深入的调查应按对应组件版本文档进行。[Kubernetes 排障入口](https://kubernetes.io/docs/tasks/debug/debug-cluster/)可作为索引；其中操作并不自动适合生产环境或 1.28，执行前要核对范围与版本。
