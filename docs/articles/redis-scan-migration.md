# 第十四章 SCAN、键迁移与数据切换

SCAN 用于逐步发现数据，迁移还要处理取值、期限、持续写入与目标切换。可以先掌握完整游标迭代，再把发现结果用于受控的校验和迁移流程；数据删除作为有明确范围的独立维护步骤处理。

本章以 Redis Open Source 7.2.0 为参照，较早引入的能力标明版本。TTL（Time to Live，生存时间）表示剩余有效期。`redis` 代码块是 Redis 命令，`text` 代码块是伪代码、语法模板或推演。

## 1. SCAN 的完整迭代

新增伪代码：

```text
cursor = "0"
repeat:
    cursor, keys = SCAN(cursor, MATCH="demo:*", COUNT=100)
    对 keys 做限速、可重复的处理
until cursor == "0"
```

第一次传入 0，继续使用返回游标，直到返回 0。中间一批没有匹配项，并不代表结束；COUNT 是工作量提示，不是精确页大小。

完整迭代对全程持续存在的元素有相应的返回保证，但可能重复返回；迭代期间新增或删除的元素不具备快照语义。因此，应用需要去重，或采用可安全重复执行的操作。[SCAN 的保证](https://redis.io/docs/latest/commands/scan/)

Cursor（游标）是服务端返回的后续遍历位置标记，不是页码，不能自行加一。下面仅是可能的回复结构，128、256 不是固定结果：

```text
SCAN 0 MATCH demo:*     → cursor="128", keys=[]
SCAN 128 MATCH demo:*   → cursor="256", keys=[demo:a, demo:b]
SCAN 256 MATCH demo:*   → cursor="0",   keys=[]
```

第一批为空也必须继续；只有返回游标为 0 才结束本轮。MATCH 是取出候选后的过滤条件，不代表底层只检查匹配键；匹配比例低时，可能连续出现空批次。COUNT 可以在后续调用中调整，是工作量提示而非精确返回数量，也不是按前缀建立的索引。

| 整轮迭代期间的情况 | 完整迭代的保证 |
| ------------------ | -------------- |
| 元素始终存在       | 至少返回一次   |
| 元素始终不存在     | 不会返回       |
| 期间新增或删除     | 是否返回不确定 |
| 同一个元素         | 可能重复返回   |

这些保证以正确衔接游标并完成整轮为前提；集合大小保持有界时才有终止保证，持续无界增长可能让一轮迟迟无法结束。SCAN 自 Redis Open Source 2.8.0 提供，不是某个时点的数据快照；处理重复结果时应去重或保证幂等（Idempotency，重复执行不重复产生副作用）。[SCAN 的过滤、COUNT 与终止条件](https://redis.io/docs/latest/commands/scan/)

## 2. 从遍历结果到受控维护的条件 {#_2-为何不保留-keys-xargs-del}

KEYS 可能在一个调用中遍历大量键；简单 shell 拆词又不适合任意二进制键名。就算换成 SCAN，直接把结果接到 DEL，也没有解决目标范围、并发变化、键重建和恢复问题。

应先保存发现清单并确认作用对象，再按获准维护方案分批处理。扫描副本也会占用它的资源，可能拖慢复制或影响读服务，不是无影响捷径。

Redis Cluster（集群）中一次普通 SCAN 针对所连接节点的相应数据，不是自动扫描整个集群；全局发现需要覆盖负责数据的主节点，并处理拓扑变化。扫描期间槽迁移可能让键跨节点移动，单次遍历各节点不能视为全局快照，还需去重、复核和按协议重新扫描。Cluster 只支持 DB 0（Database 0，逻辑数据库 0）；槽迁移与普通值复制不同，见 [第 23 章 Cluster 路由](/articles/redis-cluster-routing.html)和 [第 24 章 Cluster 运维](/articles/redis-cluster-operations.html)。[Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

## 3. DUMP / RESTORE 搬运什么

DUMP 生成序列化值，不自动把原 TTL 作为一个完整业务迁移流程一起带走。RESTORE 的 ttl 参数、绝对期限选项、版本格式与覆盖行为必须明确。

| 命令    | 搬运中的作用                                 |
| ------- | -------------------------------------------- |
| DUMP    | 返回键值的二进制序列化表示，不包含其过期时刻 |
| PTTL    | 读取剩余 TTL，单位毫秒                       |
| RESTORE | 从兼容的序列化数据恢复键，并单独设置期限     |

例如先在源端读取，命令未执行；前提是存在待迁移的 `demo:source`：

```redis
DUMP demo:source
PTTL demo:source
```

目标端恢复的语法模板如下，`<serialized-value>` 必须由客户端按二进制参数传入实际 DUMP 结果，不能把占位符当成命令参数直接运行：

```text
RESTORE demo:target 5000 <serialized-value>
```

RESTORE 的相对 TTL 单位为毫秒，0 表示永久键；默认目标已存在会报错，Redis Open Source 3.0.0 起的 REPLACE 才允许覆盖。它会校验数据校验和及 RDB（Redis Database，数据库快照）格式版本，不能假设新版本或扩展类型的载荷一定能恢复到旧版本。[DUMP](https://redis.io/docs/latest/commands/dump/) · [RESTORE](https://redis.io/docs/latest/commands/restore/)

如果先读取值、再读取期限，而源端在此期间仍在变化，两次结果就可能构成不一致的视图。仅比较键的数量，也不能证明类型、值和过期条件一致。

```text
T1：DUMP demo:source，取得旧值
T2：应用更新源键，同时可能修改其期限
T3：PTTL demo:source，取得更新后的剩余期限
T4：目标 RESTORE，旧值却配上另一个时点的期限
```

两次独立读取不构成原子读取。严格迁移需要建立一致性协议：冻结写入要覆盖全部写入方；双写要处理失败、顺序和删除；增量日志要有完整捕获及衔接边界；原子读取值与期限的方案也要验证其阻塞成本和适用范围。选择其中一项并不自动消除所有竞态。

新增纸面场景：读取 PTTL=5000 后，搬运耗时 2 秒；到目标 RESTORE 时仍使用相对 ttl=5000，会把原来的到期时刻延后约 2 秒。RESTORE 的相对 ttl 使用毫秒，0 表示不设置期限，而不是“马上到期”。

| 源状态                      | 迁移协议应怎样区分                                 |
| --------------------------- | -------------------------------------------------- |
| 无期限，PTTL=-1             | 明确按持久键处理，仍需确认取值版本一致             |
| 不存在，PTTL=-2，或取值失败 | 不应凭旧值恢复成永久键，重新确认并按协议跳过或处理 |
| 仍有效，PTTL 为正           | 扣除搬运耗时或保留适用的绝对截止时间               |
| 运输期间已到期              | 不能把剩余时间截成 0 后调用 RESTORE                |

PTTL=0 也不是无期限的标志：它可能是仍可见但只剩极短时间的键。应重新核对截止时间并按迁移协议处理，不能把这个 0 直接传给 RESTORE，意外将临近过期数据变为永久数据。

Redis Open Source 5.0.0 起的 RESTORE ABSTTL 可使用绝对 Unix 毫秒时间戳，即自 1970-01-01 00:00:00 UTC 起的毫秒数。但源与目标时钟、时间测量和一致性读取仍需保证；它不单独修复值与期限之间的竞态。此表是迁移设计条件，不是已验证的通用迁移程序。[RESTORE 参数与版本](https://redis.io/docs/latest/commands/restore/)

MOVE 是同一实例逻辑 DB 之间的命令，Cluster 仅有 DB 0，MOVE 不是跨 Cluster 节点搬迁工具；不要把它和槽迁移混为一谈。数据格式及恢复边界可结合 [第 19 章 RDB/AOF](/articles/redis-rdb-aof.html)理解，其中 AOF（Append Only File，只追加文件）是另一种持久化机制。

## 4. MIGRATE 的成功与超时

MIGRATE 在源和目标间协调搬运，COPY 和 REPLACE 等参数改变删除与覆盖语义。它不是通用的跨系统两阶段事务。

以单键、未指定 COPY 的成功路径为例，逻辑过程是：

```text
源端序列化键值 → 建立或复用目标连接 → 目标 RESTORE 恢复值和期限
              → 目标返回 OK → 源端删除原键 → 返回 OK
```

COPY 保留源键，REPLACE 允许覆盖目标同名键。迁移会消耗两端处理器、内存和网络资源，源端与目标端的相关处理会阻塞其他工作，大键尤其要评估；它不是后台执行且无阻塞的在线同步器。

出现 IOERR 或超时后，键可能只在源端，也可能两端都存在，需要按文档检查。timeout 描述通信中的适用空闲条件，不是“整个任务保证在这几毫秒内完成”。[MIGRATE 的故障语义](https://redis.io/docs/latest/commands/migrate/)

| 结果     | 如何判断和处理                                                       |
| -------- | -------------------------------------------------------------------- |
| OK       | 本次命令成功；是否保留源键取决于 COPY                                |
| NOKEY    | 源端没有可迁移键，不是数据传输错误；批量时表示全部指定键都不存在     |
| IOERR    | 通信错误或超时，检查两端，不能据此判定数据必然丢失                   |
| 其他 ERR | 根据认证、目标冲突或恢复错误处理；批量时还要逐键核实是否已有部分成功 |

超时可能发生在目标尚未恢复时，也可能发生在目标恢复成功但源端没有收到回复时；后一种情况会留下两份。不能不检查目标就无条件重试，尤其不能盲目加 REPLACE 覆盖目标的新写入。应比较业务标识、值和版本号，再按迁移协议处理；还需排除并发更新、自然过期等额外变化。

| 能力                    | Redis Open Source 起始版本 | 用途                                          |
| ----------------------- | -------------------------- | --------------------------------------------- |
| MIGRATE                 | 2.6.0                      | 基础键迁移                                    |
| COPY、REPLACE           | 3.0.0                      | 保留源键、允许覆盖目标                        |
| KEYS                    | 3.0.6                      | 原 key 参数传空字符串，再在 KEYS 后指定多个键 |
| AUTH password           | 4.0.7                      | 以口令向目标认证；目标使用 ACL 时对应默认用户 |
| AUTH2 username password | 6.0.0                      | 指定目标 ACL 用户名和口令                     |

ACL（Access Control List，访问控制列表）控制用户及其可用权限。上述认证发生在源 Redis 连接目标时，不替代调用者对源端的认证；凭据还涉及日志和传输保护。KEYS 只减少逐键传输往返，不包含持续写入同步、最终切换和回退协议。[MIGRATE 参数历史](https://redis.io/docs/latest/commands/migrate/)

因此本章不提供包含真实地址、认证与 REPLACE 的一键迁移命令。

## 5. 在线迁移需要业务切换协议

![范围、初始复制、校验与写入切换](/assets/notes/redis/redis-study-migration.svg)

redis-migrate-tool 的安装与兼容记录按其历史版本理解。实际选择工具时，应分别验证 Redis 版本、模块类型、Functions 和多段 AOF 等对象是否可完整表示。

迁移验收至少应覆盖值与类型、TTL、持续写入、扩展结构、脚本或函数、客户端路由，以及最后的写入边界。抽样可以提供参考，但少量样本全部正确，并不能证明全部数据在整个时段内都一致。

在线迁移可以按下面七步组织，每步都要由所选工具和业务协议支撑：

1. **确定范围**：记录源、目标、版本、类型、TTL、写入方和冲突处理规则，准备恢复方案。
2. **初始复制**：通过 SCAN 等方式发现并搬运已有数据，处理重复和失败，不能当成一致快照。
3. **同步持续写入**：与初始复制并行捕获新建、更新和删除；明确增量起点、顺序及去重，避免旧的初始数据覆盖新的增量。
4. **校验两端**：比较关键值、类型、期限和业务版本，检查增量延迟及缺失；数量相等只是其中一项。
5. **建立最终写入边界**：暂停或围栏所有旧端写入方，等待边界前增量应用完，再作最终校验，防止校验后又有遗漏写入。
6. **切换客户端**：更新连接与路由，处理连接池旧连接，确认新写入只去预定目标。
7. **观察与回退**：监控错误、延迟和关键业务，按预定协议处理新端写入后再考虑回退。

增量捕获必须覆盖初始复制的整个变动窗口，不能复制完成后才开始。持续无界增长、无法追平增量或没有最终写入边界时，不应宣布迁移完成。观测指标与验证思路见 [第 30 章可观测性](/articles/redis-observability.html)。

## 6. 回退条件也要提前写

切到新库之后又产生写入，直接切回旧库可能丢失这些变化。回退需要明确暂停写入、反向同步或按权威源重建的策略。

保留旧环境不等于自动具备无损回退能力。先定义恢复点、恢复时间与可接受差异，再安排隔离验证与实际迁移。
