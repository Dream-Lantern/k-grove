# 第十二章 Quorum、Dynamo 与 Gossip

> 阅读标签：Quorum模型 / Dynamo2007历史案例。

Quorum 是足以参与某项决定或观察的成员集合。读写协议分别设置参与门槛，再结合集合交集、版本与恢复规则提供保证。本章先用固定副本集合计算交集，再看 Dynamo 和 Gossip 如何处理成员、版本及副本差异。

## 1. R、W、N 的集合含义

在固定 N 个副本中，写操作等待 W 份适用确认，读取 R 份结果。R+W>N 保证任意这样的读集合与写集合至少相交；2W>N 保证两个写集合相交。这是集合条件，不是完整一致性证明。

![五副本中的读写集合交集](/assets/notes/distributed-systems/dist-quorum.svg)

使用多数时，W 为 floor(N/2)+1，五副本的多数是三。具体存储协议也可能允许非多数写，此时应按它的读写门槛与版本规则分析语义。

## 2. 交集之外的版本与恢复规则 {#_2-交集为什么还不等于线性一致}

交集中的副本可能包含未完成的写入或并发版本，也可能落后于另一次读取已返回的状态。版本如何生成、部分成功的写入如何处理，以及读取是否执行修复或写回，都会影响最终的一致性模型。

反例思路：写 v1 仅到达一个副本后卡住；某次读接触它并返回 v1，之后另一次不含该副本的读又返回 v0。如果没有后续写与额外协议，这种“新—旧倒退”不能只靠 R+W>N 排除。不要把“选最高版本”写成对任意并发情况都充分。

## 3. Dynamo 的机制组合

Dynamo 2007 论文组合了一致性哈希、版本、适用的 quorum-like 读写、故障期间临时接收和副本修复。sloppy quorum 允许使用偏好列表以外的健康节点时，实际参与集合可能变化，不能直接拿固定集合的交集公式证明实时一致。[Dynamo 原论文 §4](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)

Hinted handoff 用于把临时代收的数据交还给相应节点；读修复与反熵处理副本差异。它们不意味着业务冲突消失，仍需要确定如何解释并发版本。本章不是当前 DynamoDB 产品的内部实现说明。

## 4. 可用性取决于读写各自门槛

| 固定三副本示例 | 可失去多少副本仍满足数量条件 | 代价                                 |
| -------------- | ---------------------------- | ------------------------------------ |
| R=1，W=3       | 读可失去 2，写不能失去 1     | 写必须等齐；额外协议条件仍需满足     |
| R=2，W=2       | 读写各可失去 1               | 两边都需要多数                       |
| R=3，W=1       | 写可失去 2，读不能失去 1     | 读依赖全部；不能据此单独断言线性一致 |

无法满足门槛时，应结合业务截止时间选择失败、降级或重试，而不是将“无限重试”视为唯一正确的 API 行为。即使 W=N、R=1，也不能脱离具体协议和故障模型直接判定为 CP。

## 5. Gossip 的成员传播与暂时分歧 {#_5-gossip-传播什么-不保证什么}

Gossip 常以周期性、部分节点间的信息交换传播成员或状态；具体选择对象、push/pull、传播周期和修复机制依实现而异。传播周期、是否回传以及重复联系的处理，均属于具体实现的选择。

概率传播可以有良好扩展性，但存在冗余、延迟与暂时分歧。不能把理想混合模型中的传播轮数当成任意故障网络的硬时限，也不能把成员传播直接等同共识决策。需要唯一选主或不可冲突提交时，还要相应权威协议。
