# 第十二章 Quorum、Dynamo 与 Gossip

> 阅读标签：Quorum模型 / Dynamo2007历史案例。

法定集合（Quorum）是按协议足以参与某项决定或观察的成员集合。读写协议分别设置参与门槛，再结合集合交集、版本与恢复规则提供保证。本章先用固定副本集合计算交集，再看 Dynamo 和 Gossip 如何处理成员、版本及副本差异。Dynamo 指 2007 年论文中的历史系统，不是当前 DynamoDB 的内部实现说明。

## 1. R、W、N 的集合含义

| 参数 | 对一个数据对象的含义 |
| --- | --- |
| N | 目标副本数量，不是整个集群的物理节点总数，也不是虚拟节点位置数 |
| R | 成功读取需要取得的适用副本响应数量 |
| W | 成功写入需要取得的适用副本确认数量 |

在固定的 N 个不同副本中，`R + W > N` 保证任意满足门槛的读集合与写集合至少相交；`2W > N` 保证两个写集合相交。如果两个集合不相交，它们的大小之和最多为 N，因此这两个不等式可以排除不相交。这是集合条件，不是完整一致性协议；确认是否持久、版本如何选择、操作如何完成都还要定义。[Dynamo §4.3、§4.5](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)

教学例子：`N=5、R=3、W=3`，一次写确认集合为 `{A,B,C}`，一次读响应集合为 `{C,D,E}`，交集为 `{C}`。C 让这次读有机会获知该写的版本，但不能代替并发版本选择与恢复规则。

![五副本中的读写集合交集](/assets/notes/distributed-systems/dist-quorum.svg)

使用多数时，W 为 floor(N/2)+1，五副本的多数是三。具体存储协议也可能允许非多数写，此时应按它的读写门槛与版本规则分析语义。

## 2. 交集之外的版本与恢复规则 {#_2-交集为什么还不等于线性一致}

交集中的副本可能包含未完成的写入或并发版本，也可能落后于另一次读取已返回的状态。版本如何生成、部分成功的写入如何处理，以及读取是否执行修复或写回，都会影响最终的一致性模型。

教学反例：固定三个副本，`R=2、W=2`，初值都是 v0。一笔尚未完成的写 v1 只到达 A；第一次读从 `{A,B}` 取结果并直接返回较新的 v1。该读返回后，第二次读从 `{B,C}` 又返回 v0。虽然 `R+W=4>3`，仍发生新—旧倒退：这笔写尚未取得 W 份确认，而没有写回或其他协议的读取已把它暴露给客户端。要解释第一次读就需认为 v1 生效，随后却又回退，所以不能据此声称线性一致。该例是教学构造，不是 Dynamo 故障实测。

即使写已取得 W 份确认，交集也只是证明的一部分：多个并发写是否存在统一顺序、版本信息是否完整、读是否执行必要修复，都需按协议分析。“总是选最高版本”也不能自动消除不可比较的并发版本。

## 3. Dynamo 的机制组合

Dynamo 2007 组合了一致性哈希、因果版本、quorum-like 读写、故障期间临时接收和副本修复。请求协调节点（Coordinator）负责一次请求的版本和副本交互，不等于一个经过共识选出的全局唯一 Leader。偏好列表（Preference List）为对象给出按顺序选择的不同物理节点，通常长于 N，以便越过不可达成员。[Dynamo §4.3～4.5](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)

### 向量时钟记录版本因果

向量时钟（Vector Clock）用多个节点计数器记录一个版本已包含的更新历史。缺少的分量按 0 处理；若 V 的每个分量都小于或等于 U，且至少一个严格更小，则 U 支配 V，V 可视为 U 的祖先。若两个方向都不成立，则版本并发、不可比较；向量完全相等表示没有从计数中区分出新的因果进度。

物理时间戳较大可能只是机器时钟较快，不能可靠证明写入看过另一个版本。向量记录的是版本依赖，不要求节点的墙上时钟完全一致。沿用第三章概念，以下按 [Dynamo §4.4](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf) 构造完整教学历史，A、B、C 是协调写入的节点：

| 版本 | 向量时钟 | 来自哪里 |
| --- | --- | --- |
| D1 | `[(A,1)]` | A 创建初版 |
| D2 | `[(A,2)]` | A 基于 D1 再更新，D2 支配 D1 |
| D3 | `[(A,2),(B,1)]` | B 基于 D2 更新 |
| D4 | `[(A,2),(C,1)]` | C 独立基于 D2 更新 |
| D5 | `[(A,3),(B,1),(C,1)]` | 应用合并 D3、D4，并由 A 协调写回；先取分量最大值，再增加 A 的计数 |

D3 在 B 分量更大，D4 在 C 分量更大，互不支配；二者都包含 D2 的历史。教学购物车例子：两人读到同一个 D2，一人添加书得到 D3，另一人添加笔得到 D4。读取返回两个并发版本及其上下文；应用按“保留两次添加”的规则合并，并在写回时携带两条历史，生成 D5，使它支配二者。

![D1 到 D5 的向量时钟演化、并发分支及合并后继](/assets/notes/distributed-systems/dist-dynamo-vector-clock.svg)

向量时钟检测因果关系，不会自动理解业务冲突。删除、数量修改和整对象覆盖都要定义合并语义；简单并集可能让删除项复活。若丢弃某个分支的上下文，合并结果也不能正确表达已包含两条历史。上述比较假设保留完整向量；原论文的向量截断优化会限制祖先关系的精确判定。

### Sloppy Quorum 与临时代收

宽松法定集合（Sloppy Quorum）允许在扩展偏好列表中选择前 N 个健康节点，它们不一定是正常情况下的前 N 个目标节点。这里是越过原目标集合，不是任意选择“偏好列表以外”的节点；可用性依赖实际可达副本与响应条件，不能据此自动保证线性一致。[Dynamo §4.5～4.6](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)

教学简化：对象目标副本为 A、B、C，N=3，A 不可达。协调者沿偏好列表跳过 A，选择 B、C 和替代节点 D；D 临时保存本应给 A 的数据，并在元数据中记录目标 A。A 恢复后，D 尝试移交，成功后才可按协议清理临时代收副本。这就是提示移交（Hinted Handoff）；D 不是永久增加的第四个目标副本。

实际读写集合变化后，固定集合证明的前提就变了。比如 W=2 的写先从 `{B,D}` 获得确认，C 的传播暂时延迟；A 恢复但还未接收移交，随后 R=2 的读先从 `{A,C}` 得到旧版本。尽管 `R+W>N`，这两个实际集合没有交集。这个教学分支说明需要核对实际参与节点，而不是由参数直接证明最新读取。Dynamo 的实际选点与 Coordinator 行为仍按偏好列表及当时的可达性确定。

### 三种恢复机制各有触发条件

| 机制 | 触发与用途 | 局限 |
| --- | --- | --- |
| 提示移交（Hinted Handoff） | 目标节点恢复时，将故障期间代收的数据交还给它 | 适合临时故障；代收节点也可能在移交前失效 |
| 读修复（Read Repair） | 读取收集版本时发现落后副本，把可判定的新版本或协调后的结果补给它 | 依赖读取流量；不被读取的数据可能长期不触发；不能擅自覆盖未解决的并发分支 |
| 反熵（Anti-Entropy） | 后台比较共同数据范围，发现并修复长期副本差异 | 需要可达性、持续修复和仍存在的更新来源；不理解业务冲突 |

例如 A 恢复时先由 D 移交，而 B 还漏了某个后续版本，可以在读取时被修复；长期无人读取的范围则依靠后台反熵。三者互补，不能把一次移交当作所有副本已经一致。依据见 [Dynamo §4.6～4.7、§5 的读修复流程](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)。

### Merkle Tree 缩小差异范围

默克尔树（Merkle Tree）把数据项哈希为叶子摘要，再逐层把子摘要组合成父摘要。两个副本先比较根；根不同，再比较子树，逐步定位需同步的范围，避免每次先传输全部数据。Dynamo 用它比较双方共同负责的键范围。[原论文 §4.7](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)

八键教学模型：两个副本的 K1～K8 排序相同，仅 K6 的值不同，一边为 v6，另一边为 v6'。叶子取 `H(key,value)`，父节点按相同顺序组合子摘要，则比较路径为：

```text
K1～K8：根不同
├─ K1～K4：摘要相同，跳过
└─ K5～K8：摘要不同
   ├─ K5～K6：摘要不同
   │  ├─ K5：摘要相同
   │  └─ K6：定位到值差异，再传输相应版本数据
   └─ K7～K8：摘要相同，跳过
```

这是简化树模型，需要相同数据范围、键顺序、编码和建树规则；摘要相等的可靠性还依赖哈希算法及碰撞假设。它帮助定位差异，不决定 v6 与 v6' 哪个该保留，也不能从摘要重建已永久丢失的数据。版本比较与业务合并仍是后续步骤。

## 4. 可用性取决于读写各自门槛

| 固定三副本示例 | 可失去多少副本仍满足数量条件 | 代价                                 |
| -------------- | ---------------------------- | ------------------------------------ |
| R=1，W=3       | 读可失去 2，写不能失去 1     | 写必须等齐；额外协议条件仍需满足     |
| R=2，W=2       | 读写各可失去 1               | 两边都需要多数                       |
| R=3，W=1       | 写可失去 2，读不能失去 1     | 读依赖全部；不能据此单独断言线性一致 |

无法满足门槛时，应结合业务截止时间选择失败、降级或重试，而不是将“无限重试”视为唯一正确的 API 行为。即使 W=N、R=1，也不能脱离具体协议和故障模型直接判定为 CP。

表中的容忍数量只表示仍可满足当前读或写的**数量门槛**。网络可达性、响应时限、版本及失败处理协议同样影响操作能否成功；读写集合相交不自动提供实时线性一致性。

## 5. Gossip 的成员传播与暂时分歧 {#_5-gossip-传播什么-不保证什么}

流言传播协议（Gossip Protocol）通过节点周期性地与少量其他节点交换信息，逐步传播成员视图（Membership）或状态。推送（Push）把已知信息发送给对方；拉取（Pull）向对方索取缺失信息，也可组合成双向交换。随机选择部分邻居避免每次都让所有节点两两通信，有利于扩展，但会产生重复传播与暂时分歧。

故障检测（Failure Detection）与成员变更还要分清。教学例子：A 无法访问 B，但 C 仍可访问 B；A 的“不可达”观察不能证明 B 全局死亡。Dynamo 后来的设计用本地故障观察避开失败通信，正式加入/移除则通过显式成员变更及 Gossip 传播，而不是一次超时就永久重分配整个环。[Dynamo §4.8](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)

信息从 A 传给 C、再传给其他节点需要时间，不同节点可能暂时保存不同成员历史。在更新停止、网络最终连通且交换与合并持续完成等条件下，视图可以最终收敛（Eventual Convergence）；这不是已经完成共识，更不能单独证明全局唯一 Leader 或唯一提交顺序。

概率传播可以有良好扩展性，但存在冗余、延迟与暂时分歧。不能把理想混合模型中的传播轮数当成任意故障网络的硬时限，也不能把成员传播直接等同共识决策。需要唯一选主或不可冲突提交时，还要相应权威协议。
