# 第二十二章 Saga、TCC、Outbox 与跨服务一致性

> 阅读标签：通用协议/应用模型，具体前提见本章。

跨服务业务通常分多步改变订单、支付和库存状态。各步的提交、外部可见与补偿方式可能不同，因此需要记录过程并设计恢复路径。Saga、TCC 和 Outbox 分别从补偿、资源预留和事件发布入手，处理这些边界上的一致性问题。

## 1. 先缩小真正需要原子的范围

先问一句：需要始终成立的那条规则（不变量），能不能在一个事务里守住？比如“可售 + 已预留 + 已售 = 总库存”，只要库存表在同一个库，一条约束就够，不必拆成三个服务再去协调。拆服务只是手段；把库存预留和可售数量放在一起约束，往往比事后对账更直接。

确需跨服务时，要分清两件事：“全局原子提交”要求所有参与方在同一时刻一起成功或一起失败；“多步可恢复流程”允许中间状态被别人看到，只保证流程最后走到一个确定的业务结果。两者都有合理用途，但后者在任意一瞬间并不满足全局 ACID。

## 2. Saga：提交分步发生，失败靠补偿

Saga 将长流程拆为局部事务及对应补偿。订单教学流程为：预留库存 → 请求支付 → 确认订单；若支付明确失败，则取消预留。各步骤可能已对外可见，补偿是新的业务操作，时间并不会倒流。[Saga 原论文](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)

退款可能延迟，补偿可能失败，重试也可能重复执行。因此需要记录流程状态、步骤 ID、调用结果与补偿进度。支付结果未知时，应先查询或对账；退款的同时再次扣款会造成重复扣款。

### 正向继续与反向补偿

失败后的路线取决于业务是否还允许继续。Backward Recovery（反向恢复）用补偿修正已完成的步骤；Forward Recovery（正向恢复）从可靠保存的进度继续未完成步骤。例如确认订单暂时不可用，修复后可以继续确认，不必立刻退款。原论文也讨论先退回保存点、再继续执行的混合方式；保存点和可重试步骤必须有可靠记录。

下面是订单业务的教学推演，各步分别提交自己的本地事务：

```text
创建订单 → 预留库存 → 支付成功 → 确认订单 → 完成
                                  ↓ 确认明确失败，业务决定取消
                     标记取消中 → 退款 → 释放库存 → 记录补偿结果
```

“取消订单”先标记为取消中，表示禁止后续确认；退款与库存释放完成后才进入取消终态。补偿通常按已完成步骤的依赖关系逆向安排，具体顺序由业务约束决定；机械倒放所有接口会违反这些依赖。若支付结果未知，应先用支付幂等键查询、对账，确认是否扣款，再选择继续确认或退款。补偿失败要保存待重试状态，超出自动处理能力时转人工处理。

![Saga 正向继续与反向补偿](/assets/notes/distributed-systems/dist-saga-flow.svg)

Saga 的各次局部提交可能被其他事务观察到，其隔离范围弱于传统 ACID 事务。可将库存保持为预留状态，在确认前检查订单状态，并用版本条件更新阻止旧请求覆盖新决定。这些措施减少中间状态的影响，但仍需业务定义哪些状态允许被读取和操作。[Saga 原论文 §4—6](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)

## 3. TCC：先预留，再确认或取消

Try 预留业务资源，Confirm 消耗预留，Cancel 释放预留。它把可回退性设计进接口，例如把库存从“可售”转为“已预留”，发货留到 Confirm 之后。

实现需要处理重复 Confirm/Cancel、Cancel 先于迟到 Try、空回滚和资源悬挂；这些保证来自实现，三段函数名本身提供不了。具体框架有相应状态与防护机制，采用时必须固定版本验证。[Apache Seata 的 TCC 模式说明](https://seata.apache.org/docs/dev/mode/tcc-mode/)

以预留两件库存为教学例子，Confirm 与 Cancel 是 Try 成功后的两条替代路线：

| 阶段             | available_stock（可售） | reserved_stock（预留） | sold_stock（已售） |
| ---------------- | ----------------------: | ---------------------: | -----------------: |
| 初始             |                      10 |                      0 |                  0 |
| Try 预留 2 件后  |                       8 |                      2 |                  0 |
| 选择 Confirm 后  |                       8 |                      0 |                  2 |
| 或选择 Cancel 后 |                      10 |                      0 |                  0 |

参与者用事务 ID、分支 ID 标识一次预留，持久化记录资源数量及分支状态。状态转换与库存变更应在同一本地事务中完成，并通过唯一约束、条件更新等串行化同一分支的并发请求。Try 重试按原预留返回；Confirm 重试按原销售结果返回；Cancel 重试按原释放结果返回。

| 异常                     | 发生条件                           | 处理要点                               |
| ------------------------ | ---------------------------------- | -------------------------------------- |
| Empty Rollback（空回滚） | Cancel 到达时，没有成功 Try 的记录 | 记录取消标记，释放动作不作用于库存     |
| Idempotency（幂等）      | Try、Confirm 或 Cancel 重复到达    | 查分支状态，已完成的同一操作返回原结果 |
| Suspension（悬挂）       | 取消已完成，迟到的 Try 又尝试预留  | 检查取消标记，拒绝迟到 Try             |

空回滚解决“没有预留时如何取消”，悬挂解决“取消后如何挡住晚到的预留”，两者出现在不同时间点。取消标记的保留期必须覆盖协议允许的重试与迟到窗口，取消后立即删除会留下悬挂窗口。Confirm 与 Cancel 只能有一个生效：协调者必须可靠保存统一决定，参与者只能从预留态进入其中一个终态，冲突的另一种请求只返回冲突结果，资源保持不变。

![TCC 库存分支与异常防护](/assets/notes/distributed-systems/dist-tcc-state.svg)

TCC 在业务接口层管理资源，需要协调者和参与者持久化状态；Try 通常提交业务预留的本地事务，与数据库 XA Prepare 不同。各服务完成 Confirm 的时间仍可不同，全局原子可见性仍需另行保证。框架的具体防护需按版本配置核对，例如 Seata 官方对 **1.5.1** 的说明介绍了 `tcc_fence_log` 和可选的 `useTCCFence`；这里的库存状态图是教学设计，不是照搬该表的字段或默认配置。[Seata 1.5.1 TCC Fence 说明](https://seata.apache.org/blog/seata-tcc-fence/)

## 4. Outbox 原子保存业务数据与事件意图 {#_4-outbox-解决哪个双写问题}

先提交订单再发事件，中间崩溃会丢事件；先发事件再提交订单，事务回滚后消费者可能处理一笔不存在的订单。Outbox 把业务数据与待发送事件放进同一个本地事务，后续通过 relay 或 CDC 发布。

![业务提交、Outbox 与幂等消费](/assets/notes/distributed-systems/dist-outbox.svg)

教学伪代码，仅表达原子边界：

```text
同一本地事务：
    写入订单 o-42 的状态
    写入 outbox 事件 e-42 与订单版本
提交
独立发布器：读取已提交事件，发送并按协议记录进度
消费者：在自己的事务中去重 e-42 并更新本地业务
```

发布器可能发送成功但尚未记录进度就崩溃，因此仍可能重复发送；消费者要幂等，事件顺序也需设计。Outbox 能原子保住的只有“业务状态”和“待发布的意图”这两样；消费者那边的数据库不在这笔事务里，消费端仍需自己去重。[Transactional Outbox 模式原始说明](https://microservices.io/patterns/data/transactional-outbox.html)

### 发布器从哪里取得事件

Polling Publisher（轮询发布器）定期查找 Outbox 中未发布的记录，适合能够直接查询业务库、希望实现较简单的场景；需要处理扫描索引、抢占任务、轮询延迟，以及多 worker 的同聚合排序。CDC（Change Data Capture，变更数据捕获）则从数据库变更日志捕获已经提交的 Outbox 记录，适合已有日志订阅基础设施的场景；需要管理日志位置、保留期、重启恢复和连接器的顺序保证。两者都要处理重复发布。

下面是一种教学表结构，字段名属于教学约定，框架规范另有定义：

| 字段                    | 用途                                                   |
| ----------------------- | ------------------------------------------------------ |
| `event_id`              | 事件唯一 ID，供消费端去重                              |
| `aggregate_id`          | 所属订单等业务聚合的 ID                                |
| `aggregate_version`     | 该聚合的业务版本，用于检测旧事件和缺口                 |
| `event_type`、`payload` | 事件类型与内容                                         |
| `created_at`            | 创建时间，用于排查与运维；版本排序靠 aggregate_version |
| `published_at`          | 轮询方案可用的发布进度；发送确认后记录                 |

CDC 通常维护自己的日志消费位置，不一定回写每条记录的 `published_at`。无论采用哪种方案，都应区分“源事务已经提交”和“Broker 已接收消息”；后者的确认之后、发布进度持久化之前仍有崩溃窗口。

### 发布顺序与消费去重分别处理 {#去重不修复发布乱序}

同一订单先提交 E1(version=1)，再提交 E2(version=2)。若两个 relay 先发布 E2、再发布 E1，那么即使把 Kafka Key 都设成同一个 order_id，分区也只保证“同一订单进同一分区、按进入顺序排队”，它不会把已经颠倒的 E1、E2 重新排回来。Key 保留的是发布顺序，数据库里的业务版本顺序并不随之恢复；event_id 去重管的是同 ID 重复，不同 ID 的旧版本仍可能覆盖新状态。

例如 `order-1001` 产生 `E1(v1) → E2(v2) → E3(v3)`。多个 Relay Worker 可以并行处理不同订单；处理同一订单时则需要串行归属、分区调度或其他经验证的顺序协议，任由 worker 抢到哪条就先发哪条，会打乱同一订单的顺序。

可按业务聚合串行发布，或选择并验证保留所需提交顺序的CDC路径；消费者还应识别同ID重复、旧版本、版本缺口。遇到version=2而尚缺version=1时，是等待、补取还是采用允许跳变的状态快照，要由业务定义。

在本章选用的数据库幂等方案中，去重记录与业务效果**必须在同一本地事务内提交**，并用唯一约束等处理并发；“尽量”放在一起满足不了这个边界。外部 HTTP 副作用无法加入该事务时，需要对端幂等键或其他替代协议，两步独立写与同一事务的保证不同。[Kafka中的对应推演](/articles/kafka-order-events.html)

一个容易遗漏的失败窗口是：消费者收到 E1 → 单独提交去重记录 → 更新业务之前崩溃。重投 E1 时，去重记录让消费者跳过处理，业务效果反而永远缺失。正确的数据库事务边界是：

```text
BEGIN
  按 event_id 检查并插入去重记录（唯一约束处理并发重复）
  校验 aggregate_version；若缺版本则回滚并安排等待或补取
  更新本地业务状态
COMMIT
提交成功后才向 Broker 确认消费
```

事务失败时两种写入一起回滚；事务成功但消费确认丢失时，重投通过去重记录安全跳过。这里保护的是消费端本地数据库；外部 HTTP 操作仍需对端幂等键或另行持久化任务并可靠执行。

## 5. 按业务条件比较协调路线 {#_5-不要混淆选择条件}

| 路线   | 主要协调方式                   | 仍需承担的边界                          |
| ------ | ------------------------------ | --------------------------------------- |
| 2PC    | 参与资源准备并接受统一提交决定 | Prepared 资源占用、故障恢复与参与者能力 |
| Saga   | 局部提交与可恢复补偿           | 中间可见、补偿失败、业务终态            |
| TCC    | 业务资源预留与确认/取消        | 接口侵入、乱序与幂等                    |
| Outbox | 本地数据与事件意图原子保存     | 传递重复、消费状态和投影延迟            |

这些机制并不相互排斥，例如 Saga 可以通过 Outbox 发送事件。选择时应依据不变量、可逆性与容错目标，缩写是否流行与选择无关。
