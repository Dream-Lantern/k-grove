# 第二十一章 CPU、内存与阻塞的分层排查

> 阅读标签：现代Linux指标口径 / 通用排查方法。

排查程序延迟或资源占用时，先区分任务正在执行、等待调度还是等待外部条件，再关联同一时间窗内的证据。本章按 CPU、内存和阻塞组织观察方法，帮助从现象形成可检验的假设；本文未对主机运行诊断。

## 1. 从症状确定观察对象

记录进程/线程、系统版本、CPU 核数、容器或作业限制、负载与开始变慢的时间。没有共同时间窗的 CPU 截图与磁盘统计，不能直接拼成因果链。

![从症状到可检验假设](/assets/notes/operating-systems/os-triage.svg)

例如，请求延迟上升而 CPU 利用率很低时，程序可能正在等待远程 I/O、锁或连接池，不一定是 CPU 资源不足；CPU 利用率很高时，也需进一步区分实际计算、忙自旋与回收工作。

## 2. 调度等待与 I/O 等待

很多可运行实体竞争有限 CPU，可能产生调度等待；线程睡眠则可能因为设备、条件变量或其他依赖。唤醒后还可能排队，不能把“已唤醒日志”当成应用已继续执行的时间。

单个 load、平均利用率或一个线程状态是线索，不是完整根因。多核上某一核饱和与全机平均利用率不高可以同时发生。

## 3. 虚拟大小、RSS 与缺页统计 {#_3-内存数字怎样解释}

虚拟大小描述地址范围，RSS 描述适用驻留统计，页缓存可被多个对象使用；共享页在多进程求和时可能重复计算。分配器保留、文件缓存和真正无法回收的增长有不同原因。

minor fault 增长不必然有磁盘 I/O，major fault 应结合时间窗、文件访问和回收状态；swap 使用过不等于当前正在剧烈交换。Linux 计数定义可参照 [getrusage](https://man7.org/linux/man-pages/man2/getrusage.2.html)。

## 4. 按等待关系区分竞争、饥饿与死锁 {#_4-锁等待不能用死锁一个词概括}

短暂竞争、优先级问题、线程饥饿、等待外部条件与真正死锁，都可能表现为线程不前进。需要等待关系、持锁者状态、超时和调用栈等证据。

在确认等待环与无法推进的条件之前，不应直接判定死锁；反复重启后暂时恢复，也不意味着已经定位根因。应结合同步协议状态与应用业务进度判断。

## 5. 安全的验证顺序

先保存只读证据和假设，再设计最小变化、回退与验收。清缓存、关闭 swap、杀线程、改调度优先级、写内核参数都可能影响使用，不属于本次文档整理授权。

本册提供机制、版本依据与纸面练习，尚无内核运行验收记录。开展实践时，应先选择隔离 Linux 环境与确切版本，再按观察、假设、最小变化和验收的顺序进行。
