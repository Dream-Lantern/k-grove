# 第二十一章 CPU、内存与阻塞的分层排查

> 阅读标签：现代 Linux 指标口径与只读 Runbook（操作手册）；三个故障案例均为教学假设。

服务请求延迟升高时，先区分任务正在执行、等待调度还是等待外部条件，再关联同一时间窗的证据。本章按处理器、内存、I/O 和同步等待形成可检验假设，不对真实服务主机执行故障注入或资源调整。示例命令可在有访问权限的 Linux 环境运行；工具缺失、权限或接口不支持要记录，不能把空输出当成“没有瓶颈”。

## 1. 从症状确定观察对象

| 维度       | 记录内容                                                                        |
| ---------- | ------------------------------------------------------------------------------- |
| 时间       | 何时开始、持续多久、基线与异常窗口，使用同一时区和采样间隔                      |
| 对象       | 进程标识符（PID，Process ID）、线程标识符（TID，Thread ID）、服务实例与部署版本 |
| 系统和资源 | 内核、架构、逻辑处理器（CPU，Central Processing Unit）数量、亲和性、容器限制    |
| 负载       | 请求速率、并发、请求大小及其变化                                                |
| 症状       | 吞吐、错误率及第 95/99 百分位延迟（P95/P99）                                    |
| 对照       | 正常窗口与异常窗口中相同口径的数据及近期变更                                    |

[![固定请求窗口后按执行、排队、内存或等待证据分支验证假设](/assets/notes/operating-systems/os-triage.svg)](/assets/notes/operating-systems/os-triage.svg)

不同时间窗的 CPU 截图与磁盘累计数，不能拼成因果链。请求样本也要保证相同接口/实例及统计口径。高 CPU 可能是计算、自旋或回收；低 CPU 也可能被网络、锁、连接池或单线程热点限制。

### 可复制的只读采集入口

下面使用 Bash；默认 `pid=$$` 观察当前 shell，排查自己的服务时把 pid 改为其十进制 PID，把 tid 改成该进程中的实际 TID。变量不能写成带尖括号的占位符。进程退出或 PID 复用时须重新核对身份和启动时间。

```bash
pid=$$
tid=$pid
date -Is
uname -a
lscpu
ps -L -p "$pid" -o pid,tid,psr,stat,pcpu,comm
cat /proc/loadavg
cat "/proc/$pid/task/$tid/status"
```

`ps` 的 pcpu 通常是进程/线程存续期间的比例，不是刚才一秒的瞬时值，psr 是适用的处理器位置记录，不证明采样此刻正在运行。需要区间对照时，可用有限次数 `top -H -b -d 1 -n 3 -p "$pid"`，先确认工具口径；多核总占用/单核 100% 的显示模式也可能不同。[ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

## 2. 调度等待与 I/O 等待

| 观察         | 能说明什么                                             | 不能直接说明什么                                 |
| ------------ | ------------------------------------------------------ | ------------------------------------------------ |
| R            | 运行中或可运行                                         | 线程此刻必在 CPU 上、没有排队                    |
| S            | 可中断睡眠                                             | 一定故障；网络、同步、定时等正常等待也可能如此   |
| D            | 不可中断等待                                           | 必然是本地磁盘；具体内核等待对象还要查           |
| Load Average | Linux 运行队列与有关不可中断任务的 1/5/15 分钟平均负载 | CPU 使用百分比、单线程延迟或独立根因             |
| CPU 利用率   | 按工具定义的执行时间比例                               | 全是有效业务计算；整机低也不能排除一个关键核饱和 |

多个可运行实体竞争有限 CPU 会排队；线程被唤醒后也可能等调度，不能以唤醒日志代替真正恢复执行的时间。结合 status 的 `Cpus_allowed_list` 查看亲和性，再核对控制组（cgroup，control group）的 CPU 配额；配额受限可能在整机仍空闲时发生。[proc_pid_status(5)](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html)、[proc_loadavg(5)](https://man7.org/linux/man-pages/man5/proc_loadavg.5.html)

若可读，可观察 `/proc/$pid/task/$tid/schedstat`：相应字段包含运行时间、运行队列等待时间和调度片段计数。是否收集有效等待统计依赖内核构建/运行设置；用同窗差值，字段为零或不可用不能直接证明没有等待。本章不打开统计开关。[Linux 调度统计文档](https://docs.kernel.org/scheduler/sched-stats.html)

### iowait 的边界

`/proc/stat` 的 iowait（工具常显示 %wa）是 CPU 时间统计中的特殊归类，**不是某个线程实际 I/O 延迟，也不表示 CPU 自己在等磁盘**。多核任务迁移等因素使归类存在限制，手册还提醒其计数在某些条件下可能下降。不能把它当作所有任务等待比例或据此单独定根因。[proc_stat(5)](https://man7.org/linux/man-pages/man5/proc_stat.5.html)

将它与同窗请求延迟、线程状态、文件/网络活动、设备统计和资源压力交叉核对；低 %wa 不能排除远端网络或连接池等待，高 %wa 也不直接证明某一块磁盘就是原因。

## 3. 虚拟大小、RSS 与缺页统计 {#_3-内存数字怎样解释}

虚拟内存大小（VMS，Virtual Memory Size）是虚拟空间规模；常驻集大小（RSS，Resident Set Size）统计适用驻留内存；按比例分摊的常驻大小（PSS，Proportional Set Size）把共享页按共享关系分摊。它们不是同一项“独占物理内存”。

假设 A/B 各有私有驻留 40 MiB，并且恰好两者共享同一组 20 MiB 页，无其他共享者：

| 指标 | A      | B      | 求和解释                                  |
| ---- | ------ | ------ | ----------------------------------------- |
| RSS  | 60 MiB | 60 MiB | 120 MiB，重复计入了共享页                 |
| PSS  | 50 MiB | 50 MiB | 100 MiB，等于本例 40+40+20 的实际页面总量 |

[![两个进程的私有驻留与共享页如何分别计入 RSS 和 PSS](/assets/notes/operating-systems/os-rss-pss.svg)](/assets/notes/operating-systems/os-rss-pss.svg)

```bash
cat "/proc/$pid/status"
if [ -r "/proc/$pid/smaps_rollup" ]; then
    cat "/proc/$pid/smaps_rollup"
fi
cat /proc/meminfo
vmstat 1 5
```

status 中部分 RSS 统计有精度限制；smaps_rollup 是否存在、字段及权限随内核而变，读取也可能需要遍历映射，不能对大量进程高频轮询而称为“无开销”。缺少 rollup 时可按需读 smaps，但成本通常更高。[proc_pid_smaps(5)](https://man7.org/linux/man-pages/man5/proc_pid_smaps.5.html)

分配器保留、文件缓存和无法回收的增长有不同原因；不能把 RSS、文件页缓存、容器 memory.current 简单相加。vmstat 的 si/so 是相应交换活动，需确认单位和时间窗；首条报告的 CPU/I/O 等速率通常是自开机以来的平均，进程和内存列仍是瞬时值，后续周期报告才用于本次间隔对照。[vmstat(8)](https://man7.org/linux/man-pages/man8/vmstat.8.html)

次/主缺页异常（Minor/Major Page Fault）的增量需结合读取范围、缓存与回收分析；Minor 不必有设备 I/O，Major 增加也不单独证明颠簸，swap 已使用不等于正在大量换页。累计计数可由 getrusage 或 proc 接口观察，别把计数直接等同复制页数。[getrusage(2)](https://man7.org/linux/man-pages/man2/getrusage.2.html)、[第十八章](/articles/os-page-faults.html)

### PSI 与容器限制

压力停顿信息（PSI，Pressure Stall Information）衡量任务因资源不足受到的停顿，不是内存容量或 CPU 利用率：

```bash
for resource in cpu memory io; do
    file="/proc/pressure/$resource"
    if [ -r "$file" ]; then
        printf '%s\n' "$file"
        cat "$file"
    fi
done
```

| 字段               | 解释                                                       |
| ------------------ | ---------------------------------------------------------- |
| some               | 至少部分任务在相应资源上停顿的时间比例                     |
| full               | 所有非空闲任务同时停顿的相应时间比例；需区分资源和统计范围 |
| avg10/avg60/avg300 | 最近 10/60/300 秒的平滑趋势百分比，不是当前瞬时值          |
| total              | 累计停顿微秒数，取同一范围、同字段差值后可分析自选窗口     |

例如某字段 total 在 2 秒里增长 100000 微秒，对应该字段约 5% 的窗口比例，是纸面计算而非本机输出。系统级 CPU full 未定义，相关版本为兼容性报告零；不能据此断言没有 CPU 压力。PSI 接口依赖内核支持，cgroup 的语境也要区分。[Linux PSI 文档](https://docs.kernel.org/accounting/psi.html)

先用下列只读命令识别目标成员关系和可见挂载，再确定其 cgroup v2 目录；不能假设所有容器都位于同一固定路径：

```bash
cat "/proc/$pid/cgroup"
findmnt -t cgroup2
```

例如挂载根为 `/`、挂载点 `/sys/fs/cgroup`、成员路径 `/service/demo` 时，才可据此组合目录。容器命名空间和挂载根可能改变这种对应；需核对目标进程视角与祖先限制。确认后把目录填入下面变量，默认留空会跳过，不读取猜测路径：

```bash
cgdir=''
if [ -n "$cgdir" ] && [ -d "$cgdir" ]; then
    for field in memory.current memory.max memory.events memory.pressure cpu.max cpu.stat; do
        if [ -r "$cgdir/$field" ]; then
            printf '%s\n' "$field"
            cat "$cgdir/$field"
        fi
    done
fi
```

memory.current 是组内当前计费，memory.max 是适用硬上限（max 不表示祖先或全机无限）；memory.events 的 high/max/oom/oom_kill 等计数含义不同，用同窗增量并区分层级。memory.pressure 是组内内存压力。cpu.max 配额/周期限制 CPU 时间，不等于固定绑定几个核；cpu.stat 的节流计数变化可辅助判断，不能单独解释全部延迟。[cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)

## 4. 按等待关系区分竞争、饥饿与死锁 {#_4-锁等待不能用死锁一个词概括}

短暂竞争、线程饥饿、连接池限额、外部 I/O 和真正死锁都可能让请求不前进。需要线程栈/应用诊断、等待对象、持有者、超时和业务进度；futex 等待只说明某种同步路径，不能据此判定死锁。确认等待环及相关任务无法自行推进后，才能考虑死锁结论。

只在权限允许且评估开销后采集运行时线程转储；内核 stack/wchan 等接口也可能受限，不能把不可读或零值当成没有等待。反复重启暂时恢复也不证明已定位原因。[第十章等待环与恢复](/articles/os-deadlocks.html)

### 三个完整教学案例

以下数值、时间和证据组合都是**假设场景**。

#### Case A：平均 CPU 20%，P99 却从 100 ms 升到 900 ms

背景：16 个逻辑 CPU，负载窗口已对齐，一个关键线程接近单核 100%。初始假设是关键串行阶段饱和或可运行等待，而不是立即断言死循环。

| 步骤              | 安全采集与证据                                                        | 如何继续判断                                                          |
| ----------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 定位热点          | ps -L 和有限 top -H，关联目标线程与服务请求                           | 整机平均可能掩盖单线程热点；ps 累计比例还要与区间值对照               |
| 排除可用 CPU 受限 | status 的亲和性、正确 cgroup 的 cpu.max/cpu.stat、可用 schedstat 差值 | 亲和性窄、节流与排队若同窗增加，支持调度资源假设；若没有则弱化该假设  |
| 看执行内容        | 使用已有应用剖析/诊断；另行评估后才做有限栈采样                       | 业务热点、自旋、回收等需要内容证据区分，不在本轮持续追踪              |
| 验证              | 在隔离环境或受控窗口比较相同请求量下的关键阶段耗时、队列和 P99        | 热点降低但 P99 不变会反驳它是主要瓶颈；单线程 100% 本身不证明算法错误 |

边界：20% 平均与一个核饱和可以同时成立；不在排查入口擅自改亲和性、配额或调度优先级。

#### Case B：内存压力、Major 和尾延迟同时增加

背景：业务请求量相对稳定，内存压力和回收活动增加。初始假设是驻留预算不足导致文件页反复加载，或匿名工作集受限；同时保留冷文件访问等替代解释。

| 步骤       | 安全采集与证据                                                                | 如何继续判断                                                                                   |
| ---------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 分清占用   | status/适量 smaps_rollup 区分匿名、文件、共享与 PSS                           | 增长可能来自缓存或分配器保留，不直接等同泄漏                                                   |
| 对齐活动   | 周期 vmstat、Major/Minor 增量、meminfo 与 memory PSI                          | si/so、扫描/回收相关指标与停顿共同增长更支持换页/回收风险；单独 Major 不够                     |
| 核对限制   | 正确 cgroup 的 memory.current/max/events/pressure                             | 容器限制可能先于全机耗尽；oom 与 oom_kill 不是同一个事件计数                                   |
| 关联和验证 | 对照目标文件范围、设备/文件延迟、吞吐/P99，检查访问局部性与内存限制的近期变化 | 若仅首次读一份冷文件且压力不持续，颠簸假设变弱；在隔离环境缩小请求工作集后看同口径指标是否改善 |

边界：没有读存储也可能有高 Minor 成本；不用清缓存、关闭 swap 或加压“证明”假设，更不以一次正常化就认定根因。

#### Case C：CPU 低、吞吐下降、大量请求等待

背景：线程多数 S，可能有少量 D，请求队列增长。初始假设分别列为网络/数据库、连接池、锁/条件、线程池限制，而不只写“磁盘慢”。

| 步骤     | 安全采集与证据                                                   | 如何继续判断                                                         |
| -------- | ---------------------------------------------------------------- | -------------------------------------------------------------------- |
| 定位等待 | ps/status、已有运行时线程转储与请求超时记录                      | 找到等待对象及哪个业务阶段，而非仅记状态字母                         |
| 找到依赖 | 池等待长度/在用量、锁持有者、下游延迟和线程业务进度              | 池满且下游耗时增长支持依赖瓶颈；持有者持续推进则不直接叫死锁         |
| 反证     | 将同窗下游指标、资源压力、持锁/释放事件和业务日志关联            | 下游正常且形成无法推进等待环，才进一步检验死锁；futex 单点栈不够     |
| 验证     | 在隔离环境做有限依赖替身或等待路径测试，比较等待时长、队列与吞吐 | 某等待消除后业务仍慢，需保留其他瓶颈假设；不能只因重启恢复就关闭问题 |

边界：调用栈采集受权限/工具与开销限制；不擅自结束线程、强制解锁或重启服务。

## 5. 安全的验证顺序

| 顺序 | 本轮只读 Runbook 的产物                                                           |
| ---- | --------------------------------------------------------------------------------- |
| 1～3 | 确认吞吐/错误/P99 症状，固定基线与异常时间窗，记录 PID/TID、实例、版本和资源范围  |
| 4～5 | 带时间采集低风险证据，分类执行、调度、内存、I/O 与同步等待，标明工具口径/权限缺失 |
| 6～7 | 写出可被反驳的假设、替代解释和最小验证设计；有影响的实际操作需另行评估            |
| 8～9 | 用同口径对照结果，记录支持与反驳证据、结论和未解决风险                            |

例如纸面窗口 T0 记录基线，T1～T2 同步采请求和资源差值，T3 形成假设，T4 设计验证，再用相同长度窗口对照；不能拿 T1 的累计总数与另一天的请求尾延迟直接比较。**指标是证据，不是根因本身。**

本章按只读观察组织排查步骤。特定工具可能缺失、权限受限或有显著开销，先缩小进程/线程范围、频率和持续时间。
