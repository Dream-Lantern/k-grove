# 第六章 上下文切换、中断与内核栈

> 阅读标签：通用入口模型 / 0.11 TSS与抢占条件。

进入内核、保存陷入状态、选择下一个任务和恢复用户执行，彼此相关但并非同一步骤。原笔记的“五段论”有助于理解整体路径，但不能据此认为所有系统调用都会先切换到另一个线程。

## 1. 哪些状态要保存？

架构规定的返回位置、标志和栈等状态，以及入口软件保存的必要寄存器，是后续恢复执行的基础。调度切换还可能涉及地址空间、内核栈和其他线程状态，具体由哪些部分负责，取决于实现。

![入口与调度切换的区别](/assets/notes/operating-systems/os-context.svg)

不是每个寄存器都由同一个 switch_to 函数复制，也不是所有上下文都存成 PCB 中一排 ax/bx 字段。需要区分陷入帧、保存的内核调用上下文和资源描述。

## 2. 从用户态进入内核时，压到哪一个栈？

在原笔记涉及的 x86 特权切换情形中，硬件与入口路径在适用的内核栈保存返回用户态所需状态。原句“把内核栈信息压入用户栈”方向有误，不能以用户栈作为可信内核入口的任意工作区。

随后内核代码调用处理函数，继续在相应内核上下文执行。不同架构和某些专用栈有额外设计，不能把一个 x86 案例泛化成全部 CPU 的固定压栈序列。

## 3. 阻塞怎样让出 CPU？

教学路径：线程 A 发起读取、条件未满足，按同步协议进入等待；调度选择 B；保存 A 的内核续接状态并恢复 B。B 可能先从自己的内核调用处继续，再回到用户代码。

A 被唤醒并重新获得调度后，会沿自身等待结束后的路径继续执行，而不是跳到 B 的用户返回地址。每个执行流的栈都必须与其续接点匹配。

### Linux 0.11：时钟耗尽不必立即抢占内核

原版`kernel/sched.c:do_timer`在counter减到0后，若中断前CPL为内核级，执行`if (!cpl) return;`，不在这条时钟路径直接调用schedule；从用户级进入的耗尽路径才继续调度。内核也会在显式阻塞等位置让出。

所以“内核代码正在执行→时钟一到→立刻切走任意内核位置”不是0.11模型。`bread`中的等待与显式schedule要在这个前提下理解，不可把关本地中断的历史做法推广到现代SMP。

## 4. 中断返回不等于普通 ret

普通函数返回遵循调用约定；异常/中断返回还需恢复架构定义的特权与执行状态。原笔记中的 ret、iret、段寄存器和 esp 都属于特定示意，不能拼成现代 x86-64 或 RISC-V 的通用切换程序。

内核正在处理一个可立即完成的系统调用时，可能完全不调度其他任务。因此“从用户栈到内核栈”不等于“地址空间发生一次进程切换”。

## 5. Linux 0.11 与课程改写版

原版 0.11 的 include/linux/sched.h 中 switch_to 采用关联 TSS 的 ljmp 路线；课程可能把它改为软件保存寄存器与内核栈切换。两种教学代码不能标成同一份原版实现，也不能无实验地把性能差异归因于一句“不能利用流水线”。

本册以 [kernel.org 原版源码](https://www.kernel.org/pub/linux/kernel/Historic/old-versions/linux-0.11.tar.gz)核对历史路径；[xv6 的陷入与调度章节](https://pdos.csail.mit.edu/6.1810/2024/xv6/book-riscv-rev4.pdf)仅作为另一架构的对照。没有编译或运行切换代码。
