# 第二十五章 CQRS、缓存、会话、全局 ID 与任务

> 阅读标签：通用协议/应用模型，具体前提见本章。

CQRS、缓存、会话、全局 ID 和任务调度分别处理读写职责、结果复用、用户状态、操作身份与执行时机。本章作为工程速查，逐项说明它们的用途、状态来源和恢复条件，再分析组合使用时需要共同维护的业务约束。

## 1. CQRS 是职责与模型分离

CQRS（Command Query Responsibility Segregation，命令查询职责分离）将改变状态的命令与读取状态的查询在职责、模型上分开。可以共用数据库，也可以采用独立的查询存储；不是必须读写跑在不同机器，更不等于普通主从复制。

[![CQRS：事件驱动同步是一种可选实现](/assets/notes/distributed-systems/dist-cqrs.svg)](/assets/notes/distributed-systems/dist-cqrs.svg)

若查询模型异步构建，订单已提交而列表尚未出现，就需要写后读与进度策略。关键库存校验不能随意依赖有延迟的查询投影。[Microsoft CQRS 模式说明](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)

以订单系统为教学例子，一种采用异步投影的数据流是：

```text
Client → Command API → 业务校验 → Write Model（写模型）
  → 主数据库：在同一本地事务提交订单与 Outbox 事件
  → 发布器 → 消息系统 → 投影处理器更新 Read Model（读模型）
  → 查询数据库 ← Query API ← Client 查询订单列表
```

写模型执行库存、订单状态等业务规则；读模型可把订单与商品摘要预先组织为适合列表展示的数据。异步更新意味着写入成功后，投影可能还没追上。列表暂时没有新订单，不能据此重新创建订单。

| 提交后立即查看订单         | 做法与边界                                                                             |
| -------------------------- | -------------------------------------------------------------------------------------- |
| Read Your Writes（写后读） | 针对本用户最近写入，路由到能提供该结果的数据源，或等待读模型达到所需版本；需要显式设计 |
| 暂时展示写入结果           | Command 返回订单 ID、状态与版本，前端先展示，之后与查询结果协调；不表示投影已经同步    |
| 检查投影进度               | 返回并查询可比较的事件位置或业务版本；达到目标后再读，等待应有截止时间                 |
| 关键业务校验               | 直接使用权威写模型，并在相应事务或条件更新中检查，不能仅凭展示列表判断库存             |

这是 CQRS 的一种组合方式；共用数据库时仍可分离命令与查询代码，不必引入消息队列或第二个数据库。Outbox 的重复、顺序与幂等条件见[第 22 章](/articles/distributed-saga-tcc-outbox.html)。

## 2. 缓存是副本与失效协议问题

缓存通过复用结果减少昂贵查询，不只是用内存替换磁盘，也可以保存远程聚合或计算结果。Cache-Aside 中的数据库更新与缓存删除不属于同一个原子事务；较早查询的结果若迟到回填，也可能重新污染缓存。

应定义权威数据、版本、TTL、失效失败恢复和回源预算。Bloom Filter 只在正确加入与未破坏等条件下提供相应否定判断；业务漏写过滤器可能误拒真实对象，基础过滤器也不应通过随意清位删除成员。更细说明可联读 Redis 分册，本章不重复所有命令。

### Cache-Aside：慢读可以把旧值填回来

Cache-Aside（旁路缓存）由应用维护缓存：读取先查缓存，未命中则查数据库并回填；更新先提交数据库，再删除相关缓存。下面假设缓存起初未命中，商品价格为 100，两个请求没有额外协调：

| 时刻 | 请求 A：读                         | 请求 B：更新       |
| ---- | ---------------------------------- | ------------------ |
| T1   | 查询数据库，得到价格 100，尚未回填 | —                  |
| T2   | 暂停                               | 数据库提交价格 120 |
| T3   | 暂停                               | 删除缓存           |
| T4   | 把之前得到的 100 回填缓存          | 已结束             |

最终数据库是 120，缓存却是 100。删除只能清除当时的缓存，不能取消仍在途的旧查询；若回填时才开始计算 TTL（Time to Live，存活时间），它也不等于从数据库提交起计算的陈旧时间上限。

![Cache-Aside 的迟到回填竞态](/assets/notes/distributed-systems/dist-cache-aside-race.svg)

| 处理方向           | 作用与局限                                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 延迟双删           | 更新后再延迟执行一次失效，覆盖部分慢读回填；暂停可能更长、删除也可能失败，固定延迟不能证明强一致                                 |
| 版本校验           | 回填携带业务版本，并原子检查缓存侧保留的版本下界；旧版本不能越过下界。只比较当前缓存值不够：删除后若版本记录也丢了，旧值仍能写入 |
| 消息或变更日志修复 | 可靠传播失效或更新，重试并按版本处理乱序；需要监控积压，仍有传播延迟                                                             |

数据库更新与缓存删除通常没有共同原子边界。若采用版本下界或失效标记，还需定义其过期、淘汰、缓存重启后的恢复方式；不能只加一个 `version` 字段就声称竞态消失。[Cache-Aside 官方说明](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)；更细的回源与失效边界见[Redis 缓存更新](/articles/redis-cache-patterns.html)。

### Bloom Filter：用位数组筛掉部分不存在的查询

Bloom Filter（布隆过滤器）是近似集合，不保存完整成员。它使用 Bit Array（位数组），由多个 Hash Function（哈希函数）将元素映射到多个位置。插入把这些位设为 1；查询只要发现其中一位为 0，就可判定该元素没有被插入，全部为 1 则只能说“可能存在”。

教学例子：位编号为 0～7，使用两个哈希函数。插入商品 A 时得到位置 `{1,4}`，插入 B 得到 `{4,6}`，因此位 1、4、6 为 1。查询 C 若得到 `{1,6}`，虽未插入 C，也会返回可能存在，这叫 False Positive（假阳性）。查询 D 若得到 `{2,6}`，因为位 2 为 0，可判定 D 未被插入。

标准过滤器在元素正确插入、位数组未损坏且哈希配置一致的条件下，没有 False Negative（假阴性，即已插入却被判断为未插入）。这不保证“数据库里存在的元素都一定插入过过滤器”。也不能通过清空 A 的位来删除 A，因为位 4 还被 B 使用。Counting Bloom Filter（计数布隆过滤器）等变体用计数支持删除，但要正确维护插入/删除次数，并付出更多空间和实现成本。参见 Summary Cache 论文的[位数组原理](https://pages.cs.wisc.edu/~cao/papers/summary-cache/node8.html)和[计数式更新](https://pages.cs.wisc.edu/~cao/papers/summary-cache/node9.html)。

## 3. 负载均衡与会话

轮询、权重、最少连接和延迟反馈等策略优化不同指标。连接少不一定工作量小，心跳成功也不等于下游依赖健康。排除故障节点还要处理在途请求、慢请求与新实例预热。

会话粘滞让同一用户倾向同实例，但实例故障时仍需恢复状态；共享会话存储简化多实例访问，却引入存储可用性、TTL 和凭据保护问题。IP 哈希遇到 NAT、代理或地址变化，也不能等同稳定用户身份。

### 路由指标不等于实际工作量

| 策略                             | 主要依据       | 局限                                     |
| -------------------------------- | -------------- | ---------------------------------------- |
| Round Robin（轮询）              | 按节点轮转     | 不区分请求成本与节点差异                 |
| Weighted Round Robin（加权轮询） | 按配置权重分配 | 静态权重可能跟不上容量变化               |
| Least Connections（最少连接）    | 活跃连接数     | 一个长连接可能承载很多请求，连接成本不同 |
| Least Request（最少请求）        | 当前活跃请求数 | 请求复杂度不同，不宜只数历史累计请求     |
| Latency-aware（延迟感知）        | 延迟反馈       | 采样、瞬时抖动可能影响判断，需要稳定控制 |

例如 A 只有两个连接却都在执行重查询，B 有十个连接但多数空闲，最少连接未必选出真正空闲的节点。健康检查只能覆盖其实际检查范围；摘除实例时可使用 Connection Draining（连接排空），停止接收新工作并给在途请求有限完成时间，超时后按协议处理。新实例应逐步预热，负载均衡只分配工作，不能凭空增加下游容量。[负载与容量的关系：Google SRE](https://sre.google/sre-book/handling-overload/)

### 登录后实例故障，状态从哪里恢复

用户在 A 登录并建立 Session（会话），随后 A 故障，请求转到 B。此时能否继续登录状态，取决于会话状态来源：

| 方式                                 | B 如何处理                                     | 仍需处理                                                       |
| ------------------------------------ | ---------------------------------------------- | -------------------------------------------------------------- |
| Sticky Session（粘滞会话）           | 通常路由回 A；A 不可用时，本地状态不自动搬到 B | 状态复制、恢复或重新登录；粘滞本身不提供恢复                   |
| Shared Session Store（共享会话存储） | 用会话 ID 从共享存储加载状态                   | 存储可用性、TTL、注销失效、凭据与访问保护                      |
| Stateless Token（无状态令牌）        | 验证签名及声明，不必加载同一份实例内会话       | 有效期、密钥、注销撤销和权限变更；实时撤销可能重新引入共享状态 |

会话负责关联一段交互状态，Authentication（身份认证）判断是谁，Authorization（授权）判断能做什么；三者相互配合，但不能互相替代。签名令牌也不意味着其中的内容被加密。IP 可能被代理、共享或改变，不是稳定用户身份。[OWASP 会话管理说明](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

## 4. 全局 ID 的唯一性、顺序与生成条件 {#_4-全局-id-需要哪些性质}

唯一、时间有序、严格单调、不可猜测是不同需求。数据库序列或服务端分配需要可靠的状态与容错；Snowflake 类方案要处理工作节点编号冲突、时钟回退和序列容量，不能只背固定位数格式。

进一步阅读：RFC 9562 定义的 UUIDv7 使用毫秒时间字段，适合作为时间排序相关方案的一部分，但不是跨节点真实先后的证明；唯一性仍依赖正确生成与状态处理。ID 更不应直接当作授权秘密。[RFC 9562 §5.7、§6](https://datatracker.ietf.org/doc/html/rfc9562)

| ID 属性  | 含义                                               |
| -------- | -------------------------------------------------- |
| 全局唯一 | 在约定生成域和生命周期内，不同生成者不会产生重复值 |
| 时间有序 | 值大体可按时间排列，不证明分布式事件的真实先后     |
| 严格单调 | 同一明确生成域内，后一次值严格大于前一次值         |
| 不可猜测 | 难以由已知 ID 推测其他 ID；与唯一性是不同要求      |

Snowflake 类 ID 通常组合时间、Worker ID（工作节点编号）与时间片内序列。教学推演：Worker 12 上次时间为 1000，现在回退到 999；若错误地把序列重置为 0，并再次使用以前发过的 `(999,12,0)`，就会重复。回退本身不是必然重复，但忽略回退并复用组合会破坏唯一性。

常见处理包括等待时钟追上、暂时拒绝生成，或使用经证明不重复的逻辑时间与序列状态。Twitter 历史实现选择检测回退后拒绝生成；同一时间片序列耗尽则等待下一时间片。进程重启也不能忘掉仍可能冲突的历史状态，Worker ID 的分配与复用需要持久化或外部协调；新分配一个 Worker ID 并不会自动解决所有时钟问题。[Snowflake 历史源码](https://github.com/twitter-archive/snowflake/blob/snowflake-2010/src/main/scala/com/twitter/service/snowflake/IdWorker.scala)

RFC 9562 §5.7 的 UUIDv7 共 128 位：48 位 Unix 毫秒时间戳、4 位版本、2 位变体标识，其余 74 位用于随机值及规范允许的子毫秒/计数安排。时间在高位便于排序，但跨节点时钟误差、同毫秒生成和生成器状态仍影响先后与唯一性；格式本身不提供跨节点严格单调，也不应作为授权秘密。

## 5. 定时任务也需要业务执行身份

多个实例都观察到“该执行了”，并不意味着每个实例都应产生一次外部效果。调度负责生成任务实例，后续还需处理工作领取、租约、重试与业务完成确认。仅增加一把带 TTL 的锁，无法阻止旧执行者恢复后重复发送账单。

设计清单：任务键可包含计划版本与时间窗口；执行尝试有独立身份；结果按任务实例幂等提交；长任务续约失败应停止使用旧资格；需要重跑、补跑和人工恢复时能查询明确状态。这是教学框架，不冒充某调度产品的完整语义。

定时扣款的教学流程可以写为：Schedule（调度计划）→ 生成任务实例 → Worker Claim（工作进程领取）→ 执行扣款 → 记录执行结果。调度与执行分开记录，才便于判断“没触发”“没领到”“结果未知”分别发生在哪里。

| 身份或机制                          | 在扣款任务中的作用                                               |
| ----------------------------------- | ---------------------------------------------------------------- |
| Task Instance ID（任务实例 ID）     | 如“计划版本 + 账期 + 账户”，标识本次应完成的业务工作             |
| Execution Attempt ID（执行尝试 ID） | 标识某次领取与执行，重试时可变化，不能充当扣款去重键             |
| Lease（租约）                       | 在有限时间内维持领取资格；长任务需要续期并处理资格失效           |
| Fencing Token（栅栏令牌）           | 区分新旧执行代际；受保护资源确认新代际后拒绝旧令牌               |
| Idempotency Key（幂等键）           | 对同一次应收扣款保持稳定，由支付端可靠去重并支持查询结果         |
| Retry（重试）                       | 对同一业务工作再次尝试，遵守错误类型、退避和总预算               |
| Replay / Backfill（重跑 / 补跑）    | 重做历史处理或补齐漏掉的时间窗口；需明确是否允许再次产生业务效果 |

两个 Worker 同时领取时，要用数据库条件更新等原子手段决定当前归属。假设旧 Worker A 暂停，租约过期后 B 重新领取并完成扣款，A 恢复又提交结果：任务存储应校验尝试身份和代际，拒绝 A 覆盖 B；支付端则用同一个业务幂等键处理两次扣款请求。只挡住任务结果写入，仍挡不住未去重的外部扣款。

调度锁协调领取资格，不能单独保证外部副作用只发生一次。资源端校验、续约失败处理与幂等提交的更多条件见[第 15 章](/articles/distributed-locks-leases-fencing.html)；回退后 ID 的顺序问题见[时间与逻辑时钟](/articles/distributed-clocks-causality.html)。

## 6. 组合使用时确定权威状态与恢复路径 {#_6-模式不是可以直接拼接的积木}

同时采用 CQRS、缓存、会话和任务时，需要明确哪些状态是权威来源、哪些可以重建，以及允许多大延迟。高可用缓存、消息队列和锁的组合，并不自动构成正确的订单系统；恢复与验收仍须依据业务不变量。
