# 知识笔记写法与验收

## 从样稿提炼的偏好

面向需要逐步理解原理的读者，使用朴实、明确的说明。文章按知识内容安排，常见顺序为背景和用途、基本概念、正常流程、例子、异常与适用条件、要点回顾。参考页、排障记录和短条目不必采用这个顺序，也不必增加总结。

例如，介绍 Agent 时先解释模型提出动作、执行侧调用工具、结果回到上下文的循环；介绍文件系统时先区分元数据管理和数据存储，再展开客户端访问与恢复过程。读者理解正常路径后，再说明权限、超时、版本和故障条件。

## 审阅语言改为知识说明

| 原文情形                         | 改写方向                                                                         |
| -------------------------------- | -------------------------------------------------------------------------------- |
| “原笔记把 X 写成 Y，这样不准确”  | 直接解释 X 的含义和工作方式；保留必要的 X/Y 区别，将旧稿修订理由留在差异报告     |
| “不能据此证明全部功能已实现”     | 明确本节说明的是概念、指定版本源码还是实验结果，在相关部分集中交代覆盖范围       |
| “它可能也许会有效，实际还要再看” | 写出已有材料中的具体条件和未确认项；材料没有条件时继续标为待验证，不补造肯定结论 |
| 连续的“为什么、如何、是不是”标题 | 选择能概括机制的陈述式标题，兼容旧锚点；有助于理解且已回答的设问可以保留         |
| 文章末尾只有复习问题             | 按文章用途改为要点回顾，或保留问题并提供简短解答、正文位置                       |

这些是判断方向，不是替换词表。每一处改动都要保留施事者、因果、时间、范围、否定和确定程度。版本表、论文引用、反例和故障分支本身属于知识，不因读起来严谨就删除。

## 批量任务

先备份并记录文章清单、ID/URL、元数据、代码块、图片引用、外部来源和已有章节锚点。以分册为批次逐篇阅读；对长源码笔记和参考附录采用不同深度，不为了让所有文件出现 diff 而添加空洞段落。

正文可以用脚本解析、格式化和检查保护项。内容改写须针对具体段落；不能只替换问号、删“不能/可能”，或给每篇添加相同的“背景—总结”来声称完成通篇润色。涉及新增技术事实时核对对应版本的官方文档、源码或原论文；仅做表达重构时不擅自扩展事实范围。

交付时说明实际覆盖文章、保留项、技术疑点及本地验证结果。对照检查代码、图、公式、单位、链接和旧锚点，运行项目已有内容、格式、构建检查，并抽查真实页面。完成本地润色后按用户要求停下，不自动提交或推送。
